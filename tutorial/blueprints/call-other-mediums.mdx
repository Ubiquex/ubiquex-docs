title: "Calling it from a hand-written intent file"
description: "Prove a blueprint_calls entry resolves to the identical result, independent of the SDK direct import."
---

The SDK direct import you just used is one way to call a blueprint.
There's a second, real one: a hand-written intent/v1 file's own
`blueprint_calls` entry, expanded by the identical mechanism, whether
you write that file by hand or a script produces it for you. This
tutorial proves both land on the same result.

## Call it from a hand-written intent file

```bash
cat > platform.json << 'EOF'
{
  "schema_version": 1,
  "kind": "ubx:intent/v1",
  "stack": "payments",
  "intent": { "summary": "payments queue, via blueprint" },
  "resources": [],
  "destroys": [],
  "blueprint_calls": [
    {
      "name": "ci-platform",
      "blueprint": "../ci-platform",
      "args": {
        "queue_name": "pipeline-events",
        "retention_days": "3"
      }
    }
  ]
}
EOF
```

```bash
ubx plan platform.json --out other.json
```

## Compare the two

```bash
ubx resolve --from-code create_platform.go --out sdk.json
diff sdk.json other.json
```

```bash
(no output)
```

No differences. Same blueprint, same version, called two different
ways, one identical resolved result.

## Add a cross-stack reference

A blueprint param can point at another stack's own real resource, not
just a literal value. Add one, a `cross_ref` param naming the VPC a
real neighboring stack (`networking`, here) already owns, and rebuild:

```bash
cat > ../ci-platform/resources.json << 'EOF'
{
  "resources": [
    {
      "type": "aws_sqs_queue",
      "name": "pipeline-events",
      "op": "create",
      "config": {
        "name": "{queue_name}",
        "message_retention_seconds": "{retention_days * 86400}",
        "tags": { "vpc_id": "{vpc_id}" }
      }
    }
  ]
}
EOF
cat > ../ci-platform/Ubxfile << 'EOF'
lang: go

params:
  queue_name: string, required
  retention_days: number, default 14
  vpc_id: cross_ref, required

resources: ./resources.json
EOF
ubx blueprint build ../ci-platform
```

`vpc_id`, required, is declared AFTER `retention_days`'s own default,
the same natural order build.mdx already used for `queue_name` and
`retention_days`. The generated signature is still required-first,
defaulted-trailing in every language (`queueName, vpcId, opts
...Option` in Go, say), `ubx blueprint build` reorders it for you
regardless of how you declared it.

## Call it with the real value

Both call paths take the identical `"@<stack>.<type>.<name>.<attr>"`
reference, `@networking.aws_vpc.main.id`, the real VPC `networking`
already shipped. From the hand-written intent file:

```bash
cat > platform.json << 'EOF'
{
  "schema_version": 1,
  "kind": "ubx:intent/v1",
  "stack": "payments",
  "intent": { "summary": "payments queue, via blueprint" },
  "resources": [],
  "destroys": [],
  "blueprint_calls": [
    {
      "name": "ci-platform",
      "blueprint": "../ci-platform",
      "args": {
        "queue_name": "pipeline-events",
        "retention_days": "3",
        "vpc_id": "@networking.aws_vpc.main.id"
      }
    }
  ]
}
EOF
ubx plan platform.json --out other.json
```

```bash
Plan  payments · from platform.json

  + aws_sqs_queue.pipeline-events create
      message_retention_seconds: 259200
      tags:
      {
        "vpc_id": "vpc-123"
      }

delta: +1 create(s), ~0 change(s), -0 terminate(s)
```

`vpc-123`, the real id resolved off `networking`'s own ledger, not a
literal string, threaded straight into the new resource's own tags.

From the SDK, via `sdk.CrossStack`, the SDK's own real constructor for
it:

```go
ciplatform.CiPlatform(
	"pipeline-events",
	sdk.CrossStack("networking", "networking.aws_vpc.main.id"),
	ciplatform.WithRetentionDays(3),
)
```

```bash
ubx resolve --from-code create_platform.go --out sdk.json
jq '.delta.creates[0].config' sdk.json other.json
```

```bash
{
  "message_retention_seconds": 259200,
  "name": "pipeline-events",
  "tags": {
    "vpc_id": "vpc-123"
  }
}
{
  "message_retention_seconds": 259200,
  "name": "pipeline-events",
  "tags": {
    "vpc_id": "vpc-123"
  }
}
```

Same resolved config, both ways. `intent.sources` and
`resolution.resolved_at` differ between the two full proposals, real
provenance and a real timestamp, never the same across separate runs,
so this compares the resolved delta directly rather than the whole
file.

## Refuse a malformed reference

Drop the leading `@` and call it again:

```bash
cat > platform-bad.json << 'EOF'
{
  "schema_version": 1,
  "kind": "ubx:intent/v1",
  "stack": "payments",
  "intent": { "summary": "payments queue, via blueprint" },
  "resources": [],
  "destroys": [],
  "blueprint_calls": [
    {
      "name": "ci-platform",
      "blueprint": "../ci-platform",
      "args": {
        "queue_name": "pipeline-events",
        "retention_days": "3",
        "vpc_id": "networking.aws_vpc.main.id"
      }
    }
  ]
}
EOF
ubx plan platform-bad.json
```

```bash
error: param "vpc_id": "networking.aws_vpc.main.id" must start with
"@" -- expected "@<stack>.<type>.<name>.<attr-path>"
```

Refused before it ever reaches a provider. The same real check runs
regardless of which caller sent it, `cross_ref` never resolves a
string that isn't already a well-formed reference.

## What you just did

You proved directly what this whole design promises: a blueprint
called from a direct SDK import or a hand-written `blueprint_calls`
entry produces the exact same real infrastructure, byte for byte, even
when one of its params points at another stack's own real resource
instead of a literal value, and confirmed a malformed reference is
refused the same way regardless of which path sent it.

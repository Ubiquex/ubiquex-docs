Not every GCP resource type attributes cleanly yet. This tutorial shows
a real one, and the honest reason recorded for it, rather than a false
attribution.

## A type that won't attribute

Secret Manager is the real, confirmed gap: its audit entries name a
secret using the project's numeric ID, which never appears in the
resource's own observed state at all, so there's nothing to match
against.

```bash
ubx scan --stack payments --propose adopt --type google_secret_manager_secret --name db-password
```

```bash
ubx why payments.google_secret_manager_secret.db-password
```

```bash
source: audit_unattributed
  backend: gcp_audit_logs
  reason: no_matching_event
```

Not a false attribution, not a silent skip, an honest, specific reason.

## Why this is the right behavior, not a bug to hide

The alternative would be guessing at an actor and presenting it as
fact. Every real audit backend in ubx has real gaps like this one, and
every one of them is named explicitly rather than papered over.

## What you just did

You saw a genuine attribution limitation reported honestly, the same
discipline every backend in ubx follows: attribution is best-effort,
and a failure is evidence in its own right, never hidden.

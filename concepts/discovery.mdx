---
title: "Cloud-Side Discovery"
description: "Enumerating existing infrastructure directly by tag or type, no state file at all."
---

Some real infrastructure was never managed by any tool at all, someone
clicked it into existence in a console years ago, and it has no state
file anywhere describing it. That infrastructure still needs a way into
the ledger.

## How it works

Discovery enumerates real resources directly, by tag or by type, against
the live cloud API itself, with no state file involved anywhere in the
process:

```bash
ubx scan --discover --tag team=payments
```

```bash
found 4 resource(s) matching team=payments, not yet in the ledger
next: ubx accept <hash>  (record them as-is, zero blast radius)
```

## Why requiring a state file first doesn't work

If bringing existing infrastructure under the ledger always required a
Terraform state file first, anything that was ever created by hand, in
a console, with no tool involved at all, would have no path in. That's
a real, common situation, not an edge case.

## What this actually looks like

Discovering a resource never creates or changes anything on its own.
It always produces an adoption proposal with an all-zero blast radius,
recording what already, genuinely exists as the ledger's own starting
point for that resource:

```bash
ubx accept <hash>
```

```bash
accepted <hash> (stack payments)
4 resource(s) adopted, 0 changed
```

Once adopted, every one of these behaves exactly like any other ledger
entry going forward: driftable, revertable, fully part of the same real
history.

## Why it matters

Nothing about how a resource originally came to exist limits whether it
can join the ledger. A resource created by hand, years ago, with no
record anywhere, can still be brought under real, permanent tracking
starting today.

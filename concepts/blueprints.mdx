---
title: "Blueprints"
description: "Build once with AI, call many times with zero AI."
---

If your team keeps building the same pattern, an ECR repository, an SQS
queue, an IAM role and policy wired together correctly, someone ends up
re-authoring that exact shape by hand every single time, in whichever
medium they happen to be using. Every repeat is a chance to get some
small detail wrong differently than last time.

## How it works

A blueprint is a reusable pattern, drafted once, then compiled into
real, deterministic code. The AI's job happens exactly once, at build
time. Every future call to the blueprint, from any medium, involves zero
AI, ever again.

```bash
ubx blueprint build . --lang all
```

That command drafts the pattern once and compiles the result into real
Go, TypeScript, and Python packages. From here forward, calling it is
just calling a function:

```go
import ciplatform "ciplatform"

ciplatform.CiPlatform("payments-ci-artifacts", "payments-notifications")
```

The same blueprint, called instead from a diagram or from prose,
resolves to a byte-identical result, proven directly, not assumed.

## Why hand-copying a pattern doesn't work

Copy-pasting the "same" resource pattern into a new stack means every
copy can quietly drift from the original, a forgotten attribute here, a
slightly different default there. There's no way to know later which
copies actually match, or to fix a real bug in the pattern everywhere at
once.

## What this actually looks like

Every resource a blueprint produces carries a permanent record of which
blueprint, and which exact version, created it:

```bash
ubx why payments.aws_iam_role.ci-runner
```

```bash
source: blueprint
  ref: ci-platform:sha256:a1b2c3...
  (this resource's own creation is signed by the CALLING stack's own
  acceptance below)
accepted by [roozbeh] via local at 2026-08-05T14:02:11Z
```

**Stated honestly, not glossed over:** there's only one real signature
here, the calling stack's own acceptance, shown above. There's no
separate ceremony yet for a blueprint author to sign their own
definition independent of any call, `ubx why` says so directly rather
than implying a dual-signature guarantee that doesn't exist. What you
get today is a permanent, accurate record of which blueprint produced a
resource and who accepted the proposal that created it, not a second,
independent signature from the blueprint's own author.

There's also no discovery mechanism, no registry to search, no `ubx
blueprint search`. A caller points at a ref they already know, a git
URL, an OCI reference, a local path, the same way you'd already know a
Docker image tag before pulling it. See
[Distributing a Blueprint](/concepts/blueprint-distribution) for what
"already know" actually means across all four real source types.

## Why it matters

The pattern gets designed correctly once. Every future use inherits that
correctness automatically, and if the pattern itself needs a fix, it's
fixed once, in one place, for everyone who calls it.

Building it is only half the story. See
[Distributing a Blueprint](/concepts/blueprint-distribution) for how a
built blueprint actually gets from its author's machine to everyone
else's, [List Parameters & Iteration](/concepts/blueprint-list-params)
for a blueprint that produces N resources instead of one, and
[Overriding a Blueprint's Internals](/concepts/blueprint-overrides) for
patching a resolved attribute the blueprint itself doesn't expose as a

---
title: "The Four Mediums"
description: "Four ways to author intent, one resolved output."
---

Different people think about infrastructure differently. Some want to
describe intent in plain English. Some want to draw a network as boxes
and arrows. Some want the precision of real code. Forcing everyone into
one single format means fighting the format at least as often as
describing what you actually want.

## How it works

Ubx supports four separate ways to describe a change, and all four
produce the exact same kind of output underneath: a resolved delta,
ready to review and sign.

- **Markdown**: you write prose, an AI drafts a proposal from it, reading
  the target stack's own name and config first (see
  [Context-Aware Drafting](/concepts/context-aware-drafting)).
- **Chat**: the same AI drafting, as a live conversation instead of a
  static file.
- **Diagram**: you draw real topology in D2, a structural parser reads
  it directly, no AI involved at all.
- **SDK**: you write real code in Go, TypeScript, or Python,
  `ubx.Resource(...)` calls are deterministic function calls, also no
  AI.

```bash
ubx plan --from-doc platform.md          # markdown
ubx chat                                  # chat
ubx plan --from-diagram platform.d2       # diagram
ubx plan --from-code create_platform.go   # SDK
```

## Why picking just one medium doesn't work

If ubx only supported prose, someone who wants compiler-checked
correctness for a reusable pattern would have to fight a language never
built for that. If it only supported diagrams, describing a nuanced IAM
policy in boxes and arrows would be awkward at best. Different parts of
the same real infrastructure genuinely suit different mediums, and
forcing one choice on everything creates friction nobody needs.

## What this actually looks like

The same underlying resource, described two different ways, resolves to
the identical result:

```bash
ubx plan --from-doc platform.md --stack payments
ubx plan --from-code create_platform.go
```

```bash
resolved: payments: 1 create(s), 0 change(s), 0 terminate(s)
```

Both commands land on the same delta shape. Everything after this point,
review, signing, shipping, works identically no matter which medium
produced it.

## Why it matters

You pick the medium that fits how you're already thinking about a given
piece of infrastructure, not the one ubx happens to support best. The
review and trust guarantees never change based on that choice.

---

Every example so far calls a blueprint once and gets back one instance.
Some patterns are naturally plural instead, one subnet per availability
zone, say, where the number of resources depends on a list the caller
passes in, not a fixed count baked into the blueprint.

## How it works

A `list(string)` or `list(number)` param, always required (a list param
has no notion of an unwritten default to fall back to):

```
# Ubxfile
params:
  vpc_id: string, required
  availability_zones: list(string), required

resources: ./resources.json
```

```json
// resources.json
{
  "resources": [
    {
      "type": "subnet",
      "name": "subnet-{availability_zones}",
      "op": "create",
      "for_each": "availability_zones",
      "config": {
        "availability_zone": "{availability_zones}",
        "cidr_block": "10.0.{availability_zones_index}.0/24",
        "vpc_id": "{vpc_id}"
      }
    }
  ]
}
```

The `for_each` field on the ONE resource that iterates names the list
param directly -- a real, structured field, set by whoever produced this
document, never inferred from prose. Inside that resource's own config,
two tokens carry a real, per-language meaning: the bare
`{availability_zones}` means the current loop element, and
`{availability_zones_index}` means its zero-based position. Referencing
either token on a different resource, or the bare list token anywhere
with no `for_each` declared for it, is a build-time error, never a
silent wrong substitution.

```go
func VpcSubnets(vpcId string, availabilityZones []string) []*ubx.Computed {
	var subnetList []*ubx.Computed
	for availabilityZonesIndex, availabilityZonesValue := range availabilityZones {
		item := ubx.Resource(Subnet, fmt.Sprintf("subnet-%v", availabilityZonesValue), SubnetConfig{
			AvailabilityZone: availabilityZonesValue,
			CidrBlock:        fmt.Sprintf("10.0.%v.0/24", availabilityZonesIndex),
			VpcId:            vpcId,
		})
		subnetList = append(subnetList, item)
	}
	return subnetList
}
```

TypeScript and Python compile the identical loop idiomatically,
`Array.prototype.forEach` and `enumerate()` in place of Go's `range`, the
same two tokens resolved the same way in each. No new runtime construct
exists in any of the three SDKs for this, real Go/TypeScript/Python
already have a `for` loop, so the whole feature is compiling a
structured `for_each` field down to an ordinary one.

## Why this isn't a new templating language

Terraform needed dedicated `count`/`for_each` syntax because HCL itself
has no loop construct. A blueprint compiles to real source code in a
real language that already has one, so there was nothing to invent
beyond deciding what the two tokens mean inside the one resource that
declares the iteration.

## Calling it

A caller in any of the three languages passes a real, native list
straight in, no wrapper type:

```go
vpcsubnets.VpcSubnets("vpc-123", []string{"eu-central-1a", "eu-central-1b", "eu-central-1c"})
```

```ts
vpcSubnets("vpc-123", ["eu-central-1a", "eu-central-1b", "eu-central-1c"]);
```

```python
vpc_subnets("vpc-123", ["eu-central-1a", "eu-central-1b", "eu-central-1c"])
```

A hand-written intent/v1 file's own `blueprint_calls` entry passes the
same list as one comma-separated string instead, the identical
`args: map[string]string` shape every scalar param already uses:

```json
{
  "blueprint_calls": [
    {
      "name": "vpc subnets call",
      "blueprint": "../vpc-subnets",
      "args": {
        "vpc_id": "vpc-0123456789abcdef0",
        "availability_zones": "eu-central-1a, eu-central-1b, eu-central-1c"
      }
    }
  ]
}
```

The blueprint's own already-compiled function runs the loop for real, at
the moment that call is expanded, exactly the way a scalar-param call
already runs the rest of the function, so this needed no new expansion
mechanism either.

## What this doesn't do

Three constraints are designed refusals, not gaps found later:

- **At most one iterating resource per blueprint.** Multiple simultaneous
  loops in one blueprint is real, unexplored complexity, not attempted.
- **An individual iteration is never addressable.** The iterating
  resource can't be the target of a sibling's own reference or a
  `depends_on`, only the compiled function's returned list exposes the
  instances it created, one at a time isn't reachable any other way.
- **A blueprint with an iterating resource can't also declare
  `outputs:`.** Combining a per-iteration return list with named
  single-instance outputs is real future work, not something this
  version does.

Every one of these is a build-time error naming exactly what's wrong,
never a silent best-effort result.

## Why it matters

A pattern that's naturally plural, N subnets, N availability zones, N
of anything a caller doesn't know the count of until they call it, gets
the same "build once, call many, zero AI after that" guarantee as a
single-instance blueprint. The caller writes an ordinary list literal;
the loop itself is real generated code, not a runtime interpretation of
one.

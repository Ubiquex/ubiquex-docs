---
title: "Ledger stores"
description: "Where the ledger's own JSON lives -- the in-repo git directory, or a configured remote object store"
---

Two separate storage questions, decided separately. **Authoring mediums**
(intent files, diagrams, SDK code, dialogues) always live in git as repo
assets — human-authored, PR-reviewed, pinned into a proposal by content
hash. Nothing configurable there. **The ledger's own JSON** (`proposals/`,
`applies/`) is different: it gets a configurable **store**, behind a
`LedgerStore` interface. The in-repo git directory — today's behavior,
and everything on this site outside this page — is the reference
implementation and the permanent default. A remote object store (`s3://`
today; `gs://`/`azblob://` designed, not yet wired) is for larger-than-repo
ledgers, org-central ledgers without a checkout, and WORM/retention tiers.

<Note>
  Vocabulary: this is a ledger **store** — the config key is `store`,
  matching the `LedgerStore` interface name — never a "backend." There's
  no server and no database; every store holds the same
  content-addressed, hash-chained JSON objects, just at a different
  address.
</Note>

## Configuring a store

```hcl
# .ubx/config.hcl
ledger = {
  store = "s3://acme-ledger/acme/prod/"
}
```

Absent, or `store = "git"`, is the unchanged default — every command
behaves exactly as it always has, `--ledger-dir` and all. Naming a
remote store instead is the only thing that changes anything.

## Addressing: derived by rule, never mapped per stack

A ledger address is always `<configured store>/<stack>/` — the stack
name is an address segment, appended automatically, never configured
separately:

```
s3://acme-ledger/acme/prod/          ← the configured store
├── payments/{proposals,applies,heads,...}   ← stack "payments"
└── network/{proposals,applies,heads,...}    ← stack "network"
```

A new stack needs zero setup — its own prefix appears the first time
anything is appended to it — and each stack under a store gets its own
independent head and hash chain (git-local's flat, single-chain layout,
where several stacks can share one interleaved chain, is kept forever as
the supported legacy shape; a remote store's own chain is always
per-stack).

## A real consequence: `--stack` is required to open a remote ledger

Git-local's flat layout means a command never had to know a proposal's
stack *before* opening the ledger — there's only ever one ledger for a
given `--ledger-dir`. A remote store's own per-stack addressing breaks
that assumption on purpose: opening a ledger at all means knowing which
stack's own address to open. Where a command's own argument already
names a stack — an intent file (`ubx resolve`), a proposal file
(`ubx accept`) — nothing new is required. Every command whose only
argument is a bare hash gained a `--stack` flag, required once a
stack's own config names a remote store: `ubx ship <proposal-id>`,
`ubx why <proposal-id>` (a resource-address argument to `why` already
names its own stack and needs nothing extra). `ubx status` and
`ubx scan --all` go one step further — a remote store has no single
"every stack" to enumerate, so `--stack` becomes outright required
there, not just optional-with-a-fallback (see [`ubx status`](/cli/status)'s
own note on this):

```text
$ ubx ship 3ff1769e2c4d2cadc8e492cce9ae5b465b9263b3f39a5aae946617ae8fc028c0 --provider ./fakeprovider
ship: --stack is required to open a remote ledger store (.ubx/config's [ledger] store is "s3://ubx-states/acme/prod/", not git) -- a remote store's own per-stack chain means opening one at all requires knowing which stack first
```

```text
$ ubx ship 3ff1769e2c4d2cadc8e492cce9ae5b465b9263b3f39a5aae946617ae8fc028c0 --stack payments --provider ./fakeprovider
applied: payments.fake_widget.s3livecheck
1 resource(s), 1 applied, 0 failed, 0 still unknown -- outcome: applied
```

## A worked example, live against real S3

The full `resolve` → `accept` → `ship` flow, backed by a real S3 bucket
instead of a local directory — the resource itself here is a test
fixture, but the ledger objects are genuinely written to and read back
from S3:

```text
$ ubx resolve intent.json --provider ./fakeprovider --out resolved.json
resolved: payments: 1 create(s), 0 modify(ies), 0 destroy(s)
```

```text
$ ubx accept resolved.json
accepted 3ff1769e2c4d2cadc8e492cce9ae5b465b9263b3f39a5aae946617ae8fc028c0 (stack payments)
```

```text
$ ubx ship 3ff1769e2c4d2cadc8e492cce9ae5b465b9263b3f39a5aae946617ae8fc028c0 --stack payments --provider ./fakeprovider
applied: payments.fake_widget.s3livecheck
1 resource(s), 1 applied, 0 failed, 0 still unknown -- outcome: applied
```

Reading the bucket directly afterward (not through `ubx` at all) confirms
the same objects the design predicts actually landed at the derived
address: `proposals/<id>.prop.json`, `applies/<id>.attempt-1.apply.json`,
`heads/genesis`, and the best-effort `head-hint` cache, all under the
stack's own `acme/prod/payments/` prefix.

## `$cross` by stack name

A [`$cross` reference](/concepts/proposal) can pin a neighbor either by
an explicit `ledger_dir` (a real path — the git-local shape, permanent)
or, once a stack is backed by a remote store, by the neighbor's own
**stack name**:

```json
{
  "tags": {
    "vpc_ref": {"$cross": {"stack": "networking", "to": "networking.fake_widget.main-vpc.id"}}
  }
}
```

`"stack"` resolves against the *current* stack's own `[ledger].store`
— the derived address is `<that store>/networking/`, the identical rule
[Addressing](#addressing-derived-by-rule-never-mapped-per-stack) above
describes, never a separately-configured path. The two forms are
mutually exclusive; giving both is refused outright, and giving neither
(or `"stack"` when the current stack has no base store to resolve
against — a git-local stack) is refused too, naming `ledger_dir` as the
git-local alternative.

### `[ledger.external]`: when a neighbor lives under a different base

The rare case — a neighbor stack addressed under a *different* store
than your own — is an override table, per stack name:

```hcl
ledger = {
  store = "s3://acme-ledger/acme/prod/"

  external = {
    "other-team" = "s3://other-team-ledger/other-team/prod/"
  }
}
```

A `$cross` by `"stack": "other-team"` resolves against this override
instead of the current stack's own store; every other stack name still
resolves against the current stack's own store as usual.

## A worked example, live against real S3: two stacks, one base, `$cross` by name

Two real stacks (`networking`, `payments`) under one real S3 base.
`networking` creates a resource first:

```text
$ ubx resolve networking-intent.json --provider ./fakeprovider --out networking-resolved.json
resolved: networking: 1 create(s), 0 modify(ies), 0 destroy(s)
$ ubx accept networking-resolved.json
accepted 11cb78278141bff345b955ac908e5ca07e65ace051a6469867e564c71c36f894 (stack networking)
$ ubx ship 11cb78278141bff345b955ac908e5ca07e65ace051a6469867e564c71c36f894 --stack networking --provider ./fakeprovider
applied: networking.fake_widget.main-vpc
1 resource(s), 1 applied, 0 failed, 0 still unknown -- outcome: applied
```

`payments`' own intent file names no `ledger_dir` at all — only
`{"$cross": {"stack": "networking", "to": "networking.fake_widget.main-vpc.id"}}`.
Resolving it derives the real address and pins the real head:

```text
$ ubx resolve payments-intent.json --provider ./fakeprovider --out payments-resolved.json
resolved: payments: 1 create(s), 0 modify(ies), 0 destroy(s)
```

```json
{
  "resolution": {
    "inputs": [
      {
        "kind": "cross_stack_pin",
        "resource": "networking.fake_widget.main-vpc",
        "observed_hash": "88e05d8509dc31a8b493122c99634f07a70ca795322fc41590dada1ab5e3930b",
        "pinned_head": "11cb78278141bff345b955ac908e5ca07e65ace051a6469867e564c71c36f894",
        "ledger_dir": "s3://ubx-states/acme/prod/networking/"
      }
    ]
  }
}
```

`ledger_dir` here is fully resolved — the real S3 address `"stack"`
derived it into, not the bare stack name. Accepting while the pin is
fresh succeeds normally:

```text
$ ubx accept payments-resolved.json
accepted 9082648d20a885915c80c65ddf35bff20fe5a2c3ad9fc880648ca74bdb716feb (stack payments)
```

A second `payments` proposal, resolved against the identical pin, is
then correctly **refused** once `networking`'s real head genuinely
advances — a real second proposal accepted against it, not a simulated
one:

```text
$ ubx accept networking-resolved-2.json
accepted ac5c0bf69d86bca315fd59e013727c72ad7285fb8b6723af6ed4283a1affe5d9 (stack networking)
$ ubx accept payments-resolved-2.json
accept: resolve: cross-stack pin is stale -- the neighbor ledger has advanced since this proposal was resolved: networking.fake_widget.main-vpc (ledger s3://ubx-states/acme/prod/networking/) pinned at 11cb78278141bff345b955ac908e5ca07e65ace051a6469867e564c71c36f894, now ac5c0bf69d86bca315fd59e013727c72ad7285fb8b6723af6ed4283a1affe5d9
```

Exit `1` — the same "resolved-time truth vs. accept-time reality"
staleness check [row 5 of the resolver's own adversarial
program](https://github.com/Ubiquex/ubiquex/blob/main/docs/resolver-adversarial.md)
already proved for git-local neighbors, now proven for a real remote
one too. Reading the bucket directly afterward (not through `ubx` at
all) confirmed every object at exactly the addresses this design
predicts, under each stack's own prefix — cleaned up afterward.

## The PR-acceptance ceremony: git signs, the remote store records

`ubx accept --from-merge`'s own verification ([`.ubx accept`](/cli/accept)'s
own reference, [Why trust the record](/concepts/trust-model)) is entirely
about **git and GitHub history** — the merge commit exists, the proposal
file at that commit still hashes to the PR body's own trailer, the
reviewers are whatever the GitHub API says right now — and none of that
changes for a stack whose store is remote. What changes is *where the
accepted record ends up living*, never *what's verified or how*: git
stays the signing surface, the configured `LedgerStore` becomes the
system of record. Once the unchanged git/GitHub verification succeeds,
`ubx accept --from-merge` opens the stack's own configured store — the
identical `[ledger]`-aware open local `ubx accept` already uses — and
writes the accepted record through it, CAS-guarded exactly like every
other accept. The git-committed proposal file is never deleted or
treated as disposable — git history stays permanent regardless — but
`ubx why`/`ubx status`/a later accept's own head check all read the
mirrored, authoritative copy in the configured store from this point on,
never the git-committed file directly.

Real transcript: a PR opened and merged against a real repo, accepted
against a stack backed by real S3:

```text
$ gh pr merge 4 --repo acme/infra --merge
$ ubx accept --from-merge edf42bbcce8c6719d5bc97df1004b794123641a1 \
    --repo-dir . --proposal-file .ubx/live-verify/ceremony.prop.json \
    --github-repo acme/infra
accepted b1f852714813431b6d62cac6c333f459e911d0cbfe69069b6d290ea6b8f06126 (stack ceremony) via PR #4, 0 approver(s)
```

Reading the bucket directly afterward (not through `ubx` at all)
confirms the accepted record — full `acceptance.method: "pr_merge"`,
`merge_sha`, `pr_number` — landed at exactly `<store>/<stack>/proposals/
<id>.prop.json`, the same derived address every other command reads
from:

```text
$ aws s3api get-object --bucket acme-ledger --key acme/prod/ceremony/proposals/b1f852714813431b6d62cac6c333f459e911d0cbfe69069b6d290ea6b8f06126.prop.json /tmp/readback.json
$ cat /tmp/readback.json
{
  "...": "...",
  "acceptance": {
    "method": "pr_merge",
    "merge_sha": "edf42bbcce8c6719d5bc97df1004b794123641a1",
    "pr_number": 4,
    "proposal_file": ".ubx/live-verify/ceremony.prop.json",
    "accepted_at": "2026-07-19T00:09:27Z"
  },
  "status": "accepted"
}
```

## What's wired today, and what isn't yet

<Note>
  `ubx resolve`, `ubx accept` (both local and `--from-merge`),
  `ubx ship`, `ubx why`, `ubx status`, `ubx scan`/`--all`,
  `ubx revert-plan`, `ubx writeback`, and the MCP surface all read
  `[ledger]`'s own `store` key now — the full primary CLI surface. Only
  `ubx propose` doesn't, because it never touches a ledger at all: it
  computes a proposal's canonical hash from a file, nothing else.
</Note>

`gs://` (GCS) and `azblob://` (Azure Blob Storage) are designed the same
way as `s3://` — one shared implementation, parameterized by whichever
`gocloud.dev/blob` driver opens the URL — but aren't wired yet: their own
driver packages pull in the full Azure SDK and GCP's own
monitoring/tracing stack, dozens of new dependencies apiece, confirmed
directly rather than assumed cheap just because the code path is shared.
Orphaned-proposal garbage collection and a cross-stack pin chain longer
than one hop are both named, real gaps too — neither is covered by any
adversarial row yet.

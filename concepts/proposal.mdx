---
title: "Proposal"
description: "The unit of change ubx records: a typed, hashed proposal"
---

Everything ubx records — a hand-authored change, an adopted resource, a detected
drift — is a **proposal**. A proposal is a JSON document with a fixed shape:
what changed (`delta`), why (`intent`), what it was resolved against (`resolution`),
its cost and blast radius, and, once accepted, who signed off on it and how.

## Kinds

A proposal has a `kind`. Two kinds are generated automatically by `ubx scan`:

- **`adoption`** — a resource ubx has never recorded before. Its `delta.creates`
  holds a full snapshot of the resource's observed state.
- **`drift_adopt`** — a resource ubx has recorded before, whose live state no
  longer matches what the ledger has for it. Its `delta.modifies` holds only the
  attributes that changed, as a before/after diff.

A third kind, **`change`**, is for a proposal you write by hand (or that some
other tool generates) — a change you're proposing to make, rather than something
`ubx scan` already observed.

Both `adoption` and `drift_adopt` proposals always have an all-zero
`blast_radius` — they record what's already true in the cloud, they don't
propose making anything happen.

## Identity is a hash, not a number

A proposal's `id` is the SHA-256 hash of its own canonical content (everything
except `id`, `acceptance`, and `status` — those are filled in once the proposal
is accepted, so they can't be part of what's hashed). There's no sequential
numbering. Two proposals with byte-for-byte identical content, resolved
independently, hash to the same ID.

## A minimal example

```json
{
  "schema_version": 1,
  "stack": "payments",
  "parent": "",
  "kind": "change",
  "intent": {
    "summary": "provision the payments database",
    "sources": [{ "kind": "manual_edit", "ref": "PR #42" }]
  },
  "delta": {
    "creates": [{ "stack": "payments", "type": "aws_db_instance", "name": "payments-db" }]
  },
  "resolution": { "resolved_at": "2026-07-12T00:00:00Z" },
  "cost_delta": { "monthly_usd": 59 },
  "blast_radius": { "creates": 1, "modifies": 0, "destroys": 0 },
  "status": "draft"
}
```

Accepting it computes the hash, fills in `id`/`status`/`acceptance`, and appends
it to the ledger:

```bash
ubx accept proposal.json --ledger-dir .
```

```text
accepted 89f98a80c66dc1eab122080eb33166980e9b69b0b119a141b978a270aa6ddea1 (stack payments)
```

```bash
ubx why 89f98a80c66dc1eab122080eb33166980e9b69b0b119a141b978a270aa6ddea1 --ledger-dir .
```

```text
proposal 89f98a80c66dc1eab122080eb33166980e9b69b0b119a141b978a270aa6ddea1 (change)
stack:  payments
status: accepted
intent: provision the payments database
  source: manual_edit PR #42 (content_hash=)
accepted by [roozbeh] via local at 2026-07-11T15:42:26Z
blast radius: +1 ~0 -0
```

## Acceptance

Acceptance binds a signature to the exact hash. There are two ways to accept a
proposal today:

- **`local`** — running `ubx accept proposal.json` on your own machine. Records
  who ran it (your OS username) and when.
- **`pr_merge`** — deriving acceptance from a merged, reviewed GitHub pull
  request (`ubx accept --from-merge`). Records the merge commit, the pull
  request number, and every reviewer whose most recent review was an approval.

See the [CLI reference for `ubx accept`](/cli/accept) for both flows.

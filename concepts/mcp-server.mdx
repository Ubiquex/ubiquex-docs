---
title: "MCP Server"
description: "Read-only assistant access to your own ledger and live infrastructure."
---

Asking an AI assistant a question about your infrastructure, "why does
this queue have a 14 day retention", is genuinely useful. Letting that
same assistant accidentally change something while looking for the
answer is a very different, much riskier thing. Those two capabilities
need to stay separate.

## How it works

Ubx exposes a real MCP server so an assistant can call commands like
`why`, `status`, and `scan` directly, connected like this:

```json
{
  "mcpServers": {
    "ubx": { "command": "ubx", "args": ["mcp"] }
  }
}
```

Against your ledger and your live infrastructure, every tool this
server exposes is read-only. Nothing it offers can create, modify, or
destroy a real resource, by design, not by convention. A separate group
of tools helps an assistant author a blueprint, a reusable pattern, not
a live resource, see
[AI-Assisted Blueprint Authoring](/concepts/mcp-blueprint-tools) for
what those cover and where the same line gets drawn again.

## Why exposing write access "just in case" doesn't work

An assistant that could both answer questions and make changes would
mean every question you ask carries a small, real risk of an unintended
side effect. Keeping the server strictly read-only removes that risk
entirely, an assistant connected this way can help you understand your
infrastructure, never change it.

## What this actually looks like

A question answered through the MCP server reads the exact same ledger
`ubx why` would read directly:

```bash
ubx why payments.aws_sqs_queue.pipeline-events
```

There's no separate, assistant-specific view of your infrastructure
that could ever disagree with the real one, it's the same command,
the same data, just reachable through a different interface.

## Why it matters

You get real, grounded answers about your own infrastructure's actual
history, from an assistant that structurally cannot change anything
while helping you understand it.

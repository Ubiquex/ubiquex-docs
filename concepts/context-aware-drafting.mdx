---
title: "Context-Aware Drafting"
description: "The AI can read a stack's own name and config before drafting. It still can't touch anything."
---

A document can genuinely depend on which real environment it's targeting.
"If this is production, enable KMS encryption and 14-day retention" is a
completely reasonable sentence to write, but before this, the AI had no
way to check. Every conditional like it either got guessed silently (the
one thing this project never allows) or blocked on a question that a
human with the same information could have answered from the stack name
alone.

## How it works

Before producing a draft, the AI can call one read-only tool,
`read_stack_config`. It returns the target stack's own name and a small,
fixed set of its real `.ubx/config` values, nothing else. No ledger read,
no live infrastructure state, no cost data, no write or execution
authority of any kind, the same containment every other AI-facing surface
in this project already has (see
[The AI Trust Boundary](/concepts/trust-boundary)).

```bash
cat payments-logs.md
```

```bash
Create an S3 bucket called payments-logs. If this is a
production environment, enable KMS encryption and 14-day log
retention. Otherwise, use default (AES256) encryption and
1-day log retention.
```

```bash
ubx plan --from-doc payments-logs.md --stack app3
```

```bash
AI defaults — you are signing these:

◦ Determined this is a production environment because the
  stack's own config reports github_repo
  'acme/app3-production-infra', whose name explicitly
  identifies it as production infrastructure; applied the
  document's production branch: KMS encryption and 14-day
  log retention.
    affects: aws_s3_bucket.payments-logs
```

The stack is named `app3`, nothing about that name says "production." The
AI worked it out from the real `.ubx/config`, `github_repo =
"acme/app3-production-infra"`, and named exactly which fact justified the
choice.

## Why "just ask a question" doesn't work for this

Before this, every conditional that depended on the target environment
blocked, every time, even when the answer was sitting in a config file a
human reviewer would have checked anyway. That's not a safety property,
it's friction with no corresponding benefit: the human still has to
answer a question the config file already answered. A tool with genuine
review-worthy ambiguity should block. A tool that could have looked
something up shouldn't have to ask instead.

## What this actually looks like when context genuinely can't resolve it

Making better-informed guesses doesn't mean guessing more often. Rerun
the identical document against a stack whose config gives no real signal
either way:

```bash
ubx plan --from-doc payments-logs.md --stack widgets
```

```bash
Questions (1):
  - [blocking -- review before accepting] The document's
    encryption/retention settings depend on whether this is
    a 'production environment', but the stack's own config
    (checked via read_stack_config) only exposed the stack
    name 'widgets' and its GitHub repo 'acme/widgets-infra'
    -- neither indicates an environment tier. Could not
    determine if 'widgets' is production. Defaulted to the
    non-production branch, but this should be confirmed.
```

The tool was genuinely called, "checked via `read_stack_config`" is in the
question text itself, it just had nothing useful to say. The AI didn't
fabricate a plausible-looking answer to avoid asking. It still blocked,
exactly as it always has when a real conflict can't be resolved from
what's actually known.

## What's deliberately out of scope

`read_stack_config` answers with `config.Stack` plus a small, fixed
subset of `.ubx/config`, its provider source, ledger store location,
GitHub repo, and similar. It never returns anything from `[intent]`
(that table holds API key references) or any freeform provider-config
table this project makes no promise is secret-free. It never reads the
ledger, never fetches a provider schema, never estimates cost, those
remain real, separate, later capabilities, not something this tool
quietly grew into. And it's markdown/chat only: a blueprint's own
resources get their context through real, declared parameters (see
[Blueprints](/concepts/blueprints)) instead, this tool plays no part in
building one.

## Why it matters

The review ceremony doesn't go away, every context-derived choice still
lands in the receipt you sign, exactly like every other assumption or
default the AI makes. What changes is how often you're asked something
you'd have answered from the stack's own name or config anyway. A
question you'd have answered by reading a config file yourself is a
question worth resolving without you.

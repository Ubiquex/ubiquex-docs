---
title: "Secrets"
description: "References and salted fingerprints, never material -- how ubx keeps secrets out of the ledger"
---

The ledger is forever — git history, once pushed, is essentially
permanent. That's the whole point for infrastructure change history, but
it's exactly the wrong property for a database password, an API key, or a
private key: `ubx` must be able to *detect* that a sensitive value
changed without ever *recording* what it changed to or from. **The
ledger holds references and salted fingerprints, never material.**

## What gets redacted, and when

Every provider schema flags some attributes `Sensitive` — the same flag
Terraform providers themselves define. Immediately after every live read
(`ubx scan`, `scan --all`, drift detection, revert), before that state is
hashed or written anywhere, `ubx` walks the schema's `Sensitive` flags
over what it just observed and replaces each flagged value — wholesale,
whatever its own shape (a string, a list, a nested object) — with:

```json
{ "$redacted": { "sha256": "<salted hash of the real value>" } }
```

This happens whether the sensitive attribute sits at the top level, or
nested inside a block, a list, a set, or a map of blocks — real provider
schemas were checked directly (both `hashicorp/aws` and `hashicorp/google`)
rather than assumed, and nested sensitivity turned out to be common, not
a hypothetical edge case: roughly as many `Sensitive` attributes appear
nested at least one level deep as appear at the top level.

By the time a proposal is generated, hashed, or written to disk, the real
value has never existed in any of `ubx`'s own persistent state — only the
fingerprint has.

## A worked example

Adopting a resource with a sensitive `master_password` attribute:

```bash
ubx scan --provider ./fakeprovider \
  --stack payments --type fake_db_instance --name payments-db \
  --lookup '{"id":"payments-db"}' \
  --ledger-dir . --out adopt.json
```

```text
new: payments.fake_db_instance.payments-db (908322392cb434395924801e90f8b2ffe840578c8fcc68a479ecd00982660df2) -- generated a "adoption" proposal
```

`adopt.json`'s snapshot carries the fingerprint, never the real password:

```json
{
  "state": {
    "id": "payments-db",
    "master_password": { "$redacted": { "sha256": "ec692fb3a62ce3280ae79fc116ddac0f791213afd2a9111d395e46637321e3f3" } },
    "name": null
  }
}
```

Scanning again against the *same* real password reports no drift — the
salted hash is deterministic for a given salt and value, so an unchanged
secret never looks like a change:

```text
no drift: payments.fake_db_instance.payments-db matches the ledger (observed_hash ...)
```

Once the real password actually rotates, the next scan detects it — the
same [drift](/concepts/drift) mechanism as any other attribute, just with
both sides redacted:

```bash
ubx scan --provider ./fakeprovider \
  --stack payments --type fake_db_instance --name payments-db \
  --lookup '{"id":"payments-db"}' \
  --ledger-dir . --out drift.json --no-attribution
```

```text
drifted: payments.fake_db_instance.payments-db (1346ebba4d73da12e63cddd2c7b7ba4d3804e292c7f698eb8d31a62f185b2561) -- generated a "drift_adopt" proposal
```

```json
{
  "delta": {
    "modifies": [
      {
        "target": { "stack": "payments", "type": "fake_db_instance", "name": "payments-db" },
        "before": { "master_password": { "$redacted": { "sha256": "ec692fb3a62ce3280ae79fc116ddac0f791213afd2a9111d395e46637321e3f3" } } },
        "after":  { "master_password": { "$redacted": { "sha256": "c5767f19c9d0cf38f0f352ce12027e64d14a49855ba10c72065e164c76001143" } } }
      }
    ]
  }
}
```

`before`/`after` are the *whole* `$redacted` object — never a sub-path
into it — the same "before/after hold only the attributes that changed"
convention every other diff in this project follows, applied at the
right granularity for a single value that happens to be redacted.

[`ubx why`](/cli/why) renders this in words instead of raw JSON:

```text
change: payments.fake_db_instance.payments-db: master_password: (redacted) -> (redacted)
```

## The salt: per ledger directory, generated on first use, never committed

The fingerprint is `sha256(salt || the real value, canonicalized)`, not a
bare unsalted hash — an unsalted hash of a plausible-but-not-astronomical
secret space (a common password, say) would be dictionary-attackable
straight out of the ledger. The salt lives at `.ubx/salt`, generated from
`crypto/rand` the first time anything needs it, alongside the existing
`.ubx/config`/`.ubx/ledger.lock`/`.ubx/lock` (see [Ledger](/concepts/ledger)).
`ubx` also makes sure `.ubx/salt` is listed in the ledger directory's
`.gitignore` — creating a minimal one if none exists — as a safety net
against an operator's own `git add -A` habit, on top of the file already
being `0600`.

**`.ubx/salt` must never be committed.** Stated honestly, not glossed
over: losing or regenerating it doesn't leak anything and doesn't make
detection blind — a scan always re-reads live state fresh regardless of
the salt. What it *does* break is equality comparison across history:
every subsequently-computed fingerprint for an unchanged real secret no
longer matches what's already in the ledger, so the very next scan
reports every sensitive attribute as drifted once, a false positive, not
a missed detection. Everything resettles against the new salt from that
point on.

## `writeback` and `revert-plan` always decline a redacted attribute

[`ubx writeback`](/cli/writeback) and [`ubx revert-plan`](/cli/revert-plan)
both correct `.tf` source from what the ledger recorded — but a redacted
value is a fingerprint, not the real material, and neither command will
ever write it into source control as if it were:

```text
$ ubx writeback <id> --ledger-dir . --tf-dir tf --write
payments.fake_db_instance.payments-db (tf/db.tf):
  declined: master_password -- value is redacted -- ubx cannot write secret material to .tf; restore this attribute from your secret store manually
```

The file is left completely untouched — no hash, no `$redacted` marker,
nothing lands in `.tf`. Restoring the real value is always a manual step:
`ubx` genuinely doesn't know what it was, redacted or not, and never
pretends otherwise.

## Bulk onboarding

[`ubx scan --all`](/cli/scan#bulk-onboarding-all) adopts resources with
sensitive fields exactly the same way — cleanly, with redaction applied —
and its batch summary reports how many attributes were redacted across
the whole walk, so redaction being applied is visible, not a silent side
effect:

```text
3 adopted, 0 skipped, 2 attribute(s) redacted
```

## What's explicitly out of scope

- **`resolution.inputs[].lookup`** (the `--lookup` value used to find a
  resource) is never redacted — see [Resource lookup conventions](/cli/lookup#--lookup-never-needs-and-never-redacts-secret-material)
  for why that's safe: no real provider schema this project has checked
  ever needs secret material to *locate* a resource, only to read one
  back.
- **A provider that negotiates wire protocol v6** and expresses a nested
  sensitive attribute via the modern `NestedType` mechanism (rather than
  the legacy nested-block mechanism every currently-integrated provider
  uses) isn't covered yet — both `hashicorp/aws` and `hashicorp/google`
  negotiate protocol v5, where `NestedType` doesn't exist on the wire at
  all, so this is a real gap only for a provider `ubx` doesn't support
  today.

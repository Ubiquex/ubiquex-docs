---
title: "Attribution"
description: "Identifying who caused a drift, via AWS CloudTrail, GCP Cloud Audit Logs, or Azure Activity Log"
---

When `ubx scan` detects [drift](/concepts/drift), it makes a best-effort attempt
to identify who caused it, by searching the cloud's own audit trail — AWS
CloudTrail, GCP Cloud Audit Logs, or Azure's Activity Log (see
[below](#beyond-aws-gcp-via-cloud-audit-logs))
— for the management event responsible. This happens automatically — no extra
flag needed — and never blocks the drift from being recorded, even when
attribution fails outright.

## What gets recorded

Every `drift_adopt` proposal's `intent.sources` gains one of two kinds of entry
(for an AWS resource — see [Beyond AWS](#beyond-aws-gcp-via-cloud-audit-logs)
for GCP's own `gcp_audit`/`audit_unattributed` pair, or
[Azure's](#azure-via-activity-log) `azure_activity_log`/`audit_unattributed`):

- **`cloudtrail`** — a matched CloudTrail event: the actor's IAM ARN, the event
  name, when it happened, and the source IP it came from.
- **`cloudtrail_unattributed`** — attribution was attempted and failed, with a
  `reason`. This is recorded as evidence in its own right, not silently omitted.

### A matched event

```bash
ubx why acad3e426d36fb90df66f319a56e11ae8723fd6380caf9ee0b897335c4480e3d --ledger-dir .
```

```text
proposal acad3e426d36fb90df66f319a56e11ae8723fd6380caf9ee0b897335c4480e3d (drift_adopt)
stack:  payments
status: accepted
intent: record drift on payments.aws_s3_bucket.payments-artifacts observed outside the ledger
  source: cloudtrail -- arn:aws:iam::123456789012:user/alice PutBucketTagging at 2026-07-11T14:02:17Z from 203.0.113.42
    event 9910b32a-2f22-44b9-8d18-88cd3b95841a (content_hash=sha256:1b7c9a2e4f6d8c0a3b5e7f9012345678deadbeefcafebabe0123456789abcde)
accepted by [roozbeh] via local at 2026-07-11T15:43:25Z
blast radius: +0 ~0 -0
```

### An unattributed drift

```text
  source: cloudtrail_unattributed -- too recent for CloudTrail to have delivered a matching event yet
```

## Why attribution can fail

`reason` is one of four values (the same four regardless of which backend
attempted the search — `cloudtrail_unattributed`/`audit_unattributed`
both use them):

| Reason | Meaning |
| --- | --- |
| `no_matching_event` | The search ran successfully, over a wide enough window to rule out delivery delay, but no event matched this resource. |
| `delivery_window` | The search window is narrower than the backend's own typical event-delivery latency (up to ~15 minutes for CloudTrail) — a real event may simply not have propagated yet. |
| `not_logged` | The search itself couldn't run — no credentials, no access, or the backend isn't reachable. |
| `not_configured` | The backend itself needs operator configuration `ubx` has no way to derive on its own, and that configuration is absent — today, only `k8s_audit_logs` (see [Kubernetes and Helm](#kubernetes-and-helm-eks-audit-logs) below); AWS's region, GCP's project, and Azure's subscription are all always derivable from `--provider-config`, so `cloudtrail`/`gcp_audit`/`azure_activity_log` never produce this reason. |

## Scope

Attribution searches AWS CloudTrail **management events** only, over
`LookupEvents` — the same events CloudTrail's default ~90-day event history
already retains, no trail configuration required. It does not use CloudTrail
Lake, and it does not look at data events (S3 object-level access, for example).

The search window is always `[the resource's last recorded observation, now]` —
read back from the ledger itself, never an arbitrary lookback.

## Turning it off

Pass `--no-attribution` to `ubx scan` to skip the CloudTrail search entirely for
that invocation.

## Beyond AWS: GCP via Cloud Audit Logs

`ubx`'s own attribution logic (which identity value to search by,
exact-match filtering, never guessing between several candidate events) is
written against one small interface — "search this platform's audit trail
for events referencing a resource, in a time window" — not against
CloudTrail's API directly. CloudTrail was the first implementation of that
interface; GCP's Cloud Audit Logs is the second, live as of `ubiquex-cli`'s
UBI-21.

Scanning a GCP resource with `--source hashicorp/google` (or a
`hashicorp/google` `--provider` binary) picks this backend automatically —
no separate flag. It searches Admin Activity audit logs (GCP's always-on
equivalent of CloudTrail's management events) for the resource, over the
same `[last ledger observation, scan time]` window every backend uses.

```bash
ubx scan --source hashicorp/google --provider-version 7.40.0 \
  --stack demo --type google_pubsub_topic --name my-topic \
  --lookup '{"id":"projects/my-project/topics/my-topic","name":"my-topic"}' \
  --provider-config '{"project":"my-project"}' \
  --ledger-dir .
```

```json
{
  "kind": "drift_adopt",
  "intent": {
    "summary": "record drift on demo.google_pubsub_topic.my-topic observed outside the ledger",
    "sources": [
      {
        "kind": "gcp_audit",
        "ref": "1qptahtcj5h",
        "content_hash": "sha256:4aee4ed033bcebc6c6328781450f28274164869e2456c94a5c73c93a9d4cf3d6",
        "event_id": "1qptahtcj5h",
        "event_name": "google.pubsub.v1.Publisher.UpdateTopic",
        "event_time": "2026-07-16T21:58:45Z",
        "actor_arn": "me@roozbeh.net",
        "source_ip": "93.228.76.41"
      }
    ]
  }
}
```

`gcp_audit` reuses `cloudtrail`'s own fields rather than inventing
GCP-specific ones — `actor_arn` carries the GCP principal's email address
here, not an ARN. When attribution fails, GCP proposals get the
generalized `audit_unattributed` kind (a `backend` field, `"gcp_audit_logs"`,
names which platform came up empty) instead of `cloudtrail_unattributed` —
which itself isn't going anywhere: every existing AWS ledger entry keeps it,
unchanged, permanently, and new AWS proposals keep using it too.

<Warning>
  Not every GCP resource type correlates correctly yet. GCP's own audit log
  entries don't consistently name the resource the same way across
  services — Pub/Sub's entries use the project ID (matching what `ubx`
  already observed, so correlation works, as shown above); Secret Manager's
  entries instead use the numeric project number, which `ubx` has no way to
  connect back to the resource it just scanned. A `google_secret_manager_secret`
  drift will report `audit_unattributed`/`no_matching_event` even when a
  real, matching audit log entry exists. See
  [`ubiquex-cli`'s own STATE.md](https://github.com/Ubiquex/ubiquex-cli) for
  the full finding.
</Warning>

Cloud Audit Logs' own delivery latency was measured directly (the same
"don't assume, measure" discipline CloudTrail's own ~2-minute finding
followed): one Pub/Sub mutation became queryable in about 18 seconds — much
faster than CloudTrail, and with no published latency ceiling the way
CloudTrail has a documented ~15-minute one.

## Azure via Activity Log

Scanning an Azure resource with `--source hashicorp/azurerm` picks a third
backend automatically — Azure Monitor's **Activity Log**, filtered to its
Administrative category (Azure's own always-on equivalent of CloudTrail's
management events / GCP's Admin Activity logs), over the same
`[last ledger observation, scan time]` window every backend uses.

```bash
ubx scan --source hashicorp/azurerm --provider-version 5.0.0 \
  --stack demo --type azurerm_resource_group --name my-rg \
  --lookup '{"id":"/subscriptions/<sub>/resourceGroups/my-rg","name":"my-rg"}' \
  --provider-config '{"subscription_id":"<sub>","use_cli":true,"features":[{}]}' \
  --ledger-dir .
```

```json
{
  "kind": "drift_adopt",
  "intent": {
    "summary": "record drift on demo.azurerm_resource_group.my-rg observed outside the ledger",
    "sources": [
      {
        "kind": "azure_activity_log",
        "ref": "57fdfc27-8c5d-40ec-9142-0a39fef00151",
        "content_hash": "sha256:5e9bcae50c528ff67ced2fcb051c96f99e19077e688c7d5b9794393e31e497dd",
        "event_id": "57fdfc27-8c5d-40ec-9142-0a39fef00151",
        "event_name": "Update resource group",
        "event_time": "2026-07-29T17:31:18Z",
        "actor_arn": "me@roozbeh.net",
        "source_ip": "2003:d4:c701:5ccd:3c1e:62e6:4c87:53f9"
      }
    ]
  }
}
```

Real, unedited output from a live-verified drift. `azure_activity_log`
reuses `cloudtrail`'s own fields, same as GCP — `actor_arn` carries the
Azure AD principal (a UPN or service principal object id) here, not an
ARN. When attribution fails, Azure proposals get the same generalized
`audit_unattributed` kind GCP uses (`backend`, `"azure_activity_log"`).

<Warning>
  A real, materially dangerous correlation gap was found and fixed while
  building this backend, not assumed clean: Azure Activity Log's own
  `resourceId` field comes back **lowercase**
  (`.../resourcegroups/<name>`), while the azurerm provider's own
  observed `"id"` attribute — the exact value `ubx` searches by — is
  **camelCase** (`.../resourceGroups/<name>`). A naive exact match
  against the raw id silently found zero events every time, with no
  error, indistinguishable from a genuine no-event case. Fixed:
  `ubx` now matches Azure Activity Log events against a resource's `id`
  case-insensitively. If you're integrating against Azure's Activity Log
  API directly yourself, this casing mismatch is worth knowing about
  independent of `ubx`.
</Warning>

Activity Log's own delivery latency was measured directly, the same
"don't assume, measure" discipline CloudTrail's and GCP's own findings
followed: a resource group update became queryable roughly 60–90 seconds
after the API call returned — slower than GCP's measured ~18 seconds,
faster than CloudTrail's documented ~15-minute ceiling.

## Kubernetes and Helm: EKS audit logs

Scanning a `kubernetes_*`/`helm_release` resource picks a fourth
backend automatically — against the EKS control plane's own
**audit** log stream (Kubernetes' `audit.k8s.io/v1` event schema:
`objectRef`, `user`, `sourceIPs`, `verb`, timestamps), delivered to
CloudWatch Logs. This is a different signal from CloudTrail entirely —
CloudTrail sees AWS API calls like `CreateCluster`; it has no visibility
into `kubectl apply`.

<Note>
  Dispatch is by which provider *scanned* the resource
  (`--source hashicorp/kubernetes`/`hashicorp/helm`), not by which cloud
  hosts it — an EKS cluster's own drift (scanned via
  `--source hashicorp/aws`, an `aws_eks_cluster` resource) stays exactly
  as CloudTrail-attributable as any other AWS resource.
</Note>

**Unlike AWS/GCP, this backend requires explicit, optional configuration**
— there's nothing in `--provider-config` that implies "which EKS cluster,
which CloudWatch log group" the way a region or project does. A new
`.ubx/config` table:

```toml
[k8s_audit]
cluster = "my-eks-cluster"
region = "us-east-1"
# log_group is optional -- defaults to /aws/eks/<cluster>/cluster
```

Left unconfigured, a `kubernetes_*`/`helm_release` drift's attribution
records `audit_unattributed`/`not_configured` — recorded as evidence in
its own right, same as every other unattributed reason, and never
blocking the drift from being detected or accepted:

```text
  source: audit_unattributed -- ...
```

<Warning>
  The EKS audit-log leg wasn't live-verified against a real EKS cluster
  this session — provisioning one is real, hourly-billed cloud
  infrastructure, judged out of proportion to attempt without checking in
  first, unlike the free/local `kind` cluster used to verify
  `kubernetes_*`/`helm_release` resource scanning itself (see
  [Resource lookup conventions](/cli/lookup#kubernetes-and-helm)).
  This backend's own correlation logic was checked as far as a local cluster
  allows: a `kubernetes_*` resource's own `id` attribute is confirmed to
  be `<namespace>/<name>`, exactly one of the candidate identity shapes
  it builds from a real Kubernetes audit event's `objectRef` — so
  the matching mechanism is believed sound, not confirmed end-to-end
  against a real EKS audit event the way CloudTrail's and GCP's own
  attribution were each confirmed against a real match. `DeliveryLag`
  ships as a documented, conservative placeholder (5 minutes), not a
  measured figure. See [`ubiquex-cli`'s own STATE.md](https://github.com/Ubiquex/ubiquex-cli)
  for the full writeup.
</Warning>

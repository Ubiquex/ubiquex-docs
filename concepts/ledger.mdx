---
title: "The Ledger"
description: "A permanent record of every change, never a mutable snapshot."
---

Imagine someone on your team opens a security group port by clicking
around in the AWS console, by hand, without telling anyone. A week
later something breaks, and you need to know: who changed that, and
when? With most infrastructure tools, the honest answer is: nobody
knows. The tool only remembers what your infrastructure looks like
*right now*. It has no memory of how it got that way.

## How it works

In ubx, every real change you make gets written down as a **proposal**,
a permanent record answering three questions: what changed, why, and
who agreed to it. "Agreed to it" means someone actually reviewed the
change and typed `yes` to confirm it, the same way you'd approve a pull
request before it merges. That's what "signed" means here: a real
person's real confirmation, recorded alongside the change itself.

Every time you make a change, a new proposal gets added. Nothing ever
replaces an older one. If you ship five changes to the same resource
over a month, you end up with five separate, permanent records, one per
change, each one still there, still readable, forever.

```bash
ls ledger/proposals/
```

```bash
45f63ce108492f6581fe452cc96421ca50195abae1c365ec3b76d700c38a8974.prop.json
8224643bbbc5ac77873005df504f1a6bd3dce76457c523876e0047ca60fb6e42.prop.json
c53c22fae1ae2fd81eee0e1bade10c1a40b83de5b019ceee26480e08d5fd0e6c.prop.json
```

Every one of those is a real file. Five changes means five files, all
still sitting there. None of them ever gets deleted or rewritten to
make room for the next one.

A useful comparison if you've used Git: a Git commit doesn't erase the
commits before it, it just adds one more entry to a history that keeps
growing. The ledger works the same way.

## Why not just keep the latest state

The simplest possible design would be to just remember what your
infrastructure looks like right now, and overwrite that record every
time something changes. It's tempting because it's simple: one file,
always up to date.

The problem is that this design can only ever answer one question,
"what does my infrastructure look like right now." It can never answer
"what did it look like three changes ago" or "who made that particular
change," because the old answer is gone the instant a new one exists.

```bash
# a "keep the latest state" design: one file, replaced every time
ship-change   # the record is replaced
ship-change   # replaced again
              # the version from the FIRST change is just gone
```

```bash
# ubx: a new file every time, nothing overwritten
ubx ship <hash-1>  # ledger/proposals/<hash-1>.prop.json is written
ubx ship <hash-2>  # ledger/proposals/<hash-2>.prop.json is ALSO written
                    # <hash-1>.prop.json is still there, untouched
```

Ubx doesn't have a single file like that at all. "What does my
infrastructure look like right now" is worked out by reading the
*entire* history and combining it, every time you ask (this combining
step is covered in [FoldState](/concepts/foldstate), if you want the
full detail). The point for now: the history itself, not a snapshot, is
the only thing ubx actually stores.

## What this actually looks like

Say two real changes were made to the same resource, a week apart.
Here's what asking about that resource's history actually shows you:

```bash
ubx why payments.aws_sqs_queue.pipeline-events
```

```bash
change 45f63ce1... (accepted 2026-08-04, roozbeh)
  created: message_retention_seconds = 86400

change 8224643b... (accepted 2026-08-05, roozbeh)
  modified: message_retention_seconds 86400 -> 1209600
```

Both of these are real, permanent records, still sitting on disk exactly
as they were written. The second one didn't overwrite or erase the
first. `ubx why` isn't cleverly reconstructing this story from scattered
logs, it's just reading the ledger back to you, in the order it
genuinely happened.

## Why it matters

You never have to trust a snapshot, or dig through Slack messages and
commit histories trying to piece together what happened. Every question
about "how did this get this way" has one real answer, sitting right
there, that can never quietly go stale or get silently overwritten by
whatever change comes next.

The ledger is where accepted [proposals](/concepts/proposal) live. It's a plain
directory on disk — every ubx command that reads or writes it takes a
`--ledger-dir` flag (defaulting to the current directory).

## On disk

```text
<ledger-dir>/
  ledger/proposals/<id>.prop.json   # one file per accepted proposal
  .ubx/ledger.lock                  # the current head: the most recently accepted id
  .ubx/lock                         # concurrency lock -- see "Concurrent access" below
```

Each proposal file is the full accepted proposal — hash, delta, resolution,
acceptance, everything. `ledger.lock` holds nothing but the head hash.
`.ubx/lock` is a different file with a different job (concurrency, not the
head pointer) — see below — and [`.ubx/config`](/cli/config) is a third,
also unrelated file in the same directory.

## It's a chain, not a set

Every proposal's `parent` field is the ledger's head hash at the moment it was
resolved. Accepting a proposal checks that `parent` still matches the current
head before appending — if something else was accepted in the meantime, the
proposal is stale and has to be re-resolved. This is what makes the ledger a
chain: you can walk it backwards from the head, through `parent`, all the way
to the first proposal (whose `parent` is empty).

## Stacks are independent, but not physically separated

A resource's address is `<stack>.<type>.<name>` — for example,
`payments.aws_db_instance.payments-db`. The `stack` is just a name you choose to
group related resources; there's no separate command to create one. Every
proposal belongs to exactly one stack, and `ubx why <stack>.<type>.<name>`
resolves a resource's history within its stack.

"Independent" describes how you *think about* stacks, not how the ledger is
physically laid out: one `--ledger-dir` is one chain on disk, and nothing
stops proposals for several different stacks from living in that same
directory, interleaved in accepted order — `stack` is a field recorded on
each proposal, not a separate directory ubx enforces per stack. Whether you
give each stack its own `--ledger-dir` or share one across several is a
deployment choice either way works correctly; [`ubx status`](/cli/status)'s
"every resource, every stack, by default" report depends on the shared-directory
shape being sound, and it is.

## Concurrent access

`.ubx/lock` makes it safe for a person and CI to both be working against
the same ledger directory at once. It's acquired only around the
ledger-mutating step of [`ubx accept`](/cli/accept) (both the local and
`--from-merge` tiers) — [`ubx scan`](/cli/scan), [`ubx why`](/cli/why), and
[`ubx status`](/cli/status) never write to the ledger, so they never
acquire it and are never blocked by it, no matter how long an accept
elsewhere is holding it.

If another process is genuinely still running and holding the lock, a
blocked `ubx accept` waits briefly and then fails clearly, naming the file
and the holder's process id:

```text
$ ubx accept proposal.json --ledger-dir .
Error: accept: append: ledger is locked by another process: .ubx/lock (held by pid 29771)
```

If the lock file names a process that's no longer running — killed, or
crashed before it could clean up after itself — that's detected
immediately (no need to wait out the contention window for a holder that
isn't there) and reported with explicit recovery guidance instead of being
silently broken or blocking forever:

```text
$ ubx accept proposal.json --ledger-dir .
Error: accept: append: stale ledger lock: holder is no longer running: .ubx/lock names pid 99999999, which is not running -- remove .ubx/lock to recover (confirm no ubx process actually holds it first)
```

`ubx` never removes `.ubx/lock` on your behalf even once it's confirmed
stale — deleting a lock file is a deliberate operator action (`rm
.ubx/lock`), not something a command that just failed to acquire it
should do for you. Either failure exits `2` (a genuine error, not an
actionable finding) — see [Exit codes](/cli/exit-codes).

## Reconstructing what's true now

The ledger never stores a resource's "current state" directly — it stores the
sequence of proposals that got it there. To answer "what does the ledger think
this resource looks like right now," ubx folds that sequence: start from the
resource's `adoption` proposal's snapshot, then apply every subsequent
`drift_adopt`'s before/after diff on top, in order. This is exactly what lets
`ubx scan` compare live state against "the ledger" for a resource that's had
several drifts recorded against it.

title: "SDK Reference"
description: "Author infrastructure as typed TypeScript, Go, or Python code, each evaluated hermetically -- no runtime package is published yet."
---

Three describe-only SDKs for authoring infrastructure as typed code, all
producing the exact same `intent/v1` shape: `@ubx/sdk` (TypeScript),
`github.com/ubiquex/ubx-sdk-go` (Go), and `ubx_sdk` (Python). All three
work today, through the CLI -- none is published yet (TypeScript's is
bundled directly inside the `ubx` binary; Go's needs a local `replace`
in your own `go.mod`; Python's runtime is likewise bundled, though its
own hermetic Python build is a separate, larger download -- see [The
hermetic evaluator](#the-python-evaluator) below), so there's no
separate install step: generate bindings, write a program, resolve it.

```bash
ubx sdk gen --out sdk/generated               # TypeScript (default) -> sdk/generated/ts/<source>/
ubx resolve --from-code payments.ts --out change.prop.json
ubx accept change.prop.json
ubx ship <proposal-id>
```

```bash
ubx sdk gen --lang go --out sdk/generated     # Go -> sdk/generated/go/<source>/
ubx resolve --from-code payments.go --out change.prop.json
ubx accept change.prop.json
ubx ship <proposal-id>
```

```bash
ubx sdk gen --lang py --out sdk/generated     # Python -> sdk/generated/py/<source>/
ubx resolve --from-code payments.py --out change.prop.json
ubx accept change.prop.json
ubx ship <proposal-id>
```

Each language writes a repo-shaped tree (own manifest, one directory per
AWS-service boundary, `--lang` its own path segment so all three can
share one `--out` without colliding) -- see [`ubx sdk
gen`](/cli/sdk-gen) for the full shape.

## TypeScript

### The runtime surface

A program's entire vocabulary is five functions and one type:

```typescript payments.ts
import { intent, resource, stack } from "@ubx/sdk";
import { Instance } from "./sdk/generated/ts/hashicorp-aws/db/instance.ts";

export default stack("payments", () => {
  intent({ summary: "provision the payments database" });

  resource(Instance, "payments", {
    engine: "postgres",
    instanceClass: "db.t3.small",
    allocatedStorage: 20,
    dbName: "payments",
    username: "payments_admin",
  });
});
```

- **`stack(name, fn)`** -- the module's default export. `fn` describes the
  stack's own desired resources; it never runs at import time, only when
  the evaluator explicitly asks for it.
- **`resource(binding, name, config)`** -- declares one resource. `binding`
  is a typed class from [`ubx sdk gen`](/cli/sdk-gen)'s own generated
  output, carrying the real provider type and field shape. Returns a
  handle for wiring into sibling resources (see `Computed<T>`, below).
- **`secret(backend, path)`** / **`cross(ledgerDir, address)`** -- typed
  constructors for a secret reference or a cross-stack reference, the
  same `$secret`/`$cross` markers a hand-written intent file already
  supports.
- **`intent({summary, sources?})`** -- the emitted document's own summary.
  Required, exactly once per stack.
- **`Computed<T>`** -- what a `resource()` call's own return value's
  fields are typed as. Never a real value: at evaluation time nothing has
  been created yet, so a just-declared resource's own `.id` is a
  *reference*, not a value. Passing one into another resource's config
  produces a `$ref`; trying to use it as a string, in arithmetic, or with
  `JSON.stringify` throws immediately, naming the address and the
  attempted operation.

Every field of a `resource()` call's return value is `Computed<T>` --
including ones the program itself just set -- and property access on a
`Computed<object>` drills recursively (`primary.settings.enabled` is
itself a valid, traceable `Computed<boolean>`).

### `ubx sdk gen`: local, pinned, offline after generation

Typed bindings are generated **locally**, from the real provider schema
your `.ubx/config` already pins -- never a published, version-matrixed
package for every provider. See [`ubx sdk gen`](/cli/sdk-gen) for the
full command reference; the short version:

```text
$ ubx sdk gen --out sdk/generated
generated 1682 resource type(s) for hashicorp/aws@6.54.0 -> sdk/generated/ts/hashicorp-aws
```

Generated files are meant to be committed to git, like any other
reviewable generated code. Evaluating a program never touches the
network -- only generation does.

### The hermetic evaluator

`ubx resolve --from-code` runs a program inside a real, locked-down [Deno](https://deno.com)
subprocess: no filesystem, network, environment, or subprocess access,
and no remote module resolution. This isn't a soft default -- it's
enforced unconditionally, with no configuration flag to widen it.

The evaluator also guards against accidental nondeterminism: `Date.now()`
and `Math.random()` throw immediately if a program calls them, and the
whole evaluation runs **twice**, as two separate subprocesses, with a
hard failure if the two runs ever disagree -- the same determinism
guarantee every other proposal-producing path in `ubx` makes.

## Go

### The runtime surface

The same five-function vocabulary, in Go -- `sdk.Stack`, `sdk.Resource`,
`sdk.Secret`, `sdk.Cross`, `sdk.Intent`, and `*sdk.Computed` in place of
`Computed<T>`:

```go payments.go
package main

import (
	sdk "github.com/ubiquex/ubx-sdk-go/runtime"

	db "github.com/ubiquex/ubx-sdk-aws/db"
)

func main() {
	sdk.Main(sdk.Stack("payments", func() {
		sdk.Intent(sdk.IntentInfo{Summary: "provision the payments database"})

		sdk.Resource(db.Instance, "payments", db.InstanceConfig{
			Engine:           "postgres",
			InstanceClass:    "db.t3.small",
			AllocatedStorage: 20,
			DbName:           "payments",
			Username:         "payments_admin",
		})
	}))
}
```

- **`sdk.Stack(name, fn)` / `sdk.Main(def)`** -- `fn` describes the
  stack's own desired resources; `sdk.Main` is what a program's own
  `main()` calls to evaluate it and print the result. Go has no
  import-time module-execution model the way TypeScript's default export
  does, so this is the one small piece of boilerplate every Go SDK
  program's `main()` has.
- **`sdk.Resource(binding, name, config)`** -- declares one resource.
  `config` is a typed struct from [`ubx sdk gen --lang
  go`](/cli/sdk-gen)'s own generated output. Returns a `*sdk.Computed`
  handle for wiring into sibling resources.
- **`sdk.Secret(backend, path)`** / **`sdk.Cross(ledgerDir, address)`** --
  the same `$secret`/`$cross` markers TypeScript's `secret()`/`cross()`
  produce.
- **`sdk.Intent(sdk.IntentInfo{Summary, Sources})`** -- the emitted
  document's own summary. Required, exactly once per stack.
- **`*sdk.Computed`** -- what `sdk.Resource()`'s own return value is.
  Never a real value, same reasoning as TypeScript's `Computed<T>` --
  but Go has no Proxy, so drilling into a nested attribute is an
  explicit `.Field(name)` method call rather than implicit property
  access: `primary.Field("settings").Field("enabled")` instead of
  `primary.settings.enabled`.

### `ubx sdk gen --lang go`

```text
$ ubx sdk gen --lang go --out sdk/generated
generated 1682 resource type(s) for hashicorp/aws@6.54.0 -> sdk/generated/go/hashicorp-aws
```

A repo-shaped tree -- its own `go.mod` (module
`github.com/ubiquex/ubx-sdk-aws`), one package per AWS-service boundary,
real bindings, real config struct per resource type, plus a runtime
descriptor:

```go sdk/generated/go/hashicorp-aws/db/instance.go (excerpt)
package db

type InstanceConfig struct {
	AllocatedStorage any
	DbName           any
	Engine           any
	InstanceClass    any
	Username         any
	// ...every other real aws_db_instance settable attribute
}

var Instance = sdk.ResourceBinding{
	WireType: "aws_db_instance",
	Fields: sdk.FieldMap{
		"AllocatedStorage": sdk.FieldSpec{WireName: "allocated_storage"},
		"DbName":           sdk.FieldSpec{WireName: "db_name"},
		// ...
	},
}
```

Every field is typed `any` (able to hold a real value, a `*sdk.Computed`
reference, or a `sdk.Secret`/`sdk.Cross` marker) -- unlike TypeScript's
generated `Config`/`Attrs` interface pair, there's no separate `Attrs`
type at all: Go's `Computed` has no static per-field shape (`.Field(name)`
works the same regardless), so there's nothing for a generated `Attrs`
type to describe. Your own program's `go.mod` needs a `require`+`replace`
pointing at the generated directory, the same local-checkout pattern the
runtime itself needs (see [`ubx sdk gen`'s own "No runtime package is
published yet"](/cli/sdk-gen#no-runtime-package-is-published-yet)) --
neither is published anywhere yet.

### The hermetic evaluator {#the-go-evaluator}

`ubx resolve --from-code <entry>.go` compiles the program to a real
binary (`go build`, `CGO_ENABLED=0`) and runs it hermetically -- not
inside a sandboxed interpreter (Go has none), but as an OS-level
restricted process: `sandbox-exec` (macOS's own process-sandboxing tool)
on macOS, [`bubblewrap`](https://github.com/containers/bubblewrap) (`bwrap`)
on Linux. Confirmed empirically to hold, not just documented as a goal:
no filesystem, network, or subprocess-spawned-network access, on either
platform. On Linux, `bwrap` must be on `PATH` -- `ubx` refuses to
evaluate unsandboxed rather than silently degrading if it's missing, or
if the environment denies creating its own namespaces (a real edge:
this can happen inside an already-hardened container, e.g. certain CI
images).

Determinism works differently than TypeScript's, and more simply:
compiled Go has no monkey-patchable `Date.now()`/`Math.random()`-style
ambient global to guard against, so there's no eager-guard layer at
all. The compiled binary runs **twice**, and any nondeterminism --
`time.Now()`, `math/rand`, anything else -- shows up as a byte
difference between the two runs and fails hard, the same determinism
guarantee every other proposal-producing path in `ubx` makes.

`go.mod` dependency resolution is restricted the same way network access
is: a program's own `go.mod` reaching for anything beyond a local
`replace` or the already-populated module cache fails the build loudly
(`GOPROXY=off`) rather than silently fetching untrusted code mid-
evaluation.

## Python

### The runtime surface

The same vocabulary again, in Python -- `sdk.stack`, `sdk.resource`,
`sdk.secret`, `sdk.cross`, `sdk.intent`, `sdk.run`, and `sdk.Computed` in
place of `Computed<T>`:

```python payments.py
import ubx_sdk as sdk
from db.instance import Instance, InstanceConfig


def describe():
    sdk.intent("provision the payments database")
    sdk.resource(Instance, "payments", InstanceConfig(
        engine="postgres",
        instance_class="db.t3.small",
        allocated_storage=20,
        db_name="payments",
        username="payments_admin",
    ))


if __name__ == "__main__":
    sdk.run("payments", describe)
```

- **`sdk.stack(name, fn)` / `sdk.run(name, fn)`** -- `fn` describes the
  stack's own desired resources; `sdk.run` is what a program's own
  `if __name__ == "__main__":` block calls to evaluate it and print the
  result -- Python's own natural entry-point idiom, the same role Go's
  explicit `func main()` plays, needing no separate generated-runner-
  script indirection the way TypeScript's evaluator does.
- **`sdk.resource(binding, name, config)`** -- declares one resource.
  `config` is a typed `@dataclass` from [`ubx sdk gen --lang
  py`](/cli/sdk-gen)'s own generated output. Returns a `sdk.Computed`
  handle for wiring into sibling resources.
- **`sdk.secret(backend, path)`** / **`sdk.cross(ledger_dir, address)`**
  -- the same `$secret`/`$cross` markers TypeScript's/Go's own
  constructors produce.
- **`sdk.intent(summary, sources=None)`** -- the emitted document's own
  summary. Required, exactly once per stack.
- **`sdk.Computed`** -- what `sdk.resource()`'s own return value is.
  Never a real value, same reasoning as `Computed<T>`/`*sdk.Computed` --
  drilling into a nested attribute is ordinary Python attribute access
  (`primary.settings.enabled`), implemented via `__getattr__` (Python's
  own native attribute-customization hook, the same mechanism countless
  dot-dict/ORM libraries already use) rather than an imitation of
  TypeScript's Proxy. Using a `Computed` as a real value -- `str()`,
  `bool()`, arithmetic, iteration -- raises immediately, naming the
  address and the attempted operation.

### `ubx sdk gen --lang py`

```text
$ ubx sdk gen --lang py --out sdk/generated
generated 1682 resource type(s) for hashicorp/aws@6.54.0 -> sdk/generated/py/hashicorp-aws
```

A repo-shaped tree -- its own `pyproject.toml` (name `ubx-sdk-aws`), one
real Python package per AWS-service boundary (`__init__.py` and all),
real `@dataclass` per resource type, plus a runtime descriptor:

```python sdk/generated/py/hashicorp-aws/db/instance.py (excerpt)
@dataclasses.dataclass
class InstanceConfig:
    allocated_storage: Any = None
    db_name: Any = None
    engine: Any = None
    instance_class: Any = None
    username: Any = None
    # ...every other real aws_db_instance settable attribute

Instance = sdk.ResourceBinding(
    wire_type="aws_db_instance",
    fields={
        "allocated_storage": sdk.FieldSpec(wire_name="allocated_storage"),
        "db_name": sdk.FieldSpec(wire_name="db_name"),
        # ...
    },
)
```

Field names need no case conversion at all here, unlike TypeScript's
camelCase or Go's PascalCase: every real provider wire name this project
generates against is already lowercase-with-underscores -- already a
valid Python identifier verbatim. The one real exception is a wire name
that collides with a Python keyword (e.g. a field literally named
`class`), closed with a trailing underscore (`class_`), the same
convention generated protobuf/thrift bindings already use -- applied at
the service-directory level too (a real, live-verified case: AWS's own
`lambda` service becomes `lambda_/`, since `lambda` is a Python
keyword). No separate `Attrs` type, for the same reason Go has none:
`Computed` has no static per-field shape. Put the generated repo's own
root (`sdk/generated/py/hashicorp-aws`) on `PYTHONPATH` to import its
service packages directly.

### The hermetic evaluator {#the-python-evaluator}

Python has no compiled-program cheat (unlike Go) and no built-in
permission model (unlike Deno) -- the hardest evaluator of the three,
and the one candidate that actually won reversed the going-in
expectation. `ubx resolve --from-code <entry>.py` runs the program under
[WASI](https://wasi.dev): [`wasmtime`](https://wasmtime.dev) running a
real, pinned CPython build compiled to WebAssembly. Confirmed
empirically to be the *strongest* isolation of any of the three
evaluators, not just an alternative: network and subprocess-spawning
are **absent as WASI capabilities**, not merely denied by a sandbox
policy -- a `_socket` module with no working `connect()`, a `subprocess`
module that raises "wasi does not support processes" outright. File
access outside the two directories the evaluator grants (the Python
standard library, and the program's own directory) fails as "no such
file or directory," not a permission error -- the path simply isn't
part of the sandboxed program's own view of the filesystem at all. The
exact same mechanism runs identically on macOS and Linux -- one
evaluator, not a different one per platform.

The CPython-WASI build itself (~40MB) is downloaded once and cached
locally (under `~/.ubx/python-wasi/`) the first time you run
`ubx resolve --from-code` against a `.py` entry -- not bundled into the
`ubx` binary itself, so installing `ubx` doesn't carry that cost for
users who never touch Python SDK programs. [`wasmtime`](https://wasmtime.dev)
itself must be on `PATH` -- `ubx` refuses to evaluate unsandboxed rather
than silently degrading if it's missing.

Determinism has one real, Python-specific wrinkle: `set`/`frozenset`
iteration order is randomized per process by default (a hash-flooding
DoS mitigation, not a bug) -- `ubx` pins `PYTHONHASHSEED=0`
unconditionally so this never surfaces as spurious nondeterminism. Plain
`dict` iteration order is unaffected either way (insertion-order,
guaranteed by the language itself since Python 3.7). Beyond that,
Python has no monkey-patchable `Date.now()`-style ambient global to
guard against either, the same simplification Go's own evaluator has --
the program runs **twice**, and any other nondeterminism shows up as a
byte difference between the two runs and fails hard.

## What a program can't do yet

- **Only creates**, in all three languages. A hermetic, sandboxed
  program has no way to check whether an address already exists in the
  ledger, so there's no way to author a `"modify"` from a program today
  -- use a hand-written intent file or [`ubx scan`](/cli/scan)'s own
  drift-generated proposals for that.
- **No published packages.** `npm install @ubx/sdk`, `go get
  github.com/ubiquex/ubx-sdk-go`, and `pip install ubx_sdk` all don't
  work yet -- every runtime ships bundled with `ubx` itself (Go's also
  needs a local `replace` pointing at a checkout). A real release of any
  of the three (mainly useful for editor/IDE convenience) hasn't
  shipped.

---
title: "ubx accept"
description: "Sign a proposal, locally or by deriving acceptance from a merged GitHub, Azure DevOps, or Bitbucket Server pull request, or a GitLab merge request."
---

Accepting is the real signing moment, the point where a proposal stops
being a draft and becomes a permanent, binding decision in the ledger.
`ubx accept` supports two genuinely different ways to do that: a local
file you sign directly, or deriving the signature entirely from a
merged, reviewed pull request (GitHub, Azure DevOps, Bitbucket Server)
or merge request (GitLab).

Before anything else, accept checks whether the proposal is fresh (has
the live resource moved since this was resolved?) and, if it destroys
anything, requires an explicit flag acknowledging that. Neither check
can be skipped by accident.

## Usage

```bash
ubx accept [proposal.json] [flags]
ubx accept --from-merge <commit-sha> --proposal-file <path> --github-repo <owner/name>
ubx accept --from-merge <commit-sha> --proposal-file <path> --gitlab-project <namespace/project>
ubx accept --from-merge <commit-sha> --proposal-file <path> --azure-devops-project <organization/project/repository>
ubx accept --from-merge <commit-sha> --proposal-file <path> --bitbucket-server-url <url> --bitbucket-server-project <PROJECTKEY/repository-slug>
ubx accept --from-merge <commit-sha> --proposal-file <path> --bitbucket-cloud-repo <workspace/repo-slug>
```

`--from-merge` always derives against exactly one platform -- exactly
one of `--github-repo`/`--gitlab-project`/`--azure-devops-project`/
`--bitbucket-server-project`/`--bitbucket-cloud-repo` is required, never
more than one, never none. `--bitbucket-server-project` is the one exception to "one flag
per platform": Bitbucket Server is self-hosted, with no single fixed
default host the other three platforms each have, so
`--bitbucket-server-url` is a real, always-required companion, not an
optional extra.

The other three platforms with a self-hosted product take an **optional**
base URL instead, since each has a real SaaS default to fall back on:
`--github-api-base-url` for GitHub Enterprise Server,
`--gitlab-api-base-url` for a self-managed GitLab, and
`--azure-devops-api-base-url` for an on-prem Azure DevOps Server. Set the
one matching the platform flag you are already using. Bitbucket Cloud has
none: it is SaaS with one fixed host.

<Note>
  These three flags are new in UBI-171. Before it, `--gitlab-api-base-url` had no flag at all, so
  `ubx accept --from-merge` could not reach a self-managed GitLab from a documented interface; the
  same gap applied to GitHub Enterprise Server and on-prem Azure DevOps Server.
</Note>

## Examples

Accepting a hand-written or resolved proposal directly:

```bash
ubx accept proposal.json --ledger-dir .
```

```bash
accepted 45f63ce10849... (stack payments)
```

Deriving acceptance from a real, merged pull request:

```bash
ubx accept --from-merge 8c1d2e... \
  --proposal-file proposals/db-replica.json \
  --github-repo acme/infra
```

```bash
accepted 45f63ce10849... (stack payments) via PR #42, 1 approver(s)
```

Deriving acceptance from a real, merged GitLab merge request:

```bash
ubx accept --from-merge 8c1d2e... \
  --proposal-file proposals/db-replica.json \
  --gitlab-project acme/infra
```

```bash
accepted 45f63ce10849... (stack payments) via MR !17, 1 approver(s)
```

Deriving acceptance from a real, merged Azure DevOps pull request:

```bash
ubx accept --from-merge 8c1d2e... \
  --proposal-file proposals/db-replica.json \
  --azure-devops-project acme-org/widgets/infra
```

```bash
accepted 45f63ce10849... (stack payments) via PR 17, 1 approver(s)
```

Deriving acceptance from a real, merged Bitbucket Server pull request:

```bash
ubx accept --from-merge 8c1d2e... \
  --proposal-file proposals/db-replica.json \
  --bitbucket-server-url https://bitbucket.example.com \
  --bitbucket-server-project PAYMENTS/payments-infra
```

```bash
accepted 45f63ce10849... (stack payments) via PR #17, 1 approver(s)
```

Deriving acceptance from a real, merged Bitbucket Cloud pull request:

```bash
ubx accept --from-merge 9601cb6... \
  --proposal-file proposals/db-replica.json \
  --bitbucket-cloud-repo acme/payments-infra
```

Bitbucket Cloud is a genuinely different platform from Bitbucket Server, not a hosted variant of
it, so it has its own flag and its own `BITBUCKET_CLOUD_TOKEN`. It needs no base URL companion:
Bitbucket Cloud is SaaS with one real, fixed host. See [Bitbucket
Cloud](/integrations/bitbucket-cloud).

## Flags

<ResponseField name="--ledger-dir" type="string" default=".">
  Root directory containing `ledger/` and `.ubx/` (default `.`).
</ResponseField>

<ResponseField name="--from-merge" type="string">
  Derive `pr_merge` acceptance from a merge commit SHA instead of accepting a local file.
</ResponseField>

<ResponseField name="--proposal-file" type="string">
  Path, within the repo, to the proposal the merge commit carries. Required with `--from-merge`.
</ResponseField>

<ResponseField name="--github-repo" type="string">
  `owner/name` of the GitHub repository. Exactly one of `--github-repo`/`--gitlab-project`/`--azure-devops-project`/`--bitbucket-server-project`/`--bitbucket-cloud-repo` is required with `--from-merge`.
</ResponseField>

<ResponseField name="--gitlab-project" type="string">
  `namespace/project` (or a numeric project ID) of the GitLab project. Exactly one of `--github-repo`/`--gitlab-project`/`--azure-devops-project`/`--bitbucket-server-project`/`--bitbucket-cloud-repo` is required with `--from-merge`.
</ResponseField>

<ResponseField name="--azure-devops-project" type="string">
  `organization/project/repository` of the Azure DevOps repo -- one more segment than GitHub's/GitLab's own flags, since Azure DevOps genuinely needs three real identifiers to address a repository, not two. Exactly one of `--github-repo`/`--gitlab-project`/`--azure-devops-project`/`--bitbucket-server-project`/`--bitbucket-cloud-repo` is required with `--from-merge`.
</ResponseField>

<ResponseField name="--bitbucket-server-url" type="string">
  Base URL of the self-hosted Bitbucket Server/Data Center instance, e.g. `https://bitbucket.example.com`. Required with `--bitbucket-server-project` -- Bitbucket Server, unlike the other three platforms, has no single fixed default host.
</ResponseField>

<ResponseField name="--bitbucket-server-project" type="string">
  `PROJECTKEY/repository-slug` of the Bitbucket Server repo. Exactly one of `--github-repo`/`--gitlab-project`/`--azure-devops-project`/`--bitbucket-server-project`/`--bitbucket-cloud-repo` is required with `--from-merge`; requires `--bitbucket-server-url`.
</ResponseField>

<ResponseField name="--bitbucket-cloud-repo" type="string">
  `workspace/repo-slug` of the Bitbucket Cloud repository. Exactly one of `--github-repo`/`--gitlab-project`/`--azure-devops-project`/`--bitbucket-server-project`/`--bitbucket-cloud-repo` is required with `--from-merge`. No base URL companion: Bitbucket Cloud is SaaS with one real, fixed host, unlike Bitbucket Server. Approvers are recorded as `account_id`s, because a Bitbucket Cloud account has no username at all.
</ResponseField>

<ResponseField name="--github-api-base-url" type="string" default="https://api.github.com">
  A GitHub Enterprise Server instance URL, e.g. `https://github.example.com`. GHES' own `/api/v3`
  path is applied for you. Leave unset for the real `github.com`.
</ResponseField>

<ResponseField name="--gitlab-api-base-url" type="string" default="https://gitlab.com">
  A self-managed GitLab instance URL, e.g. `https://gitlab.example.com`. Leave unset for the real
  `gitlab.com`.
</ResponseField>

<ResponseField name="--azure-devops-api-base-url" type="string">
  An on-prem Azure DevOps Server **collection** URL, e.g.
  `https://azuredevops.example.com/tfs/DefaultCollection`. Leave unset for the hosted Azure DevOps
  Services.
</ResponseField>

<ResponseField name="--repo-dir" type="string" default=".">
  Local git working tree to verify the merge commit's history against (default `.`).
</ResponseField>

<ResponseField name="--confirm-destroys">
  Required to accept any proposal with `blast_radius.destroys > 0`.
</ResponseField>

<ResponseField name="--reverify-with" type="string">
  Path to a provider binary: re-read the resource live and refuse if it no longer matches. Mutually exclusive with `--reverify-source`.
</ResponseField>

<ResponseField name="--reverify-source" type="string">
  Provider source to acquire for reverification (e.g. `hashicorp/aws`). Requires `--reverify-provider-version`.
</ResponseField>

<ResponseField name="--reverify-provider-version" type="string">
  Explicit provider version for reverification. Required with `--reverify-source`.
</ResponseField>

<ResponseField name="--resource-type / --resource-name" type="string">
  The resource to re-read. Required with either reverify flag.
</ResponseField>

<ResponseField name="--provider-config" type="string" default="{}">
  JSON object configuring the provider used for reverification (default `{}`).
</ResponseField>

<ResponseField name="--timeout" type="string" default="60s">
  Timeout for the reverify round trip (default `60s`).
</ResponseField>

## Notes

Cross-stack pins are always re-verified, whether or not you asked for
reverification, since checking a neighbor ledger's own head is a free,
local read, not a real provider round trip. Reverifying live state
against the provider, by contrast, stays opt-in, since it costs a real
network call.

For `--from-merge`, nothing about the acceptance is trusted from a
typed claim. The merge commit's real existence, the proposal's real
content at that commit, the real pull/merge request it belongs to, and
its real, current approving reviewers are all independently derived
from git and the platform's own API (GitHub's REST API with
`--github-repo`, GitLab's REST API with `--gitlab-project`, Azure
DevOps' REST API with `--azure-devops-project`, Bitbucket Server's own
REST API with `--bitbucket-server-url`/`--bitbucket-server-project`).
See [PR-Merge Acceptance](/concepts/pr-merge-acceptance) for the full
mechanism.

Each platform's own approval model is genuinely different, not just
differently named. GitLab has no CHANGES_REQUESTED-supersedes-APPROVED
concept -- its own merge request approvals endpoint already returns
the authoritative, current set of approvers directly, and by default
clears every existing approval when a new commit lands on the MR's
source branch (`reset_approvals_on_push`). Azure DevOps isn't binary
approve/reject at all -- a reviewer's vote is a real five-value scale
(`10` approved, `5` approved with suggestions, `0` no vote, `-5`
waiting for author, `-10` rejected); only `10` counts as an approver
here, since `5` is a real, qualified vote, not a full approval.
Bitbucket Server is the simplest of the four: a direct `approved`
boolean per reviewer, no fold or scale to interpret. On every
platform, `approvers` may legitimately be empty -- a merge with zero
approving reviews is recorded exactly as it happened, never rejected;
enforcing "this needed N approvals" is entirely the platform's own job
(branch or merge-request protection), never `ubx`'s.

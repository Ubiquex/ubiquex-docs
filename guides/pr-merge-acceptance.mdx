---
title: "PR-merge acceptance walkthrough"
description: "Getting a proposal reviewed and merged on GitHub before ubx records it as accepted"
---

[Local acceptance](/cli/accept) (`ubx accept proposal.json`) trusts whoever
runs the command. **PR-merge acceptance** instead derives acceptance from a
merged, reviewed GitHub pull request — the acceptance record is checkable
against git history and the GitHub API at any later time, not just taken on
faith. This walkthrough covers the whole flow end to end: drafting a
proposal, getting it into a mergeable PR, and accepting it once merged.

## 1. Draft the proposal

A proposal starts as a draft file — hand-written, or produced from whatever
authored the change (a dialogue, a script, a `ubx scan --surface-as pr`
receipt for drift, which handles steps 1–3 below automatically). This
walkthrough drafts one by hand:

```json proposals/pending.json
{
  "schema_version": 1,
  "stack": "payments",
  "parent": "",
  "kind": "change",
  "intent": {"summary": "postgres for payments", "sources": [{"kind": "dialogue", "ref": "d-1"}]},
  "delta": {"creates": [{"stack": "payments", "type": "aws_db_instance", "name": "payments-db"}]},
  "resolution": {"resolved_at": "2026-07-11T00:00:00Z"},
  "cost_delta": {"monthly_usd": 59},
  "blast_radius": {"creates": 1, "modifies": 0, "destroys": 0},
  "status": "draft"
}
```

A draft has no `id` or `acceptance` yet — both get added later,
`id` by hashing and `acceptance` by `ubx accept`.

## 2. Compute the trailer with `ubx propose`

```text
$ ubx propose proposals/pending.json
ubx-proposal: 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae
```

This hash is the same one [`ubx accept`](/cli/accept) will compute
internally later — `propose` never touches a ledger, it's a pure function of
the file's own content.

## 3. Open a PR carrying that trailer

Commit `proposals/pending.json` to a branch, push it, and open a pull
request whose body includes that hash as a `ubx-proposal: <hash>` line —
via the GitHub web UI, or something like:

```text
$ git checkout -b propose/payments-db
$ git add proposals/pending.json && git commit -m "propose: payments-db"
$ git push -u origin propose/payments-db
$ gh pr create --title "Provision the payments database" --body "$(cat <<'EOF'
## Provision the payments database

Adds a managed Postgres instance for the payments stack.

ubx-proposal: 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae
EOF
)"
```

The trailer is what step 5 checks against — anywhere in the body works, as
long as it's an exact `ubx-proposal: <hash>` line.

## 4. Get it reviewed and merged

Ordinary GitHub review: reviewers approve (or don't — see the note on zero
approvers below), then the PR merges to the default branch. Note the merge
commit's SHA; `ubx accept --from-merge` needs it.

## 5. Accept it with `ubx accept --from-merge`

```text
$ ubx accept --from-merge 1f4a193321c803340fcc3ae1d7bc387c74922763 \
    --repo-dir . \
    --proposal-file proposals/pending.json \
    --github-repo acme/infra \
    --ledger-dir .
accepted 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae (stack payments) via PR #42, 1 approver(s)
```

Three things happen here, in order, any one of which can reject the accept:

1. The merge commit SHA is confirmed to exist in `--repo-dir`'s git history.
2. `proposals/pending.json` is read *at that exact commit* and re-hashed;
   the result must match the merged PR's `ubx-proposal:` trailer exactly.
3. Every reviewer whose most recent review on that PR was an approval is
   recorded (a later `CHANGES_REQUESTED`, or a re-review after approving,
   supersedes an earlier approval from the same person).

### Zero approvers is normal, not an error

`ubx accept --from-merge` doesn't enforce a review policy — it's checking
that the *acceptance record* is honest about what git/GitHub history says,
not that some number of people signed off. A PR merged with no reviews at
all is accepted the same way, just with an empty approver list:

```text
$ ubx accept --from-merge 3f302d80d5a46e11394a5a58fbbd972691ffd011 \
    --repo-dir . \
    --proposal-file proposals/pending.json \
    --github-repo acme/infra \
    --ledger-dir .
accepted 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae (stack payments) via PR #42, 0 approver(s)
```

If you want N-approvals-required enforced, that's a branch protection rule
on the repo itself — `ubx accept --from-merge` will faithfully record
whatever the merge actually looked like, including zero reviewers, because
recording the truth is the point.

## 6. Confirm what got recorded with `ubx why`

```text
$ ubx why 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae --ledger-dir .
proposal 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae (change)
stack:  payments
status: accepted
intent: postgres for payments
  source: dialogue d-1 (content_hash=)
accepted by [roozbeh] via pr_merge at 2026-07-11T16:21:51Z
blast radius: +1 ~0 -0
```

## 7. Re-verify it later with `--verify-acceptance`

Anytime after, `ubx why --verify-acceptance` re-derives the same two checks
against *current* git history and the GitHub API, so you can confirm an old
acceptance record still checks out — or find out if it doesn't (a rewritten
merge commit is a hard failure; a reviewer who has since withdrawn their
approval is reported as a mismatch, not a failure, since the record was
correct at the time):

```text
$ ubx why 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae \
    --ledger-dir . --verify-acceptance --repo-dir . --github-repo acme/infra
proposal 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae (change)
stack:  payments
status: accepted
intent: postgres for payments
  source: dialogue d-1 (content_hash=)
accepted by [roozbeh] via pr_merge at 2026-07-11T16:21:51Z
blast radius: +1 ~0 -0
--- verify-acceptance ---
git: merge commit 1f4a193321c803340fcc3ae1d7bc387c74922763 exists in .
git: proposals/pending.json at that commit still hashes to 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae
github API: PR #42's approvers are unchanged ([roozbeh])
```

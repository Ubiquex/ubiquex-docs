title: "Authoring conventions for ubx propose --from-doc"
description: "Guidance for writing a document that transcribes reliably -- not a grammar ubx enforces"
---

[`ubx propose --from-doc`](/cli/propose#example-transcribing-a-document---from-doc)
accepts ordinary prose — there's no required structure, and a document that
doesn't follow anything below still works. These are patterns that reliably
improve extraction quality, worth knowing before you write one, never syntax
`ubx` parses or rejects a document for missing. What actually "works
reliably" is defined by this project's own conformance suite (golden
document-to-draft fixtures every supported adapter is checked against),
not this page.

## `@refs`

An inline `@<address>` mention — the same canonical
`<stack>.<type>.<name>` address form
[`ubx why`](/cli/why) and a hand-written intent file's own `$ref` already
use — is a strong, unambiguous signal to point at a specific existing
resource rather than describe it in prose:

```markdown
Provision it like our staging database (`@payments.aws_db_instance.staging`),
but smaller.
```

An `@ref` naming an address the model doesn't recognize as plausible (a
typo, a stack that doesn't exist) is never silently dropped or guessed at
— it becomes a `questions` entry naming the unresolved mention, the same
[ambiguity-as-visible-content](/guides/md-medium#ambiguity-is-visible-content-never-a-silent-choice)
rule every other gap in a document follows.

## Requirement phrasing

Two shapes of statement, both legal, transcribed differently:

- **Imperative, resource-shaped requests** map most reliably straight onto
  a resource entry: *"provision a `db.t3.medium` Postgres instance"*,
  *"destroy the old standby replica."* Little room for the model to
  interpret, so little shows up in `assumptions`.
- **Comparative or descriptive phrasing** — *"like staging but smaller,"*
  *"something cost-effective for a low-traffic service"* — is where this
  medium's own design center does its real work: the model has to turn a
  qualitative statement into a concrete value, and that conversion is
  exactly what gets recorded, not silently decided. See
  [The md medium](/guides/md-medium) for a full worked example.

Neither shape is "more correct" — write the way the requirement actually
occurs to you. A document mixing both (an explicit instance class for one
resource, "smaller" for another) transcribes each on its own terms.

## Cost ceilings

A stated dollar figure — *"keep this under $200/month"* — is transcribed
as context for the model's own reasoning, never as something it computes
or enforces. `ubx` has no real cost engine yet; a `cost_delta` only ever
appears on a proposal once [`ubx resolve`](/cli/resolve) produces one, and
resolving doesn't verify it against anything you wrote in a document.
If a requirement plausibly conflicts with a stated ceiling, the model
records that tension as a `questions` entry rather than silently
downsizing without saying so, or silently ignoring the ceiling — but
nothing about the document's own ceiling is ever authoritative on its
own. Treat it as a note for your own review, not a guardrail `ubx`
enforces for you.

## What never belongs in a document

Real secret material — an API key, a password, a private key — should
never be pasted into an authoring document in the first place.
[The md medium's own redaction-at-capture step](/guides/md-medium#secret-material-is-redacted-before-it-ever-leaves-your-machine)
is defense in depth for a mistake, not a reason to treat a document as a
safe place for it.

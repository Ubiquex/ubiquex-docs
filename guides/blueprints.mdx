Every other guide in this section starts a stack from scratch: an SDK
program, a diagram, or an md document, each authoring one team's own
infrastructure directly. A **blueprint** is different — it's a reusable,
parameterized TEMPLATE for a whole pattern (an ECR repo + SQS queue + IAM
role/policy/attachment for a CI pipeline, say), built once, then called
by name from any stack, any medium, any language, with real parameter
values substituted at call time.

<Note>
  **Not source-code inclusion.** A Terraform module is unaudited `.tf`
  you trust blind, re-evaluated fresh on every `terraform init`. A
  blueprint compiles to a real, content-hashed, independently
  `ubx blueprint verify`-able package — reviewed once, the exact same
  reviewed content hash cited by every caller forever, upgrading versions
  a visible, diffable act rather than a silent `terraform init -upgrade`.
</Note>

## Build once, call many

A blueprint's own resources: prose runs through the intent-provider
pipeline (the same one behind [the md medium](/guides/md-medium)) exactly
ONCE, at `ubx blueprint build` time — never again. Every subsequent call,
from any stack, in any language, via any medium, is zero-AI: a real
compiled function call (SDK), a real structural attribute read (diagram),
or a thin, bounded "map these param names" step (md — never a re-draft).
This is the entire point: two teams calling the identical blueprint get
byte-identical resolved deltas, never two subtly different AI
interpretations of the same prose.

The rest of this guide builds one real blueprint — `ci-platform`, an ECR
repository + SQS queue + IAM role/policy/attachment for a CI pipeline —
and walks it through every stage: author, build, call (all three
mediums), inspect its provenance, and distribute it (all four
mechanisms). Every transcript below is real, unedited output from the
actual `ubx` binary — nothing hand-typed.

## Author and build

A blueprint's own definition lives in an `Ubxfile` — three keys only,
found automatically the same way `docker build .` finds a `Dockerfile`:

```text Ubxfile
lang: all

params:
  repo_name: string, required
  queue_name: string, required
  retention_days: number, default 1

resources: |
  Infrastructure for our CI pipeline in eu-central-1. Note: the resource
  slugs below (container-repo, pipeline-events, ci-runner, ci-runner-access)
  are this template's own fixed internal identifiers, distinct from the
  {repo_name}/{queue_name} attribute VALUES named inside each resource --
  use the given slug as the resource's own name/identity, never the
  parameter token itself. Use each provider's own real, standard attribute
  names (e.g. "name") -- never invent a more descriptive synonym for a
  real attribute.

  1. An ECR repository, resource slug "container-repo", named
     "{repo_name}", for container images. Enable image scanning on push.
     Images should be immutable.

  2. An SQS queue, resource slug "pipeline-events", named "{queue_name}",
     for pipeline events. Standard queue. Its message retention period
     attribute is measured in SECONDS, but {retention_days} is expressed
     in DAYS -- convert it: the retention attribute's own value must be
     "{retention_days * 86400}", not the raw {retention_days} token.

  3. An IAM role, resource slug "ci-runner", named "ci-runner", that EC2
     instances can assume.

  4. A custom IAM policy, resource slug "ci-runner-access", named
     "ci-runner-access", that allows:
     - pushing and pulling images to/from the {repo_name} repository (only that one)
     - sending messages to the {queue_name} queue (only that one)
     Attach this policy to the ci-runner role.
```

`lang:` selects compiled output — `go`, `ts`, `py`, or `all` (every
language, the default when `--lang` is omitted, since the AI draft's own
cost is paid once regardless of how many languages compile from it).
`params:` become real typed function parameters in every compiled
language; `{param_name}` tokens in the prose (including simple
arithmetic, like the seconds-conversion above) are preserved literally
for the compiler to translate, never resolved to a guessed example value.

```text
$ ubx blueprint build .
drafting via claude:claude-sonnet-5… ✓
built 5 resource(s) -> /path/to/ci-platform (go, ts, py: go/bindings.go, go/ciplatform.go, go/go.mod, py/bindings.py, py/ciplatform.py, ts/bindings.ts, ts/ciplatform.ts)
```

One AI call, three real compiled packages — `go/`, `ts/`, `py/` sibling
directories, each with a typed `CiPlatform(repoName, queueName string,
opts ...Option)`-shaped function (Go's own functional-options pattern for
`retention_days`'s `default 1`; TypeScript/Python use native default
parameters instead, since neither language shares Go's syntax
limitation). `--lang go`/`--lang ts`/`--lang py` narrow to exactly one.

<Note>
  Two consecutive real drafts of the identical prose can legitimately
  split resources differently — the AI draft isn't guaranteed
  byte-identical run to run, only the resolved SHAPE is expected to match
  what the prose actually describes. `ubx blueprint build` refuses
  cleanly, naming the exact collision, if a draft ever produces two
  resources whose names collide once translated into a target language's
  own identifier rules — a real, captured example: `blueprint build (go):
  blueprint: resource names "ci-runner-access" and "ci-runner-access"
  both derive the Go identifier "CiRunnerAccess" -- rename one in
  resources.md`. Never a silent overwrite of one resource by the other.
</Note>

## Calling a blueprint

Zero AI, from any of three real mediums. All three below call the exact
same built `ci-platform` package with the exact same parameter values
(`repo_name=payments-ci-artifacts`, `queue_name=payments-notifications`,
`retention_days=14`) — resolved against the real `hashicorp/aws@6.54.0`
provider schema, a safe, apply-free operation.

### SDK: direct import

A plain SDK program — no blueprint machinery of its own — imports the
locally-built package (a real Go module `replace` directive, or your
package manager's own local-path equivalent for TS/Python) and calls its
function like any other typed function:

```go create_ci_platform.go
package main

import (
	ciplatform "ciplatform"
	sdk "github.com/ubiquex/ubx-sdk-go/runtime"
)

func main() {
	sdk.Main(sdk.Stack("payments", func() {
		sdk.Intent(sdk.IntentInfo{Summary: "CI platform for payments, direct SDK call"})
		ciplatform.CiPlatform("payments-ci-artifacts", "payments-notifications", ciplatform.WithRetentionDays(14))
	}))
}
```

```text
$ ubx resolve --from-code create_ci_platform.go --source hashicorp/aws --provider-version 6.54.0 --out resolved.json
resolved: payments: 5 create(s), 0 change(s), 0 terminate(s)
```

### SDK: direct import, Python — resolving a dependency from `requirements.txt`

Go resolves a locally-built blueprint via a `replace` directive; Python
has no equivalent "point my package manager at this local build"
mechanism at all. Instead, a Python stack declares a blueprint
dependency in an ordinary `requirements.txt`, sitting next to the entry
`.py` file, using pip's own real `<name> @ <url>` specifier syntax — no
new syntax invented:

```text requirements.txt
ci-platform @ oci://ghcr.io/ubiquex/ci-platform:v1
```

The `.py` source itself uses a plain import, no URL at all — exactly
like Go's own direct import above:

```python create_ci_platform.py
import ubx_sdk as sdk
from ciplatform import ci_platform


def build():
    sdk.intent("CI platform for payments, blueprint pulled from OCI at plan time")
    ci_platform(repo_name="payments-ci-artifacts", queue_name="payments-notifications", retention_days=7)


if __name__ == "__main__":
    sdk.run("payments", build)
```

`ubx plan`/`ubx resolve --from-code` reads `requirements.txt`, pulls and
verifies each declared dependency into ubx's own local cache (the same
`Pull`/`Verify` mechanism [OCI](#oci-a-real-live-registry) and
[git](#git) distribution already use — never a second, parallel
mechanism), and makes it importable — all BEFORE the script itself
runs. Per this project's own "never a silent network call" rule, every
pull renders a real receipt line, never a silent operation:

```text
$ ubx plan --from-code create_ci_platform.py --source hashicorp/aws --provider-version 6.54.0
pulled ci-platform @ oci://ghcr.io/ubiquex/ci-platform:v1, verified: content hash sha256:f893af6e945fe1e708af03dd60fe5372b76969579b3bdc8b70c3b4238968c885 matches (11 file(s))
Plan  payments · from create_ci_platform.py

  + aws_ecr_repository.container-repo create
      ...
  + aws_sqs_queue.pipeline-events create
      message_retention_seconds: 604800
      ...
  + aws_iam_role.ci-runner create
      ...
  + aws_iam_policy.ci-runner-access create
      ...
  + aws_iam_role_policy_attachment.ci-runner-access-attachment create
      ...

delta: +5 create(s), ~0 change(s), -0 terminate(s)
```

That's the same real, live `ghcr.io/ubiquex/ci-platform:v1` artifact
pulled above under [OCI](#oci-a-real-live-registry), resolved against the
real `hashicorp/aws@6.54.0` schema — `retention_days=7` correctly
converts to `message_retention_seconds: 604800` (7 × 86400), proving the
pulled package's own logic genuinely executed, not just that a file got
copied somewhere. A second `ubx plan` against the same
`requirements.txt` reuses the verified local cache instead of pulling
again — `pulled ci-platform @ oci://ghcr.io/ubiquex/ci-platform:v1
(cached), verified: ...` — with an identical resolved delta either way.

A dependency can equally be declared via git
(`widget-lib @ git+https://github.com/org/blueprints.git@v2#subdirectory=widget-lib`)
or a bare local path (`widget-lib @ ../shared/widget-lib`, never
cached — a local path is assumed to be actively edited, so it's pulled
fresh every time) — see [Distributing a blueprint](#distributing-a-blueprint)
below for the underlying mechanism each form reuses.

<Note>
  This mechanism resolves the DEPENDENCY, not its provenance — a resource
  produced this way carries ordinary document-sourced provenance (the
  calling script itself), not blueprint provenance. Python's own
  blueprint-CALL provenance (the gap the next section names for Go) is a
  real, separate, still-open follow-up.
</Note>

### Diagram: a `ubx_blueprint`-classed node

[The diagram medium](/guides/diagram-medium)'s own zero-AI structural
reading extends to blueprint calls: a node classed `ubx_blueprint`, a
required `blueprint:` attribute naming what to call, every other
attribute a real parameter value:

```d2 ci-platform-call.d2
platform: "ci-platform call" {
  class: ubx_blueprint
  blueprint: "/path/to/ci-platform"
  repo_name: "payments-ci-artifacts"
  queue_name: "payments-notifications"
  retention_days: "14"
}
```

```text
$ ubx propose --from-diagram ci-platform-call.d2 --stack payments --out diagram-draft.json
Questions (4):

      affects: platform.blueprint
  - [blocking -- review before accepting] node "platform.queue_name" has no class: attribute -- ubx can't infer its resource type from a label alone. Add a class: naming the real provider type (e.g. "class: aws_db_instance").
      affects: platform.queue_name
  - [blocking -- review before accepting] node "platform.repo_name" has no class: attribute -- ubx can't infer its resource type from a label alone. Add a class: naming the real provider type (e.g. "class: aws_db_instance").
      affects: platform.repo_name
  - [blocking -- review before accepting] node "platform.retention_days" has no class: attribute -- ubx can't infer its resource type from a label alone. Add a class: naming the real provider type (e.g. "class: aws_db_instance").
      affects: platform.retention_days

```

The four questions are real but harmless noise, not something to act
on — they're D2's own compiler seeing the `ubx_blueprint` node's
children (`blueprint:`, `repo_name:`, ...) as ordinary untyped nodes
before `ubx`'s own blueprint-node recognition takes over; the draft's own
`blueprint_calls` entry is unaffected and `ubx resolve` proceeds
normally:

```text
$ ubx resolve diagram-draft.json --source hashicorp/aws --provider-version 6.54.0 --out diagram-resolved.json
resolved: payments: 5 create(s), 0 change(s), 0 terminate(s)
```

### md: "Use blueprint X with..." prose

The one call site that uses AI at all — a thin, bounded mapping step
(never a re-draft of the blueprint's own resources):

```md create-ci-platform.md
# CI platform for payments, via a blueprint call

Use blueprint /path/to/ci-platform with:
  repo_name = payments-ci-artifacts
  queue_name = payments-notifications
  retention_days = 14
```

```text
$ ubx propose --from-doc create-ci-platform.md --stack payments --out md-draft.json
no assumptions, defaults, or open questions -- the document was unambiguous.
wrote draft: md-draft.json
$ ubx resolve md-draft.json --source hashicorp/aws --provider-version 6.54.0 --out md-resolved.json
resolved: payments: 5 create(s), 0 change(s), 0 terminate(s)
```

Zero hallucinated resources — the model's own job here is exactly "map
this prose onto real parameter names," nothing more.

### A known, honest gap: provenance differs by calling path

<Warning>
  **UBI-126, open.** The diagram and md calls above tag every resource
  they produce with `{"kind": "blueprint", "ref": "ci-platform:sha256:..."}`
  in its own resolved `sources` — real, inspectable, and what
  [`ubx why`](/cli/why#a-blueprint-calls-own-provenance)/[`ubx
  render`](/cli/render#example-a-blueprint-calls-own-resources-grouped)
  read below. The direct SDK-import call above does **not** — its
  resolved resources carry no blueprint provenance at all, even though
  the resolved DELTA (which resources, which config) is otherwise
  identical. Real, confirmed directly against each of the three resolved
  documents above:

  ```text
  # direct SDK import (resolved.json)
  aws_ecr_repository container-repo -> sources: None

  # diagram call (diagram-resolved.json)
  aws_ecr_repository container-repo -> sources: [{'kind': 'blueprint', 'ref': 'ci-platform:sha256:e92d28ba...'}]

  # md call (md-resolved.json)
  aws_ecr_repository container-repo -> sources: [{'kind': 'blueprint', 'ref': 'ci-platform:sha256:e92d28ba...'}]
  ```

  This is a real correctness gap, not a missing feature — the three
  calling conventions are supposed to be fully interchangeable, and their
  resolved deltas genuinely are (byte-identical, proven hermetically). If
  your stacks call blueprints via a direct SDK import today, `ubx
  why`/`ubx render` won't show that provenance until this is fixed.
  Tracked as [UBI-126](https://linear.app/ubiquex/issue/UBI-126) — the
  diagram/md path is the one to prefer meanwhile if blueprint provenance
  visibility matters to you.
</Warning>

## Distributing a blueprint

A built blueprint travels via any of four real mechanisms — all produce
the exact same thing on the other end (an ordinary local directory,
`blueprint.lock.json` included), all verified identically by [`ubx
blueprint verify`](#verify-everywhere-one-hash-scheme). `ubx blueprint
package` produces the one artifact three of the four mechanisms build on:

```text
$ ubx blueprint package ci-platform -o ci-platform-v1.tar.gz
packaged "ci-platform" -> ci-platform-v1.tar.gz (8 file(s), content hash sha256:e92d28ba064dbf0eded5ec7f64c6a0fcf51df957b96cf32df85e5d6b33b71d66)
```

### Local path

```text
$ ubx blueprint pull ./ci-platform ./pulled-local
pulled ./ci-platform -> ./pulled-local
```

### Git

Any git URL works — `https://`, `ssh://`, or (shown here, for a
self-contained example) a local `file://` repository; `--ref` picks a
branch/tag/commit, `--path` names the blueprint's own location within the
repo:

```text
$ ubx blueprint pull file:///path/to/some-org/infra-blueprints --path ci-platform ./pulled-git
pulled file:///path/to/some-org/infra-blueprints -> ./pulled-git
```

### OCI — a real, live registry

Any OCI registry works (GHCR, Docker Hub, Artifactory, Harbor — via
[ORAS](https://oras.land)), authenticated with the SAME credentials a
real `docker login`/`oras login` already established:

```text
$ ubx blueprint push ci-platform-v1.tar.gz --to oci://ghcr.io/ubiquex/ci-platform:v1
pushed "ci-platform" -> oci://ghcr.io/ubiquex/ci-platform:v1 (11 file(s), content hash sha256:f893af6e945fe1e708af03dd60fe5372b76969579b3bdc8b70c3b4238968c885)
```

That push is real, and it's still live — `ci-platform` is published
right now at
[`ghcr.io/ubiquex/ci-platform:v1`](https://github.com/orgs/ubiquex/packages/container/package/ci-platform),
usable as a genuine pull target. Its own content hash differs slightly
from the tarball built earlier in this guide — both are real
`ci-platform` builds from the identical `Ubxfile`, but from two separate
AI drafts. `package`'s own determinism guarantee is narrower than that:
re-packaging the SAME unchanged directory twice is byte-identical; two
independent drafts of the same prose can still legitimately differ in
exact generated code, even when the resolved resource SHAPE matches:

```text
$ ubx blueprint pull oci://ghcr.io/ubiquex/ci-platform:v1 ./pulled-oci
pulled oci://ghcr.io/ubiquex/ci-platform:v1 -> ./pulled-oci
$ ubx blueprint verify ./pulled-oci
verified "ci-platform": content hash sha256:f893af6e945fe1e708af03dd60fe5372b76969579b3bdc8b70c3b4238968c885 matches (11 file(s))
```

### Offline: a bare tarball file

The `package` output above is also a standalone, self-contained delivery
artifact — no network at all, air-gapped/email/support-ticket friendly:

```text
$ ubx blueprint pull ci-platform-v1.tar.gz ./pulled-offline
pulled ci-platform-v1.tar.gz -> ./pulled-offline
```

### Verify everywhere: one hash scheme

`ubx blueprint verify` recomputes a pulled directory's own content hash
and confirms it matches `blueprint.lock.json`'s declared value — the
SAME check regardless of which of the four mechanisms delivered the
content:

```text
$ ubx blueprint verify ./pulled-offline
verified "ci-platform": content hash sha256:e92d28ba064dbf0eded5ec7f64c6a0fcf51df957b96cf32df85e5d6b33b71d66 matches (8 file(s))
```

<Note>
  A blueprint's own declared `name` (derived from its directory's own
  basename at `package` time) is part of what gets hashed, alongside file
  content — re-packaging identical files from a differently-named
  directory produces a genuinely different hash. Not a bug (the hash is
  meant to identify WHICH blueprint this is, not just what bytes it
  contains) — but worth knowing if you're re-exporting a pulled blueprint
  for offline delivery: keep the directory named to match.
</Note>

This same content-hash scheme is also what makes **mirroring** trust-
preserving: pushing the identical tarball to a second, independent OCI
location (`ubx blueprint push ci-platform-v1.tar.gz --to
oci://some-other-registry/ci-platform:v1`) needs no new mechanism at
all — pulling from either location and running `verify` reports the
identical original content hash, proving the mirror is genuinely
unmodified, not just labeled as such.

## Putting it together

```
Ubxfile (params + prose)
  │  ubx blueprint build --lang all      ← AI, exactly once
  ▼
go/ ts/ py/ packages, real & compilable
  │
  ├─ called directly (SDK import)         ← zero AI, no provenance yet (UBI-126)
  ├─ called via a diagram (ubx_blueprint)  ← zero AI, full provenance
  └─ called via md ("Use blueprint X...")  ← thin AI mapping, full provenance
  │  ubx resolve → ubx accept → ubx ship
  ▼
real infrastructure, provenance-tagged
  │  ubx why / ubx render
  ▼
full chain visible: which blueprint, which version, who accepted the call
  │  ubx blueprint package
  ▼
ci-platform-v1.tar.gz
  │
  ├─ ubx blueprint pull <local dir>
  ├─ ubx blueprint pull <git URL> --ref --path
  ├─ ubx blueprint pull oci://<registry>/<repo>:<tag>   ← ghcr.io/ubiquex/ci-platform:v1, real
  └─ ubx blueprint pull <tarball file>                  ← offline, zero network
  │  ubx blueprint verify   (same check, every path)
  ▼
identical content, anywhere it lands
```

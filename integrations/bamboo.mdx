title: "Bamboo"
description: "Nightly drift watch, plan-on-pull-request, and merge-triggered shipping, running in Atlassian Bamboo."
---

Three independent plans, adapted from the [GitHub
Actions](/integrations/github-actions) reference implementation --
same real CLI contract underneath (`ubx status --drift`'s exit codes,
`ubx plan`'s own receipt, `ubx ship`'s own resolution rules), but
Bamboo's own real mechanisms for credentials, scheduling, pull request
builds, and notifications, verified independently rather than assumed
to mirror the three platforms already covered. Bamboo is meaningfully
different in character from all three: a self-hosted, Data Center
product with long-lived build agents, not a SaaS runner spun up fresh
per job.

<Note>
  This covers scheduled, pull-request-triggered, and merge-triggered
  automation only -- `ubx-agent` (UBI-28, parked) exists for the case
  this structurally can't cover: tight detection latency and an
  event-driven loop, not a cron tick or a merge hook. Nothing here is
  a substitute for that, it's what's real today.
</Note>

## The same real gap as GitLab and Azure DevOps

Confirmed once, directly against `ubx`'s own source
(`cli/accept.go`'s `--github-repo`-only flag, the `github/` package's
GitHub REST API calls), and true for every platform besides GitHub:
`ubx accept --from-merge` has no Bamboo equivalent. There's no
derivation from a Bitbucket, GitHub, or GitLab pull/merge request's
own review state through `ubx`. As with the other two, this is a real
gap in `ubx` itself, not a limitation of whatever VCS host a Bamboo
plan is watching. The honest fallback is the same: a merge-triggered
plan here ships an **already-accepted** proposal; acceptance itself
still happens through `ubx accept`'s local-file path, by a real
person, not derived automatically from the merge event.

## Prerequisites

Same as the other platforms: a stack repository with a real
`.ubx/config` and a git-local ledger already committed (see [Install
and initialize your first stack](/tutorial/setup/install)). Nothing
here runs `ubx init`.

### Installing ubx on the agent

```bash
curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
sudo mv ubx /usr/local/bin/
```

Pin an exact released version, not `latest`.

### Provider credentials: no native or AWS-maintained OIDC path

Drift-watch and ship-on-merge both need real AWS credentials.
Plan-on-pull-request, covered below, is a real, deliberate exception
the same way it is on the other three platforms -- `ubx plan`'s own
resolve step never makes a live provider call (confirmed directly
against `core/resolver/resolver.go`: no `Configure`, no live read,
ever), so it needs none. Everything below is for the two jobs that do
need a real AWS credential.

This is a real, material difference from the other three platforms,
not a smaller version of the same story. Bamboo itself has no native
OpenID Connect *issuer* capability the direction this needs -- its own
"OpenID Connect for Data Center" feature is for humans logging in to
Bamboo via an external identity provider, the opposite direction from
a build agent requesting a token that AWS trusts. There's no
AWS-maintained equivalent of GitHub's `aws-actions/configure-aws-
credentials` or the GitLab/Azure DevOps mechanisms already covered.

The only OIDC-capable path found is a **paid, third-party** Atlassian
Marketplace app -- Utoolity's "Identity Federation for AWS (Bamboo)"
-- and even that leans on Atlassian-group-to-AWS-role mapping rather
than the clean per-job workload identity federation GitHub, GitLab,
and Azure DevOps each provide natively or through an official
extension. Real, current, and worth naming honestly rather than
glossed over.

The realistic default, and what most real Bamboo/AWS setups actually
use: a long-lived IAM user's access key and secret key, stored as
Bamboo **Shared Credentials** or plan variables with a `.password`-
suffixed name (`${bamboo.aws_secret_access_key.password}`), which
masks the value in build logs. One honest caveat worth knowing:
Bamboo's own documentation describes this masking as the
`EncryptionService` *obfuscating* the value in its database, not a
substitute for real secret management -- genuine encryption-at-rest
for these values is, again, gated behind the same paid third-party
app. Scope the IAM user narrowly (drift-watch read-only, ship-on-merge
write) and rotate it like any other long-lived credential, since
there's no short-lived-token mechanism doing that for you here.

```yaml
tasks:
  - script:
      interpreter: /bin/sh
      scripts: |
        export AWS_ACCESS_KEY_ID=${bamboo.aws_access_key_id}
        export AWS_SECRET_ACCESS_KEY=${bamboo.aws_secret_access_key.password}
        ubx status --drift --stack payments \
          --source hashicorp/aws --provider-version 6.54.0 \
          --provider-config '{"region":"us-east-1"}'
```

### Caching provider binaries

Bamboo doesn't have a dedicated cache feature the way the other three
platforms do -- but it doesn't need one for this. Bamboo Data Center
agents are typically long-lived, self-hosted machines, not ephemeral
per-run containers, so `~/.ubx/providers` naturally persists on the
agent's own disk across runs with no explicit caching step at all. If
your setup instead uses genuinely ephemeral remote agents, the
provider cache directory would need to be restored from a shared
artifact each run -- real, but strictly worse than the other three
platforms' dedicated cache mechanisms, named honestly rather than
worked around with an unverified pattern.

## Workflow 1: nightly drift watch

Bamboo Specs YAML uses **Quartz-style, 6-field cron** (seconds,
minutes, hours, day-of-month, month, day-of-week), not the 5-field
Unix cron GitHub, GitLab, and Azure DevOps all use -- a real,
easy-to-get-wrong difference, not a cosmetic one. `0 0 6 ? * *` is 6am
UTC daily (`?` is Quartz's own wildcard, required in exactly one of
the day-of-month/day-of-week fields). Unlike Azure Pipelines, a
cron-triggered Bamboo build always runs at the scheduled time
regardless of whether anything changed -- no `always: true`-style
override needed here.

```yaml
version: 2
plan:
  project-key: PAYMENTS
  key: DRIFTWATCH
  name: Nightly drift watch

triggers:
  - cron: 0 0 6 ? * *

stages:
  - Drift check:
      jobs:
        - Check drift

Check drift:
  tasks:
    - checkout: default
    - script:
        interpreter: /bin/sh
        scripts: |
          curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
          sudo mv ubx /usr/local/bin/
          export AWS_ACCESS_KEY_ID=${bamboo.aws_access_key_id}
          export AWS_SECRET_ACCESS_KEY=${bamboo.aws_secret_access_key.password}
          ubx status --drift --stack payments \
            --source hashicorp/aws --provider-version 6.54.0 \
            --provider-config '{"region":"us-east-1"}'
```

`ubx status --drift`'s exit code (`0` clean, `1` drift found, `2`
unreadable, worse always wins -- see [`ubx
status`](/cli-reference/status)) fails the script task, and the job,
directly.

Bamboo's native alerting is real but the most manual of the four
platforms covered so far: unlike GitHub/GitLab's creator-scoped or
Azure DevOps' team-scoped defaults, a Bamboo plan sends no failure
notification at all until one is explicitly configured (Plan
Configuration → Notifications, or a `notifications:` block in Specs).
For a scheduled plan, "Committers" as a recipient scheme doesn't make
sense -- nobody necessarily committed anything near the failure --
so a specific "Responsible users" assignment or an explicit
recipient (email or group) is the real, workable choice, configured
for the "Failed Builds" event. As with the other platforms, no custom
script step is required to get an alert out of a *configured*
subscription, and no automatic PR or receipt gets posted anywhere --
that's `ubx-agent`'s job (UBI-28), not this plan's.

## Workflow 2: plan on pull request

`ubx plan` renders the same real receipt covered in [GitHub
Actions](/integrations/github-actions#workflow-2-plan-on-push) --
delta, blast radius, and a cost delta line when the resource's own
cost data is available -- without ever touching the ledger. As stated
above, this job needs no AWS credentials at all.

### Enabling this: plan branches, not a dedicated PR trigger type

Bamboo's own real mechanism for this is **plan branches**, confirmed
directly against Atlassian's own current documentation, not assumed
to work the way a GitHub/GitLab-style `pr:`/`rules:` trigger does.
When a plan's linked repository is Bitbucket Server, Data Center, or
Cloud, Bamboo can automatically create a plan branch -- and run it --
for every pull request opened against it. In the UI: **Plan
Configuration → Branches tab → "When a pull request is created."** In
Specs YAML, the real, equivalent key (the direct YAML counterpart of
the Java Specs API's own confirmed `createForPullRequest()` method) is:

```yaml
branches:
  create: for-pull-request
```

<Note>
  A real, honest limitation confirmed against Atlassian's own
  documentation, not glossed over: build status for a PR from a
  **forked** repository doesn't automatically appear back in
  Bitbucket, unlike a same-repository PR's. Bamboo's own real, default
  behavior already posts a same-repo PR's build status back to
  Bitbucket automatically once linked -- no scripting needed for that
  part. What still needs a script, on every platform this guide
  covers, is posting the actual `ubx plan` receipt as PR text, not
  just a pass/fail indicator.
</Note>

### The plan

```yaml
version: 2
plan:
  project-key: PAYMENTS
  key: PLANONPR
  name: Plan on pull request

branches:
  create: for-pull-request

stages:
  - Plan:
      jobs:
        - Plan

Plan:
  tasks:
    - checkout: default
    - script:
        interpreter: /bin/sh
        scripts: |
          set +e
          curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
          sudo mv ubx /usr/local/bin/
          ubx plan --ledger-dir . \
            --source hashicorp/aws --provider-version 6.54.0 \
            > plan-output.txt 2>&1
          plan_exit=$?

          python3 -c '
          import json
          body = {"text": open("plan-output.txt").read()}
          open("comment-body.json", "w").write(json.dumps(body))
          '
          curl -sf -X POST \
            -H "Authorization: Bearer ${bamboo.bitbucket_pat.password}" \
            -H "Content-Type: application/json" \
            -d @comment-body.json \
            "https://bitbucket.example.com/rest/api/1.0/projects/PAYMENTS/repos/payments-infra/pull-requests/${bamboo.repository.pr.key}/comments"

          exit $plan_exit
```

Three real, Bamboo-specific details, none obvious from copying the
other three platforms' own workflow:

- **`${bamboo.repository.pr.key}`** is the real, predefined Bamboo
  variable holding the pull request's own identifier when a plan
  branch was created from one -- confirmed directly against Atlassian's
  own current Bamboo variables reference. Bamboo calls it a "key," but
  it's the same value Bitbucket's own REST API paths expect as
  `{pullRequestId}` -- Bitbucket pull requests don't have any separate
  "key"-style identifier the way Jira issues or Bitbucket projects do.
- **There's no `bitbucket` CLI equivalent to `gh`/`glab` at all.** The
  real, current mechanism is a direct call to [Bitbucket Server's own
  pull request comments REST
  API](https://developer.atlassian.com/server/bitbucket/how-tos/updating-build-status-for-commits/)
  (`POST .../pull-requests/{pullRequestId}/comments`, a JSON body with
  a `text` field), authenticated with a Bitbucket personal access
  token stored as a Bamboo shared credential, the same
  `.password`-suffixed pattern already used for the AWS keys above --
  `${bamboo.bitbucket_pat.password}`. As on every other platform, this
  guide's own honest caveat about Bamboo's credential masking (stated
  above) applies to this token too.
- **No predefined variable exists for the Bitbucket project key or
  repository slug** -- confirmed absent from Atlassian's own variables
  reference, unlike the PR key. The plan's own `project-key: PAYMENTS`
  is already hardcoded at the top of every example in this guide, so
  the comment-posting URL above just reuses that same real, stated
  example rather than inventing an unconfirmed variable.

`set +e` at the top and capturing `plan_exit` before the comment-
posting call -- then `exit $plan_exit` as the script's own last line
-- is a single-script version of the `if: always()` pattern used on
GitHub Actions and Azure Pipelines: Bamboo Specs YAML has no separate
per-step `condition:`/`if:` keyword the way the other three platforms
do, so the whole sequence lives in one script task, with the real
resolve failure re-asserted at the very end so the job still fails on
a genuine error while the PR still gets the plan output either way.

## Workflow 3: ship on merge (real scope, stated above)

Given the gap above, this plan ships whatever is **already** accepted
in the ledger, triggered by new commits landing on `main`. It does not
derive or verify acceptance itself.

Bamboo's own real trigger types are mostly tied to a specific VCS host
(`bitbucket-server-trigger`, `bitbucket-cloud-trigger`,
`github-trigger`); `polling` is the one genuinely host-agnostic
mechanism, and Bamboo's own real default behavior -- polling the
repository on an interval, restricted to the plan's configured branch
-- covers "triggered by a push to main" honestly, if with poll-
interval latency rather than a webhook's immediacy. Teams on a
specific host should use that host's own named trigger instead for a
faster, webhook-driven equivalent.

```yaml
version: 2
plan:
  project-key: PAYMENTS
  key: SHIPONMERGE
  name: Ship on merge

triggers:
  - polling: 150

branches:
  create: manually
  default-branch:
    name: main

stages:
  - Ship:
      jobs:
        - Ship

Ship:
  tasks:
    - checkout: default
    - script:
        interpreter: /bin/sh
        scripts: |
          curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
          sudo mv ubx /usr/local/bin/
          export AWS_ACCESS_KEY_ID=${bamboo.aws_access_key_id}
          export AWS_SECRET_ACCESS_KEY=${bamboo.aws_secret_access_key.password}
          ubx ship --yes \
            --source hashicorp/aws --provider-version 6.54.0 \
            --provider-config '{"region":"us-east-1"}'
```

`ubx ship` with no `hash` resolves to the most recent unshipped,
already-accepted proposal for the stack -- see [`ubx
ship`](/cli-reference/ship). If nothing has been accepted since the
last ship, the run is a real no-op, not a failure. `--confirm-destroys`
is deliberately absent for the same reason it's absent from every
other platform's example: that acknowledgment has to already have
happened at accept time, not be silently implied by an unattended
plan run.

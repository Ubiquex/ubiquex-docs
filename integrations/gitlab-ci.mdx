Three independent pipelines, adapted from the [GitHub
Actions](/integrations/github-actions) reference implementation --
same real CLI contract underneath (`ubx status --drift`'s exit codes,
`ubx plan`'s own receipt, `ubx ship`'s own resolution rules), but
GitLab's own real mechanisms for scheduling, credentials, merge-request
events, and merge automation, verified independently rather than
assumed to mirror GitHub's.

<Note>
  This covers scheduled, merge-request-triggered, and merge-triggered
  automation only -- `ubx-agent` (UBI-28, parked) exists for the case
  this structurally
  can't cover: tight detection latency and an event-driven loop, not a
  cron tick or a merge hook. Nothing here is a substitute for that,
  it's what's real today.
</Note>

## Merge-derived acceptance

`ubx accept --from-merge` derives acceptance directly from a merged,
reviewed merge request, the GitLab counterpart to GitHub's own PR-merge
tier: the merge commit's real existence in git history, the proposal
file's real content at that commit, the real MR it belongs to, and its
real, current approving reviewers, read directly from the GitLab API.
`--from-merge` takes a `--gitlab-project namespace/project` flag,
structurally parallel to GitHub's own `--github-repo` -- confirmed
against `cli/accept.go` and the real `gitlab/` package directly, not
assumed symmetric with the GitHub guide.

GitLab's own approval model is genuinely different from GitHub's, not
just differently named -- confirmed against GitLab's own current API
docs. There's no CHANGES_REQUESTED-supersedes-APPROVED concept at
all: GitLab's merge request approvals endpoint already returns the
authoritative, current `approved_by` set directly, and by default
clears every existing approval outright when a new commit lands on the
MR's source branch (`reset_approvals_on_push`, on unless a project
turns it off). Read from an already-merged MR, `approved_by` reflects
exactly who approved the version that was actually merged either way
-- a merge with zero recorded approvers (because nobody re-approved
after a late push, or because it was never reviewed at all) is
recorded as it happened, never rejected; enforcing "this needed N
approvals" is GitLab's own job (merge request approval rules), never
`ubx`'s.

<Note>
  A real credential gap, confirmed directly against GitLab's own
  current `CI_JOB_TOKEN` documentation, not assumed working: the job
  token GitLab automatically injects into every pipeline can resolve a
  commit to its merge request, but is **not** authorized for the
  approvals endpoint at all. `ubx accept --from-merge
  --gitlab-project` needs a real, separately-provisioned **Project
  Access Token** (`read_api` scope is enough) stored as a masked,
  protected CI/CD variable -- `CI_JOB_TOKEN` alone silently isn't
  enough here, unlike GitHub Actions' own `GITHUB_TOKEN`, which already
  has read access to PR reviews out of the box.
</Note>

## Prerequisites

Same as GitHub Actions: a stack repository with a real `.ubx/config`
and a git-local ledger already committed (see [Install and initialize
your first stack](/tutorial/setup/install)). Nothing here runs `ubx
init`.

<Warning>
  **That git-local ledger is enough for Workflows 1 and 2 below, and not
  enough for Workflow 3.** Any workflow that runs `ubx accept` or `ubx
  ship` needs the repository's own `.ubx/config` to point at a real
  [remote ledger store](/tutorial/remote-stores) (S3, GCS, or Azure
  Blob) as well.

  `ubx` itself never runs `git commit`/`git push`, so an accept or ship
  written to a git-directory ledger lands only on the runner's own
  ephemeral filesystem and is gone the moment the job ends. Nothing
  errors and nothing is logged: the acceptance is simply never recorded
  anywhere.

  Drift-watch and plan-on-merge-request are unaffected, since neither
  appends to the ledger. This is the same requirement [`ubx
  server`](/server/github-setup#install-it) carries, for the same
  reason.
</Warning>

### Installing ubx in the runner

```bash
curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
mv ubx /usr/local/bin/
```

Pin an exact released version, not `latest` -- same reasoning as
pinning a provider version.

### Provider credentials: OIDC to AWS, no stored keys

Drift-watch and ship-on-merge both need real AWS credentials.
Plan-on-merge-request, covered below, is a real, deliberate exception
the same way it is in the GitHub guide -- `ubx plan`'s own resolve
step never makes a live call, so it needs none.

GitLab's OIDC mechanism, for the two jobs that do need credentials, is
structurally different from GitHub's, not just differently named. A
job requests a token explicitly with the `id_tokens` keyword, and
there's no GitLab-maintained equivalent of
`aws-actions/configure-aws-credentials` -- the real, current, GitLab-
documented pattern calls `aws sts assume-role-with-web-identity`
directly:

```yaml
ship:
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com
  script:
    - >
      creds=$(aws sts assume-role-with-web-identity
      --role-arn ${AWS_ROLE_ARN}
      --role-session-name "ubx-${CI_PROJECT_ID}-${CI_PIPELINE_ID}"
      --web-identity-token ${GITLAB_OIDC_TOKEN}
      --duration-seconds 3600
      --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]'
      --output text)
    - export AWS_ACCESS_KEY_ID=$(echo $creds | cut -d' ' -f1)
    - export AWS_SECRET_ACCESS_KEY=$(echo $creds | cut -d' ' -f2)
    - export AWS_SESSION_TOKEN=$(echo $creds | cut -d' ' -f3)
```

Setup on the AWS side:

1. Create an IAM OIDC identity provider with the provider URL set to
   your GitLab instance (`https://gitlab.com` for GitLab.com itself),
   audience `https://gitlab.com` (matching the `aud` claim requested
   above -- GitLab's own convention, not `sts.amazonaws.com` the way
   GitHub's is).
2. Create an IAM role with a trust policy scoped to the token's `sub`
   claim, which GitLab composes from the project path and ref:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/gitlab.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "gitlab.com:sub": "project_path:<GROUP>/<PROJECT>:ref_type:branch:ref:main"
      }
    }
  }]
}
```

As with GitHub, drift-watch and ship-on-merge want different real
permissions on that role -- read-only for drift-watch, write for
ship-on-merge. Two separate roles is the least-privilege choice.

```yaml
cache:

```

## Workflow 1: nightly drift watch

Scheduling in GitLab isn't part of the pipeline file the way GitHub's
`on: schedule:` is -- a **Pipeline Schedule** is a separate object,
created in the project's CI/CD → Schedules settings (or the [Pipeline
Schedules API](https://docs.gitlab.com/api/pipeline_schedules/)), with
its own cron expression, target branch, and owner. `.gitlab-ci.yml`
only needs a `rules:` condition to select which jobs actually run when
that schedule fires:

```yaml
drift-watch:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com
  cache:
    key: ubx-providers-hashicorp-aws-6.54.0
    paths:
      - ~/.ubx/providers
  script:
    - curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
    - mv ubx /usr/local/bin/
    - >
      creds=$(aws sts assume-role-with-web-identity
      --role-arn ${AWS_ROLE_ARN_DRIFT_WATCH}
      --role-session-name "ubx-drift-${CI_PIPELINE_ID}"
      --web-identity-token ${GITLAB_OIDC_TOKEN}
      --duration-seconds 3600
      --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]'
      --output text)
    - export AWS_ACCESS_KEY_ID=$(echo $creds | cut -d' ' -f1)
    - export AWS_SECRET_ACCESS_KEY=$(echo $creds | cut -d' ' -f2)
    - export AWS_SESSION_TOKEN=$(echo $creds | cut -d' ' -f3)
    - >
      ubx status --drift --stack payments
      --source hashicorp/aws --provider-version 6.54.0
      --provider-config '{"region":"us-east-1"}'
```

`ubx status --drift`'s exit code (`0` clean, `1` drift found, `2`
unreadable, worse always wins -- see [`ubx
status`](/cli-reference/status)) is exactly the job's own exit code,
same as GitHub -- the last `script` line's exit status fails the job
directly, no extra logic needed.

GitLab's own native alerting is real but differently scoped than
GitHub's: pipeline event notifications are sent to the **pipeline's
creator**, and for a scheduled pipeline that's the schedule's owner --
the user who created the Pipeline Schedule object, since a scheduled
pipeline runs with that user's own project permissions. Each user
configures their own notification level (Profile → Notifications),
including a failure-only option. As with GitHub, no custom
notification step or webhook is required to get a real alert out of
this, and no automatic PR or receipt gets posted anywhere -- that's
`ubx-agent`'s job (UBI-28), not this pipeline's.

## Workflow 2: plan on merge request

`ubx plan` renders the same real receipt covered in [GitHub
Actions](/integrations/github-actions#workflow-2-plan-on-push) --
delta, blast radius, and a cost delta line when the resource's own
cost data is available -- without ever touching the ledger. Unlike
drift-watch and ship-on-merge, this pipeline needs no AWS credentials
at all: `ubx plan`'s resolve step only ever queries the provider's
schema (confirmed directly against `core/resolver/resolver.go`, same
finding as GitHub's own guide), never a live read.

GitLab's own merge-request-pipeline mechanism is real and current, but
different in kind from GitHub's `opened`/`synchronize` event pair --
one pipeline source, `merge_request_event`, covers every pipeline run
associated with an MR, including the first one and every subsequent
push to its source branch, selected the same `rules:` way as
drift-watch's own schedule condition:

```yaml
plan:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  cache:
    key: ubx-providers-hashicorp-aws-6.54.0
    paths:
      - ~/.ubx/providers
  script:
    - curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
    - mv ubx /usr/local/bin/
    - curl -L https://gitlab.com/api/v4/projects/gitlab-org%2Fcli/packages/generic/glab/1.113.0/glab_1.113.0_linux_amd64.tar.gz | tar xz --strip-components=1 bin/glab
    - mv glab /usr/local/bin/
    - export GLAB_ENABLE_CI_AUTOLOGIN=true
    - >
      ubx plan --ledger-dir .
      --source hashicorp/aws --provider-version 6.54.0
      > plan-output.txt 2>&1
    - glab mr note create $CI_MERGE_REQUEST_IID -m "$(cat plan-output.txt)"
```

Two real GitLab-specific details, neither obvious from copying
GitHub's own workflow:

`GLAB_ENABLE_CI_AUTOLOGIN=true` is required, not automatic -- unlike
`gh` on a GitHub-hosted runner, `glab` does not auto-detect
`CI_JOB_TOKEN` by default; without this variable set, `glab mr note
create` fails with an auth error rather than silently using the job's
own real token. `glab` itself isn't preinstalled the way `gh` is on
GitHub's own runners either, so it's downloaded the same way `ubx` is
above.

`glab mr note create` has no equivalent to `gh pr comment --edit-last`
-- confirmed directly against the real, current `glab` CLI reference,
not assumed absent. Its only related flag, `--unique`, skips posting
only if a note with byte-identical content already exists, which a
changed plan output never will be; there's no "find and update my own
last note" mechanism built in. Every push to the MR posts a genuinely
new note here, not an updated one -- a real, material difference from
GitHub's guide worth knowing before relying on it, not a corner cut
silently. A team that wants GitHub's exact dedup behavior would need
to script it directly against the [Notes
API](https://docs.gitlab.com/api/notes/) (list, find the bot's last
note, `PUT` to update) -- real and possible, just genuinely more work
than the one flag GitHub's `gh` provides, not built out here to keep
this guide's own complexity proportionate to what's actually native.

## Workflow 3: ship on merge

This is the automation half of [PR-Merge
Acceptance](/concepts/pr-merge-acceptance): a proposal file, committed
to a merge request whose description carries a real `ubx-proposal:
<hash>` trailer, reviewed and merged like any other change. Once it
lands on `main`, `ubx accept --from-merge` derives the acceptance from
real, external evidence -- the merge commit's real existence in git
history, the proposal file's real content at that commit, the real
merge request it belongs to, and its real, current approving
reviewers, read directly from the GitLab API. Nothing about who
approved it is trusted from a typed claim -- the same real guarantee
GitHub's own ship-on-merge guide provides, not a weaker, ships-blind
version of it.

```yaml
ship:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "main"'
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com
  cache:
    key: ubx-providers-hashicorp-aws-6.54.0
    paths:
      - ~/.ubx/providers
  script:
    - curl -L https://github.com/Ubiquex/ubiquex/releases/download/v0.2.0/ubx_0.2.0_linux_amd64.tar.gz | tar xz
    - mv ubx /usr/local/bin/
    - >
      creds=$(aws sts assume-role-with-web-identity
      --role-arn ${AWS_ROLE_ARN_SHIP}
      --role-session-name "ubx-ship-${CI_PIPELINE_ID}"
      --web-identity-token ${GITLAB_OIDC_TOKEN}
      --duration-seconds 3600
      --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]'
      --output text)
    - export AWS_ACCESS_KEY_ID=$(echo $creds | cut -d' ' -f1)
    - export AWS_SECRET_ACCESS_KEY=$(echo $creds | cut -d' ' -f2)
    - export AWS_SESSION_TOKEN=$(echo $creds | cut -d' ' -f3)
    - export GITLAB_TOKEN=${GITLAB_API_TOKEN}
    - >
      ubx accept --from-merge $CI_COMMIT_SHA
      --proposal-file proposals/db-replica.json
      --gitlab-project $CI_PROJECT_PATH
    - >
      ubx ship --yes
      --source hashicorp/aws --provider-version 6.54.0
      --provider-config '{"region":"us-east-1"}'
```

`GITLAB_API_TOKEN` is the real Project Access Token from the Note
above, added as a masked, protected CI/CD variable (Settings → CI/CD →
Variables) -- exported here as `GITLAB_TOKEN` because that's the real,
current environment variable `ubx accept --from-merge --gitlab-project`
reads by convention, the same way `GITHUB_TOKEN` already works on the
GitHub guide. `$CI_COMMIT_SHA` and `$CI_PROJECT_PATH` are both real,
current GitLab predefined variables -- the commit that triggered this
exact pipeline run, and the project's own `namespace/project` path,
respectively.

`ubx ship` with no `hash` resolves to the most recent unshipped,
already-accepted proposal for the stack -- see [`ubx
ship`](/cli-reference/ship). If `ubx accept --from-merge` finds nothing
new to accept (a push to `main` that didn't come from a proposal's own
merge, or one already accepted), `ubx accept` itself fails loudly
rather than the ship step silently no-oping on the wrong assumption --
match this pipeline's own real proposal-file path and stack layout
before relying on it. `--confirm-destroys` is deliberately absent from
the example above, same reasoning as the GitHub guide's own: a
PR/MR-merge-derived acceptance carries the same explicit human
acknowledgment as a local one (see [`ubx
accept`](/cli-reference/accept)'s own notes) -- a stack whose changes
can destroy real resources needs that flag added consciously, not
silently implied by an unattended merge-to-main job.

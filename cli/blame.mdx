---
title: "ubx blame"
description: "Per-attribute provenance — git blame for infrastructure"
---

```text
ubx blame <address> [flags]
```

Git blame for infrastructure, and structurally impossible for the tools it
replaces: a state-file tool has no history (state is overwritten in place —
every prior value is already gone by the time you'd want to ask who set
it); a log aggregator has history but no *signed decision* to point at.
`ubx blame <address>` renders, per attribute of a resource's current folded
state: the value, which proposal **most recently set that specific
attribute**, and who's accountable for it.

<Note>
  Two different attributes on the same resource can legitimately have two
  different answers — `ubx blame` never reports "the resource's own latest
  touching proposal" for every attribute, only the proposal that actually
  set each one.
</Note>

## Flags

| Flag | Description |
| --- | --- |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--all` | show every attribute, including zero/null/empty provider defaults hidden by default within a grouped block |
| `--full-hashes` | render every hash in full instead of the default 12-char short form |
| `--json` | emit one JSON document instead of human text |
| `-h`, `--help` | help for blame |

## Example: a shipped resource

Every attribute set by the same proposal, at the same acceptance, groups
under one header line (UBI-61) — never one repeated "set by/accepted"
pair per attribute:

```text
$ ubx blame payments.fake_widget.payments-db --ledger-dir .
Blame  payments.fake_widget.payments-db

▸ 3 attribute(s) · set by 76ef883c2e8d… (change) · 2026-07-30T22:59:16Z · local
    id: "computed-id"
    name: "payments-db"
    tags.team: "payments"
```

Real, unedited output. `id` here is a provider-computed attribute that
never appeared in the resolved intent's own `config` at all — its value
and provenance both come from the real apply record (the same UBI-29
discovery path [`ubx status`](/cli/status)/[`ubx why`](/cli/why) already
use for a shipped create), never from the resolved proposal's own
possibly-stale `config`.

### `--json`

Entries stay flat here regardless of grouping — grouping is a human-render
concern only, never a schema change:

```json
{
  "format": 1,
  "address": { "stack": "payments", "type": "fake_widget", "name": "payments-db" },
  "destroyed": false,
  "entries": [
    {
      "path": "id",
      "value": "computed-id",
      "redacted": false,
      "proposal_id": "76ef883c2e8d59847766b279852fd3bcfc3fb0fc1a908ed688dd051d20b185f2",
      "kind": "change",
      "set_at": "2026-07-30T22:59:16Z",
      "acceptance_method": "local",
      "approvers": ["roozbeh"]
    }
  ]
}
```

## Example: an attribute changed after the fact, and hidden defaults

Once an attribute is modified by a later proposal — an accepted drift, say
— blame follows it there, its own group, never the whole resource lumped
into one:

```text
$ ubx blame payments.fake_widget.main-cache --ledger-dir .
Blame  payments.fake_widget.main-cache

▸ 2 attribute(s) · set by 4b632a865c88… (adoption) · 2026-07-30T22:59:32Z · local
    id: "main-cache"
    · 1 provider default(s) hidden -- --all to show

▸ 1 attribute(s) · set by 21f9dd786925… (drift_adopt) · 2026-07-30T22:59:32Z · local
    tags.env: "staging"
```

Real, unedited output — `main-cache` was originally adopted with
`tags.env: "prod"` (`name` left at its provider default, never set),
then a real drift was detected and accepted as a `drift_adopt`. `id`
was never touched by that drift, so it still blames the original
adoption, grouped with the other attribute that same proposal set;
`tags.env` alone blames the drift proposal that actually changed it.
`name`'s null/default value is hidden inside its group by default
(`--all` reveals it):

```text
$ ubx blame payments.fake_widget.main-cache --ledger-dir . --all
Blame  payments.fake_widget.main-cache

▸ 2 attribute(s) · set by 4b632a865c88… (adoption) · 2026-07-30T22:59:32Z · local
    id: "main-cache"
    name: null

▸ 1 attribute(s) · set by 21f9dd786925… (drift_adopt) · 2026-07-30T22:59:32Z · local
    tags.env: "staging"
```

## Redacted attributes still show provenance

A `$redacted` attribute's own material never renders — but who changed it,
and when, still does. That's the entire point: knowing a secret rotated,
by whom, and when, without ever seeing what it rotated to.

```text
$ ubx blame payments.fake_widget.secret-box --ledger-dir .
Blame  payments.fake_widget.secret-box

▸ 3 attribute(s) · set by 7f54de41a104… (adoption) · 2026-07-30T22:59:52Z · local
    id: "secret-box"
    master_password: (redacted)
    · 1 provider default(s) hidden -- --all to show
```

## Attribution: who signed it

Every entry names how its proposal was accepted:

- **`local`** — no signer identity beyond the method itself; this
  project's own local-accept tier doesn't record who ran `ubx accept`, a
  real, named limit, not an oversight.
- **`pr_merge`** — the real approving reviewers, exactly as recorded at
  acceptance time.
- **A `drift_adopt`-set attribute** additionally shows every
  [attributed CloudTrail/GCP-audit actor](/concepts/attribution) the
  drift proposal itself names — never collapsed to a single guessed
  cause:

```text
$ ubx blame conformance.aws_s3_bucket.ubx-states --ledger-dir .
Blame  conformance.aws_s3_bucket.ubx-states

▸ 1 attribute(s) · set by <short-id> (drift_adopt) · 2026-07-10T21:42:35Z · local
    tags.env: "staging"
    attributed to: arn:aws:iam::839333509514:user/roozbeh
```

### When attribution came back empty

A `drift_adopt` whose own CloudTrail lookback found nothing (or couldn't
run at all — denied credentials, no region/project to search in) records
that outcome, and *why*, at scan-propose time — `blame` renders the
recorded reason instead of silently showing nothing, exactly as it renders
a real attributed actor:

```text
$ ubx blame payments.fake_widget.widget-attr-blame --ledger-dir .
Blame  payments.fake_widget.widget-attr-blame

▸ 2 attribute(s) · set by 4d05e00a0845… (adoption) · 2026-07-31T00:54:11Z · local
    id: "computed-id"
    name: "widget-attr-blame"

▸ 1 attribute(s) · set by d1c637bab016… (drift_adopt) · 2026-07-31T00:54:11Z · local
    attributed: unattributed (CloudTrail visibility unavailable (denied access or not logged))
    tags.env: "staging"
```

Real output shape (captured against a hermetically credential-blanked
account — see `cli/attribution_surfacing_test.go`'s own
`TestBlame_SurfacesUnattributedReason`). A recent drift's own
`delivery_window` reason ("too recent for CloudTrail to have delivered a
matching event yet") renders the same way — see [`ubx scan`'s own
attribution section](/cli/scan#attribution-when-it-comes-back-empty) for
that specific wording, and [`ubx ship`'s own
warning](/cli/ship#a-warning-before-accepting-a-recent-unattributed-drift_adopt)
before accepting one this recent.

## A destroyed address blames its final pre-destroy state

`ubx blame` on a destroyed address doesn't come back empty — it renders a
tombstone note naming which proposal destroyed it and when, then blames
the resource's own **final, pre-destroy** attribute state, grouped the
same way as any other address:

```text
$ ubx blame payments.fake_widget.old-db --ledger-dir .
Blame  payments.fake_widget.old-db

DESTROYED by ef6f0753b005… at 2026-07-30T23:00:13Z -- blaming the final pre-destroy state

▸ 3 attribute(s) · set by 00e3e9da388a… (adoption) · 2026-07-30T23:00:13Z · local
    id: "old-db"
    · 2 provider default(s) hidden -- --all to show
```

## When it fails

An address the ledger has never recorded at all — never adopted, and
never created via a shipped change proposal — is an error, not an empty
report:

```text
$ ubx blame payments.fake_widget.never-recorded --ledger-dir .
blame: payments.fake_widget.never-recorded has no recorded history -- never adopted, and never created via a shipped change proposal
```

Every exit code is `0` (found, whether live or destroyed — both are
complete, real answers) or `2` (never recorded, or a genuine error).
`ubx blame` never itself signals exit `1` — there's no "wrong" answer a
re-derived attribute history could surface the way
[`ubx verify`](/cli/verify) finds broken hashes. See
[Exit codes](/cli/exit-codes).

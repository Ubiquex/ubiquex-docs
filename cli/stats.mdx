---
title: "ubx stats"
description: "Decision-flow metrics folded from the ledger — the thesis metric, self-measured from your own data"
---

```text
ubx stats [--stack <name>] [--since <RFC3339>] [--until <RFC3339>] [flags]
```

The product proving itself with your own data: `ubx stats` folds the
ledger into decision-flow metrics — total proposals by kind,
acceptance-method split, attribution coverage, mean time-to-decision, and
the headline number, **signed-flow drift resolution %**. Read-only,
offline, no provider needed.

<Note>
  **What this number can, and can't, measure — read this before quoting it.**
  The ledger, by construction, contains only *accepted* proposals — there's
  no durable record anywhere of a drift `ubx scan` detected but a human
  never acted on. `ubx stats` reports what fraction of the drifts it has
  any record of at all reached an explicit close-out (reverted, or
  superseded by a later drift decision) versus still sitting open. It
  can't see drift nobody ever pointed `ubx` at — that comparison needs
  independent ground truth, not an offline ledger fold.
</Note>

## Flags

| Flag | Description |
| --- | --- |
| `--stack string` | restrict the report to one stack (default: every stack the ledger holds; required for a remote `[ledger]` store) |
| `--since string` | only proposals accepted at or after this RFC3339 timestamp |
| `--until string` | only proposals accepted at or before this RFC3339 timestamp |
| `--json` | emit one JSON document instead of human text |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `-h`, `--help` | help for stats |

## Example: a mix of open, superseded, and reverted drift

```text
$ ubx stats --ledger-dir .
ubx stats: 5 proposal(s) total

By kind:
  adoption: 2
  drift_adopt: 2
  drift_revert: 1

Acceptance method:
  local: 5 (100%)

Signed-flow drift resolution: 67% (2 of 3 surfaced drift(s) resolved -- 1 adopted/superseded, 1 reverted, 1 still open)
  (measures drift THIS LEDGER has a record of -- a drift never scanned,
  or scanned and never accepted, leaves no trace for an offline fold to find)

Attribution coverage: 0% (0 of 2 drift_adopt proposal(s) carry a real actor)

Mean time-to-decision: 0s (3 sample(s))

Drift by stack:
  payments: 3
```

Real, unedited output, from a real ledger with three distinct drift
events: one resource drifted once and is still sitting open (nobody's
acted on it yet); a second resource drifted, then drifted *again* before
anyone reverted it (the first drift is "superseded" — no longer the
resource's own current state, but never explicitly reverted either); a
third resource drifted and was explicitly reverted back. `2 of 3` — 67%.

### `--json`

```json
{
  "format": 1,
  "total_proposals": 2,
  "by_kind": { "adoption": 1, "drift_adopt": 1 },
  "acceptance_method": { "local": 2 },
  "drift_resolution": {
    "surfaced_events": 1,
    "resolved_reverted": 0,
    "resolved_adopted": 0,
    "open": 1,
    "resolution_pct": 0
  },
  "attribution": {
    "attributed_drift_adopts": 0,
    "total_drift_adopts": 1,
    "coverage_pct": 0
  },
  "time_to_decision": { "mean_seconds": 0, "samples": 1 },
  "drift_by_stack": { "payments": 1 }
}
```

`resolution_pct`/`coverage_pct`/`mean_seconds` are all nullable — a
window with no drift proposals at all reports `null`, never a misleading
`0` that could be mistaken for "we checked, and it's genuinely zero."

## How "resolved" is defined

Every `drift_adopt` proposal is one surfaced-drift event. `ubx stats`
walks each address's own ordered sequence of drift-related proposals and
classifies each `drift_adopt` by whatever (if anything) touched that
same address next:

- **An immediately following `drift_revert`** — an explicit, deliberate
  close-out. Counted as **resolved: reverted**.
- **Any other later drift-related touch** (almost always: the resource
  drifted again) — never explicitly reverted, but no longer the
  address's own current state either. Counted as **resolved: adopted/
  superseded** — a real resolution path (the team kept accepting the new
  reality each time), not an oversight.
- **Nothing later at all** — this drift_adopt is still the address's own
  current, unrevisited, accepted state. Counted as **open**.

A `drift_revert` that does **not** directly follow a `drift_adopt` for
the same address — the real, common shape when a team chooses to revert
a freshly detected drift outright, rather than ever adopting it first —
is its own independent surfaced-and-resolved event, not silently
dropped.

<Note>
  A destroyed address's own open-ended drift still counts in the *history*
  (the `by_kind` totals above), but is excluded from **open** — once the
  resource itself is gone, there's nothing left to act on, so it's moot
  rather than either genuinely open or resolved.
</Note>

## Attribution coverage is independent of resolution

An unattributed drift (no real CloudTrail/GCP-audit actor, or explicitly
[`cloudtrail_unattributed`](/concepts/attribution)) still fully counts
toward — and can still resolve — the signed-flow number. It only lowers
the separate attribution-coverage percentage:

```text
$ ubx stats --ledger-dir .
...
Attribution coverage: 100% (1 of 1 drift_adopt proposal(s) carry a real actor)
```

## Time windows

`--since`/`--until` filter by `Acceptance.AcceptedAt` — the moment a
proposal entered the ledger, not when it was originally resolved:

```text
$ ubx stats --ledger-dir . --since 2026-07-01T00:00:00Z --until 2026-07-31T23:59:59Z
```

Mean time-to-decision measures a different gap — from
`Resolution.ResolvedAt` (when the proposal's own content was resolved,
e.g. a scan ran) to that same acceptance moment — averaged only over
proposals where both timestamps parse, with the real sample count always
shown alongside it.

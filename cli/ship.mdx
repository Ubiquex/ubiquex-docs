---
title: "ubx ship"
description: "Accept (local tier, if needed) and execute a drift_revert or change proposal against live cloud -- the only command that ships"
---

```text
ubx ship [hash] [flags]
```

Executes a [`drift_revert`](/concepts/drift) or `change` ([`ubx
resolve`](/cli/resolve), or [`ubx plan`](/cli/plan)'s fused equivalent)
proposal: for a `drift_revert`, restores the resource's live state to
match the ledger's recorded truth; for a `change`, creates, modifies, and
destroys resources for real, in one combined dependency order
(creates/modifies forward, destroys reversed), feeding each resource's
real shipped output into any sibling still carrying a `$computed` marker
pointing at it. **This is the one `ubx` command that changes real
infrastructure** — [`ubx accept`](/cli/accept), [`ubx why`](/cli/why),
[`ubx status`](/cli/status), [`ubx scan`](/cli/scan),
[`ubx resolve`](/cli/resolve), [`ubx plan`](/cli/plan), and
[`ubx revert-plan`](/cli/revert-plan) only ever read or record. `ubx
revert-plan` still exists and still never ships anything itself — it's
what you reach for pre-acceptance, or if you'd rather make the
correction through your own tooling; `ubx ship` is what actually does it.

Only `drift_revert` and `change` proposals are actually *executed*.
`adoption`/`drift_adopt` are record-only — accepting one already is the
whole action, there's nothing left to run against a real provider. `ubx
ship` still accepts these the exact same way (the same inline-accept-then-
confirm flow, or the same already-accepted-in-the-ledger path) — it just
reports success once acceptance lands, rather than ever reaching for a
provider at all. See [Shipping a record-only proposal](#shipping-a-record-only-proposal-adoption-drift_adopt),
below.

## `[hash]` is optional, and looked up two ways

**Bare `ubx ship`** (UBI-62) resolves to the most recent unshipped plan
for the resolved stack (`--stack`, or config's own default) — shown
explicitly before anything happens, never silently guessed. If plans for
more than one stack exist and `--stack` wasn't given, nothing is guessed
between stacks either: a TTY is prompted to choose, a non-TTY is refused
with the same list as a teaching error. See [Bare `ubx ship`](#bare-ubx-ship-the-latest-plan-for-your-stack)
below.

Given or resolved, `[hash]` is then looked up two ways:

1. **An already-accepted proposal id** in this stack's ledger — the
   four-verb ceremony's own path: [`ubx accept`](/cli/accept) (local or
   [`--from-merge`](/cli/accept#pr-merge-acceptance)) ran separately,
   before this command. Shipped immediately, no further confirmation,
   since that acceptance already was the consent moment.
2. **A plan [`ubx plan`](/cli/plan) saved** at `.ubx/plans/<hash>.json`,
   if no accepted proposal by that id exists. For **this** path only, a
   one-line summary (stack, plan age, blast radius) renders and a typed
   `yes` is required before anything is accepted or shipped — see
   [Interactive confirmation](#interactive-confirmation-the-signing-moment)
   below.

## Flags

| Flag | Description |
| --- | --- |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`); unused if `.ubx/config`'s `[ledger]` names a remote store |
| `--stack string` | which stack's ledger to open — required only when `.ubx/config`'s `[ledger]` `store` is a remote store (a bare hash carries no stack of its own); also which stack's plans are considered for a bare `ubx ship` with no hash |
| `--confirm-destroys` | required for [inline acceptance](#interactive-confirmation-the-signing-moment) of any plan with `blast_radius.destroys > 0`; unused when `<hash>` is already an accepted proposal, since that confirmation already happened at its own accept time |
| `--confirm-terminate` | alias for `--confirm-destroys` (UBI-77) — the spelling `ubx terminate`'s own `next:` hint shows, since that's the verb a human actually typed; either flag satisfies both |
| `--yes` | skip the interactive "type yes" confirmation for inline local-tier acceptance (for CI/scripts) — the receipt still renders; required on a non-TTY, which never prompts |
| `--full-hashes` | render every hash in full instead of the default 12-char short form |
| `--provider string` | path to the provider binary (mutually exclusive with `--source`) |
| `--source string` | provider source address, e.g. `hashicorp/aws` (mutually exclusive with `--provider`; requires `--provider-version`) |
| `--provider-version string` | explicit provider version to acquire (required with `--source`) |
| `--provider-config string` | JSON object configuring the provider, e.g. `{"region":"us-east-1"}` (default `{}`) |
| `--timeout duration` | overall timeout for the ship run (default `5m0s`) |
| `--json` | emit one JSON document instead of human text — see [`--json` output](#json-output) |
| `-h`, `--help` | help for ship |

## Bare `ubx ship`: the latest plan for your stack

No hash at all resolves to the most recent unshipped plan for the
resolved stack — shown explicitly, then run through the identical
confirmation flow below. With only one stack's plans sitting in
`.ubx/plans/`, `--stack` isn't even required — resolution is unambiguous
and says so:

```text
$ ubx ship --provider ./fakeprovider --ledger-dir . --yes
latest plan for stack playground: 74adc2cd40de  change  45s old
Ship  playground · 45s old · +1 create(s) ~0 change(s) -0 terminate(s)
accepted 74adc2cd40de… (stack playground) via local plan
  ✓ playground.fake_widget.q1: shipped                                            0:00

1 resource(s), 1 shipped, 0 failed, 0 still unknown -- outcome: shipped
```

`.ubx/plans/` is not stack-namespaced — it's a flat, content-hash-keyed
store shared by every stack that uses this ledger dir (the common case
for the default git-local store), so plans for more than one stack
sitting there at once is ordinary, not an edge case. Nothing is guessed
between them:

```text
$ ubx ship --provider ./fakeprovider --ledger-dir .
multiple stacks have unshipped plans -- pass --stack, or choose one:
  [1] 5f89d25fc10c  payments  change  0s old
  [2] d337cf733b71  networking  change  0s old
ship: 2 plans span more than one stack -- pass --stack or an explicit hash (non-interactive, refusing to guess)
```

A real terminal gets a prompt instead of the refusal (`Ship which plan?
[1-2]: `). Naming `--stack` resolves the ambiguity the same way, and
still goes through the identical confirmation flow — `--stack` narrows
which plan is picked, it doesn't skip the "renders, then asks" step:

```text
$ ubx ship --provider ./fakeprovider --ledger-dir . --stack payments < /dev/null
latest plan for stack payments: 5f89d25fc10c  change  6s old
Ship  payments · 6s old · +1 create(s) ~0 change(s) -0 terminate(s)
ship: refusing to ship without confirmation: not an interactive terminal -- pass --yes to confirm non-interactively (e.g. in CI/scripts)
```

A shipped or accepted plan is pruned from `.ubx/plans/` so "latest"
never re-offers it either way it was consumed.

## Interactive confirmation: the signing moment

When `[hash]` isn't yet an accepted proposal, `ubx ship` looks for a plan
[`ubx plan`](/cli/plan) saved locally and — on a real terminal, without
`--yes` — requires a typed `yes` (terraform's own consent pattern, not
`y`/`n`) before `core.Accept` ever runs. The prompt **is** the
local-tier signing moment. It does **not** re-render the full receipt
`ubx plan` already showed — that already was the review; a one-line
summary (stack, plan age, blast radius) is enough to confirm this is
still the plan being signed, without repeating every resource and
attribute a human already read (a real multi-resource receipt can run
to pages of formatted JSON under [the v2 receipt format](/cli/plan#plan-receipt-format-exact-from-the-founders-markup-resolved)):

```text
$ ubx plan intent.json --provider ./fakeprovider --ledger-dir .
Plan  sandbox4 · from intent.json

  + fake_widget.primary create
      name: "primary-widget"
      tags:
      {
        "env": "sandbox"
      }

  + fake_widget.mirror create
      name: "primary-widget"
      tags:
      {
        "peer_id": $ref:sandbox4.fake_widget.primary.id
      }

delta: +2 create(s), ~0 change(s), -0 terminate(s)

blast radius: +2 ~0 -0
cost delta: $0/mo

ubx-proposal: 9b81fb392ad7…
next: ubx ship 9b81fb392ad7

$ ubx ship 9b81fb392ad7 --provider ./fakeprovider --ledger-dir .
Ship  sandbox4 · 7s old · +2 create(s) ~0 change(s) -0 terminate(s)

Ship this to sandbox4? Only 'yes' accepted: yes
accepted 9b81fb392ad7… (stack sandbox4) via local plan
  ✓ sandbox4.fake_widget.primary: shipped                                            0:00

  ✓ sandbox4.fake_widget.mirror : shipped                                            0:00

2 resource(s), 2 shipped, 0 failed, 0 still unknown -- outcome: shipped
```

Each resource's own progress block is followed by a blank line, so a
multi-resource ship reads as clearly separated blocks rather than every
resource's transitions running together.

Typing anything else — or `--yes` never given on a non-interactive
stdin — aborts cleanly, nothing accepted or shipped, exit `0` (a
deliberate abort is not a finding or an error):

```text
$ ubx ship 754a67b0d886 --provider ./fakeprovider --ledger-dir .
...
Ship this to sandbox3? Only 'yes' accepted: nope
ship aborted -- nothing accepted or shipped
```

`--yes` skips the prompt for CI/scripts, but still renders the one-line
summary first — and a non-TTY without it refuses outright rather than
hang reading a stdin nobody's watching:

```text
$ ubx ship 754a67b0d886 --provider ./fakeprovider --ledger-dir . < /dev/null
...
ship: refusing to ship without confirmation: not an interactive terminal -- pass --yes to confirm non-interactively (e.g. in CI/scripts)
```

[`ubx why`](/cli/why) shows exactly the same `acceptance.method: "local"`
an ordinary `ubx accept` would have recorded — the prompt is a UX
addition, not a new acceptance tier. Its own ship-history transitions
still name every real state (`pending`/`in_flight`/`shipped`) in full —
that's the permanent historical record, unrelated to `ubx ship`'s own
live progress narration, which is display-only and never touches what
gets recorded:

```text
$ ubx why 9a6fcc02288afc961063eeccbdb99e56cb4ada43ee363a291e47463a715cc1b7 --ledger-dir .
proposal 9a6fcc02288a… (change)
stack:  sandbox2
status: accepted
intent: two widgets, one referencing the other
accepted by [roozbeh] via local at 2026-08-04T15:28:31Z
blast radius: +2 ~0 -0
+ fake_widget.primary create
    name: "primary-widget"
    tags:
    {
      "env": "sandbox"
    }

+ fake_widget.mirror create
    name: "primary-widget"
    tags:
    {
      "peer_id": $ref:sandbox2.fake_widget.primary.id
    }
ship history:
  attempt 1: outcome=shipped
    ...
```

A consumed plan (accepted, whether shipped cleanly afterward or not) is
pruned from `.ubx/plans/` — [bare `ubx ship`](#bare-ubx-ship-the-latest-plan-for-your-stack)
never re-offers it.

### Destroys require confirmation, even inline

`--confirm-destroys` is the exact same [acceptance-time friction
invariant](/cli/accept#confirming-a-destroy) standalone `ubx accept`
enforces — inline acceptance doesn't relax it, and it's checked BEFORE
the interactive prompt even renders (no point asking a human to type
`yes` for something that will be refused regardless):

```text
$ ubx plan destroy-intent.json --provider ./fakeprovider --ledger-dir .
Plan  sandbox5 · from destroy-intent.json

  - sandbox5.fake_widget.mirror destroy
      id: "computed-id"
      name: "mirror-widget"
      tags: {}

delta: +0 create(s), ~0 change(s), -1 terminate(s)

blast radius: +0 ~0 -1
cost delta: $0/mo

ubx-proposal: 204dfcae957e…
next: ubx ship 204dfcae957e --confirm-terminate

$ ubx ship 204dfcae957e --provider ./fakeprovider --ledger-dir . --yes
ship: this proposal has blast_radius.destroys > 0 -- pass --confirm-destroys to accept it
```

With `--confirm-destroys` (or its `--confirm-terminate` alias — the
`next:` hint above always shows this spelling, UBI-77) and `--yes`
(since this transcript is non-interactive), the destroy proceeds —
including the mandatory read-back narration every destroy goes through
(see [Shipping a destroy](#shipping-a-destroy) below). `pending`/
`in_flight` never get their own line (sub-second scaffolding, not worth
a human's attention on the happy path) — the read-back verification is
the one line that matters, and it's the one line shown:

```text
$ ubx ship 204dfcae957e --provider ./fakeprovider --ledger-dir . --confirm-terminate --yes
Ship  sandbox5 · 15s old · +0 create(s) ~0 change(s) -1 terminate(s)
accepted 204dfcae957e… (stack sandbox5) via local plan
  ⠋ sandbox5.fake_widget.mirror: provider reported success -- verifying via read-back (attempt 1/10) 0:00
  ✓ sandbox5.fake_widget.mirror: shipped · confirmed by reconciliation              0:00

1 resource(s), 1 shipped, 0 failed, 0 still unknown -- outcome: shipped
```

A stale cross-stack pin ([`resolver.VerifyPins`](/cli/resolve#cross-stack-references))
refuses inline acceptance the exact same way it refuses standalone `ubx
accept` — the neighbor ledger moving between `ubx plan` and `ubx ship` is
caught, not silently accepted against stale state; this check (and the
plan file's own hash-integrity check, next) both run before the
confirmation step too.

### The plan file's own integrity

A plan file is always written at exactly its own content hash's path.
`ubx ship` recomputes that hash on read and refuses a mismatch — a
hand-edited or corrupted plan file is never silently shipped under a
hash that no longer describes its actual content:

```text
$ ubx ship f8e95de5e90c --provider ./fakeprovider --ledger-dir . --yes
ship: plan file at .ubx/plans/f8e95de5e90ccc94ade76dacda9fbf1d50aadb9cce2d76c246d24e6dd4cfe2df.json hashes to 2ca90e90af814182c8d100c2ba27733670f629e637bf74bcf2bd7fc9b2f2ebe8, not f8e95de5e90ccc94ade76dacda9fbf1d50aadb9cce2d76c246d24e6dd4cfe2df -- stale or corrupted plan file
```

<Note>
  Every transcript on this page is the plain/`NO_COLOR` variant, for
  transcript stability — a real terminal colors these receipts (green
  creates, yellow modifies, red destroys, blue hashes) and shows the same
  content. `--json` is untouched either way.
</Note>

<Note>
  PR-merge acceptance remains available as its own separate path
  ([`ubx accept --from-merge`](/cli/accept#pr-merge-acceptance)) for teams
  who want it — inline acceptance here is local tier only, never a
  substitute for it. See [When to use the four-verb ceremony
  instead](/cli/plan#when-to-use-the-four-verb-ceremony-instead) for the
  full comparison.
</Note>

<Note>
  If `.ubx/config`'s `[ledger]` table names a remote store,
  `--stack` becomes required — a bare proposal id carries no stack of
  its own to derive the store's address from, unlike `ubx resolve`
  (which reads it from the intent file) or `ubx accept` (from the
  proposal file). See [Ledger stores](/concepts/ledger-stores) for why.

  ```text
  $ ubx ship 3ff1769e2c4d2cadc8e492cce9ae5b465b9263b3f39a5aae946617ae8fc028c0 --provider ./fakeprovider
  ship: --stack is required to open a remote ledger store (.ubx/config's [ledger] store is "s3://ubx-states/acme/prod/", not git) -- a remote store's own per-stack chain means opening one at all requires knowing which stack first
  ```
</Note>

## Shipping a record-only proposal (adoption/drift_adopt)

An `adoption` (a brand-new resource [`ubx scan`](/cli/scan) has never seen
before) or a `drift_adopt` (recording a real drift as the new signed
truth) resolve their *entire* action at acceptance — there's nothing left
to execute against a real provider. `ubx ship` still accepts these
through the exact same inline-accept-then-confirm flow as any other
plan-store hash; it just reports success the moment acceptance lands,
instead of the confusing "ship only executes drift_revert or change
proposals" a `ubx ship` on one of these used to print — after already
accepting it, making a real success look like a failure:

```text
$ ubx scan --provider ./fakeprovider --stack payments --type fake_widget --name main-cache --lookup '{"name":"main-cache"}' --ledger-dir . --no-attribution
New resource found  payments.fake_widget.main-cache

  adoption      f8d9517ad2f3     record-only · adopts into the ledger

  saved to plan store            next: ubx ship f8d9517ad2f3

$ ubx ship f8d9517ad2f3 --provider ./fakeprovider --ledger-dir . --yes
Ship  payments · 8s old · +0 create(s) ~0 change(s) -0 terminate(s)
accepted f8d9517ad2f3… (stack payments) via local plan
f8d9517ad2f3… (adoption) -- record-only, nothing to execute -- ✓ resolved
```

Real, unedited output. The interactive confirmation, `--yes`, and
`--confirm-destroys` double-consent for a destroy-carrying plan all still
apply identically before this point is ever reached — a record-only
proposal is never treated as a shortcut around consent, only around
*execution*, which it never needed in the first place. An **already**
accepted `adoption`/`drift_adopt` (found directly via its own ledger id,
not the plan-store fallback) reports the identical success line, since
the kind check runs the same way regardless of which of `ubx ship`'s two
lookup paths found it.

### A warning before accepting a recent, unattributed drift_adopt

A `drift_adopt`'s own attribution is a one-shot: [`ubx scan
--propose`](/cli/scan)'s own CloudTrail lookback either finds a real
actor or doesn't, and whatever it recorded becomes permanent the moment
this proposal is accepted — [`ubx blame`](/cli/blame)/[`ubx
why`](/cli/why) only ever replay it, never re-attempt it later. If the
drift being adopted is very recent (under 10 minutes since it was
resolved) and came back unattributed, `ubx ship` warns before accepting
it — CloudTrail's own delivery window is typically 2-5 minutes, so a
re-scan shortly afterward may still attribute it for real:

```text
$ ubx ship 03a6e26c4075 --provider ./fakeprovider --ledger-dir . --yes
Ship  payments · 7s old · +0 create(s) ~0 change(s) -0 terminate(s)
warning: this drift is 7s old and has no recorded attribution (too recent for CloudTrail to have delivered a matching event yet) -- accepting now records it as unattributed permanently; consider re-scanning in a few minutes first

accepted 03a6e26c4075… (stack payments) via local plan
03a6e26c4075… (drift_adopt) -- record-only, nothing to execute -- ✓ resolved
```

Real, unedited output — advisory only, never blocking: the plan still
ships with `--yes` (or a typed `yes` at the interactive prompt) right
after the warning. Once the drift is 10 minutes old or older, or already
carries real attribution, the warning simply doesn't print at all — see
[`ubx scan`'s own attribution section](/cli/scan#attribution-when-it-comes-back-empty)
for the display-only half of this same fix.

## Example: a clean ship

```text
$ ubx ship 817770a30b9708da1907de1af22cc5a18fcf28549d0fc4d96a828b28de3e60ab --provider ./fakeprovider
  ✓ payments.fake_widget.api-cache2: shipped                                            0:00

1 resource(s), 1 shipped, 0 failed, 0 still unknown -- outcome: shipped
```

Each resource's live transitions narrate as they happen (UBI-61) — not
buffered to the end — with elapsed time since that resource's own most
recent transition into a live phase. `pending`/`in_flight` never get their
own line (UBI-70): they're sub-second scaffolding on the happy path, not
something worth a human's attention.

<Note>
  **The elapsed time actually ticks (UBI-63/UBI-70).** A real call against
  a real, slower provider (or a read-back verification loop that needs
  several attempts, each with real backoff between them) can take a while
  with nothing new to report. On a real terminal, the raw provider-call
  wait shows one live "shipping" line, and the read-back verification wait
  shows one live "verifying via read-back (attempt N/M)" line — both
  re-rendered roughly once a second, in place (a carriage return), rather
  than sitting frozen until the eventual terminal event finally arrives
  with the real total. Errors along the way still get their own permanent
  line — the noise cut is about the happy path repeating itself, never
  about hiding a real problem. Real, unedited transcript — a destroy
  whose read-back keeps finding the resource present through the full
  10-attempt retry budget (`FAKEPROVIDER_APPLY_MODE=lying-destroy`, the
  fixture's dedicated "provider claims success but doesn't actually
  delete anything" mode — checked directly against the current fixture
  before writing this: the fixture's own DEFAULT mode, `FAKEPROVIDER_APPLY_MODE`
  left unset, actually completes a destroy correctly, so `lying-destroy`
  is the one that reproduces this scenario, not the unset default this
  page previously named. The non-TTY/piped capture every transcript on
  this page uses — each real attempt still gets its own discrete line,
  in-place overwrite being a terminal-only concept a log file has no use
  for):

  ```text
  ⠋ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 1/10) 0:00
  ⠙ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 2/10) 0:00
  ⠹ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 3/10) 0:00
  ⠸ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 4/10) 0:00
  ⠼ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 5/10) 0:01
  ⠴ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 6/10) 0:03
  ⠦ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 7/10) 0:08
  ⠧ payments.fake_widget.ci-notifications: provider reported success -- verifying via read-back (attempt 8/10) 0:18
  ```

## Example: idempotent re-run

Every resource already `applied` in a prior attempt is skipped — re-running
`ubx ship` against a proposal that already fully shipped is a genuine no-op,
not an empty response:

```text
$ ubx ship 9a6fcc02288afc961063eeccbdb99e56cb4ada43ee363a291e47463a715cc1b7 --provider ./fakeprovider --ledger-dir .
9a6fcc02288afc961063eeccbdb99e56cb4ada43ee363a291e47463a715cc1b7: already fully shipped -- nothing to do
```

This is exit `0`, and writes no new [apply record](/concepts/apply-record)
at all — see [Idempotency](/concepts/apply-record#idempotency-safe-to-re-run-any-number-of-times).

## Example: a provider rejects the change

A real, structured error from the provider (not a timeout or transport
failure) ends that resource's attempt immediately — never silently retried:

```text
$ ubx ship fef59cd0c9430e6ebe5dcbc685910ea7fbd26fdaf8284d5b2fe05851a030d5ba --provider ./fakeprovider
Ship  payments · 7s old · +1 create(s) ~0 change(s) -0 terminate(s)
accepted fef59cd0c943… (stack payments) via local plan
  ! payments.fake_widget.api-cache-reject: provider returned 1 diagnostic error(s): invalid attribute value: fakeprovider: simulated terminal diagnostic
  ✗ payments.fake_widget.api-cache-reject: failed                                             0:00

1 resource(s), 0 shipped, 1 failed, 0 still unknown -- outcome: failed
ship: failed (see above)
```

The error gets its own line the moment it happens (UBI-70) — not just at
the very end, once every other resource in the whole ship run has also
finished. `ubx ship`'s own trailing report no longer repeats it a second
time as a separate `terminal: ...` line the way it once did — the live
line above is now the only rendering of it; [`ubx why`](/cli/why) still
records the identical detail permanently, as `error (terminal): ...` on
that resource's own transition history.

## Example: a redacted restore target is declined, not shipped

A `drift_revert` whose restore value is itself a [`$redacted`](/concepts/secrets)
marker — the ledger holds a salted hash, never the real material — is
declined outright. `ubx ship` will never construct a live shipment from
it, on this run or any future one; the message points at `ubx
revert-plan`'s own manual-reconciliation path:

```text
$ ubx ship 8eb9596d46ee --provider ./fakeprovider --ledger-dir . --yes
Ship  payments · 8s old · +0 create(s) ~1 change(s) -0 terminate(s)
accepted 8eb9596d46ee… (stack payments) via local plan
  ! payments.fake_secret_resource.secret-box: declined: after value(s) at api_key are redacted -- the ledger holds a salted hash, not the real secret material, and ubx will never construct a live apply from it; use `ubx revert-plan` for this resource's manual reconciliation steps instead

1 resource(s), 0 shipped, 1 failed, 0 still unknown -- outcome: failed
ship: failed (see above)
```

<Warning>
  **A real, current gap found while re-verifying this page (UBI-82), not
  fixed here — this is a docs-only sweep, and this string lives in
  `core/executor/ship.go`, not a doc file.** The declined-redacted
  message above still literally says "ubx will never construct a live
  **apply** from it" — one of two places the real UBI-79 vocabulary sweep
  missed (the other is the blocked-dependency message under [Shipping a
  `change` proposal](#shipping-a-change-proposal-a-real-create-chain)
  below): both use "apply" as a noun for "a live ship/execution," the

## Shipping a `change` proposal: a real create chain

A `change` proposal ([`ubx resolve`](/cli/resolve)'s own output) is shipped
the same way — creates and modifies together, in real dependency order.
Here `api-cache-mirror` cross-references `api-cache`'s `name` (concrete)
and its schema-`Computed` `id` (left as `$computed` at resolve time,
substituted with the real shipped value mid-walk):

never loses the value the second one needs.

### A dependent create outrunning its own dependency's visibility

A real cloud provider's own successful create of a resource doesn't
guarantee that resource is *immediately* visible to another call that
references it — AWS IAM is the well-documented case: `CreateRole` can
return success before the role is visible to a subsequent
`AttachRolePolicy` call, even though nothing about `ubx`'s own dependency
ordering was wrong (the role really did ship first). `ubx ship` retries a
dependent's own create through the identical backoff budget the
[post-destroy read-back](#a-provider-that-reports-success-without-it-being-true)
below already uses (~64 seconds, escalating), narrowly scoped: only when
the failure names an already-shipped same-batch dependency and looks
not-found-shaped ("not found," "does not exist," "no such," "cannot be
found," and close variants) — a real, permanent failure (a bad ARN, an
invalid policy document) still fails immediately, unretried, exactly as
before this existed.

```text
$ ubx ship 77aea682649c06029d44454cc3308c7ecec229d88d44023773fb39c2a9b1cb87 --provider ./fakeprovider
  ✓ payments.fake_widget.api-cache       : shipped                                            0:00

  ⠋ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 1/10) 0:00
  ⠙ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 2/10) 0:00
  ✓ payments.fake_widget.api-cache-mirror: shipped                                            0:00

2 resource(s), 2 shipped, 0 failed, 0 still unknown -- outcome: shipped
```

Every retry is logged to `ubx why`'s own reconciliation trail, the same
way a destroy's read-back attempts are:

```text
$ ubx why 77aea682649c06029d44454cc3308c7ecec229d88d44023773fb39c2a9b1cb87
...
    payments.fake_widget.api-cache-mirror:
      pending at 2026-08-02T19:03:27Z
      in_flight at 2026-08-02T19:03:27Z
      shipped at 2026-08-02T19:03:27Z
      reconcile: inconclusive at 2026-08-02T19:03:27Z -- references a same-batch dependency that just shipped -- retrying to allow for real propagation lag (AWS IAM's own well-documented eventual-consistency window, UBI-92): provider returned 1 diagnostic error(s): NoSuchEntity: ...
      reconcile: inconclusive at 2026-08-02T19:03:27Z -- provider returned 1 diagnostic error(s): NoSuchEntity: ...
      reconcile: applied at 2026-08-02T19:03:27Z -- dependency became visible, retry succeeded
```

Real propagation lag resolves in low single-digit seconds — so `ubx ship`
doesn't wait out the full ~64-second budget to find out a dependency will
never become visible at all (most commonly: the reference was authored
against an assumed identity that doesn't match what the dependency
actually shipped as, a permanent mismatch no amount of retrying can fix).
Once elapsed retry time clearly exceeds realistic lag with zero change in
outcome, `ubx ship` gives up early — around 19 seconds, not 64 — with an
honest message rather than grinding out the remaining budget:

```text
$ ubx ship 5a5f219593e37c6e4255cc5a092aaa4b4015c97e7f9f9f14f647023de420d986 --provider ./fakeprovider
  ✓ payments.fake_widget.api-cache       : shipped                                            0:00

  ⠋ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 1/10) 0:00
  ⠙ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 2/10) 0:00
  ⠹ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 3/10) 0:00
  ⠸ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 4/10) 0:00
  ⠼ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 5/10) 0:01
  ⠴ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 6/10) 0:03
  ⠦ payments.fake_widget.api-cache-mirror: dependency just shipped -- retrying to allow for provider propagation lag (attempt 7/10) 0:08
  ! payments.fake_widget.api-cache-mirror: 18.75s of retrying produced zero change in outcome (real provider propagation lag resolves in low single-digit seconds) -- this does not appear to exist and may never have been created under the identity referenced; verify the reference actually matches the shipped dependency's real assigned name/id, not an assumed one: provider returned 1 diagnostic error(s): NoSuchEntity: ...
  ✗ payments.fake_widget.api-cache-mirror: failed                                             0:18

2 resource(s), 1 shipped, 1 failed, 0 still unknown -- outcome: partially_shipped
ship: partially_applied (see above)
```

The original provider diagnostic is never discarded — it's wrapped inside
the honest message (`ubx why` shows both), never a silent hang and never
a different, invented error in its place.

## Shipping a destroy

resource"](/cli/resolve#destroying-a-resource)) ships through the exact
same state machine, mixed in with any creates/modifies in the same
proposal via one combined dependency walk -- never a separate pass. Before
the risky call, `ubx ship` re-reads the target live and compares it
against what was signed away: present and matching proceeds; present but
different is refused (the operator never reviewed that exact state);
already gone is a low-friction success, never a refusal (there's nothing
left to lose):

`widget-b` above never reaches `in_flight` at all -- its own freshness

**A clean `ApplyResourceChange` response is never sufficient by itself
to earn `destroyed`** — found live, against a real `google_pubsub_topic`:
the provider reported success (no error, no diagnostics — the identical
shape a genuine destroy produces) while never actually deleting the
resource, confirmed independently via Cloud Audit Logs. So `ubx ship`
always re-reads the target after the call, whether it reported success
or timed out ambiguously: gone confirms `destroyed` (but only because
the precheck above already confirmed it was there moments earlier -- a
bare not-found read alone is never enough to conclude anything); still
there is handled two different ways depending on what the call itself
said. If the call was ambiguous (an RPC timeout, say), a still-present
read is immediately conclusive — `failed`, the call never landed,
retried normally on the next `ubx ship` invocation. If the call reported
success, a still-present read is *not* immediately conclusive — real
propagation lag can look identical to a lie for a while — so it's
retried through the same backoff budget described below, resolving a
distinctly-worded `failed` (the provider's own claim never checked out)
only once that budget is genuinely exhausted. A destroy is idempotent
the same way every other kind is -- already-`applied` (whether the
outcome was `destroyed` or the target was already gone) is skipped
entirely on re-run.

<Note>
  **Real cloud eventual consistency, budgeted for, not silently
  ignored**: real AWS SQS, for instance, can keep reporting a queue as
  present for well beyond the ~60 seconds its own documentation
  suggests, after `DeleteQueue` already succeeded. The post-destroy
  read-back's own retry budget is sized for this — roughly a minute of
  backoff, starting fast (an honest, synchronously-consistent provider,
  the common case, resolves on the very first read, no added delay at
  all) and growing to accommodate a real slow tail. If a destroy is
  still present once that full budget is spent, `ubx ship` calls it
  plainly: either an ordinary `failed` (the call was ambiguous and never
  landed) or, more seriously, `provider_reported_success_but_present`
  (the provider's own claimed success didn't check out) — never
  silently upgraded to `destroyed` either way, and never left in a vague
  `unknown_post_timeout` limbo once the read-back itself gave a clear,
  repeated answer.
</Note>

`ubx ship` will refuse to have shipped this proposal in the first place
unless it was accepted with [`--confirm-destroys`](/cli/accept#confirming-a-destroy)
-- that gate lives in `ubx accept`, not here, since a proposal already
carrying an `Acceptance` was already confirmed at that point.

## Shipping across multiple providers

A stack with a real [`[providers]` table](/cli/config#multi-provider-stacks)
in `.ubx/config` ships a `change` proposal spanning more than one
provider binary as ONE signed unit -- `ubx resolve` already recorded
which provider owns each resource; `ubx ship` reads that back and
launches each one lazily, only the providers this specific proposal's
own resources actually need, each configured from its own
`[provider_configs]` entry. `--provider`/`--source`/`--provider-config`
are ignored (with a warning) once `[providers]` is declared -- the same
staging [`ubx resolve`'s own note](/cli/resolve) describes.

A resource whose own provider can't launch at all fails on its own,
terminally -- it never blocks a sibling resource against a different,
already-fine provider:

Real transcript, a genuine registry-sourced provider (`hashicorp/random`
— no cloud dependency, nothing billed, chosen so this could be verified
live rather than reconstructed by hand): resolved and accepted against
`[providers]` pinned to `3.6.1`, then the pin moved to `3.5.0` before
shipping:

```text
$ ubx ship a675bd9d1268150fb5404011a45c4b8a851da06eb8aec6234e3ff2f516b53272 --ledger-dir . --yes
```

</Note>

## Exit code: the CI contract

| Exit code | Meaning |
| --- | --- |
| `0` | every resource shipped (including a genuine no-op: already fully shipped) |
| `1` | `partially_applied` or `failed` — an actionable finding: retry, or investigate why |
| `2` | bad input (proposal not found, wrong kind, not accepted), or a genuine provider/ledger failure |

See [Exit codes](/cli/exit-codes) for the full per-verb reference.

## Freshness, re-verified per resource

Unlike a one-shot command, `ubx ship` can run long enough, resource to
resource, that reality moves *during* the run. Freshness is re-checked
immediately before **each** resource's own attempt, not once at the start —
a resource that drifts a second time between acceptance and its own turn in
the queue is refused, not bulldozed; resources already shipped earlier in
the same run stand untouched. See [Apply record](/concepts/apply-record) for
the full state machine.

---
title: "ubx ship"
description: "Execute an accepted drift_revert or change proposal against live cloud -- the only command that applies"
---

```text
ubx ship <proposal-id> [flags]
```

Executes an already-*accepted* [`drift_revert`](/concepts/drift) or
`change` ([`ubx resolve`](/cli/resolve)) proposal: for a `drift_revert`,
restores the resource's live state to match the ledger's recorded truth;
for a `change`, creates, modifies, and destroys resources for real, in one
combined dependency order (creates/modifies forward, destroys reversed),
feeding each resource's real applied output into any sibling still
carrying a `$computed` marker pointing at it. **This is the
one `ubx` command that changes real infrastructure** —
[`ubx accept`](/cli/accept), [`ubx why`](/cli/why),
[`ubx status`](/cli/status), [`ubx scan`](/cli/scan),
[`ubx resolve`](/cli/resolve), and [`ubx revert-plan`](/cli/revert-plan)
only ever read or record. `ubx revert-plan` still exists and still never
applies anything itself — it's what you reach for pre-acceptance, or if
you'd rather apply the correction through your own tooling; `ubx ship` is
what actually does it, post-acceptance.

Only `drift_revert` and `change` proposals can be shipped. Every other kind
is record-only — accepting an `adoption`/`drift_adopt` already is the
whole action, there's nothing to execute.

## Flags

| Flag | Description |
| --- | --- |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--provider string` | path to the provider binary (mutually exclusive with `--source`) |
| `--source string` | provider source address, e.g. `hashicorp/aws` (mutually exclusive with `--provider`; requires `--provider-version`) |
| `--provider-version string` | explicit provider version to acquire (required with `--source`) |
| `--provider-config string` | JSON object configuring the provider, e.g. `{"region":"us-east-1"}` (default `{}`) |
| `--timeout duration` | overall timeout for the ship run (default `5m0s`) |
| `--json` | emit one JSON document instead of human text — see [`--json` output](#json-output) |
| `-h`, `--help` | help for ship |

## Example: a clean apply

```text
$ ubx ship 44793cf195a9ae122df0fc68b805a75a6e07324b7a8a9fc6d2fd9415f1b0275e --provider ./terraform-provider-aws
applied: payments.fake_widget.api-cache
1 resource(s), 1 applied, 0 failed, 0 still unknown -- outcome: applied
```

## Example: idempotent re-run

Every resource already `applied` in a prior attempt is skipped — re-running
`ubx ship` against a proposal that already fully shipped is a genuine no-op,
not an empty response:

```text
$ ubx ship 8fa7a1498d41886a0f68138539d05876deee940a94edbac912c947d2529de56f --provider ./terraform-provider-aws
8fa7a1498d41886a0f68138539d05876deee940a94edbac912c947d2529de56f: already fully applied -- nothing to do
```

This is exit `0`, and writes no new [apply record](/concepts/apply-record)
at all — see [Idempotency](/concepts/apply-record#idempotency-safe-to-re-run-any-number-of-times).

## Example: a provider rejects the change

A real, structured error from the provider (not a timeout or transport
failure) ends that resource's attempt immediately — never silently retried:

```text
$ ubx ship 5e773920c109e45cf432a406f0f809b960ea3163c53f4e92a060d5ed94a87dbe --provider ./terraform-provider-aws
failed: payments.fake_widget.api-cache
  terminal: provider returned 1 diagnostic error(s): invalid attribute value: ...
1 resource(s), 0 applied, 1 failed, 0 still unknown -- outcome: failed
```

## Example: a redacted restore target is declined, not applied

A `drift_revert` whose restore value is itself a [`$redacted`](/concepts/secrets)
marker — the ledger holds a salted hash, never the real material — is
declined outright. `ubx ship` will never construct a live apply from it, on
this run or any future one; the message points at `ubx revert-plan`'s own
manual-reconciliation path:

```text
$ ubx ship 8c0b1b07cffccf20c1c59a95be2bb22f85fd9b7110f7695afd9e9ca75f9506ca --provider ./terraform-provider-aws
pending: payments.fake_widget.secret-box
  terminal: declined: after value(s) at tags.master_password are redacted -- the ledger holds a salted hash, not the real secret material, and ubx will never construct a live apply from it; use `ubx revert-plan` for this resource's manual reconciliation steps instead
1 resource(s), 0 applied, 1 failed, 0 still unknown -- outcome: failed
```

This is permanent, not transient: the same proposal declines identically on
every future `ubx ship` re-run, since the redacted value never changes. The
only way past it is restoring the real value out-of-band and recording the
correction through a fresh `ubx scan`/`ubx accept` cycle.

## Shipping a `change` proposal: a real create chain

A `change` proposal ([`ubx resolve`](/cli/resolve)'s own output) is shipped
the same way — creates and modifies together, in real dependency order.
Here `api-cache-mirror` cross-references `api-cache`'s `name` (concrete)
and its schema-`Computed` `id` (left as `$computed` at resolve time,
substituted with the real applied value mid-walk):

```text
$ ubx ship 2b4cb167dc39efc36fe16dec13947f189ff10e68863038f63dfd753d3fc34c9d --provider ./fakeprovider
applied: payments.fake_widget.api-cache
applied: payments.fake_widget.api-cache-mirror
2 resource(s), 2 applied, 0 failed, 0 still unknown -- outcome: applied
```

`api-cache` ships first (nothing depends on it being ordered any other
way); `api-cache-mirror` is never even attempted until `api-cache` reaches
`applied` — [`ubx why`](/cli/why) shows both:

```text
$ ubx why 2b4cb167dc39efc36fe16dec13947f189ff10e68863038f63dfd753d3fc34c9d
apply history:
  attempt 1: outcome=applied
    payments.fake_widget.api-cache:
      pending at 2026-07-17T14:32:37Z
      in_flight at 2026-07-17T14:32:37Z
      applied at 2026-07-17T14:32:37Z
    payments.fake_widget.api-cache-mirror:
      pending at 2026-07-17T14:32:37Z
      in_flight at 2026-07-17T14:32:37Z
      applied at 2026-07-17T14:32:37Z
```

<Note>
  Live-verified against real AWS, not just the fixture above: a real
  two-resource create chain (`aws_sqs_queue` + `aws_sqs_queue_policy`,
  the policy's `queue_url` only known once the queue itself exists),
  shipped for real, killed with a real `kill -9` between the queue
  applying and the policy starting, and correctly recovered on re-run —
  the dependent completed using the queue's REAL recorded output, never
  re-creating the queue or losing the value. See
  docs/reliability-report.md's own UBI-27 section (in the `ubiquex-cli`
  repo) for the full transcripts, including a real bug this work found
  and fixed along the way (a create never called the provider's
  `Configure` step, since unlike a modify it never goes through a read
  first — surfaced against a real provider as a bare transport error, not
  a clean configuration failure).
</Note>

A resource whose dependency hasn't applied yet is never attempted —
blocked with a named reason, not silently skipped or guessed at:

```text
$ ubx ship 0eb5887c4ee2da168467202856fa59970e1cc33dd330ec89263a7325d5d48f80 --provider ./fakeprovider
failed: payments.fake_widget.primary
  terminal: provider returned 1 diagnostic error(s): invalid attribute value: fakeprovider: simulated terminal diagnostic
pending: payments.fake_widget.mirror
  terminal: blocked: dependency payments.fake_widget.primary has not applied -- refusing to ship a resource ahead of what it depends on
2 resource(s), 0 applied, 2 failed, 0 still unknown -- outcome: failed
```

Killed and re-run, a `change` proposal's already-applied resources are
recognized exactly like a `drift_revert`'s (idempotency, above) — with one
addition: a still-pending dependent recovers its dependency's real applied
output from the ledger's own history, not just from what the current
`ubx ship` invocation itself computed, so a kill between two resources
never loses the value the second one needs.

<Note>
  A `partially_applied` outcome (some resources of a multi-resource revert
  applied, others not — most commonly because reality drifted a *second*
  time between acceptance and shipping) is exercised by the hermetic
  adversarial test suite rather than shown here as its own transcript; the
  mechanism is the same "outcome" field, just a third value alongside
  `applied`/`failed`. See [Apply record — the state machine](/concepts/apply-record#the-state-machine)
  for the full behavior.
</Note>

## Shipping a destroy

A `change` proposal's `delta.destroys` ([`ubx resolve`'s own "Destroying a
resource"](/cli/resolve#destroying-a-resource)) ships through the exact
same state machine, mixed in with any creates/modifies in the same
proposal via one combined dependency walk -- never a separate pass. Before
the risky call, `ubx ship` re-reads the target live and compares it
against what was signed away: present and matching proceeds; present but
different is refused (the operator never reviewed that exact state);
already gone is a low-friction success, never a refusal (there's nothing
left to lose):

```text
$ ubx ship a32a2ba327df634f9fd4c95cb18ec44406fb2433a6f9f1f98766b5b58e3e7086 --provider ./fakeprovider
applied: payments.fake_widget.old-widget
1 resource(s), 1 applied, 0 failed, 0 still unknown -- outcome: applied
```

`--json` shows the two-step reconciliation this precheck-then-confirm
shape actually produces -- `present_matches` (the live re-read, right
before the destroy call) followed by `destroyed` (the confirmation after):

```text
$ ubx ship a32a2ba327df634f9fd4c95cb18ec44406fb2433a6f9f1f98766b5b58e3e7086 --provider ./fakeprovider --json
```
```json
{
  "apply_record": {
    "resources": [
      {
        "address": {"stack": "payments", "type": "fake_widget", "name": "old-widget"},
        "transitions": [
          {"state": "pending", "at": "2026-07-18T00:56:30Z"},
          {"state": "in_flight", "at": "2026-07-18T00:56:30Z"},
          {"state": "applied", "at": "2026-07-18T00:56:30Z"}
        ],
        "reconciliation": [
          {"at": "2026-07-18T00:56:30Z", "outcome": "present_matches"},
          {"at": "2026-07-18T00:56:30Z", "outcome": "destroyed"}
        ]
      }
    ],
    "summary": {"outcome": "applied", "resources_applied": 1, "resources_failed": 0, "resources_still_unknown": 0}
  }
}
```

If the target is present but **drifted** from what was signed away, the
destroy is refused outright -- never reaching `in_flight`, never calling
`ApplyResourceChange` at all. Destroying state the operator never actually
reviewed defeats the whole reason `delta.destroys[].state` is carried
inline in the proposal:

```text
$ ubx ship 25e51271019ca2c9556b9680a138a04bb1fcbf2f196c5b4ada094684372f8a04 --provider ./fakeprovider
pending: payments.fake_widget.solo-widget
  terminal: destroy target drifted since it was signed away -- refusing to destroy state that was never reviewed
1 resource(s), 0 applied, 1 failed, 0 still unknown -- outcome: failed
```

The only way past this is a fresh `ubx scan`/`ubx accept` cycle recording
the new state, then a fresh destroy resolved and accepted against it.

If the target is **already gone** by the time its own turn in this batch
comes, that's a low-friction success, never a refusal -- there's nothing
left to lose that the operator didn't already implicitly ask to lose:

```text
$ ubx ship a4d89541006efb6d773d3afeee876cee667350125a648c344732c291e7c0664f --provider ./fakeprovider
applied: payments.fake_widget.widget-a
applied: payments.fake_widget.widget-b
2 resource(s), 2 applied, 0 failed, 0 still unknown -- outcome: applied
```

```json
{
  "resources": [
    {
      "address": {"stack": "payments", "type": "fake_widget", "name": "widget-b"},
      "transitions": [
        {"state": "pending", "at": "2026-07-18T02:52:40Z"},
        {"state": "applied", "at": "2026-07-18T02:52:40Z", "detail": "already absent before this attempt"}
      ],
      "reconciliation": [
        {"at": "2026-07-18T02:52:40Z", "outcome": "already_absent"}
      ]
    }
  ]
}
```

`widget-b` above never reaches `in_flight` at all -- its own freshness
precheck read comes back not-found, and that alone is enough to conclude
`already_absent`, since nothing has landed here yet for this attempt to
have caused it.

If the destroy's own `ApplyResourceChange` call times out ambiguously
instead, `ubx ship` reconciles by reading the target again: gone confirms
`destroyed` (but only because the precheck above already confirmed it was
there moments earlier -- a bare not-found read alone is never enough to
conclude anything); still there confirms `failed` (the call never
landed), retried normally on the next `ubx ship` invocation. A destroy is
idempotent the same way every other kind is -- already-`applied` (whether
the outcome was `destroyed` or the target was already gone) is skipped
entirely on re-run.

<Note>
  **A real, named limitation, not silently rounded away**: this
  reconciliation read is retried a handful of times, quickly (a few
  attempts, milliseconds apart) -- enough for an ordinary RPC hiccup, but
  not for a cloud provider's own genuine deletion-visibility lag. Real AWS
  SQS, for instance, can keep reporting a queue as present for well beyond
  the ~60 seconds its own documentation suggests, after `DeleteQueue`
  already succeeded. If that lag outlasts the retry budget, the resource is
  left honestly `unknown_post_timeout` rather than guessed at either
  way — a later, ordinary `ubx ship` re-run against the same proposal
  reconciles it correctly once the provider's own view catches up. This is
  a real, currently open gap in the retry budget itself (tracked
  separately, not specific to destroys), not evidence the destroy failed
  to land.
</Note>

`ubx ship` will refuse to have shipped this proposal in the first place
unless it was accepted with [`--confirm-destroys`](/cli/accept#confirming-a-destroy)
-- that gate lives in `ubx accept`, not here, since a proposal already
carrying an `Acceptance` was already confirmed at that point.

## Shipping across multiple providers

A stack with a real [`[providers]` table](/cli/config#multi-provider-stacks)
in `.ubx/config` ships a `change` proposal spanning more than one
provider binary as ONE signed unit -- `ubx resolve` already recorded
which provider owns each resource; `ubx ship` reads that back and
launches each one lazily, only the providers this specific proposal's
own resources actually need, each configured from its own
`[provider_configs]` entry. `--provider`/`--source`/`--provider-config`
are ignored (with a warning) once `[providers]` is declared -- the same
staging [`ubx resolve`'s own note](/cli/resolve) describes.

A resource whose own provider can't launch at all fails on its own,
terminally -- it never blocks a sibling resource against a different,
already-fine provider:

```text
$ ubx ship 9927129ddc5f0ba5fc14fd18c6bbd55ac39caf00cdcc54614fee11d0283ab22c --ledger-dir .
pending: payments.aws_db_instance.main
  terminal: provider unavailable: provider "hashicorp/aws" is pinned to 6.61.0 in this stack's [providers] config, but this proposal recorded 6.60.0 -- re-resolve against the current config
```

The transcript above is a version pin moving out from under an
already-signed proposal (`[providers]`'s own pin advanced to `6.61.0`
after this proposal was resolved and signed against `6.60.0`) -- refused
outright, never silently launched against whichever version happens to
be current. A launch failure for an unreachable registry or bad
credentials reports the identical shape (`provider unavailable: ...`,
naming the real cause) -- the outcome seals `partially_applied` when at
least one other resource, against a different provider, still lands
normally.

<Note>
  `ubx scan`/`ubx status --drift` don't read `[providers]` yet -- see
  [`.ubx/config`'s own note](/cli/config#multi-provider-stacks).
</Note>

`apply_record` is the full [apply record](/concepts/apply-record) itself —

happened when this shipped" — wrapped, not re-derived into a bespoke shape,
the same convention [`ubx why --json`](/cli/why#json-output) already
established for `proposal`.

## Exit code: the CI contract

| Exit code | Meaning |
| --- | --- |
| `0` | every resource applied (including a genuine no-op: already fully applied) |
| `1` | `partially_applied` or `failed` — an actionable finding: retry, or investigate why |
| `2` | bad input (proposal not found, wrong kind, not accepted), or a genuine provider/ledger failure |

See [Exit codes](/cli/exit-codes) for the full per-verb reference.

## Freshness, re-verified per resource

Unlike a one-shot command, `ubx ship` can run long enough, resource to
resource, that reality moves *during* the run. Freshness is re-checked
immediately before **each** resource's own attempt, not once at the start —
a resource that drifts a second time between acceptance and its own turn in
the queue is refused, not bulldozed; resources already applied earlier in
the same run stand untouched. See [Apply record](/concepts/apply-record) for
the full state machine.

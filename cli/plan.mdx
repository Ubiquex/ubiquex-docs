---
title: "ubx plan"
description: "Resolve any medium input into a draft proposal, render its full receipt, and save it as a hash-addressed plan for ubx ship"
---

```text
ubx plan [flags]
ubx plan <intent-file> (--provider <path> | --source <src> --provider-version <v>) [flags]
ubx plan --from-code <entry>.ts|.go|.py [flags]
ubx plan --from-doc <file>.md --stack <stack> [flags]
ubx plan --from-diagram <file>.d2 --stack <stack> [flags]
```

`ubx plan` fuses [`ubx propose`](/cli/propose) + [`ubx resolve`](/cli/resolve)
+ a preview render into one command — the terraform-shaped half of this
project's two-step workflow (`ubx plan`, then [`ubx ship <hash>`](/cli/ship)).
Exactly one input is required:

- **an intent file** (the positional argument) — a hand-written
  [`ubx:intent/v1` document](/cli/resolve#the-intent-file), resolved exactly
  like `ubx resolve` would.
- **`--from-code <entry>.ts|.go|.py`** — a [SDK program](/cli/resolve#authoring-in-typescript)
  in TypeScript, Go, or Python, dispatched by extension to the same
  hermetic evaluator `ubx resolve --from-code` uses for each language.
- **`--from-doc <file>.md --stack <stack>`** — a markdown authoring document,
  transcribed into an intent draft via the configured [`[intent]` provider adapter](/cli/config#intent)
  exactly like [`ubx propose --from-doc`](/cli/propose), then resolved in the
  same command. Since the intent-provider call is a real, seconds-long
  network round trip, a progress line renders before the receipt:
  ```text
  drafting via claude:claude-opus-4-8… ✓ · resolving…
  ```
  `ubx propose --from-doc` never shows this (it doesn't resolve, so "·
  resolving…" would be a lie there); parsing a `.d2` diagram or
  evaluating an SDK program is effectively instant, so neither
  `--from-diagram` nor `--from-code` shows one either.
- **`--from-diagram <file>.d2 --stack <stack>`** — a [D2 diagram](/guides/diagram-medium)'s
  own topology, parsed exactly like [`ubx propose --from-diagram`](/cli/propose),
  then resolved in the same command.
- **bare, no argument or flag** — auto-detects a single medium file in
  `--ledger-dir` and plans it as if you'd passed the matching flag
  yourself. See [Medium auto-detection](#medium-auto-detection), below.

Every input resolves through the identical, unmodified
[`core/resolver.Resolve`](/cli/resolve) every other entry point already
uses — same invariants, same orphan/pin checks, same failure modes. Its
full receipt renders to the terminal, and the resolved-but-unaccepted
proposal is saved at `.ubx/plans/<hash>.json`, keyed by the exact hash
[`ubx ship <hash>`](/cli/ship) will later look for.

**`ubx plan` never touches a ledger** — nothing here is accepted or
applied, exactly like `ubx resolve`/`ubx propose` today. Run `ubx ship
<hash>` to accept (local tier) and apply in one step, or hand the saved
plan to `ubx propose`/`ubx accept` for the full four-verb ceremony (a
separate PR-body trailer hash, PR-merge signing) if your team wants that
instead — see [When to use the four-verb ceremony](#when-to-use-the-four-verb-ceremony-instead).

<Note>
  The md/diagram media's own established "draft, then a separate human
  checkpoint before resolving" posture ([`ubx propose --from-doc`/`--from-diagram`](/cli/propose))
  is deliberately **not** reproduced here: `ubx plan`'s own receipt, covering
  the full resolved proposal — delta, cost, blast radius — alongside any
  assumptions/defaults/questions the draft carried, already serves as that
  checkpoint, rendered before anything is saved. `ubx propose --from-doc`/
  `--from-diagram` keep their exact existing draft-only behavior, unchanged,
  for teams that specifically want an extra checkpoint as its own step.
</Note>

## Flags

| Flag | Description |
| --- | --- |
| `--from-code string` | evaluate a TypeScript (`@ubx/sdk`), Go (`ubx-sdk-go`), or Python (`ubx_sdk`) SDK program, dispatched by extension, instead of reading an intent file |
| `--from-diagram string` | path to a `.d2` diagram — transcribes its topology into an intent/v1 draft, then resolves it |
| `--from-doc string` | path to a markdown authoring document — transcribes it into an intent/v1 draft via the configured `[intent]` provider, then resolves it |
| `--stack string` | target stack name (required with `--from-doc`/`--from-diagram`; the intent-file and `--from-code` inputs already name their own stack) |
| `--summary string` | `intent.summary` for the draft (only with `--from-diagram` — defaults to a generated summary naming the stack and resource count) |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) — also where the plan is saved, at `.ubx/plans/<hash>.json` |
| `--provider string` | path to the provider binary (mutually exclusive with `--source`) |
| `--source string` | provider source address, e.g. `hashicorp/aws` (mutually exclusive with `--provider`; requires `--provider-version`) |
| `--provider-version string` | explicit provider version to acquire (required with `--source`) |
| `--known-dependent stringArray` | `ledger_dir` of a neighbor stack to check for cross-stack orphan references before destroying (repeatable) |
| `--neighbor-ledger stringArray` | `<stack>=<path>` mapping a diagram's own cross-stack reference to a real ledger directory (repeatable, only with `--from-diagram`) |
| `--out string` | additionally write the full resolved proposal here (the plan is always saved under `.ubx/plans/` regardless) |
| `--timeout duration` | timeout for provider/schema acquisition, drafting (`--from-doc`), and evaluation (`--from-code`) — one shared budget (default `2m0s`) |
| `--full-hashes` | render every hash in full instead of the default 12-char short form |
| `--show-defaults` | render the full "AI defaults" block regardless of [`[intent] show_defaults`](/cli/config#show_defaults-the-ai-defaults-block) (mutually exclusive with `--hide-defaults`) |
| `--hide-defaults` | collapse the "AI defaults" block to a one-line count regardless of `[intent] show_defaults` (mutually exclusive with `--show-defaults`) — full detail is always in the saved plan file and the signed proposal either way |
| `-h`, `--help` | help for plan |

<Note>
  UBI-61's own visual language: colored, symbol-led output (green `+`
  creates, yellow `~` modifies, red `-` destroys, blue hashes) on a real
  terminal — `NO_COLOR` and any non-TTY (a pipe, a redirect, `mint`/CI
  transcripts) get the identical plain text shown below, and `--json` is
  untouched either way.
</Note>

## Medium auto-detection

Run `ubx plan` with no positional argument and no `--from-*` flag, and it
looks for exactly one medium file in `--ledger-dir` (default `.`) and
plans it automatically — an authoring `.md` doc, a `.d2` diagram, or a
`.ts`/`.go`/`.py` SDK program:

```text
$ ls
widget.ts

$ ubx plan --provider ./fakeprovider
Plan  sandbox · from widget.ts

  + fake_widget.widget1 create
      name: "widget1"

delta: +1 create(s), ~0 modify(ies), -0 destroy(s)

blast radius: +1 ~0 -0
cost delta: $0/mo

ubx-proposal: c49cf3986285…
next: ubx ship c49cf3986285
```

A README (or `CHANGELOG.md`/`LICENSE`/`CONTRIBUTING.md`/etc.) sitting
right next to a real medium is never itself mistaken for one — the
detection rules skip a fixed, case-insensitive denylist of well-known
project-meta markdown filenames:

```text
$ ls
README.md   widget.ts

$ ubx plan --provider ./fakeprovider
Plan  sandbox · from widget.ts

  + fake_widget.widget1 create
      name: "widget1"

delta: +1 create(s), ~0 modify(ies), -0 destroy(s)

blast radius: +1 ~0 -0
cost delta: $0/mo

ubx-proposal: b07eaf5162c2…
next: ubx ship b07eaf5162c2
```

More than one real candidate is never guessed between — a teaching
error lists each one with its own correct flag:

```text
$ ls
platform.md   topology.d2

$ ubx plan
plan: multiple mediums found: platform.md, topology.d2 -- pick one: ubx plan --from-doc platform.md | ubx plan --from-diagram topology.d2
```

<Note>
  A `.ts`/`.go`/`.py` file is only ever a candidate if its own content
  carries the real SDK import (`"@ubx/sdk"` for TypeScript,
  `github.com/ubiquex/ubx-sdk-go` for Go, `import ubx_sdk` for Python) —
  a bare extension match would false-positive on an arbitrary source
  file sitting in the same directory (a near-certainty for `.go`, since
  `ubx` itself is a Go module). One consequence worth knowing: a small
  helper/bindings file that merely *imports types* from `@ubx/sdk`
  (rather than being the runnable entry point itself) also carries that
  same import string, so it counts as its own separate candidate too —
  keep an SDK-authored stack's entry point and its own type bindings in
  different directories (or pass `--from-code` explicitly) if this
  happens in practice.
</Note>

`--from-doc`/`--from-diagram`/`--from-code` remain for explicit
selection at any time — auto-detection only ever runs when none of them
(and no positional argument) was given.

## Example: a two-resource create chain

```json intent.json
{
  "schema_version": 1,
  "kind": "ubx:intent/v1",
  "stack": "sandbox",
  "intent": {"summary": "a widget and its mirror, for the two-step flow"},
  "resources": [
    {
      "type": "fake_widget",
      "name": "primary",
      "op": "create",
      "config": {"name": "primary-widget", "tags": {"env": "sandbox"}}
    },
    {
      "type": "fake_widget",
      "name": "mirror",
      "op": "create",
      "config": {
        "name": {"$ref": {"to": "sandbox.fake_widget.primary.name"}},
        "tags": {"peer_id": {"$ref": {"to": "sandbox.fake_widget.primary.id"}}}
      }
    }
  ]
}
```

```text
$ ubx plan intent.json --provider ./fakeprovider --ledger-dir .
Plan  sandbox · from intent.json

  + fake_widget.primary create
      name: "primary-widget"
      tags:
      {
        "env": "sandbox"
      }

  + fake_widget.mirror create
      name: "primary-widget"
      tags:
      {
        "peer_id": $ref:sandbox.fake_widget.primary.id
      }

delta: +2 create(s), ~0 modify(ies), -0 destroy(s)

blast radius: +2 ~0 -0
cost delta: $0/mo

ubx-proposal: afb94ca765bb…
next: ubx ship afb94ca765bb
```

Every resolved config key renders, not just the ones the intent file set
explicitly — `mirror`'s own `tags.peer_id` shows as `$ref:sandbox.fake_widget.primary.id`
since it isn't resolved until `primary` actually applies (see
[`ubx ship`'s own create-chain example](/cli/ship#a-two-resource-create-chain)
for what it becomes for real). This is a **display-only** convention for
the resolved `$computed` marker underneath — the real wire format for an
unresolved reference is (and stays) the `{"$ref": {"to": "..."}}` object,
resolved away before the ledger ever sees it; only the *rendering* of the
`$computed` marker that reference resolves to borrows this terse
dotted-address notation, for readability. A JSON-valued attribute (like
`tags`, a map) renders as a formatted, indented block, never a
single-line escaped string. `cost_delta` renders whatever
`core/resolver` already computed — `$0/mo` today, unchanged by this
command; there's no cost-estimation engine yet. The last two lines are
the ones that matter for the next step: the hash (short by default —
`--full-hashes` opts into the full form; `.ubx/plans/` on disk is an
implementation detail, never printed) and the ship-able handoff.

## Example: AI defaults render as their own titled block

`--from-doc`/`--from-diagram` carry whatever ambiguity content the intent
provider or diagram parse produced straight through to the same receipt —
resolved delta and draft-time ambiguity, together, in one review.
Assumptions and defaults merge into one purple **"AI defaults — you are
signing these:"** block (docs/cli-output-spec.md principle 4: this is
what a human is actually being asked to sign off on); blocking questions
get their own red block, rendered first, when there are any:

```text
$ ubx plan --from-diagram topo.d2 --stack payments --neighbor-ledger shared=../shared --ledger-dir .
Plan  payments · from topo.d2

  + fake_widget.main-widget create

delta: +1 create(s), ~0 modify(ies), -0 destroy(s)

blast radius: +1 ~0 -0
cost delta: $0/mo

AI defaults — you are signing these:

◦ resource "payments.fake_widget.main-widget" is drawn with a relationship to external reference "shared.fake_widget.other-widget" -- the diagram medium does not yet emit a wire-level $cross reference for a topology-only edge with no named attribute. Add an explicit $cross reference in the resource's own config by hand if this needs to be enforced structurally.
    affects: payments.fake_widget.main-widget

ubx-proposal: 09a63d993039…
next: ubx ship 09a63d993039
```

<Note>
  This is the default (`[intent] show_defaults = true`) — for repeat use
  on a familiar stack, `[intent] show_defaults = false` (or a one-off
  `--hide-defaults`) collapses assumptions/defaults to a one-line count
  instead, without ever omitting them from the saved plan file or the
  signed proposal. Blocking questions are never collapsed, either way.
  See [`show_defaults`](/cli/config#show_defaults-the-ai-defaults-block)
  for the full behavior and why the default is `true`.
</Note>

## Example: destroys still require confirmation, at ship time

`ubx plan` never accepts anything, so it never asks for
`--confirm-destroys` itself — but the destroy still renders in full, red-led,
the same "make the content visible, not just the decision" `ubx resolve`
already applies to `delta.destroys`:

```text
$ ubx plan destroy-intent.json --provider ./fakeprovider --ledger-dir .
Plan  sandbox · from destroy-intent.json

  - destroy: sandbox.fake_widget.mirror
    id: "computed-id"
    name: "primary-widget"
    tags: {"peer_id":"computed-id"}

delta: +0 create(s), ~0 modify(ies), -1 destroy(s)

blast radius: +0 ~0 -1
cost delta: $0/mo

ubx-proposal: 6ae8d6812bc4…
next: ubx ship 6ae8d6812bc4
```

The confirmation gate itself lives in [`ubx ship`](/cli/ship#shipping-a-destroy),
at the moment this plan is actually accepted:

```text
$ ubx ship 6ae8d6812bc4 --provider ./fakeprovider --ledger-dir . --yes
ship: this proposal has blast_radius.destroys > 0 -- pass --confirm-destroys to accept it
```

See [`ubx ship`'s own "Shipping a destroy"](/cli/ship#shipping-a-destroy) for
the full destroy lifecycle once confirmed — freshness precheck, the
already-gone case, and everything else is identical whether the proposal
came from `ubx plan` or the four-verb ceremony.

## The plan file

`.ubx/plans/<hash>.json` holds the exact resolved [proposal](/concepts/proposal)
`ubx plan` printed the receipt for — a plain, human-readable JSON file, not
a binary format. It sits alongside `.ubx/salt`/`.ubx/lock`, never inside
`ledger/`: a plan is a draft, not a recorded decision, until `ubx ship`
actually accepts it.

<Note>
  The filename **is** the proposal's own content hash — the same hash
  `id` becomes once it's accepted. `ubx ship` verifies this on read: a
  hand-edited or corrupted plan file whose content no longer hashes to
  its own filename is refused outright, never shipped under a hash that
  no longer describes it.
</Note>

## When to use the four-verb ceremony instead

`ubx plan`/`ubx ship` is a fast path, not a replacement — the underlying
machinery (`core/resolver.Resolve`, `core.Accept`, `executor.Ship`) is
completely unchanged, and nothing about the four-verb ceremony is
deprecated. Reach for `ubx resolve` → `ubx propose` → `ubx accept
--from-merge` → `ubx ship` instead of the fused path when your team binds
acceptance to a real review process:

- **PR-merge acceptance** — [`ubx propose <resolved.json>`](/cli/propose)
  prints the trailer hash for a PR body, review happens on GitHub, and
  [`ubx accept --from-merge`](/cli/accept#pr-merge-acceptance) derives
  acceptance from the merge itself rather than trusting a local `ubx
  ship` run. See [PR-merge acceptance](/guides/pr-merge-acceptance) for
  the full walkthrough.
- **A separate draft-review checkpoint** for the md/diagram media —
  `ubx propose --from-doc`/`--from-diagram` stop at the draft, letting a
  human review the raw ambiguity content on its own before anyone runs
  `ubx resolve` against it at all.

Both paths produce the exact same signed [proposal](/concepts/proposal)
shape and go through the exact same invariants — which one you reach for
is about your team's own review process, not a difference in what `ubx`
enforces.

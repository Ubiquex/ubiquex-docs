---
title: "ubx accept"
description: "Accept a proposal -- locally, with optional freshness reverification, or derived from a merged GitHub pull request -- and append it to the ledger"
---

```text
ubx accept [proposal.json] [flags]
ubx accept --from-merge <sha> --proposal-file <path> --github-repo <owner/name> [flags]
```

Signs a [proposal](/concepts/proposal) and appends it to the
[ledger](/concepts/ledger), using one of two acceptance tiers.

## Flags

| Flag | Description |
| --- | --- |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--confirm-destroys` | required to accept any proposal with `blast_radius.destroys > 0` |
| `--reverify-with string` | path to a provider binary: re-read the resource live and refuse to accept if it no longer matches the proposal's recorded observation (stale). Mutually exclusive with `--reverify-source` |
| `--reverify-source string` | provider source address to acquire for reverification, e.g. `hashicorp/aws` (mutually exclusive with `--reverify-with`; requires `--reverify-provider-version`) |
| `--reverify-provider-version string` | explicit provider version to acquire for reverification (required with `--reverify-source`) |
| `--resource-type string` | resource type to re-read (required with `--reverify-with`/`--reverify-source`) |
| `--resource-name string` | resource name to re-read (required with `--reverify-with`/`--reverify-source`) |
| `--provider-config string` | JSON object configuring the provider, used with `--reverify-with`/`--reverify-source` (default `{}`) |
| `--timeout duration` | timeout for the reverify provider round trip (default `1m0s`) |
| `--from-merge string` | derive `pr_merge` acceptance from a merge commit SHA instead of accepting a local file |
| `--repo-dir string` | local git working tree to verify `--from-merge`'s commit history against (default `.`) |
| `--proposal-file string` | path, within the repo, to the proposal file the merge commit carries (required with `--from-merge`) |
| `--github-repo string` | owner/name of the GitHub repository (required with `--from-merge`) |
| `-h`, `--help` | help for accept |

## Local acceptance

`ubx accept proposal.json` signs a file on disk, recording your OS username
and the current time as `local` acceptance.

```text
$ ubx accept adopt.json --ledger-dir .
accepted 16223f8b731dcc40bafb9b0ad8337e9153c82257087eba8b2a17b20503171ca1 (stack payments)
```

### Reverifying freshness before accepting

A proposal captures live state at the moment `ubx scan` ran. If real time
passes between generating a proposal and accepting it, reality may have moved
on again. `--reverify-with` (or `--reverify-source` for registry acquisition)
re-reads the resource — using the exact lookup key already recorded in the
proposal's `resolution.inputs`, not a new `--lookup` you supply — and refuses
to accept if the fresh read no longer matches what the proposal recorded.

Passes when nothing changed since the scan:

```text
$ ubx accept adopt.json --ledger-dir . \
    --reverify-with ./terraform-provider-aws \
    --resource-type fake_widget --resource-name api-cache2
accepted 58e572309efe8dcbff5c2b98f112bdca2511acdee16c3e9c35081bbd2d3790bf (stack payments)
```

Blocked when the resource changed out from under the proposal:

```text
$ ubx accept adopt.json --ledger-dir . \
    --reverify-with ./terraform-provider-aws \
    --resource-type fake_widget --resource-name api-cache3
Error: accept: stale observation: reality changed since this proposal was generated: payments.fake_widget.api-cache3 recorded b5afdb3fb4bf5480300afee266988d93afe18054575db5a32ef4975b71d91334, now 028056c53f2b3ed9b25280b101479c28d7cf8f57ffe517e3556e13a0db596ff4
```

A blocked reverification never touches the ledger — nothing is written. It
exits `1`, the same as a rejected `--from-merge` acceptance below — see
[Exit codes](/cli/exit-codes).

`--reverify-source`/`--reverify-provider-version` reverify by acquiring the
provider from a registry instead of pointing at a local binary — the same
`UBX_PROVIDER_MIRROR` → cache → live-registry resolution order
[`ubx scan`'s `--source`](/cli/scan#acquiring-a-provider-by-source-provider-version-instead-of-provider)
uses:

```text
$ ubx accept rv-adopt.json --ledger-dir . \
    --reverify-source acme/widget --reverify-provider-version 6.54.0 \
    --resource-type fake_widget --resource-name registry-widget2
accepted 151fbb18bef7e0b4344853df70d56c6df98579b43f677962c6a0b792c1ad2778 (stack payments)
```

### Confirming a destroy

Any proposal with `blast_radius.destroys > 0` is refused unless
`--confirm-destroys` is given, every time -- the only acceptance-time check
in this command that isn't detecting staleness or verifying evidence
against reality. The proposal is already fully valid, resolve-time
orphan-checked (see [`ubx resolve`'s own "Destroying a
resource"](/cli/resolve#destroying-a-resource)), and fresh by the time
this gate is reached -- its only job is making sure a human actually meant
to accept something with teeth.

```text
$ ubx accept destroy.json --ledger-dir .
Error: accept: this proposal has blast_radius.destroys > 0 -- pass --confirm-destroys to accept it
```

Nothing is written to the ledger. Exits `1`, the same tier as a blocked
reverification or a stale cross-stack pin -- see [Exit
codes](/cli/exit-codes).

```text
$ ubx accept destroy.json --ledger-dir . --confirm-destroys
accepted 331ead727636764d150c9255a0f437880731c8f76cb24d6f41aa4150bfd20f6f (stack payments)
```

`--confirm-destroys` applies to both acceptance tiers -- a `--from-merge`
acceptance carrying destroys needs it exactly as a local file does. There
is no way to configure this away (no `.ubx/config` default, no
environment variable) -- it's a per-invocation acknowledgment, not a
one-time setting.

### Cross-stack pin verification

A proposal [`ubx resolve`](/cli/resolve) produced from an intent file with
a `$cross` reference carries a `cross_stack_pin` resolution input: the
neighbor ledger's `ledger_dir` and its head *at resolve time*
(`pinned_head`). `ubx accept` -- both local and `--from-merge` -- always
re-derives that neighbor ledger's *current* head and refuses the proposal
if it's moved on since, the same "resolved-time truth vs. accept-time
reality" shape `--reverify-with` already enforces for live cloud state, one
level up. This check runs unconditionally, with no flag to opt in or out:
unlike a live provider round trip, reading a neighbor ledger's head is a
free, local filesystem read.

Passes when the neighbor hasn't moved since resolve:

```text
$ ubx accept payments/resolved.json --ledger-dir payments
accepted c77dadcd84d9a8b31c33517752e3f2336f7e45b1ef6836dfbdbfdb59e240d6ba (stack payments)
```

Blocked once the neighbor ledger (`networking` here) has advanced --
someone else accepted a proposal there in the meantime:

```text
$ ubx accept payments/resolved2.json --ledger-dir payments
Error: accept: resolve: cross-stack pin is stale -- the neighbor ledger has advanced since this proposal was resolved: networking.fake_widget.vpc (ledger /tmp/ubx-resolve-docs5/networking) pinned at 7a069a2a22e2b4edc6e1ed3aae58108415371c3a9dc6b72c19fc62c6acb9bd33, now dbc6c8e07631cdf860abccbfcdbb7236a7f59407cd855650dd25bae9ef672f2f
```

Exits `1`, the same tier as a blocked `--reverify-with` reverification --
and nothing is written to the ledger.

## PR-merge acceptance

`ubx accept --from-merge` derives acceptance from a merged GitHub pull
request instead of trusting a local file directly. It:

1. Confirms the merge commit SHA exists in `--repo-dir`'s git history.
2. Reads `--proposal-file` at that exact commit and hashes it, checking that
   hash against the `ubx-proposal: <hash>` trailer in the merged PR's body
   (the trailer [`ubx propose`](/cli/propose) computes, or that
   `ubx scan --surface-as pr` writes automatically).
3. Records every reviewer whose most recent review on that PR was an
   approval — a later `CHANGES_REQUESTED`, or a re-review after approving,
   supersedes an earlier approval from the same person.

Zero approvers is a normal, unblocked outcome — this tier's guarantee is that
the *acceptance record* is checkable against git/GitHub history, not that a
review policy was satisfied. Enforcing "N approvals required" is a decision
to make in your own repo's branch protection, not something `ubx accept`
itself gates on.

If the trailer's hash doesn't match what `--proposal-file` actually hashes to
at that commit, the merge commit no longer exists in `--repo-dir`'s history,
the file is absent from that commit, no pull request is associated with the
commit at all, or the PR body has no trailer to read — the claimed acceptance
doesn't check out, and `ubx accept --from-merge` refuses it and exits `1` (see
[Exit codes](/cli/exit-codes)). Nothing is ever appended to the ledger in
these cases.

```text
$ ubx accept --from-merge 1f4a193321c803340fcc3ae1d7bc387c74922763 \
    --repo-dir . \
    --proposal-file proposals/pending.json \
    --github-repo acme/infra \
    --ledger-dir .
accepted 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae (stack payments) via PR #42, 1 approver(s)
```

`ubx accept --from-merge` reads a `GITHUB_TOKEN` environment variable for API
access; an empty token still works against public repos, at a much lower
rate limit.

<Note>
  `--github-repo` falls back to [`.ubx/config`](/cli/config)'s `github_repo`
  if not given explicitly.
</Note>

<Note>
  If the stack named inside the proposal file has a remote
  [`[ledger]` store](/concepts/ledger-stores) configured, the accepted
  record is mirrored there — the same CAS-guarded write local `ubx accept`
  already does — right after the git/GitHub verification above succeeds,
  never before it. Git stays the signing surface either way: the merge
  commit and the committed proposal file are still what everything above
  verifies against, permanently, regardless of which store ends up holding
  the accepted record. See [Ledger stores' own PR-acceptance
  section](/concepts/ledger-stores#the-pr-acceptance-ceremony-git-signs-the-remote-store-records)
  for the full mechanism and a real transcript against S3.
</Note>

<Note>
  Every `ubx accept` (local or `--from-merge`) briefly locks the ledger
  directory (`.ubx/lock`) so a concurrent accept from another person or a
  CI job can't race it — see [Ledger: Concurrent
  access](/concepts/ledger#concurrent-access). `ubx scan`/`ubx why`/`ubx
  status` never take this lock and are never blocked by it.
</Note>

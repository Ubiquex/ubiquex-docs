title: "Resource lookup conventions"
description: "What --lookup needs to actually find a resource, per type -- AWS, GCP, and Azure"
---

[`ubx scan`](/cli/scan)'s `--lookup` flag is a JSON object identifying the
resource to the provider — most examples in these docs show
`{"id": "..."}`, and for most types that's genuinely enough. A handful of
common types need more than `id` alone, or use a different field as `id`
entirely, and get this wrong silently: the provider's `ReadResource` call
succeeds but reads back a resource that doesn't match what you meant, or
reads back `null` for the field you assumed was set. This page exists so
that's not a surprise.

<Note>
  `ubx` doesn't only rely on you having read this page first: for
  `aws_s3_bucket`, `aws_iam_role`, and `aws_iam_user` specifically, a scan
  that hits this exact mistake (their own natural-key attribute given
  alone, without `id`) gets a teaching error naming the fix directly —
  e.g. `aws_s3_bucket's lookup must include "id" -- bucket alone is not
  enough`, with a link back to this page. See
  [Exit codes](/cli/exit-codes) for how that failure counts toward the CI
  contract (it's exit `2`, a genuine error, not an actionable finding).
</Note>

## AWS: types with a confirmed non-default lookup shape

These seven types have been verified against the real AWS provider (not
just a test fixture) as part of `ubiquex`'s internal conformance suite —
their lookup requirement below is empirically confirmed, not assumed from
the schema:

| Type | Required `--lookup` shape | Why |
| --- | --- | --- |
| `aws_s3_bucket` | `{"id": "<name>", "bucket": "<name>"}` | `id` and `bucket` are both the bucket name. Sending only `bucket` reads back `null`. |
| `aws_iam_role` | `{"id": "<role-name>", "name": "<role-name>"}` | `id` and `name` are both the role name (not the ARN). `name` alone reads back `null`. |
| `aws_iam_user` | `{"id": "<user-name>", "name": "<user-name>"}` | Same shape as `aws_iam_role`: `id`/`name` are both the user name; `name` alone reads back `null`. |
| `aws_iam_policy` | `{"id": "<policy-arn>"}` | `id` **is** the ARN (unlike role/user, which use the name) — no separate `name` or `arn` key needed. |
| `aws_sqs_queue` | `{"id": "<queue-url>"}` | `id` **is** the queue URL, not the ARN (though `arn` is also surfaced by the schema). |
| `aws_sns_topic` | `{"id": "<topic-arn>"}` | `id` **is** the topic ARN, same pattern as `aws_iam_policy`. |
| `aws_vpc` | `{"id": "<vpc-id>"}` | Standard — `id` is the `vpc-*` id, and that's all the lookup needs. Listed here because it's a type people reach for immediately, and it turns out to need nothing special. |

## Every other AWS type

Every other AWS type `ubx` has been tested against — roughly forty more,
covering compute, network, storage, database, DNS, messaging, and
observability — defaults to `{"id": "<the resource's id>"}` and nothing
more, matching the schema each type's provider itself declares.

<Note>
  That default is verified against each type's real `GetProviderSchema`
  response (free, no credentials or API round trip needed), and against a
  fixture that proves ubx's own scan/diff pipeline handles that type's
  attribute shape correctly. It is **not** independently verified against a
  real provider's live `ReadResource` call the way the seven types above
  are — those seven were specifically flagged because a live call is the
  only way something like "`bucket` alone reads back null" would ever
  surface. If `--lookup '{"id": "..."}'` reads back an unexpected or empty
  result for a type not listed above, that's the first thing to suspect.
</Note>

## GCP

`ubx` also speaks to `hashicorp/google` the same way it speaks to
`hashicorp/aws` — same wire protocol, same `--source`/`--provider`
acquisition (see [Installation](/getting-started/installation)). It
negotiates tfplugin protocol v5, the same version `hashicorp/aws` speaks.

GCP support is newer than AWS's: `ubiquex`'s internal conformance suite
tracks about 40 GCP resource types across compute, network, IAM, storage,
SQL, and DNS, with identity fields checked against the real
`hashicorp/google` schema. Five have been live-verified against a real
account so far:

| Type | Required `--lookup` shape | Why |
| --- | --- | --- |
| `google_service_account` | `{"id": "projects/<project>/serviceAccounts/<email>"}` | `id` (the full resource path) alone is sufficient — same shape as `aws_iam_policy`. |
| `google_project_iam_custom_role` | `{"id": "projects/<project>/roles/<role_id>"}` | `id` (the full resource path) alone is sufficient, same as `google_service_account`. |
| `google_storage_bucket` | `{"id": "<name>", "name": "<name>"}` | `id` and `name` are both the bucket name, and **both are required together** — unlike `aws_s3_bucket`, where `id` alone already works. `id` alone errors outright; `name` alone reads back `null`. |
| `google_pubsub_topic` | `{"id": "projects/<project>/topics/<name>", "name": "<name>"}` | `id` alone doesn't error and doesn't read back `null` — it succeeds, but the topic's own `name` attribute comes back empty. A more dangerous mistake than any AWS type shows: nothing signals that anything went wrong. |
| `google_secret_manager_secret` | `{"id": "projects/<project>/secrets/<name>", "secret_id": "<name>"}` | Same silent-incomplete-read shape as `google_pubsub_topic` — `id` alone succeeds but with `name`/`secret_id` empty or `null`. |

<Warning>
  `google_pubsub_topic` and `google_secret_manager_secret`'s `id`-alone
  mistake does **not** produce [a teaching error](#every-other-aws-type) or
  even a failure — `ubx scan` reports a normal `new`/`drifted` outcome and
  writes a proposal with genuinely incomplete data. Nothing here saves you
  from getting this specific one wrong except reading this table first.
</Warning>

Every other tracked GCP type defaults to `{"id": "<the resource's id>"}`,
same as AWS's own default — not yet independently verified against a real
account the way the five above are.

## Azure

`ubx` also speaks to `hashicorp/azurerm` the same way it speaks to any
other provider — same `--source`/`--provider` acquisition. It negotiates
tfplugin protocol v5, the same version `hashicorp/aws`/`hashicorp/google`
speak. (`azure/azapi`, a separate, much smaller Azure provider that models
every ARM resource through a handful of generic types rather than one type
per resource, negotiates v6 instead — the first provider source this
project has onboarded that doesn't speak v5. `ubx` isn't set up to scan
`azapi_*` types the way it is `azurerm_*` ones; see the internal
architecture notes if you're curious why.)

Azure support is newer than AWS's/GCP's: `ubiquex`'s internal
conformance suite tracks 42 azurerm resource types across compute,
network, IAM, storage, database, DNS, and messaging, with identity fields
checked against the real `hashicorp/azurerm` schema. Unlike GCP's own
varied `id`/`self_link`/`uid` shapes, every azurerm type has both `id`
(the full ARM resource path) and `name` as flat top-level attributes — a
materially simpler, more AWS-like schema shape. Five types have been
live-verified against a real subscription so far:

| Type | Required `--lookup` shape | Why |
| --- | --- | --- |
| `azurerm_storage_account` | `{"id": "/subscriptions/.../storageAccounts/<name>"}` | `id` (the full ARM path) alone is sufficient — the opposite of `google_storage_bucket`'s own "both required" trap; azurerm's ARM id already fully qualifies the resource. |
| `azurerm_storage_container` | `{"id": "/subscriptions/.../storageAccounts/<account>/blobServices/default/containers/<name>"}` | Same shape as `azurerm_storage_account`. |
| `azurerm_key_vault` | `{"id": "/subscriptions/.../vaults/<name>"}` | Same shape. Azure Key Vault's own soft-delete default means a *deleted* vault's name stays reserved for up to 90 days — if you're recreating one under the same name, you may need to purge the old one first. |
| `azurerm_user_assigned_identity` | `{"id": "/subscriptions/.../userAssignedIdentities/<name>"}` | Same shape — `id` alone, same as `google_service_account`. |
| `azurerm_resource_group` | `{"id": "/subscriptions/<sub>/resourceGroups/<name>"}` | `id` alone is sufficient, but its own shape is the one real surprise here: a resource group's id is just `/subscriptions/<sub>/resourceGroups/<name>` — **not** the `resourceGroups/<rg>/providers/<namespace>/<type>/<name>` shape every other azurerm type's own id follows. A resource group is its own top-level scope, never nested inside another resource group's own path. |

<Note>
  Every other tracked azurerm type defaults to `{"id": "<the resource's
  full ARM path>"}`, same as AWS's/GCP's own default — not yet
  independently verified against a real subscription the way the five
  above are. Given every sampled type's schema has both `id` and `name`
  as flat attributes (no GCP-style nesting variation), the default is a
  reasonable bet, but — per the GCP lesson above — a reasonable-looking
  schema is not proof; treat an unverified azurerm type with the same
  caution as an unverified GCP one.
</Note>

## Kubernetes and Helm

`ubx` also speaks to `hashicorp/kubernetes` and `hashicorp/helm` the same
way it speaks to any other provider — same `--source`/`--provider`
acquisition. Both negotiate tfplugin protocol v5, same as
`hashicorp/aws`/`hashicorp/google`.

<Note>
  Every `kubernetes_*` resource type models its `metadata` (and, for
  workload types, `spec`) block as a **list of one item**, not a bare
  object — a real Terraform SDKv2 convention, confirmed directly against
  the real `hashicorp/kubernetes` 2.35.1 schema. This might suggest
  `--lookup` needs to be shaped `{"metadata": [{"name": "...",
  "namespace": "..."}]}` — it does not. See the table below: `id` alone
  is genuinely sufficient, confirmed live against a real cluster, not
  assumed from the schema shape.
</Note>

| Type | Required `--lookup` shape | Why |
| --- | --- | --- |
| `kubernetes_config_map_v1` | `{"id": "<namespace>/<name>"}` | `id` alone is sufficient — the provider parses namespace/name out of it internally. |
| `kubernetes_secret_v1` | `{"id": "<namespace>/<name>"}` | Same shape as `kubernetes_config_map_v1`. `data`/`binary_data` are redacted (see [Secrets](/concepts/secrets)) regardless of how it's looked up. |
| `kubernetes_deployment_v1` | `{"id": "<namespace>/<name>"}` | Same shape, confirmed on a workload type (`spec` is also list-nested, same as `metadata`). |
| `kubernetes_service_v1` | `{"id": "<namespace>/<name>"}` | Same shape. |
| `kubernetes_namespace_v1` | `{"id": "<name>"}` | Cluster-scoped — no namespace prefix at all, unlike every namespaced type above. |

Every other `kubernetes_*` type in `ubx`'s conformance registry defaults
to the same `{"id": "<namespace>/<name>"}` shape (or `{"id": "<name>"}`
for the other cluster-scoped RBAC types — `kubernetes_cluster_role_v1`,
`kubernetes_cluster_role_binding_v1`) — not yet independently verified
against a real cluster the way the five above are.

`helm_release` is the opposite case: it has no list-nested blocks at all
(a flatter, AWS/GCP-shaped identity), but `id` alone is **not** enough —
confirmed live, the required shape is all three together:

| Type | Required `--lookup` shape | Why |
| --- | --- | --- |
| `helm_release` | `{"id": "<release-name>", "name": "<release-name>", "namespace": "<namespace>"}` | `id` alone (or `name`/`namespace` alone) doesn't read the release back — all three are needed together. |

```bash
ubx scan --source hashicorp/kubernetes --provider-version 2.35.1 \
  --stack platform --type kubernetes_secret_v1 --name app-secret \
  --lookup '{"id":"ubx-test/app-secret"}' \
  --provider-config '{"config_path":"~/.kube/config","config_context":"my-cluster"}' \
  --ledger-dir .
```

`hashicorp/helm`'s own provider config nests its Kubernetes connection
inside a list-wrapped `kubernetes` block too (the same NestingList
convention as `metadata` above, confirmed against the real schema):

```bash
ubx scan --source hashicorp/helm --provider-version 2.17.0 \
  --stack platform --type helm_release --name myrelease \
  --lookup '{"id":"myrelease","name":"myrelease","namespace":"ubx-test"}' \
  --provider-config '{"kubernetes":[{"config_path":"~/.kube/config","config_context":"my-cluster"}]}' \
  --ledger-dir .
```

## `--lookup` never needs, and never redacts, secret material

Every type this project has checked against a real provider schema (see
[Secrets](/concepts/secrets)) confirms the same thing: an
identity/lookup-worthy attribute (`id`, `name`, `arn`, `bucket`) is never
also flagged `Sensitive` — you never need a password or API key to find a
resource, only to read one back. Because of that, `--lookup` is passed
through to the ledger's `resolution.inputs[].lookup` unredacted (needed
verbatim so `ubx accept --reverify-with`/`--reverify-source` can re-read
the same resource later) — this is safe precisely because no real
resource type ever requires secret material there in the first place.

---
title: "ubx providers check"
description: "Query the real Terraform Registry for a newer version of every provider pinned in [providers] -- the reusable primitive behind automated version-pin PRs"
---

```text
ubx providers check [--write] [--timeout duration]
```

Reads `.ubx/config`'s own [`[providers]` table](/cli/config#multi-provider-stacks)
(the same source of truth `ubx resolve`/`ubx ship`/[`ubx sdk gen`](/cli/sdk-gen)
already read) and queries the real, unauthenticated Terraform Registry
"list versions" endpoint --
`https://registry.terraform.io/v1/providers/:namespace/:type/versions` --
for each declared provider's own latest real release, excluding
pre-releases.

<Note>
  This is a genuinely different concern from [`ubx sdk gen`](/cli/sdk-gen)'s
  own provider-binding automation. `ubx sdk gen` keeps generated SDK
  BINDINGS current against a REPO's own pinned version (and, for the real
  live `ubx-sdk-*` repos, has its own separate GitHub Actions automation).
  `ubx providers check` is about the actual provider BINARY version a
  stack's own `.ubx/config` pins -- "Dependabot, but for a pinned
  Terraform provider version." Genuinely unrelated wire protocols too:
  this command's own registry query never downloads or verifies a
  provider binary at all (that's `provider.Acquire`'s own job, against a
  different registry -- see [Provider acquisition](/concepts/trust-model)),
  it only ever asks "what's the latest version number."
</Note>

## Example

```toml .ubx/config
providers = {
  "hashicorp/aws" = "6.50.0"
}
```

```text
$ ubx providers check
hashicorp/aws: 6.50.0 -> 6.58.0 available
providers check: a newer version is available for at least one provider (see above)
```

Exit code matches [`ubx status --drift`](/cli/status)'s own established
contract: `0` if every pin is already current, `1` if a newer version is
available for at least one provider (a real, actionable signal a CI
workflow can branch on -- never a hard failure on its own), `2` on a real
error (registry unreachable, no `[providers]` declared).

## `--write`: bump the pin in place

```text
$ ubx providers check --write
hashicorp/aws: 6.50.0 -> 6.58.0 available
hashicorp/aws: wrote 6.50.0 -> 6.58.0 in /path/to/.ubx/config.hcl
providers check: a newer version is available for at least one provider (see above)
```

Rewrites the affected provider's own version pin, **in place**, in
whichever real file the [cascade](/cli/config#the-cascade)'s own
provenance names as that key's source -- a targeted substitution of just
the one `"<source>" = "<version>"` line, preserving every other line
(comments, formatting, unrelated keys) untouched. Never a full re-parse/
re-serialize of the file.

`--write` never commits, never opens a pull request, never touches git at
all -- that stays the caller's own job. See [Keeping provider versions
current](/guides/provider-version-watch) for a real, complete GitHub
Actions workflow built on top of this command.

## Flags

| Flag | Description |
| --- | --- |
| `--write` | rewrite each newer-version provider's own pin in place, in the real file its cascade provenance names -- never commits, never opens a PR |
| `--timeout duration` | timeout for querying the registry, applied per provider, not once for the whole command (default `30s`) |
| `-h`, `--help` | help for check |

## Why a subcommand, not just a GitHub Actions snippet

This exists as a first-class `ubx` primitive rather than boilerplate
copy-pasted into a workflow file for three reasons: it works identically
from GitLab CI, a local cron job, or a human's own terminal, not just
GitHub Actions; the registry-check and version-comparison logic (real
semver, pre-release-aware) is hermetically tested Go code instead of
shell embedded in YAML; and `ubx` already owns the one piece of
information this check actually needs -- `.ubx/config`'s own real,
parsed `[providers]` table and its own cascade provenance -- rather than
a script re-deriving "where is this pin declared" by hand.

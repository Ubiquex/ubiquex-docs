---
title: "ubx status"
description: "Report every resource the ledger knows about, optionally comparing against live state"
---

```text
ubx status [--drift] [--stack <name>] [flags]
```

Walks every resource the [ledger](/concepts/ledger) has ever recorded — every
stack by default, or one via `--stack` — and reports each one's address and
latest recorded state. This is a fleet-wide report, not a single-address
check: where [`ubx scan`](/cli/scan) answers "has *this* resource drifted?",
`ubx status` answers "what does the ledger know about, and (optionally) which
of it has drifted?" across everything at once.

Ledger-only and `--drift` are genuinely two different capabilities, not one
capability with a default:

- **Ledger-only** (no `--drift`): reads only the ledger itself. No provider is
  launched, no cloud credentials are needed. Fast, and safe to run anywhere
  the ledger directory is readable.
- **`--drift`**: additionally launches one provider (resolved exactly like
  `ubx scan`'s own `--provider`/`--source`+`--provider-version`) and, for
  every resource, re-reads its live state using that resource's own recorded
  [lookup key](/cli/lookup) — nothing needs to be re-supplied, since it was
  already persisted in the ledger for exactly this reason. Classifies each
  resource as `clean`, `drifted`, or `unreadable`.

## Flags

| Flag | Description |
| --- | --- |
| `--stack string` | restrict the report to one stack (default: every stack the ledger holds) |
| `--drift` | also compare each resource against live state (requires `--provider`, or `--source`+`--provider-version`) |
| `--provider string` | path to the provider binary (mutually exclusive with `--source`; only used with `--drift`) |
| `--source string` | provider source address, e.g. `hashicorp/aws` (mutually exclusive with `--provider`; requires `--provider-version`; only used with `--drift`) |
| `--provider-version string` | explicit provider version to acquire (required with `--source`; only used with `--drift`) |
| `--provider-config string` | JSON object configuring the provider, e.g. `{"region":"us-east-1"}` (only used with `--drift`) (default `{}`) |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--timeout duration` | overall timeout for the fleet walk (only used with `--drift`) (default `1m0s`) |
| `--json` | emit one JSON document instead of human text — see [`--json` output](#json-output) |
| `-h`, `--help` | help for status |

## Examples

### The short daily-command form, with `.ubx/config`

With a [`.ubx/config`](/cli/config) in place supplying `[provider]`/
`[provider_config]`, `--drift` needs nothing else:

```text
$ ubx status --ledger-dir . --drift
clean: payments.fake_widget.api-cache: adoption a28700b248d3… (accepted 2026-07-16T18:29:29Z)
1 resource(s), 0 drifted, 0 unreadable
```

<Note>
  Config's `stack` default is deliberately **not** applied to `--stack`
  here, unlike every other command it applies to. `--stack`'s absence means
  "every stack" — a configured default would silently turn that into "just
  my one stack," the opposite of what makes a fleet-wide report useful. Pass
  `--stack` explicitly whenever you want to filter.
</Note>

<Warning>
  "Every stack by default" is a **git-local-only** capability. A remote
  [`[ledger]` store](/concepts/ledger-stores) addresses one independent
  chain per stack — there is no single "every stack" to enumerate there,
  so `--stack` stops being optional and becomes required outright:

  ```text
  $ ubx status
  status: --stack is required to open a remote ledger store (.ubx/config's [ledger] store is "s3://acme-ledger/acme/prod/", not git) -- a remote store's own per-stack chain means opening one at all requires knowing which stack first
  ```

  Passing `--stack` opens exactly that stack's own chain — see
  [Ledger stores](/concepts/ledger-stores) for a full `resolve` → `accept`
  → `ship` transcript against a real remote store.
</Warning>

### Ledger-only

```text
$ ubx status --ledger-dir .
network.fake_widget.main-vpc: adoption 7d8d5792e06c… (accepted 2026-07-16T16:54:45Z)
payments.fake_widget.api-cache: adoption bdbb0b5098bf… (accepted 2026-07-16T16:54:45Z)
2 resource(s) (ledger-only, no live comparison)
```

No provider was launched for this — the report comes entirely from the
ledger's own accepted history. `--stack` filters it:

```text
$ ubx status --ledger-dir . --stack payments
payments.fake_widget.api-cache: adoption bdbb0b5098bf… (accepted 2026-07-16T16:54:45Z)
1 resource(s) (ledger-only, no live comparison)
```

<Note>
  A resource shipped from a [`ubx resolve`](/cli/resolve) `change`
  proposal (real, not just adopted) is fully first-class here too — no
  extra step needed. Real transcript, right after shipping a two-resource
  AWS create chain (a queue plus a policy that depends on it):

  ```text
  $ ubx status --ledger-dir .
  ubi29demo.aws_sqs_queue.ubi29-queue: change 533d958735cc… (accepted 2026-07-17T15:17:21Z)
  ubi29demo.aws_sqs_queue_policy.ubi29-queue-policy: change 533d958735cc… (accepted 2026-07-17T15:17:21Z)
  2 resource(s) (ledger-only, no live comparison)
  ```

  `kind` reads `change` here rather than `adoption` — a real, meaningful
  signal: this resource's genesis was `ubx ship`, not a scan discovering
  something that already existed. See [`ubx why`'s own genesis-by-create
  section](/cli/why#a-resources-genesis-is-a-shipped-create) for the full
  story this same resource's address unlocks.
</Note>

<Note>
  A resource fully destroyed by `ubx ship` (a `change` proposal's own
  `delta.destroys`, accepted with
  [`--confirm-destroys`](/cli/accept#confirming-a-destroy)) drops out of
  this report entirely, the moment the destroy seals — not because it was
  removed from the ledger (its full history is still there, permanently;
  see [`ubx why`](/cli/why#a-resources-tombstone-destroyed-via-ubx-ship)),
  but because "what to actively watch" excludes anything the ledger itself
  confirms is gone. Recreating a resource under the identical address
  later (a genuine tear-down-and-rebuild) makes it reappear here exactly
  as if it were new — because, as far as this report's own ground truth is
  concerned, it is.
</Note>

### `--drift`, all clean

```text
$ ubx status --ledger-dir . --drift --provider ./terraform-provider-aws
clean: network.fake_widget.main-vpc: adoption 7d8d5792e06c… (accepted 2026-07-16T16:54:45Z)
clean: payments.fake_widget.api-cache: adoption bdbb0b5098bf… (accepted 2026-07-16T16:54:45Z)
2 resource(s), 0 drifted, 0 unreadable
```

### `--drift`, something drifted

A drifted entry shows the actual attribute-level diff inline — the same
before/after rendering [`ubx why`](/cli/why) uses for a `modify` — plus a
`next:` handoff, rather than a bare "drifted" verdict a human has to go
digging from. The handoff is just `ubx scan --propose both` now: flag-free
scan (UBI-49) resolves the stack from the cascade and walks every tracked
address (this one included) with no `--type`/`--name` needed:

```text
$ ubx status --ledger-dir . --drift --provider ./fakeprovider
drifted: payments.fake_widget.api-cache: adoption a34d77e8c620… (accepted 2026-07-31T00:52:47Z)
    ~ tags.owner: (absent) -> "someone-else"
    next: ubx scan --propose both
1 resource(s), 1 drifted, 0 unreadable
```

If a *prior* drift on this exact address was already adopted (and so
carries whatever CloudTrail attribution that `scan --propose` cycle
recorded), a `who:` line surfaces it — explicitly as recorded history, not
a live attempt for the drift being shown right now (attribution is
`scan --propose`'s own CloudTrail-lookback job; `status --drift` never runs
one itself, just to render one line):

```text
$ ubx status --ledger-dir . --drift --provider ./fakeprovider
drifted: payments.fake_widget.api-cache: drift_adopt 470ead18a0c2… (accepted 2026-07-31T00:53:11Z)
    ~ tags.owner: "someone-else" -> "someone-else-again"
    who: arn:aws:iam::123456789012:user/roozbeh · TagResource · 2026-07-31T00:00:00Z (recorded at drift_adopt)
    next: ubx scan --propose both
1 resource(s), 1 drifted, 0 unreadable
```

No prior adopt at all (the common case for a resource only ever adopted,
never drifted before) means no `who:` line — omitted entirely, never a
placeholder.

### `--drift`, something unreadable

A resource whose ledger entry predates the
[lookup](/concepts/proposal)-persisting amendment (or one the provider
otherwise can't read — an unknown type, denied credentials, a transient
failure) is reported `unreadable` and the walk continues; it never aborts the
report:

```text
$ ubx status --ledger-dir . --drift --provider ./terraform-provider-aws
clean: network.fake_widget.main-vpc: adoption 7d8d5792e06c… (accepted 2026-07-16T16:54:45Z)
clean: payments.fake_widget.api-cache: adoption bdbb0b5098bf… (accepted 2026-07-16T16:54:45Z)
unreadable: payments.fake_widget.legacy-widget: adoption 98d37e766f62… (accepted 2026-07-16T16:55:30Z) -- no lookup key recorded for this resource (authored before the resolution.inputs lookup amendment, or never had one)
3 resource(s), 0 drifted, 1 unreadable
```

## Drift across multiple providers

A stack with a real [`[providers]` table](/cli/config#multi-provider-stacks)
in `.ubx/config` needs no `--provider`/`--source` at all for `--drift` --
each fleet entry routes to its own provider instead. A resource created or
last touched by [`ubx ship`](/cli/ship) already has its own provider
recorded (`ubx resolve` decided it, at resolve time); a legacy or adopted
entry with no recorded provider of its own gets one inferred fresh by
type, checked against every declared provider -- the identical mechanism
a brand-new resource's own `ubx resolve` already uses, never a second one
invented here. Either way, only the providers actually needed are
launched, lazily, once each -- never one launch per resource:

```text
$ ubx status --ledger-dir . --drift
clean: payments.aws_db_instance.main: adoption b4734afddffb… (accepted 2026-07-18T12:58:38Z)
clean: payments.helm_release.app: adoption 920f73b8bf6e… (accepted 2026-07-18T12:58:38Z)
2 resource(s), 0 drifted, 0 unreadable
```

Both resources above were adopted individually (no recorded provider of
their own) -- `hashicorp/aws` and `hashicorp/helm` were each launched
once, inferred by type, and reused for every resource that type owns. A
real out-of-band change against either is caught exactly like the
single-provider case (each drifted line also renders its own attribute
diff and `next:` handoff, exactly like the single-provider example
above -- omitted here since the two providers involved aren't the
fakeprovider fixture):

```text
$ ubx status --ledger-dir . --drift
drifted: payments.aws_db_instance.main: adoption b4734afddffb… (accepted 2026-07-18T12:58:38Z)
drifted: payments.helm_release.app: adoption 920f73b8bf6e… (accepted 2026-07-18T12:58:38Z)
2 resource(s), 2 drifted, 0 unreadable
```

<Note>
  `--provider`/`--source`/`--provider-version`/`--provider-config` are
  ignored (with a warning) once `[providers]` is declared -- the same
  staging [`ubx resolve`'s own note](/cli/resolve) describes. A type no
  declared provider owns, or one two declared providers both claim,
  reports that resource `unreadable` (`provider unavailable: ...`) and
  the walk continues -- it never aborts the rest of the report.
</Note>

## `--json` output

`--json` replaces the human text with one JSON document on stdout. Ledger-only
mode (no `--drift`):

```text
$ ubx status --ledger-dir . --json
{
  "format": 1,
  "drift_checked": false,
  "resources": [
    {
      "address": {"stack": "payments", "type": "fake_widget", "name": "api-cache"},
      "kind": "adoption",
      "proposal_id": "c145574aad282cdae58be48f10c8a1da42cd5f11ecb3f4a7c5b85517fa4569fe",
      "accepted_at": "2026-07-16T19:31:00Z"
    }
  ],
  "summary": {"total": 1, "drifted": 0, "unreadable": 0}
}
```

`drift_checked` is `false` here on purpose — every resource's `status` field
is omitted entirely, not set to an empty string, so a consumer can never
mistake "we didn't check" for "0 drifted." With `--drift`, every resource
gets a `status` of `"clean"`, `"drifted"`, or `"unreadable"` (plus a
`reason` string when `"unreadable"`), and `drift_checked` is `true`:

```text
$ ubx status --ledger-dir . --drift --provider ./terraform-provider-aws --json
{
  "format": 1,
  "drift_checked": true,
  "resources": [
    {
      "address": {"stack": "payments", "type": "fake_widget", "name": "api-cache"},
      "kind": "drift_adopt",
      "proposal_id": "dc4bb1e0dd0f8ec7083d0d5e3d418121598b01de53ef3436250a9ce82364ac30",
      "accepted_at": "2026-07-16T19:31:01Z",
      "status": "clean"
    }
  ],
  "summary": {"total": 1, "drifted": 0, "unreadable": 0}
}
```

`summary` mirrors the human view's own trailing count line. Exit code
follows the same worse-wins rule described below regardless of `--json` --
see [Exit codes](/cli/exit-codes).

## Exit code: the CI contract

`ubx status --drift` is meant to gate a pipeline step, not just print a
report for a human to read -- the same 0/1/2 contract every `ubx` verb
follows (see [Exit codes](/cli/exit-codes) for the full reference), applied
to a fleet-wide walk:

| Exit code | Meaning |
| --- | --- |
| `0` | clean (or ledger-only mode, which has nothing to report drift on) |
| `1` | at least one resource drifted, nothing unreadable |
| `2` | at least one resource was unreadable, or the command failed outright (e.g. the provider couldn't be launched at all) |

Whichever is worse always wins if more than one applies — an unreadable
resource alongside a drifted one still exits `2`, not `1`. A CI step can gate
on this directly:

```bash
ubx status --drift --source hashicorp/aws --provider-version 6.54.0
case $? in
  0) echo "clean" ;;
  1) echo "drift detected" && exit 1 ;;
  2) echo "unreadable resource or command failure" && exit 1 ;;
esac
```

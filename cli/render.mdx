---
title: "ubx render"
description: "Emit the canonical D2 diagram, or a readable markdown current-state document, of a stack's own live, resolved resources"
---

```text
ubx render --stack <name> [--md] [--out <path>] [--check] [flags]
ubx render --md --from-drift <address> [flags]
ubx render --md --sync-overrides [--write] [flags]
```

The render half of [the diagram medium](/guides/diagram-medium) — the literal
converse of [`ubx propose --from-diagram`](/cli/propose#example-transcribing-a-diagram---from-diagram).
Walks a stack's own live resources (the same [`ledger`](/concepts/ledger)
fleet walk [`ubx status`](/cli/status) already performs) and emits either
the canonical [D2](https://d2lang.com) rendering of their current, resolved
shape (the default) or, with `--md`, a readable markdown "current state"
document — both share the identical ledger read, so the two formats can
never disagree about WHICH resources exist or how they're grouped, only how
that same real data is presented. A top-level node per live resource,
`class:` naming its real type, an attribute `tooltip:` from real ledger
truth, and dependency/cross-stack edges drawn from each resource's own
creating proposal. A resource created by a blueprint call (a signed,
reusable, parameterized proposal template — `ubx blueprint build`/`ubx
resolve`'s own `blueprint_calls`) is the one exception to "flat" — see
[Example: a blueprint call's own resources, grouped](#example-a-blueprint-calls-own-resources-grouped)
below. Never writes to the ledger, never resolves anything — a pure read
(except `--from-drift`/`--sync-overrides`, which launch a provider to
compare against live state, the same read `ubx status --drift` already
performs — never a write either).

<Note>
  `--from-drift`/`--sync-overrides` are a genuinely different render mode
  covered on its own page — [Overrides: making drift
  stick](/guides/overrides) — generating a real, mechanical (zero AI)
  override statement from actual drift, in whichever medium the calling
  stack is authored in.
</Note>

<Note>
  No GUESSED containers. There's no canonical grouping basis to invent (by
  type? by dependency cluster? by a diagram's own original authored
  structure, which `render` has no access to and shouldn't need) that
  wouldn't be an unreviewable guess baked into every emitted diagram — a
  human editing the emitted file by hand can add their own grouping
  afterward, the same "generated, reviewable, human-editable-adjacent
  artifact" posture [`ubx sdk gen`](/cli/sdk-gen)'s own bindings already
  established. A blueprint call's own resources are the one real
  exception, not a contradiction of this: which blueprint produced a
  resource is real, resolved-time truth recorded on the resource's own
  creating proposal (the same place a `depends_on` edge already comes
  from), never a guess at structure `render` doesn't actually have.
</Note>

## Flags

| Flag | Description |
| --- | --- |
| `--stack string` | which stack to render — required (a render always covers exactly one stack) |
| `--md` | emit a readable markdown current-state document instead of the default D2 diagram |
| `--out string` | write the rendered file here instead of stdout |
| `--check` | don't write — byte-compare the freshly emitted render against `--out`'s own current content, exiting `1` on any difference (requires `--out`) |
| `--from-drift string` | generate a single override statement for one drifted resource's own address, in the calling stack's own authoring medium (requires `--md`) |
| `--sync-overrides` | walk the whole stack's drift and generate an override statement for every drifted resource (requires `--md`; mechanical, zero AI) |
| `--write` | with `--sync-overrides`, append the generated statement(s) into the calling stack's own source file (diagram/md authoring only) |
| `--provider string` | path to the provider binary (only used with `--from-drift`/`--sync-overrides`) |
| `--source string` / `--provider-version string` | provider source + version, instead of `--provider` (only used with `--from-drift`/`--sync-overrides`) |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `-h`, `--help` | help for render |

## Example: rendering a live stack

Given a `payments` stack with two resources already shipped — a `main-vpc`
and a `payments-db` that `$ref`-depends on it:

```text
$ ubx render --stack payments --ledger-dir . --out rendered/payments.d2
wrote rendered/payments.d2
```

```d2 rendered/payments.d2
classes: {
  fake_widget
}
r0: "main-vpc" {
  class: fake_widget
  tooltip: "id: computed-id; name: main-vpc; tags: {}"
}
r1: "payments-db" {
  class: fake_widget
  tooltip: "id: computed-id; name: main-vpc; tags: {}"
}
r1 -> r0
```

This is real, unedited output (against the hermetic `fakeprovider`, which is
why the type is `fake_widget` rather than a real cloud type — the mechanism
is identical for any real provider). `r0`/`r1` are synthetic, deterministic
keys assigned in `(type, name)`-sorted order — never the resource's own
name, since two different-typed resources can legally share a name (only
the full `(type, name)` pair is unique in a ledger address), and a key
joining them with `.` would collide with D2's own container-nesting
separator. Nothing about readability is lost: the resource's own name still
renders in full as the node's own label, and its type is right there in
`class:`.

`r1 -> r0` is `payments-db`'s own real `depends_on` edge, read back from its
own creating proposal — the literal converse of `ubx propose --from-diagram`'s
own edge → `depends_on` translation.

## Example: a cross-stack reference

A resource whose own config holds a `$cross` reference into another stack
renders as an edge into a dedicated reference node, annotated with the real
pinned neighbor head:

```text
$ ubx render --stack payments --ledger-dir .
classes: {
  external
  fake_widget
}
r0: "consumer" {
  class: fake_widget
  tooltip: "id: computed-id; name: shared-widget; tags: {}"
}
r1: "main-vpc" {
  class: fake_widget
  tooltip: "id: computed-id; name: main-vpc; tags: {}"
}
r2: "payments-db" {
  class: fake_widget
  tooltip: "id: computed-id; name: main-vpc; tags: {}"
}
ref0: "@networking.fake_widget.main" {
  class: external
  tooltip: "pinned_head: cadee2897cb50edfdb848a9664dff2c336285e043204a090544d47d358e5e345"
}
r0 -> ref0
r2 -> r1
```

`ref0`'s own label, `"@networking.fake_widget.main"`, is exactly the
address form [the diagram medium's cross-stack
grammar](/guides/diagram-medium#the-cross-structural-limitation) reads back
in — render and parse share one convention, not two. `pinned_head` is the
neighbor ledger's own real `Head()` at the moment `consumer`'s own `$cross`
reference resolved; two resources pinning the identical neighbor address
share one reference node rather than drawing a redundant duplicate.

## Example: a blueprint call's own resources, grouped

A resource created by [a blueprint call](/guides/blueprints) carries a
`{"kind": "blueprint", "ref": "<name>:<content_hash>"}` entry in its own
recorded provenance
(see [`ubx why`'s own blueprint provenance section](/cli/why#a-blueprint-calls-own-provenance)) —
`render` groups every resource sharing the same ref into one dashed-border
container, labeled with the ref itself. Real, unedited output — a
`ci-platform` blueprint (ECR repo + SQS queue + IAM role + policy +
attachment) called once for the `payments` stack, shipped against real
`hashicorp/aws@6.54.0`:

```text
$ ubx render --stack payments --ledger-dir .
classes: {
  aws_ecr_repository
  aws_iam_policy
  aws_iam_role
  aws_iam_role_policy_attachment
  aws_sqs_queue
}
bp0: "ci-platform:sha256:f893af6e945f…" {
  style.stroke-dash: 3
  style.fill: transparent
  r0: "container-repo" {
    class: aws_ecr_repository
    tooltip: "arn: arn:aws:ecr:us-east-1:839333509514:repository/payments-ci-artifacts-md; ..."
  }
  r1: "ci-runner-access" {
    class: aws_iam_policy
    tooltip: "arn: arn:aws:iam::839333509514:policy/ci-runner-access; ..."
  }
  r2: "ci-runner" {
    class: aws_iam_role
    tooltip: "arn: arn:aws:iam::839333509514:role/ci-runner; ..."
  }
  r3: "ci-runner-access-attachment" {
    class: aws_iam_role_policy_attachment
    tooltip: "id: ci-runner/arn:aws:iam::839333509514:policy/ci-runner-access; ..."
  }
  r4: "pipeline-events" {
    class: aws_sqs_queue
    tooltip: "arn: arn:aws:sqs:us-east-1:839333509514:payments-notifications-md; ..."
  }
}
bp0.r1 -> bp0.r0
bp0.r1 -> bp0.r4
bp0.r3 -> bp0.r1
```

All five resources came from the SAME blueprint call, so all five nest
under the SAME single container (`bp0`) — a second, unrelated blueprint
call would get its own `bp1`, sorted by ref. `r0`..`r4` are still the
identical synthetic, deterministic per-resource keys `render` always
assigns; the container just adds one more level of D2 nesting around
them, so an edge between two grouped resources uses the container-
qualified path (`bp0.r1 -> bp0.r0`, never a bare `r1 -> r0`) — real D2
syntax, the only way an edge can actually reach a nested node. A resource
NOT created by a blueprint call renders exactly as the earlier examples
on this page show — top-level, ungrouped, byte-identical to a stack that
never called a blueprint at all.

## Example: markdown current-state document

`--md` walks the identical live resources shown above and emits a readable
document instead of D2 — grouped by blueprint origin (if any), then by
type, real applied attributes as formatted bullets (never a raw JSON
dump), dependency edges, and `(redacted)` for any sensitive attribute.
Real, unedited output against the same `payments` stack:

```text
$ ubx render --md --stack payments --ledger-dir .
# payments — current state

_Generated by `ubx render --md` from the ledger. This is CURRENT STATE -- what exists right now -- never hand-edited; edit the authoring source (SDK/diagram/md) and re-resolve/ship instead. The authoring document(s) that created these resources remain separate, historical evidence of individual decisions, and are not meant to stay current. See `ubx why`/`ubx blame` for how a resource got this way._

### fake_widget

#### mirror

- `id`: computed-id
- `name`: primary-widget
- `tags`: (empty)
- depends on: `payments.fake_widget.primary`

#### primary

- `id`: computed-id
- `name`: primary-widget
- `tags`:
  - `env`: prod
```

<Note>
  This document is **generated**, never hand-edited — the header states
  this explicitly. It answers "what exists right now"; the authoring
  source (an SDK program, a diagram, an md draft) remains separate,
  historical evidence of individual decisions, and [`ubx why`](/cli/why)/
  [`ubx blame`](/cli/blame) remain the answer to "how did it get this
  way." `--check` (below) works identically for `--md` output — byte-compare
  against a committed copy, exit `1` on drift.
</Note>

## `render --check`

Re-emits and byte-compares against `--out`'s own current content — the same
"regenerate, meant to be committed and diffed" discipline
[`ubx sdk gen`](/cli/sdk-gen) already established, but a real, first-class
command mode rather than leaving the diff-and-fail step to `git diff`
outside the tool:

```text
$ ubx render --stack payments --ledger-dir . --out rendered/payments.d2 --check
render --check: rendered/payments.d2 matches the current resolved state
```

Once the ledger changes (a new resource shipped, in this case) without the
committed file being regenerated, `--check` catches it — a real, actionable
finding, not a hard error:

```text
$ ubx render --stack payments --ledger-dir . --out rendered/payments.d2 --check
--- rendered/payments.d2 (before)
+++ rendered/payments.d2 (after)
@@ -1,12 +1,22 @@
 classes: {
+  external
   fake_widget
 }
-r0: "main-vpc" {
+r0: "consumer" {
   class: fake_widget
+  tooltip: "id: computed-id; name: shared-widget; tags: {}"
+}
+r1: "main-vpc" {
+  class: fake_widget
   tooltip: "id: computed-id; name: main-vpc; tags: {}"
 }
-r1: "payments-db" {
+r2: "payments-db" {
   class: fake_widget
   tooltip: "id: computed-id; name: main-vpc; tags: {}"
 }
-r1 -> r0
+ref0: "@networking.fake_widget.main" {
+  class: external
+  tooltip: "pinned_head: cadee2897cb50edfdb848a9664dff2c336285e043204a090544d47d358e5e345"
+}
+r0 -> ref0
+r2 -> r1

render --check: rendered/payments.d2 is stale -- re-run "ubx render --stack payments --out rendered/payments.d2" and commit the result
```

Exit code `1` — a real, actionable finding (the committed `rendered/` copy
needs regenerating and committing), not a hard error. A missing `--out`
file behaves the same way, naming the exact command to run:

```text
$ ubx render --stack payments --ledger-dir . --out rendered/payments.d2 --check
render --check: rendered/payments.d2 does not exist yet -- run "ubx render --stack payments --out rendered/payments.d2" and commit the result
```

`--check` without `--out` is refused outright — there's nothing to compare
against:

```text
$ ubx render --stack payments --ledger-dir . --check
render: --check requires --out (the committed file to compare against)
```

Every exit code above is `1` (a real finding) or `2` (a hard error) — see
[Exit codes](/cli/exit-codes).

## Determinism

Two `render` runs against an unchanged ledger produce byte-identical
output — `d2format.Format` (D2's own canonical formatter, confirmed
idempotent) is reused directly as the canonical serializer, and every
internal ordering (resources by `(type, name)`, attributes by key, edges by
source then target) is sorted explicitly. This is what makes `--check`'s
own byte-compare meaningful at all.

---
title: "ubx scan"
description: "Compare one resource's live state against the ledger and generate a proposal if it differs"
---

```text
ubx scan --stack <name> --type <type> --name <name> (--provider <path> | --source <src> --provider-version <v>) [flags]
ubx scan --all --tfstate <path> (--provider <path> | --source <src> --provider-version <v>) [flags]
ubx scan --discover --tag <key=value> [--tag <key=value> ...] --region <region> --stack <stack> (--provider <path> | --source <src> --provider-version <v>) [flags]
```

Reads one resource's live state — via a Terraform provider binary, speaking
the provider protocol directly — and compares it against the
[ledger](/concepts/ledger). Exactly one of three outcomes follows: `new`
(never seen this address before), `drifted` (the ledger has a record, but
live state no longer matches it), or `no drift` (matches; nothing happens).
See [Drift](/concepts/drift) for what each outcome means and what kind of
proposal it generates. `new` and `drifted` exit `1` (a proposal was
generated — an actionable finding, not a failure); `no drift` exits `0`. See
[Exit codes](/cli/exit-codes) for the full contract, including `--all`'s own
skipped-resource case.

On drift, `ubx scan` also attempts [CloudTrail attribution](/concepts/attribution)
by default, and can optionally surface the drift as a GitHub issue or pull
request instead of just printing the proposal.

`--all --tfstate <path>` is a different mode entirely: instead of one
resource, it walks every resource in a Terraform state file and generates
an adoption proposal for each — see [Bulk onboarding](#bulk-onboarding-all)
below.

`--discover --tag <key=value>` is a third mode: instead of a tfstate file,
it enumerates real, tagged resources directly from the cloud account via
the AWS Resource Groups Tagging API — for accounts that were never under
Terraform management at all — see [Cloud-side
discovery](#cloud-side-discovery---discover) below.

## Flags

| Flag | Description |
| --- | --- |
| `--stack string` | stack name the resource belongs to (**required unless `--all`**, where it defaults to the state file's own basename) |
| `--type string` | resource type, e.g. `aws_s3_bucket` (**required unless `--all`**) |
| `--name string` | resource name within the stack (**required unless `--all`**) |
| `--lookup string` | JSON object identifying the resource to the provider, e.g. `{"id":"..."}` (default `{}`) — see [Resource lookup conventions](/cli/lookup), most types need more than just `id` |
| `--propose string` | on drift, which resolution(s) to generate: `adopt` (`drift_adopt`), `revert` (`drift_revert`), or `both` (default `adopt`) — no effect on a `new` resource, which always generates `adoption` |
| `--provider string` | path to the provider binary (mutually exclusive with `--source`) |
| `--source string` | provider source address, e.g. `hashicorp/aws` (mutually exclusive with `--provider`; requires `--provider-version`) |
| `--provider-version string` | explicit provider version to acquire, e.g. `6.54.0` (required with `--source`; no "latest" resolution) |
| `--provider-config string` | JSON object configuring the provider, e.g. `{"region":"us-east-1"}` (default `{}`) |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--out string` | write the generated proposal here instead of stdout (single-resource mode only) |
| `--timeout duration` | overall timeout for the scan, or the whole `--all` walk (default `1m0s`) |
| `--no-attribution` | skip audit-log attribution: drift attribution for drift proposals, or genesis attribution (who created it) for `--discover`'s own adoption proposals |
| `--surface-as string` | on drift, open a GitHub `"issue"` or `"pr"` with a receipt instead of just printing the proposal (requires `--github-repo`; not available with `--propose revert`) |
| `--github-repo string` | owner/name of the GitHub repository to surface drift in (required with `--surface-as`) |
| `--tf-dir string` | directory of `.tf` files to compute a best-effort write-back preview diff from, for the receipt (optional) |
| `--all` | bulk onboarding: enumerate every resource in `--tfstate` instead of scanning a single `--type`/`--name` resource |
| `--tfstate string` | path to a Terraform state v4 JSON file, read once as a bulk-onboarding enumeration source (required with `--all`) |
| `--out-dir string` | write each `--all`/`--discover`-generated proposal to its own file in this directory, instead of printing all of them to stdout |
| `--discover` | cloud-side discovery: enumerate resources via the AWS Resource Groups Tagging API instead of a tfstate file, generating an adoption proposal for each — requires `--tag` |
| `--tag stringArray` | `key=value` tag filter for `--discover` (repeatable; multiple `--tag` with the same key OR-combine, different keys AND-combine) |
| `--discover-type stringArray` | Terraform resource type allowlist for `--discover` (repeatable, e.g. `aws_sqs_queue`) — narrows client-side; omit to classify every tag-matched resource |
| `--region string` | AWS region to enumerate with `--discover` (the tagging API is itself regional) |
| `--limit int` | refuse `--discover` without `--yes` past this many adoptable resources (default `100`) |
| `--yes` | confirm proceeding past `--discover`'s own `--limit` |
| `--suggest-stacks` | with `--discover`, print a read-only stack-grouping preview instead of writing proposals — writes nothing, assigns nothing |
| `--stack-tag string` | with `--discover --suggest-stacks`, the tag key to group discovered resources by (omit to fall back to a naming-prefix heuristic) |
| `--json` | emit one JSON document instead of human text (single-resource scan only, not `--all`, `--discover`, or `--surface-as`) — see [`--json` output](#json-output) |
| `-h`, `--help` | help for scan |

`--provider` is the direct "point at a binary on disk" workflow. `--source`
+ `--provider-version` instead acquires the provider from a registry (UBI-8)
— version pins only, no `"latest"` resolution.

## Examples

### The short daily-command form, with `.ubx/config`

Every example below spells out `--stack`/`--provider`/`--provider-config` in
full. With a [`.ubx/config`](/cli/config) in place (`stack = "payments"`,
`[provider] path = "..."`, `[provider_config] region = "us-east-1"`), the same
scan is just:

```text
$ ubx scan --type fake_widget --name api-cache --lookup '{"name":"api-cache","tags":{"env":"prod"}}' --ledger-dir .
new: payments.fake_widget.api-cache (5c04c1c9c937a742ad32c319ffe75c550c344ed51bbee6d95dd14a12186daa4d) -- generated a "adoption" proposal
```

An explicit `--stack`/`--provider` still always overrides config — see
[`.ubx/config`'s precedence rules](/cli/config#precedence).

### A never-before-seen resource ("new")

```text
$ ubx scan --provider ./terraform-provider-aws \
    --stack payments --type fake_widget --name api-cache \
    --lookup '{"name":"api-cache","tags":{"env":"prod"}}' \
    --ledger-dir . --out adopt.json --no-attribution
new: payments.fake_widget.api-cache (5c04c1c9c937a742ad32c319ffe75c550c344ed51bbee6d95dd14a12186daa4d) -- generated a "adoption" proposal
```

### A resource that has drifted from the ledger

{

  "kind": "drift_adopt",
  "intent": {
    "summary": "record drift on payments.fake_widget.api-cache observed outside the ledger"
  },
  "delta": {

### A `Sensitive`-flagged attribute is redacted before it's ever written

Any attribute the provider's own schema flags `Sensitive` — a database
password, an API key, a private key — is replaced with a salted
fingerprint before the proposal is written or hashed, never the real
value:

```text
$ ubx scan --provider ./fakeprovider \
    --stack payments --type fake_db_instance --name payments-db \
    --lookup '{"id":"payments-db"}' \
    --ledger-dir . --out adopt.json
new: payments.fake_db_instance.payments-db (908322392cb434395924801e90f8b2ffe840578c8fcc68a479ecd00982660df2) -- generated a "adoption" proposal
```

```json
{
  "state": {
    "id": "payments-db",
    "master_password": { "$redacted": { "sha256": "ec692fb3a62ce3280ae79fc116ddac0f791213afd2a9111d395e46637321e3f3" } },
    "name": null
  }
}
```

Drift detection still works exactly as before over a redacted attribute:
scanning again against the *same* real password reports no drift (same
salt, same value, same hash); scanning after the real password actually
rotates reports drift, with `before`/`after` both showing `(redacted)` at
different hashes. See [Secrets](/concepts/secrets) for the full mechanism,
including the per-ledger salt and what losing it means.

### After accepting that drift, scanning again matches ("no drift")

```text
$ ubx scan --provider ./terraform-provider-aws \
    --stack payments --type fake_widget --name api-cache \
    --lookup '{"name":"api-cache","tags":{"env":"staging"}}' \
    --ledger-dir . --no-attribution
no drift: payments.fake_widget.api-cache matches the ledger (observed_hash 41a2bac0bb6d4e320bfff58928f939de1e73d6cdd30ee7e611e2dd7777115589)
```

### Generating a revert proposal instead of (or alongside) adopt

`--propose revert` generates a `drift_revert` proposal instead of the default
`drift_adopt` — the corrective direction: `before` is the observed (drifted)
value, `after` is the value being restored to. `--propose both` generates
both, as two alternative resolutions to the same detected drift:

```text
$ ubx scan --provider ./terraform-provider-aws \
    --stack payments --type fake_widget --name api-cache \
    --lookup '{"name":"api-cache","tags":{"env":"staging"}}' \
    --ledger-dir . --no-attribution --propose revert
drifted: payments.fake_widget.api-cache (41a2bac0bb6d4e320bfff58928f939de1e73d6cdd30ee7e611e2dd7777115589) -- generated a "drift_revert" proposal
```

See [Drift](/concepts/drift#two-resolutions-to-a-drift-adopt-or-revert) for
the full model, and [`ubx revert-plan`](/cli/revert-plan) for what an accepted
`drift_revert` produces.

### Surfacing drift as a GitHub issue

```text
$ ubx scan --provider ./terraform-provider-aws \
    --stack payments --type fake_widget --name widget-surface \
    --lookup '{"name":"widget-surface","tags":{"env":"staging"}}' \
    --ledger-dir . --no-attribution \
    --surface-as issue --github-repo acme/infra --tf-dir ./tf
opened issue https://github.com/acme/infra/issues/5
drifted: payments.fake_widget.widget-surface (73628692262376ab6636f0dd549624a103d7378b070654dd3c6812edcd3459ed) -- generated a "drift_adopt" proposal
```

The issue body carries the full receipt: intent, kind, stack, blast radius,
a `.tf` write-back preview diff (when `--tf-dir` is given), and the full
proposal JSON in a collapsed `<details>` block. An issue needs only
issue-write permission on the token, since nothing is committed.

### Surfacing drift as a pull request instead

```text
$ ubx scan --provider ./terraform-provider-aws \
    --stack payments --type fake_widget --name widget-pr \
    --lookup '{"name":"widget-pr","tags":{"env":"staging"}}' \
    --ledger-dir . --no-attribution \
    --surface-as pr --github-repo acme/infra --tf-dir ./tf
opened pull request https://github.com/acme/infra/pull/11
drifted: payments.fake_widget.widget-pr (5db59844c8f38c80151103deae8a9ce43291b69783169079fadc8f49d7135850) -- generated a "drift_adopt" proposal
```

`pr` mode commits the proposal file to a new `ubx-drift/<stack>-<type>-<name>`
branch and opens a PR whose body starts with a `ubx-proposal: <hash>`
trailer — the same trailer `ubx propose` prints, ready for
`ubx accept --from-merge` once the PR is reviewed and merged. Because it
commits and opens a PR, this mode needs contents write and pull-request write
permission on the token, not just issue-write — that's the real
security-relevant choice between the two modes, not a stylistic one: pick
`issue` if you only want a heads-up with no write access to the repo's
contents, `pr` if you want the drift to be mergeable straight into the
acceptance flow.

`--surface-as` only fires on a `drifted` outcome — a `new` scan never
surfaces anything, since there's no drift to report.

### Acquiring a provider by `--source`/`--provider-version` instead of `--provider`

`--source`/`--provider-version` acquires the provider binary instead of
pointing at one already on disk, in this order: `UBX_PROVIDER_MIRROR` (a
local directory you populate yourself — a hit is used as-is, unverified,
since a local file is trusted differently than a network download), then
ubx's own verified-binary cache (`~/.ubx/providers/...`), then — only if
both miss — a live registry round trip that downloads the provider archive
and its detached signature and verifies both before ever running it.

```text
$ export UBX_PROVIDER_MIRROR=/tmp/ubx-mirror
$ ubx scan --source acme/widget --provider-version 6.54.0 \
    --stack payments --type fake_widget --name registry-widget \
    --lookup '{"name":"registry-widget","tags":{"env":"prod"}}' \
    --ledger-dir . --out adopt.json
new: payments.fake_widget.registry-widget (d4691981cdd944e56500f3c323e2f57545fdb84a1991ab786d0d506ea3e50b70) -- generated a "adoption" proposal
```

Resolved this way, the generated proposal's `resolution.inputs` entry also
carries a `provider_checksum` — the SHA-256 of the exact binary that
produced the observation — which a `--provider`-only scan never has, since
nothing was verified to attribute a checksum to:

```json
{
  "resolution": {
    "inputs": [
      {
        "kind": "live_state",
        "resource": "payments.fake_widget.registry-widget",
        "observed_hash": "d4691981cdd944e56500f3c323e2f57545fdb84a1991ab786d0d506ea3e50b70",
        "lookup": {"name": "registry-widget", "tags": {"env": "prod"}},
        "provider_checksum": "sha256:dbf9e315000f0bc2cb02eed73d41790a973933addff65b7a1b0faca0b10d8179"
      }
    ]
  }
}
```

<Note>
  This example resolves through `UBX_PROVIDER_MIRROR`, not a live registry
  download — the mirror is a real, first-class resolution path (not a
  test-only shortcut), and it's the one reproducible without live registry
  credentials and network access. The live-registry path (query, download,
  verify a detached signature against a registry-served signing key, verify
  the archive checksum, extract) runs identically whether or not a mirror
  is configured — it's simply skipped here because the mirror already
  satisfied the request.
</Note>

## Kubernetes and Helm

`ubx` scans `hashicorp/kubernetes`/`hashicorp/helm` resources the same
way it scans any other type — see [Resource lookup conventions](/cli/lookup#kubernetes-and-helm)
for the confirmed `--lookup` shape per type. This transcript adopts a
real `kubernetes_secret_v1` against a real (local `kind`) cluster,
confirming redaction (see [Secrets](/concepts/secrets)) and drift
detection both work end to end:

```bash
ubx scan --source hashicorp/kubernetes --provider-version 2.35.1 \
  --stack k8stest --type kubernetes_secret_v1 --name app-secret \
  --lookup '{"id":"ubx-test/app-secret"}' \
  --provider-config '{"config_path":"~/.kube/config","config_context":"kind-ubx-conformance"}' \
  --ledger-dir . --out secret-adopt.json
```

```text
new: k8stest.kubernetes_secret_v1.app-secret (f29bcb4abea8c5c82b1a6516fd37586982a680de564dab05fcc33bc3176525f0) -- generated a "adoption" proposal
```

```json
{
  "data": { "$redacted": { "sha256": "87bc05ef04ea757fe8e8dffe2622038c73bba034efc1074938f9c956ce226328" } },
  "id": "ubx-test/app-secret",
  "metadata": [
    { "name": "app-secret", "namespace": "ubx-test", "resource_version": "732", "uid": "49e5ecc3-e6f8-47c4-831f-76f36ade0cdd", "...": "..." }
  ],
  "type": "Opaque"
}
```

After accepting and rotating the real secret out of band (`kubectl patch
secret app-secret ... --type merge -p '{"stringData":{"password":"..."}}'`),
scanning again correctly detects drift — `before`/`after` both
`$redacted`, at different hashes:

```json
{
  "before": { "data": { "$redacted": { "sha256": "87bc05ef04ea757fe8e8dffe2622038c73bba034efc1074938f9c956ce226328" } } },
  "after":  { "data": { "$redacted": { "sha256": "02e1e2bda3fbd6ab07723ed405035dee6794bf60e11fde58f1455aabf0ff669a" } } }
}
```

<Note>
  Every `kubernetes_*` mutation also always shows a `metadata` change
  alongside the semantic one — any real mutation bumps the object's own
  `resource_version`, and `metadata` diffs as a whole value (it's a
  list-nested block, compared atomically like any array). Expected, not
  a bug — see [Resource lookup conventions](/cli/lookup#kubernetes-and-helm)
  for why `metadata` is list-nested at all.
</Note>

`helm_release` is a resource like any other — adopted, drift-detected,
and diffed on its own Terraform-observed attributes, never by parsing the
chart's rendered manifests or tracking the individual Kubernetes objects
a release manages (that's explicitly out of scope). A real
`helm upgrade --set` shows up as `metadata[0].values` changing — the
top-level `values`/`chart` attributes stay `null` on an ordinary adopt
scan, since the provider never backfills them from a live read.

<Note>
  `metadata[0].values`/`metadata[0].notes` and `manifest` are always
  redacted, regardless of what any individual chart's values actually
  contain — see the `Warning` below for why. So a real values-drift
  transcript always shows the redacted form:

  ```json
  {
    "before": { "metadata": [{ "values": { "$redacted": { "sha256": "e696297b3c59898c2a7ef3a5991b5518d108dde87e95fac57eabb0315f19476b" } }, "...": "..." }] },
    "after":  { "metadata": [{ "values": { "$redacted": { "sha256": "4dfeec5d17ec69255e7bb910bf6c60b85081a6551d5080c2722da1f0f1a34874" } }, "...": "..." }] }
  }
  ```
</Note>

<Warning>
  Neither `manifest` nor `metadata[0].values`/`metadata[0].notes` are
  `Sensitive`-flagged in the real schema — a value that started sensitive
  (a `set_sensitive` password used at apply time, say) can still appear
  in plaintext there if a chart template renders it into the release's
  resolved output, since schema-driven redaction alone protects only the
  input attribute it's declared on, not everywhere that value might get
  echoed into a derived, computed field. **`ubx` doesn't stop at the
  provider's own schema for this reason**: `helm_release.manifest`/
  `metadata.values`/`metadata.notes` are force-redacted via a small,
  `ubx`-owned override table, regardless of what the schema itself
  flags — see [Secrets](/concepts/secrets#the-providers-schema-is-a-floor-not-a-ceiling).
</Warning>

## Bulk onboarding (`--all`)

A team with hundreds of resources can't adopt them one `--lookup` at a
time. `ubx scan --all --tfstate <path>` walks every managed resource in a
Terraform state file and generates one `adoption` proposal per resource —
reusing the exact same read-and-compare pipeline a single `ubx scan`
invocation already runs, once per resource. See
[Onboarding an existing Terraform-managed account](/guides/onboarding) for
the full walkthrough; this section covers the mechanics.

**The state file is read once, and never again.** It's a source of
*identity* — how to look a resource up — not of truth: every proposal's
recorded state still comes from a live read against the actual provider,
never from the state file's own recorded attribute values. `ubx` doesn't
open the file a second time, watch it, or reconcile against it later; the
ledger owns everything from the moment these proposals are accepted.

```text
$ ubx scan --all --tfstate prod.tfstate --provider ./terraform-provider-aws \
    --ledger-dir . --out-dir proposals
adopted: prod.fake_widget.api -> proposals/prod.fake_widget.api.json
adopted: prod.fake_widget.worker[0] -> proposals/prod.fake_widget.worker_0_.json
adopted: prod.fake_widget.worker[1] -> proposals/prod.fake_widget.worker_1_.json
adopted: prod.fake_widget.network.cache -> proposals/prod.fake_widget.network.cache.json
4 adopted, 0 skipped, 0 attribute(s) redacted
```

A few things happened here worth naming explicitly:

- **Stack** defaulted to `prod` — the state file's own basename
  (`prod.tfstate`) with its extension stripped, since no `--stack` was
  given. Pass `--stack` to override it.
- **`count`/`for_each` instances** (`worker[0]`, `worker[1]`) address the
  same way Terraform itself does — folded into the resource's name, since
  a ubx address has no separate index concept.
- **A resource inside `module.network`** (`network.cache`) got its module
  path folded into its name too, not just noted in the proposal's
  `intent.summary` — two different modules can each declare a same-type,
  same-name resource, and only the fold keeps their addresses from
  colliding. Module paths never create a separate *stack*, though — that's
  still a plain `--stack` decision, not automatic.
- **Data sources were skipped entirely, silently** — nothing in state that
  isn't `"mode": "managed"` is a resource `ubx` could ever adopt.
- **The summary's `attribute(s) redacted` count** is how many
  `Sensitive`-flagged attributes were replaced with a salted fingerprint
  across the whole batch — a resource with sensitive fields adopts
  cleanly, with this count as the only visible sign anything was
  redacted. See [Secrets](/concepts/secrets).

### What gets skipped, and why

A resource whose type the provider doesn't recognize, or whose state entry
has no `id` attribute to build a lookup from, is skipped with a reason —
never a reason to abort the rest of the batch:

```text
$ ubx scan --all --tfstate legacy.tfstate --provider ./terraform-provider-aws --ledger-dir .
adopted: legacy.fake_widget.good
{ ... }
skipped: legacy.aws_ancient_thing.relic -- scan legacy.aws_ancient_thing.relic: unknown resource type: "aws_ancient_thing"
skipped: legacy.fake_widget.no-id -- state instance has no id attribute
1 adopted, 2 skipped, 0 attribute(s) redacted
--- skipped ---
no identity in state: 1
provider read failed: 1
```

Running `--all` again after some proposals are already accepted skips
those specific resources too, reported as `already known to the ledger` —
`--all` is safe to re-run over the same state file as you work through a
large batch of proposal files.

Any skips at all — of any reason — exit `1`, the walk's own "an actionable
finding, not a failure" outcome (see [Exit codes](/cli/exit-codes)); a
completely clean `--all` walk with nothing skipped exits `0`.

<Note>
  `ubx accept` remains per-proposal and deliberate. `--all` only ever
  *generates* proposals — bulk **acceptance** isn't part of this command,
  on purpose: generating 300 proposals in one pass is a genuine time-saver,
  but auto-accepting 300 of them would be a different, much bigger claim of
  authority this trust chain doesn't make anywhere else.
</Note>

### `--all` across multiple providers

A state file spanning more than one provider's resources needs no
`--provider`/`--source` at all with a real
[`[providers]` table](/cli/config#multi-provider-stacks) in `.ubx/config` —
every enumerated resource gets its own provider inferred fresh by type,
checked against the declared set (a tfstate-imported resource has no
ledger history of its own to carry a recorded provider forward from, so
this always runs, for every resource, unlike `ubx status --drift`'s own
mixed legacy/explicit case):

```text
$ ubx scan --all --tfstate prod.tfstate --stack payments --ledger-dir .
adopted: payments.aws_db_instance.main
{ ... }
adopted: payments.helm_release.app
{ ... }
2 adopted, 0 skipped, 0 attribute(s) redacted
```

`aws_db_instance.main` routed to `hashicorp/aws`, `helm_release.app` to
`hashicorp/helm` — each declared provider launched once, lazily, and
reused for every resource its own schema owns. A type no declared
provider recognizes (or one two declared providers both claim) is
skipped with the same `provider read failed` reason a genuine read
failure gets, never aborting the rest of the batch.

## Cloud-side discovery (`--discover`)

`--all --tfstate` needs a Terraform state file to source resource
identity from. `--discover` doesn't — it enumerates real, tagged
resources directly from the cloud account itself, via the AWS Resource
Groups Tagging API, for ClickOps-heavy, half-terraformed, or inherited/
acquired accounts that were never under Terraform management at all.
See [Cloud-side discovery](/guides/cloud-discovery) for the full
walkthrough; this section covers the mechanics.

```text
ubx scan --discover --tag <key=value> [--tag <key=value> ...] \
    [--discover-type <type> ...] --region <region> \
    --stack <stack> (--provider <path> | --source <src> --provider-version <v>) \
    [--limit <n>] [--yes] [--no-attribution] --out-dir <dir>
```

`--tag` (repeatable) is the primary, and only, scoping mechanism —
whole-account (untagged) enumeration isn't a supported mode; the
realistic path is always tag-scoped. Real transcripts below, against a
real, hand-tagged AWS account (never touched by `ubx` itself before
discovery ran):

```text
$ ubx scan --discover --tag Project=payments --region us-east-1 --stack payments \
    --source hashicorp/aws --provider-version 6.54.0 --out-dir proposals
2 resource(s) matched, 2 adoptable
adopted: payments.aws_iam_policy.ubx-finale-payments-policy-1785361681 (from arn:aws:iam::839333509514:policy/ubx-finale-payments-policy-1785361681) -> proposals/payments.aws_iam_policy.ubx-finale-payments-policy-1785361681.json
adopted: payments.aws_sqs_queue.ubx-finale-payments-queue-1785361665 (from arn:aws:sqs:us-east-1:839333509514:ubx-finale-payments-queue-1785361665) -> proposals/payments.aws_sqs_queue.ubx-finale-payments-queue-1785361665.json
2 adopted, 0 skipped, 0 attribute(s) redacted
```

Both resources were created by hand, via the plain `aws` CLI — never
`ubx`. `--discover` found them by tag, resolved each ARN into the real
lookup shape its own type actually needs (an IAM policy's `id` **is**
its ARN; an SQS queue's `id` is its real queue URL, constructed from
the ARN's own region/account/queue-name, not a substring of the ARN
itself), and read each one live through the exact same
`ReadResource`/`core.RunScan` pipeline every other adoption path
already uses. The generated proposal is otherwise an ordinary
`adoption` proposal — accept and ship it exactly like any other.

### `--type` narrows client-side, `--region` because the API is regional

`--discover-type` (repeatable Terraform type names, not AWS service
namespaces) narrows which discovered ARNs are even considered — a
single ARN-parsing pass decides both "which lookup-shape tier" and
"does this match `--discover-type`," so there's no second type-name
translation table to keep in sync. `--region` is required because the
tagging API itself is regional — never silently inferred from wherever
the provider happens to be configured.

### Coverage gaps surface honestly, never silently

Not every AWS resource type has a known lookup-shape translation yet.
A discovered resource whose type isn't classified is reported, not
dropped — real transcript, a DynamoDB table tagged alongside an S3
bucket that *does* have a known translation:

```text
$ ubx scan --discover --tag Project=networking --region us-east-1 --stack networking \
    --source hashicorp/aws --provider-version 6.54.0 --out-dir proposals
2 resource(s) matched, 1 adoptable
discovered: arn:aws:dynamodb:us-east-1:839333509514:table/ubx-finale-networking-table-1785361702 (unknown type) -- not yet adoptable: not yet adoptable: no known lookup shape for this type
adopted: networking.aws_s3_bucket.ubx-finale-networking-bucket-1785361691 (from arn:aws:s3:::ubx-finale-networking-bucket-1785361691) -> proposals/networking.aws_s3_bucket.ubx-finale-networking-bucket-1785361691.json
1 adopted, 1 skipped, 0 attribute(s) redacted
--- skipped ---
discovered, not yet adoptable: 1
```

The DynamoDB table is genuinely, currently unsupported — nothing was
hidden or guessed at. Exit code follows the same "any skip at all is
an actionable finding" convention `--all` already established: `1`
here, `0` for a run where every matched resource adopts cleanly.

### Stack grouping: a reviewable suggestion, never an assignment

`--stack <name>` is required to actually write proposals, same as
everywhere else. `--suggest-stacks` is a separate, read-only preview
first — groups discovered resources by a tag you name (or a
naming-prefix heuristic if you don't), and writes nothing at all:

```text
$ ubx scan --discover --tag ubx-finale-marker=<marker> --region us-east-1 \
    --suggest-stacks --stack-tag Project
networking: 2 resource(s)
  arn:aws:dynamodb:us-east-1:839333509514:table/ubx-finale-networking-table-1785361702
  arn:aws:s3:::ubx-finale-networking-bucket-1785361691
payments: 2 resource(s)
  arn:aws:iam::839333509514:policy/ubx-finale-payments-policy-1785361681
  arn:aws:sqs:us-east-1:839333509514:ubx-finale-payments-queue-1785361665
2 group(s), 4 resource(s) total -- nothing written; re-run with --stack <name> per group to adopt
```

Review the suggestion, then re-run `--discover` once per group with an
explicit `--stack` — the same two commands above.

### Genesis attribution: who created it, best-effort

A discovered resource `ubx` never saw created can still often say who
made it — the same audit-log attribution mechanism [drift](/concepts/
attribution) already uses, pointed at the resource's own creation event
instead of whatever caused the most recent drift. Real transcript,
`ubx why` on the accepted SQS queue's own id:

```text
$ ubx why 28cee930e54d2df7cd719bdba70922fe2a16c4453dc3a4ed673011724e6bca4a --ledger-dir .
proposal 28cee930e54d2df7cd719bdba70922fe2a16c4453dc3a4ed673011724e6bca4a (adoption)
stack:  payments
status: accepted
intent: adopt existing payments.aws_sqs_queue.ubx-finale-payments-queue-1785361665 into the ledger (discovered by scan)
  source: cloudtrail -- arn:aws:iam::839333509514:user/roozbeh CreateQueue at 2026-07-29T21:47:45Z from 93.228.76.41
    event 7c8610fc-512c-493c-8044-884737a671e9 (content_hash=sha256:9b6ddbc474a9be3fbece3eba9393b401930696f30a2712f6adb7c7af3af1ec4c)
accepted by [roozbeh] via local at 2026-07-29T21:51:02Z
blast radius: +0 ~0 -0
```

`arn:aws:iam::839333509514:user/roozbeh` is the *real* IAM user who
created this queue via the plain `aws` CLI, minutes before discovery
ran — `ubx` never saw the creation happen, and still knows who did it.
This is purely a bonus: a resource adopts successfully with or without
a match. `--no-attribution` skips it entirely (no source recorded at
all, not even an unattributed one); by default, a resource whose
creation event hasn't been found yet — outside the search window,
predates CloudTrail's own retention, or of a type discovery has no
creation-verb knowledge for yet — gets an honest `cloudtrail_unattributed`
source instead of nothing:

```json
{"kind": "cloudtrail_unattributed", "reason": "no_matching_event"}
```

## `--json` output

`--json` (single-resource scan only) replaces the human text entirely with
one JSON document on stdout — never mixed with human-readable lines, and
stable across releases within the same `"format"` version (see
[Exit codes](/cli/exit-codes) for the same versioning convention applied
elsewhere). `--out` still writes the proposal file(s) to disk exactly as
without `--json`; `--json` only changes what goes to stdout.

```text
$ ubx scan --provider ./terraform-provider-aws --stack payments --type fake_widget \
    --name api-cache --lookup '{"name":"api-cache","tags":{"env":"prod"}}' \
    --ledger-dir . --json
{
  "format": 1,
  "address": {
    "stack": "payments",
    "type": "fake_widget",
    "name": "api-cache"
  },
  "outcome": "new",
  "observed_hash": "5c04c1c9c937a742ad32c319ffe75c550c344ed51bbee6d95dd14a12186daa4d",
  "proposals": [
    { "...": "the full generated proposal, byte-identical to the non-JSON form's own proposal JSON" }
  ]
}
```

`outcome` is `"new"`, `"drifted"`, or `"unchanged"` — the same three-way
classification [Drift](/concepts/drift) describes. `proposals` is empty for
`"unchanged"`, has one entry for `"new"` or a single `--propose` value, and
two entries for `--propose both`. Exit code follows the usual contract:
`1` for `"new"`/`"drifted"` (a proposal was generated), `0` for
`"unchanged"` — see [Exit codes](/cli/exit-codes).

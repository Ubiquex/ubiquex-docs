title: ".ubx/config"
description: "Project defaults, cascaded per directory, in HCL, TOML, or YAML"
---

`.ubx/config` lets a team stop repeating `--stack`, `--source`/`--provider-version`
(or `--provider`), `--provider-config`, `--github-repo`, and `--tf-dir` on every
`ubx` invocation. Generate one with [`ubx init`](/cli/init), or hand-write it in
whichever of the three supported formats you prefer.

## Formats: HCL canonical, TOML forever, YAML strict

<Note>
  One internal config shape underneath all three — the cascade, merge, and
  provenance logic described below never knows or cares which format
  produced a given value.
</Note>

**HCL is canonical** — what `ubx init` writes by default, and what every
example on this page uses. Values are literal only: no variables,
functions, or interpolation. A stray `"${…}"` or a function call is a
hard parse error, not a silent no-op:

```hcl
# .ubx/config.hcl
stack = "payments"

providers = {
  "hashicorp/aws" = "6.60.0"
}
```

**TOML is fully supported, forever** — the original format, still
deterministic, still exactly what `ubx init --format=toml` writes:

```toml
# .ubx/config.toml
stack = "payments"

[providers]
"hashicorp/aws" = "6.60.0"
```

**YAML is supported in strict mode** — `ubx init --format=yaml` writes
fully-quoted, unambiguous output on purpose. The classic YAML footguns
this project worried about are handled two different ways: `no`/`yes`/
`on`/`off` already parse as plain strings (not booleans) in the YAML
library `ubx` uses, so there's nothing to reject there; a bare, unquoted
number that would silently lose information — `6.60` parsing as the
float `6.6`, for instance, quietly dropping the distinction between a
version string `"6.60"` and `"6.6"` — **is** a hard error:

```text
$ ubx config
config: load config: parse /path/.ubx/config.yaml: /path/.ubx/config.yaml: hashicorp/aws: "6.60" would silently narrow to 6.6 -- quote it if a string was meant (e.g. a version like "6.60"), or write its exact canonical form if a number was meant
```

Quote it and it loads cleanly:

```yaml
# .ubx/config.yaml
providers:
  "hashicorp/aws": "6.60"
```

Only one format is read per directory. Discovery order is
`config.hcl` → `config.toml` → `config` (the original, extensionless
TOML name, kept forever) → `config.yaml` — first found wins for that
directory; a second format file sitting alongside the winner is never
read, never merged, and never warned about.

## Discovery: a per-key cascade, not just nearest-wins

`ubx` walks from the current working directory upward, collecting
**every** `.ubx/config*` it finds along the way — not just the nearest
one — until a [cascade ceiling](#cascade-ceiling-where-the-walk-stops)
stops it. Each directory contributes at most one file (per the format
discovery order above). The values then merge **per key**, not per file:
the nearest directory to define a given key wins that key specifically,
and a table's keys merge independently of each other, so a child
directory overriding one setting never wipes out its siblings from a
parent:

```hcl
# repo root: .ubx/config.hcl
github_repo = "acme/infra"
tf_dir      = "./terraform"
```

```hcl
# payments/.ubx/config.hcl
stack = "payments"
```

```text
$ cd payments && ubx config
github_repo = acme/infra  <- /repo/.ubx/config.hcl
stack = payments          <- /repo/payments/.ubx/config.hcl
tf_dir = ./terraform      <- /repo/.ubx/config.hcl
```

The stack directory only had to declare the one key it actually differs
on — `github_repo`/`tf_dir` came from the root without being repeated.
This is also true across formats: a repo root's `config.toml`, an
intermediate directory's `config.hcl`, and a leaf directory's
`config.yaml` all merge into one cascade exactly the same way; nothing
about the merge itself is format-specific.

This is independent of `--ledger-dir`: your project's defaults are a
property of where you're standing when you run `ubx`, not of wherever
`--ledger-dir` happens to point. No config file anywhere in the walk
isn't an error — every value it could have supplied just falls through
to that flag's own ordinary default, or to "required and absent."

## Cascade ceiling: where the walk stops

An unbounded upward walk would be exactly the kind of powerful, silently
wrong thing worth worrying about — reading some unrelated ancestor
directory's config just because it happened to exist. Three rules,
checked in this order at every directory the walk visits:

1. **`root = true`** — a directory can declare itself the top of the
   cascade, editorconfig-style. That directory's own other keys still
   apply (this is an *inclusive* stop, not "ignore this file too"); the
   walk just never reads anything farther up.
2. **No `root` marker anywhere → the git repo boundary is the implicit
   ceiling.** The directory containing `.git` (a directory for an
   ordinary checkout, a file for a worktree or submodule — either
   counts) is still included, then the walk stops. Most projects never
   need to write `root = true` at all — the repo root already is one.
3. **Outside any repo → `$HOME` or the filesystem root**, reached
   naturally by the same walk once neither of the first two rules ever
   fires.

```hcl
# grandparent/.ubx/config.hcl
github_repo = "should-never-be-read"
```

```hcl
# grandparent/parent/.ubx/config.hcl
root   = true
tf_dir = "./terraform"
```

```hcl
# grandparent/parent/child/.ubx/config.hcl
stack = "payments"
```

```text
$ cd grandparent/parent/child && ubx config
root = true           <- /grandparent/parent/.ubx/config.hcl
stack = payments      <- /grandparent/parent/child/.ubx/config.hcl
tf_dir = ./terraform  <- /grandparent/parent/.ubx/config.hcl
cascade stopped at: root marker (/grandparent/parent/.ubx/config.hcl)
```

`github_repo` from the grandparent never appears — the walk stopped at
`root = true` before ever reaching it. A directory with no `root` key,
inside an ordinary git checkout, gets the same protection for free:

```text
$ cd repo/payments && ubx config
github_repo = acme/infra  <- /repo/.ubx/config.hcl
stack = payments          <- /repo/payments/.ubx/config.hcl
tf_dir = ./terraform      <- /repo/.ubx/config.hcl
cascade stopped at: repo boundary (/repo)
```

## Provenance: `ubx config`

Because a cascade is powerful and can be invisibly wrong, `ubx config`
prints every effective value and exactly which file supplied it, plus
where and why the walk stopped:

```text
ubx config
```

```text
github_repo = acme/infra  <- /repo/.ubx/config.hcl
stack = payments          <- /repo/payments/.ubx/config.hcl
tf_dir = ./terraform      <- /repo/.ubx/config.hcl
cascade stopped at: repo boundary (/repo)
```

If nothing was found anywhere in the walk, the ceiling still prints —
there's always *some* reason the walk ended where it did:

```text
$ ubx config
no .ubx/config found (checked every directory from here up to the filesystem root)
cascade stopped at: filesystem root (/)
```

<Note>
  `ubx config` prints exactly what the merged cascade contains,
  including a key it also warned about as unrecognized (see "Unknown
  keys," below) — the view's job is showing what's actually there, not
  silently filtering a second time.
</Note>

## Precedence

For every value config can supply, the rule is the same everywhere it
applies: **an explicitly-passed CLI flag always wins; otherwise config fills
the gap if it has a value; otherwise, whatever "required and absent" already
meant for that flag applies, unchanged.** Config is a second place to find a
value — never a new rule about which values are required.

[`ubx scan --all`](/cli/scan#bulk-onboarding-all)'s own filename-derived
stack default sits *after* config in this chain: CLI flag, then config, then
the state file's own basename.

## What it covers

```hcl
# .ubx/config.hcl

stack       = "payments"
github_repo = "acme/infra"
tf_dir      = "./terraform"

providers = {
  "hashicorp/aws" = "6.60.0"
}

provider_configs = {
  "hashicorp/aws" = {
    region = "us-east-1"
  }
}
```

| Key | Maps to | Used by |
| --- | --- | --- |
| `stack` | `--stack` | [`ubx scan`](/cli/scan) (single-resource mode; `--all` falls back to it after the flag, before the filename default) |
| `providers` | *(no flag equivalent — `ubx init --source`/`--provider-version` writes it)* | [`ubx resolve`](/cli/resolve), [`ubx plan`](/cli/plan), [`ubx ship`](/cli/ship), [`ubx status --drift`](/cli/status), [`ubx scan --all`](/cli/scan) — the modern, preferred shape, single- or multi-provider alike; see [Multi-provider stacks](#multi-provider-stacks), below |
| `provider_configs` | *(no flag equivalent — `ubx init --provider-config`/`--region` writes it)* | same as `providers`, above — per-source configuration |
| `provider.path` | `--provider` | a local/dev escape hatch only (`ubx init --provider <path>`) — [`ubx scan`](/cli/scan), [`ubx status --drift`](/cli/status); see [`provider`: the legacy single-provider shape](#provider-the-legacy-single-provider-shape) |
| `provider.source` + `provider.version` | `--source` + `--provider-version` | same legacy shape as `provider.path`, for a registry source instead of a local binary |
| `provider_config` | `--provider-config` | configuration for the legacy `provider` shape above |
| `github_repo` | `--github-repo` | [`ubx accept --from-merge`](/cli/accept), [`ubx why --verify-acceptance`](/cli/why), [`ubx scan --surface-as`](/cli/scan) |
| `tf_dir` | `--tf-dir` | [`ubx writeback`](/cli/writeback), [`ubx revert-plan`](/cli/revert-plan), [`ubx scan --surface-as`](/cli/scan)'s receipt preview |
| `ledger.store` | *(no flag equivalent)* | [`ubx resolve`](/cli/resolve), [`ubx accept`](/cli/accept) (local), [`ubx ship`](/cli/ship) — see [Ledger stores](/concepts/ledger-stores) for which commands read this so far |
| `intent.adapter` / `intent.model` / `intent.key_ref` | *(no flag equivalent)* | [`ubx propose --from-doc`](/cli/propose#example-transcribing-a-document---from-doc) — see [`intent`](#intent), below |
| `root` | *(no flag equivalent)* | every command, indirectly — stops the cascade walk from reading anything farther up; see [Cascade ceiling](#cascade-ceiling-where-the-walk-stops) |

<Note>
  `ubx init` (UBI-59) writes `providers`/`provider_configs` by default,
  never the legacy `provider`/`provider_config` singular shape, even for a
  single-provider stack — see [`ubx init`](/cli/init). The legacy shape
  still works, forever, and is still the only shape available for a local
  binary path (`--provider`, below) — but a brand-new stack has no reason
  to ever write it by hand.
</Note>

<Note>
  `--ledger-dir` is deliberately not one of these. A wrong provider region
  fails loudly on the first read; a wrong ledger directory could make a
  command silently look at the wrong ledger entirely — more consequential
  to get wrong by accident, and out of scope for this file on purpose.
</Note>

### `provider`: the legacy single-provider shape

`path` (a local binary) and `source`/`version` (registry acquisition) are
mutually exclusive, exactly like the `--provider`/`--source` flags
themselves — config never has to re-decide that rule, it's the same
validation either way. `path` has no equivalent in the modern
`providers` map below (no local-path slot) — it's the one case where
this shape stays the only option, a deliberate local/dev escape hatch,
not an oversight. For a registry source, prefer `providers` instead —
`ubx init` writes it there by default, and every command that reads a
declared provider set checks `providers` first.

### `provider_config`

A freeform table — whatever keys the provider you're using actually needs
(`region` for AWS, say). Marshaled straight to the JSON string every
`--provider-config` flag already accepts. Configures the legacy `provider`
shape above — for `providers`, use `provider_configs` instead (below).

### Multi-provider stacks

`providers` declares a stack's whole provider set — source → pinned
version, explicit pins only — and `provider_configs` gives each one its
own configuration, keyed by that same source. It's written the same way
whether a stack has one provider or several; the "multi-provider" framing
is about what the shape was built for, not a minimum size to use it.
`ubx init` writes exactly one entry here for a single-provider stack —
the example below just shows the second provider a real multi-provider
stack (an `aws_db_instance` a `helm_release` depends on, one payments
stack, two provider binaries) actually needs:

```hcl
providers = {
  "hashicorp/aws"  = "6.60.0"
  "hashicorp/helm" = "3.0.2"
}

provider_configs = {
  "hashicorp/aws" = {
    region = "us-east-1"
  }
  "hashicorp/helm" = {
    kubeconfig = "~/.kube/config"
  }
}
```

<Note>
  In TOML this is `[providers]` plus `[provider_configs."hashicorp/aws"]`
  — dotted table headers, same content. Quoted keys like
  `"hashicorp/aws"` are only valid as *attribute-object* keys in HCL, not
  as HCL block arguments, which is why both tables are written as
  `key = { ... }` rather than a block.
</Note>

Once `providers` is non-empty, it becomes the authority for that
stack: `ubx resolve` launches every declared provider and asks each
one's own schema which types it owns (never guessed from a type's own
name) — never just the one `--provider`/`--source` used to name. A
resolved proposal records the *actual* winner on every resource, right
alongside it:

```text
$ ubx resolve intent.json --ledger-dir .
resolved: payments: 2 create(s), 0 modify(ies), 0 destroy(s)
```

```json
{
  "delta": {
    "creates": [
      { "name": "main", "provider": {"source": "hashicorp/aws", "version": "6.60.0"}, "...": "..." },
      { "name": "app", "provider": {"source": "hashicorp/helm", "version": "3.0.2"}, "...": "..." }
    ]
  }
}
```

[`ubx ship`](/cli/ship) reads that same recorded `provider` field back —
never re-inferring it — launching each one lazily, only the providers a
given proposal's own resources actually need, each configured from its
*own* `provider_configs` entry (AWS's own region config is never
handed to Helm's `Configure` call, or vice versa). A resource whose own
provider fails to launch fails on its own, terminally — a sibling
resource against a different, already-fine provider is never blocked by
it:

```text
$ ubx ship 9927129ddc5f0ba5fc14fd18c6bbd55ac39caf00cdcc54614fee11d0283ab22c --ledger-dir .
pending: payments.aws_db_instance.main
  terminal: provider unavailable: provider "hashicorp/aws" is pinned to 6.61.0 in this stack's providers config, but this proposal recorded 6.60.0 -- re-resolve against the current config
```

That specific transcript is a **version pin changing out from under an
already-signed proposal** — `providers`'s own pin moved to `6.61.0`
after this proposal was resolved and signed against `6.60.0` — refused
outright, never silently launched against whichever version happens to
be current. A proposal is signed against a specific provider version;
running something other than what was reviewed is exactly the kind of
drift this project exists to catch, not reproduce. Re-resolving against
the current config (a fresh `ubx resolve` → `ubx accept`) clears it.

<Note>
  `providers`/`provider_configs` are entirely optional — a
  single-provider stack (the common case today) keeps working exactly as
  it always has: no `providers` table means `ubx resolve`/`ubx ship`
  fall back to `--provider`/`--source`+`--provider-version`+
  `--provider-config` (or `provider`/`provider_config`, above)
  unchanged, byte for byte.
</Note>

Passing `--provider`/`--source`/`--provider-version`/`--provider-config`
against a stack that **also** declares a real `providers` table
doesn't silently pick one or the other — it warns, and the table wins:

```text
$ ubx resolve intent.json --ledger-dir . --source hashicorp/aws --provider-version 6.60.0
warning: --source, --provider-version ignored -- this stack declares a [providers] table in .ubx/config, which is the authority for a multi-provider stack
resolved: payments: 2 create(s), 0 modify(ies), 0 destroy(s)
```

<Note>
  `ubx scan --all`/`ubx status --drift` read `providers` too — see
  [`ubx status`'s own multi-provider section](/cli/status#drift-across-multiple-providers)
  and [`ubx scan`'s own](/cli/scan#--all-across-multiple-providers). A
  fleet entry with its own recorded provider (a resource created or
  last touched by `ubx ship`) routes straight there; a legacy/adopted
  entry with none gets one inferred fresh by type against the declared
  set — the identical mechanism `ubx resolve` already uses for a
  brand-new resource. `ubx scan --type/--name` (a single, already-known
  resource) needs no `providers` at all — pass `--provider`/`--source`
  directly, exactly as a single-provider stack always has.
</Note>

### `k8s_audit`

The one config table with no CLI flag equivalent — entirely optional,
and unlike `provider`/`provider_config`, config-only:

```hcl
k8s_audit = {
  cluster = "my-eks-cluster"
  region  = "us-east-1"
  # log_group = "/aws/eks/my-eks-cluster/cluster"  # optional; defaults to this shape from cluster
}
```

Which EKS cluster's control-plane audit log to search for
`kubernetes_*`/`helm_release` drift attribution (see
[Attribution](/concepts/attribution#kubernetes-and-helm-eks-audit-logs)) —
unlike AWS's region or GCP's project, there's nothing in `--provider-config`
that implies this, so it needs its own explicit table. Absent, or
`cluster` unset: such a drift's attribution records
`audit_unattributed`/`not_configured`, never blocking detection.

### `ledger`

Which [`LedgerStore`](/concepts/ledger-stores) backs this stack, and
optionally, per-stack `$cross` overrides:

```hcl
ledger = {
  store = "s3://acme-ledger/acme/prod/"

  external = {
    networking = "s3://other-org-ledger/other-org/prod/"
  }
}
```

Absent, or `store = "git"`, is the unchanged default — today's exact
in-repo directory behavior, driven by `--ledger-dir` alone. A stack name
is always appended as a further path segment automatically; it's never
configured here. `external` is optional: it overrides, per stack name,
which base store a [`$cross`](/concepts/ledger-stores#cross-by-stack-name)
reference resolves against, for the rare case where a neighbor stack
lives under a *different* base store than your own. See
[Ledger stores](/concepts/ledger-stores) for the full addressing model
and exactly which commands read this table so far.

<Note>
  `ledger.external`'s own keys are quoted-key attribute-object entries
  (`external = { networking = "..." }`), not a nested HCL block — a
  stack name isn't always a bare HCL identifier, and quoted keys are
  only valid in the attribute-object form, the same reason `providers`/
  `provider_configs` are written this way too (see
  [Multi-provider stacks](#multi-provider-stacks), above).
</Note>

`ubx config` itself derives and prints the full resolved address once a
stack is known, either from `--stack` or from config's own `stack`
default:

```text
$ ubx config --stack payments
ledger.store = s3://acme-ledger/acme/prod/  <- /repo/.ubx/config.hcl
ledger address (stack "payments"): s3://acme-ledger/acme/prod/payments/
```

Without a stack to derive against, it says so rather than guessing one:

```text
$ ubx config
ledger.store = s3://acme-ledger/acme/prod/  <- /repo/.ubx/config.hcl
ledger address: [ledger] store is a remote store, but no stack is known to derive it against (pass --stack)
```

No derived-address line is printed at all when `[ledger]` is absent or
`store = "git"` — there's no address to derive, since git-local's own
flat layout uses `--ledger-dir` directly.

### `intent`

Which [intent provider](/guides/md-medium) adapter transcribes a markdown
document into a draft for [`ubx propose --from-doc`](/cli/propose#example-transcribing-a-document---from-doc)
— or a live conversation into a draft for [`ubx chat`](/guides/chat) —
and how it authenticates. The same `[intent]` table configures both; there
is no separate config for chat.

```hcl
intent = {
  adapter = "claude"
  key_ref = { env = "ANTHROPIC_API_KEY" }
}
```

| Key | Meaning |
| --- | --- |
| `adapter` | which intent provider to use. Only `"claude"` exists today; unset defaults to it |
| `model` | which model that adapter uses. Unset falls back to the adapter's own default (`claude-opus-4-8` for `"claude"`) |
| `key_ref.env` | the environment variable holding the real API key |
| `auth` | Gemini's own API-key-vs-Vertex-AI split (`"api_key"` or `"vertex"`) — no Gemini adapter is built yet; this key is reserved |
| `vertex.project` / `vertex.location` | consulted only when `auth = "vertex"` — reserved alongside it |

<Warning>
  `key_ref.env` is a reference, never the key itself — the same rule
  covering [secrets](/concepts/secrets) in the ledger applies one layer up,
  to `ubx`'s own config: a literal API key sitting in a git-tracked config
  file is compromised the moment anyone else clones the repo. `key_ref`
  omitted entirely (no `[intent]`, or `intent = { adapter = "claude" }`
  alone) is a deliberate, valid choice too — it falls through to the
  adapter's own ambient credential resolution (an `ANTHROPIC_API_KEY`
  already in the environment, or a stored `ant auth login` profile).
  What's *not* valid is naming an environment variable that turns out to
  be empty — that's refused loudly, not silently treated as "no key
  configured":

  ```text
  $ ubx propose --from-doc payments.md --stack payments
  propose --from-doc: intent: key_ref.env names "ANTHROPIC_API_KEY", but that environment variable is unset or empty
  ```
</Warning>

`ubx config` shows exactly which file supplied each `intent.*` value, the
same as every other key:

```text
$ ubx config --stack payments
intent.adapter = claude                 <- /tmp/repo/.ubx/config.hcl
intent.key_ref.env = ANTHROPIC_API_KEY  <- /tmp/repo/.ubx/config.hcl
stack = payments                        <- /tmp/repo/.ubx/config.hcl
```

## Unknown keys warn, they don't fail

A typo, or a field a different `ubx` version doesn't recognize, is reported
by name and the file it came from, and otherwise ignored — never a hard
failure blocking every command in a project until someone fixes it. This
works identically across all three formats:

```text
$ ubx scan --type fake_widget --name api-cache --lookup '{"name":"api-cache"}' --ledger-dir .
warning: /path/to/.ubx/config.hcl: unknown config key "retention_days" (ignored)
New resource found  payments.fake_widget.api-cache

  adoption      f4bf7ff27ac4     +0 create(s) ~0 modify(ies) -0 destroy(s)

  saved to plan store            next: ubx ship f4bf7ff27ac4
```

A config file that isn't valid **at all** in its own format — malformed
TOML, an HCL file with a non-literal expression, a YAML document whose
top level isn't a mapping — is a different matter: a hard error for the
whole file, since there's no partial, best-effort way to read something
that doesn't parse. It contributes nothing to the cascade, not even its
own otherwise-fine keys.

<Warning>
  This is TOML-specific, and doesn't apply to HCL or YAML at all: root-level
  keys (`stack`, `github_repo`, `tf_dir`) must come **before** any `[table]`
  header in a `.ubx/config.toml` file. In TOML, a bare key written after a
  `[table]` section belongs to that table, not the document root — no
  matter how many blank lines separate them. `ubx init --format=toml`
  always generates them in the right order; if you're hand-editing a TOML
  config and one of these three keys doesn't seem to be taking effect,
  check it isn't sitting after `[provider]` or `[provider_config]` by
  mistake. HCL and YAML's own table syntax has no such ordering rule.
</Warning>

## User-global `~/.ubx/config`

A file at `~/.ubx/config` (same three-format discovery) is consulted
too, but **outside** the cascade above entirely — it's never a layer the
upward walk itself passes through, and it's always the single
lowest-priority source, folded in underneath whatever the project
cascade supplies.

The reason it's structurally separate, not just deprioritized: **a
checkout must resolve identically on every machine.** A project-truth
key — `stack`, `providers`, `provider_configs`, `ledger` — read from a
per-user file would mean the same commit means two different things for
two different people. So `~/.ubx/config` is **allowlist-only**: every
top-level key found there is checked against a small, fixed list of
genuinely personal-preference settings — today, exactly one,
`init_format` (see [`ubx init`](/cli/init)) — and anything else, whether
it's a real project key or just a typo, is a **hard error**, not a
warning:

```text
$ ubx config
config: load config: user-global config: /home/alice/.ubx/config: "stack" is not allowed here -- user-global config may only supply personal-preference keys (currently: init_format), never project-truth keys (stack, providers, provider_configs, ledger, ...), so a checkout resolves identically on every machine; move "stack" to the project's own .ubx/config instead
```

The normal cascade's own "unknown keys warn, they don't fail" leniency
deliberately does not extend here — a project-truth key silently
arriving from `$HOME` is a correctness problem, not a
forward-compatibility convenience.

<Note>
  If `$HOME` itself happens to be the cascade's own ceiling (running
  `ubx` with no repo structure above it at all), `$HOME`'s config is
  already read once as an ordinary cascade layer — it's never *also*
  checked against the personal-preference allowlist a second time. A
  file is either a cascade layer or the user-global one, never both.
</Note>

## The short daily-command form

With the config above in place:


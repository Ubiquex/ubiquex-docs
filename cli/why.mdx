---
title: "ubx why"
description: "Explain an accepted proposal, or a resource's full proposal history"
---

```text
ubx why <proposal-id> [flags]
ubx why <stack>.<type>.<name> [flags]
```

Explains either one accepted [proposal](/concepts/proposal) (by its full
64-character hex hash), or a resource's entire recorded history (by its
`<stack>.<type>.<name>` address) — newest first. Which form runs is decided
purely by whether the argument matches the 64-hex-char shape; anything else
is tried as a resource address.

## Flags

| Flag | Description |
| --- | --- |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--verify-acceptance` | re-derive a `pr_merge` proposal's acceptance against git history + the GitHub API and report whether it still checks out |
| `--repo-dir string` | local git working tree to verify `--verify-acceptance`'s merge commit against (default `.`) |
| `--github-repo string` | owner/name of the GitHub repository, for `--verify-acceptance`'s reviewer re-check (the git-history re-check runs without it) |
| `--json` | emit one JSON document instead of human text — see [`--json` output](#json-output) |
| `-h`, `--help` | help for why |

## Looking up one proposal by ID

```text
$ ubx why 4efe22a32782139b26e99599f00e713c0b99470e7ca69a752b5f96194e8ac1e0 --ledger-dir .
proposal 4efe22a32782139b26e99599f00e713c0b99470e7ca69a752b5f96194e8ac1e0 (drift_adopt)
stack:  payments
status: accepted
intent: record drift on payments.fake_widget.api-cache observed outside the ledger
accepted by [roozbeh] via local at 2026-07-16T22:56:26Z
blast radius: +0 ~0 -0
change: payments.fake_widget.api-cache: tags.env: "prod" -> "staging"
```

Each changed attribute gets its own `change:` line, `<address>: <path>:
<before> -> <after>` — for every kind that carries a real delta
(`drift_adopt`, `drift_revert`, `change`), not just an adoption's
all-or-nothing snapshot.

## Looking up a resource's full history

```text
$ ubx why payments.fake_widget.api-cache --ledger-dir .
payments.fake_widget.api-cache: 2 proposal(s), newest first
- drift_adopt 4efe22a32782… (2026-07-16T22:56:26Z): record drift on payments.fake_widget.api-cache observed outside the ledger
    change: payments.fake_widget.api-cache: tags.env: "prod" -> "staging"
- adoption fe772892ff49… (2026-07-16T22:56:26Z): adopt existing payments.fake_widget.api-cache into the ledger (discovered by scan)
```

The truncated IDs in this compact chain view are a display-only
abbreviation — pass the full ID (from a raw ledger file, or `ubx why`'s own
single-proposal view) to look one up directly; the truncated form is never
accepted as a lookup argument itself.

## A redacted attribute

If the changed attribute is one the provider flagged `Sensitive` (see
[Secrets](/concepts/secrets)), `why` renders `(redacted)` in place of the
value on both sides — never the salted hash, never the real material:

```text
$ ubx why 895622ca77a31d9061b850a2cb99d06d64c6576d810f81cca82e001c167f4749 --ledger-dir .
proposal 895622ca77a31d9061b850a2cb99d06d64c6576d810f81cca82e001c167f4749 (drift_adopt)
stack:  payments
status: accepted
intent: record drift on payments.fake_db_instance.payments-db observed outside the ledger
accepted by [roozbeh] via local at 2026-07-16T22:53:55Z
blast radius: +0 ~0 -0
change: payments.fake_db_instance.payments-db: master_password: (redacted) -> (redacted)
```

`--json` carries the same information as the actual `$redacted` marker
(`{"$redacted": {"sha256": "..."}}`) rather than the word "(redacted)" —
still never the real material, since the JSON payload is the same
already-redacted proposal the human view describes in words.

## Re-verifying a PR-merge acceptance

`--verify-acceptance` re-checks a `pr_merge` acceptance against current git
history and, if `--github-repo` is given, the GitHub API's current reviewer
state:

```text
$ ubx why 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae \
    --ledger-dir . \
    --verify-acceptance --repo-dir . --github-repo acme/infra
proposal 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae (change)
stack:  payments
status: accepted
intent: postgres for payments
  source: dialogue d-1 (content_hash=)
accepted by [roozbeh] via pr_merge at 2026-07-11T16:10:34Z
blast radius: +1 ~0 -0
--- verify-acceptance ---
git: merge commit 1f4a193321c803340fcc3ae1d7bc387c74922763 exists in .
git: proposals/pending.json at that commit still hashes to 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae
github API: PR #42's approvers are unchanged ([roozbeh])
```

Two independent checks run: whether the merge commit and proposal-file hash
still check out against git history (reported clearly if not — a commit
rewritten out of history, or a file whose content no longer matches, is a
serious finding), and whether the PR's current approvers still match what
was recorded (reported as a `MISMATCH` — the ledger correctly recorded what
was true at acceptance time; a reviewer later withdrawing their approval is
exactly what this check exists to surface, not evidence the ledger entry
itself is wrong). Either case is always *reported*, never silently dropped —
and both exit `1`, an actionable finding rather than success, since the
claimed acceptance no longer checks out or a reviewer's stance has changed
(see [Exit codes](/cli/exit-codes)). That's a different thing from a genuine
tool error (git or the GitHub API itself failing), which exits `2`. Running
it against a `local` acceptance, or a proposal with no acceptance at all,
reports "nothing to re-verify" and exits `0` rather than erroring.

<Note>
  `--github-repo` falls back to [`.ubx/config`](/cli/config)'s `github_repo`
  if not given explicitly.
</Note>

## `--json` output

`--json` replaces the human text with one JSON document on stdout. Exactly
one of `proposal` (single-id form) or `chain` (resource-address form) is
set, never both:

```text
$ ubx why dc4bb1e0dd0f8ec7083d0d5e3d418121598b01de53ef3436250a9ce82364ac30 --ledger-dir . --json
{
  "format": 1,
  "proposal": { "...": "the full proposal, same shape ubx accept/ubx scan already produce" }
}
```

```text
$ ubx why payments.fake_widget.api-cache --ledger-dir . --json
{
  "format": 1,
  "chain": [
    { "...": "newest proposal" },
    { "...": "oldest proposal" }
  ]
}
```

`chain` is ordered newest first, matching the human view's own ordering.
Adding `--verify-acceptance --json` embeds a `verify_acceptance` object
alongside `proposal` instead of (or in addition to) printing the
`--- verify-acceptance ---` text block:

```json
{
  "format": 1,
  "proposal": { "...": "..." },
  "verify_acceptance": {
    "applicable": true,
    "method": "pr_merge",
    "git_ok": true,
    "reviewers_checked": true,
    "reviewers_match": false,
    "current_approvers": [],
    "recorded_approvers": ["roozbeh"]
  }
}
```

`applicable` is `false` (every other field omitted or zero-valued) for a
`local` acceptance or a proposal with no acceptance at all -- confirmed
above, where this exact proposal's `local` acceptance yields
`"applicable": false`. `git_ok: false` means the merge commit or
proposal-file hash no longer check out against git history; the exit code
still carries the actionable-finding signal (see
[Exit codes](/cli/exit-codes)) -- the JSON payload isn't the only place
this shows up, since a script gating on exit code alone must still see it.
`reviewers_checked` is `false` if `--github-repo` wasn't given --
`reviewers_match`/`current_approvers`/`recorded_approvers` are only
meaningful when it's `true`.

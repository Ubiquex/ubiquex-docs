---
title: "ubx why"
description: "Explain an accepted proposal, or a resource's full proposal history"
---

```text
ubx why <proposal-id> [flags]
ubx why <stack>.<type>.<name> [flags]
```

Explains either one accepted [proposal](/concepts/proposal) (by its full
64-character hex hash), or a resource's entire recorded history (by its
`<stack>.<type>.<name>` address) — newest first. Which form runs is decided
purely by whether the argument matches the 64-hex-char shape; anything else
is tried as a resource address.

## Flags

| Flag | Description |
| --- | --- |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--stack string` | which stack's ledger to open, for a bare proposal-id argument — required only when `.ubx/config`'s `[ledger]` store is a remote store (a resource-address argument already names its own stack); unused for the default git store |
| `--verify-acceptance` | re-derive a `pr_merge` proposal's acceptance against git history + the GitHub API and report whether it still checks out |
| `--repo-dir string` | local git working tree to verify `--verify-acceptance`'s merge commit against (default `.`) |
| `--github-repo string` | owner/name of the GitHub repository, for `--verify-acceptance`'s reviewer re-check (the git-history re-check runs without it) |
| `--dialogue` | if this proposal's `intent.sources` names a captured [`ubx chat`](/guides/chat) dialogue, read and render the actual conversation behind it — change proposal → the draft it came from → the real conversation. See [Rendering a captured dialogue](#rendering-a-captured-dialogue), below |
| `--json` | emit one JSON document instead of human text — see [`--json` output](#json-output) |
| `--full-hashes` | render every hash in full instead of the default 12-char short form |
| `-h`, `--help` | help for why |

## Looking up one proposal by ID

```text
$ ubx why 7b97e26c9ec0b82c1a8d15f32e7ba85a50065f8c138a5ce1e5e2aabcd0e23001 --ledger-dir .
proposal 7b97e26c9ec0… (drift_adopt)
stack:  payments
status: accepted
intent: record drift on payments.fake_widget.api-cache observed outside the ledger
accepted by [roozbeh] via local at 2026-07-30T23:11:29Z
blast radius: +0 ~0 -0
~ change: payments.fake_widget.api-cache: tags.env: "prod" -> "staging"
```

Only the argument stays a full 64-char hash — the header line it echoes back
truncates to 12 chars + `…` by default; pass `--full-hashes` to render it in
full instead. Each changed attribute gets its own `~ change:` line
(color-coded by verb — the same `+`/`~`/`-` create/modify/destroy language
[`ubx plan`](/cli/plan)/[`ubx ship`](/cli/ship) already use), `<address>:
<path>: <before> -> <after>` — for every kind that carries a real delta
(`drift_adopt`, `drift_revert`, `change`). An `adoption` proposal instead
gets a bare `+ <type>.<name> create` line with no attribute breakdown (its
own all-or-nothing snapshot) — see the resource-history example below.

<Note>
  A bare proposal-id argument (unlike the resource-address form below)
  carries no stack of its own — for the default git store this is fine,
  the flat legacy layout has only ever had one ledger per `--ledger-dir`.
  Once a stack's own `.ubx/config` names a [remote store](/concepts/ledger-stores),
  opening a ledger at all means knowing which stack's address to open
  first, so `--stack` becomes required for this form specifically:

  ```text
  $ ubx why 3ff1769e2c4d2cadc8e492cce9ae5b465b9263b3f39a5aae946617ae8fc028c0
  why: --stack is required to open a remote ledger store (.ubx/config's [ledger] store is "s3://acme-ledger/acme/prod/", not git) -- a remote store's own per-stack chain means opening one at all requires knowing which stack first
  ```

  A resource-address argument never needs it — its own `<stack>.<type>.<name>` already names the stack unambiguously.
</Note>

## Rendering a captured dialogue

If a proposal's own `intent.sources` names a dialogue captured by
[`ubx chat`](/guides/chat), `--dialogue` walks all the way back to it —
change proposal → the draft it came from → the actual turns typed. Real,
unedited output, against a proposal accepted from a real chat session:

```text
$ ubx why 2467ee0b6bd83c664cb1e228d2a4adf42b262d9557c56b0223ece9ca3f64f13f --dialogue --ledger-dir .
proposal 2467ee0b6bd8… (change)
stack:  payments
status: accepted
intent: Create a smaller multi-AZ Postgres database for the payments service, modeled on the staging database.
  source: dialogue dialogues/bcb5b373f239719331b717d06f5ce6e07470c97bd54145488103d7c7196237dc.dlg.json (content_hash=sha256:bcb5b373f239719331b717d06f5ce6e07470c97bd54145488103d7c7196237dc)
  source: intent_provider claude:claude-opus-4-8 (content_hash=sha256:ba83af15bbbfbac1bed213315495b7e541ccf3bafed580454319da5bf0c1f4cd)
accepted by [roozbeh] via local at 2026-07-27T22:34:22Z
blast radius: +1 ~0 -0

conversation (claude / claude-opus-4-8, started 2026-07-27T22:31:06Z):
  [Turn 1, 2026-07-27T22:31:06Z]: We need a Postgres database for the payments service, like our staging database but smaller.
  [Turn 2, 2026-07-27T22:31:23Z]: Make it multi-az.
```

`--dialogue` is purely additive — the same proposal, without the flag,
renders exactly as the transcript at the top of this page already shows,
with no `conversation:` section at all. A proposal with no dialogue
source (it wasn't drafted via `ubx chat`, or the file can't be read)
still says so explicitly rather than rendering nothing:

```text
$ ubx why 4efe22a32782139b26e99599f00e713c0b99470e7ca69a752b5f96194e8ac1e0 --dialogue --ledger-dir .
proposal 4efe22a32782… (drift_adopt)
...

--dialogue: this proposal has no captured dialogue source (it wasn't drafted via `ubx chat`, or the file couldn't be read)
```

## A promoted proposal

If a proposal was produced by [`ubx promote`](/cli/promote), its
`intent.sources` carries an additive `promotion` entry alongside
whatever the fresh re-resolution itself produced (`document`, here) —
rendered as the literal human story [`docs/architecture.md`'s own
"Environments & promotion"
design](https://github.com/Ubiquex/ubiquex/blob/main/docs/architecture.md)
(in the `ubiquex` repo) names, "promoted from `<base>/<short source
id>`":

```text
$ ubx why 0c24102e9eee73b224a37ba6c504092faff13722443a89dfaa0f5cc18a4d8c9e --ledger-dir prod
proposal 0c24102e9eee… (change)
stack:  payments
status: accepted
intent: 2 resource(s) authored via payments.d2 for stack "payments"
  source: document payments.d2 (content_hash=sha256:5ca5d1fa95fdd76c521164c907011b8e6a4fde3a6ec6523885e47f888047058c)
  source: promoted from staging/7e71587ad039…
accepted by [roozbeh] via local at 2026-07-30T23:13:16Z
blast radius: +2 ~0 -0
+ fake_widget.main-vpc create
+ fake_widget.payments-db create
```

`base` is the source's own stack base — a remote [`LedgerStore`](/concepts/ledger-stores)
address if one is configured, or the source's own `--ledger-dir` for the
default git-local store (`staging` here — the directory `ubx promote` was
pointed at via its own `--ledger-dir`, distinct from `--to prod`, the target
this proposal was actually accepted into). The referenced id is truncated the
same presentation-only way the resource-history chain view already truncates
ids below — pass it in full to `ubx why <id> --ledger-dir <source-dir>`
to look up the source proposal directly and compare the two side by
side. A proposal promoted more than once (`ubx promote` run again
against an already-promoted, now-accepted proposal) gets exactly one new
`promotion` entry per hop, naming its own immediate source — see the
[promotion guide's own "Re-promoting a promoted
proposal"](/guides/promotion#re-promoting-a-promoted-proposal) for why
the chain is walked one hop at a time rather than flattened into one
proposal's own sources.

Nothing here is ever validated for equality against the source — see the
[promotion guide's own "Evidence, not a
pin"](/guides/promotion#evidence-not-a-pin).

## Looking up a resource's full history

```text
$ ubx why payments.fake_widget.api-cache --ledger-dir .
payments.fake_widget.api-cache: 2 proposal(s), newest first
- drift_adopt 7b97e26c9ec0… (2026-07-30T23:11:29Z): record drift on payments.fake_widget.api-cache observed outside the ledger
    ~ change: payments.fake_widget.api-cache: tags.env: "prod" -> "staging"
- adoption 761b63052cb0… (2026-07-30T23:11:29Z): adopt existing payments.fake_widget.api-cache into the ledger (discovered by scan)
    + fake_widget.api-cache create
```

Note the `adoption` entry gets its own `+ <type>.<name> create` line here
too — no attribute breakdown (an adoption is an all-or-nothing snapshot,
never a per-attribute delta), just the same `+` create marker every other
kind uses. The truncated IDs in this compact chain view are a display-only
abbreviation — pass the full ID (from a raw ledger file, or `ubx why`'s own
single-proposal view) to look one up directly; the truncated form is never
accepted as a lookup argument itself.

A resource's oldest entry (last in this newest-first list) is its
**genesis** — either an `adoption` (discovered by `ubx scan`, as above) or
a shipped `change` proposal (created by [`ubx resolve`](/cli/resolve) +
[`ubx ship`](/cli/ship)) — see below.

## A redacted attribute

If the changed attribute is one the provider flagged `Sensitive` (see
[Secrets](/concepts/secrets)), `why` renders `(redacted)` in place of the
value on both sides — never the salted hash, never the real material:

```text
$ ubx why 257bb893b89a8fd2b1d3194d5b1e13880d3945629a91bf8834356e86911cf569 --ledger-dir .
proposal 257bb893b89a… (drift_adopt)
stack:  payments
status: accepted
intent: record drift on payments.fake_db_instance.payments-db observed outside the ledger
accepted by [roozbeh] via local at 2026-07-30T23:11:20Z
blast radius: +0 ~0 -0
~ change: payments.fake_db_instance.payments-db: master_password: (redacted) -> (redacted)
```

`--json` carries the same information as the actual `$redacted` marker
(`{"$redacted": {"sha256": "..."}}`) rather than the word "(redacted)" —
still never the real material, since the JSON payload is the same
already-redacted proposal the human view describes in words.

## A shipped `drift_revert` or `change` proposal's ship history

If the proposal is a `drift_revert` or `change` that's been executed by
[`ubx ship`](/cli/ship), the single-proposal view appends a "ship
history" section — every attempt, oldest first, sealed or not, with each
resource's own state-machine transitions and any reconciliation the
executor had to do:

<Note>
  **The three transcripts below (this one, the UBI-29 create-chain
  further down, and the UBI-30 destroy-tombstone further still) are real,
  historical output from real live AWS investigations — not fakeprovider
  fixtures — captured before the ship/shipped vocabulary sweep (UBI-79)
  and left exactly as originally recorded, not hand-edited (UBI-82,
  2026-08-04).** CLAUDE.md's own standing rule forbids an agent from
  running `ubx ship` against real cloud for routine re-verification like
  this, so honestly updating these transcripts' own literal wording
  ("apply history," "outcome=applied") would require a founder-run live
  re-verification against real AWS, not a docs edit. Until that happens,
  they stay byte-for-byte what actually happened; the prose describing
  them above and below uses today's real vocabulary ("ship history"),
  matching what a fresh `ubx why` actually prints now — only the
  transcripts themselves are historical.
</Note>

See [Apply record](/concepts/apply-record) for the full state machine this

## A resource's genesis is a shipped create

A resource created by [`ubx resolve`](/cli/resolve) + `ubx ship` (rather
than discovered by `ubx scan`) has no `adoption` proposal at all — its
**genesis** (the oldest entry in its address chain) is the `change`
proposal that created it, ship history included. Real transcript: a
two-resource AWS chain (`aws_sqs_queue` + `aws_sqs_queue_policy`) shipped,
then drifted twice — once by a benign side effect of shipping the two
resources together (the queue's own `policy` attribute changing once its
policy resource attached), once by a real out-of-band `aws sqs tag-queue`
call:

```text
$ ubx why ubi29demo.aws_sqs_queue.ubi29-queue --ledger-dir .

    source: cloudtrail_unattributed -- too recent for CloudTrail to have delivered a matching event yet
    change: ubi29demo.aws_sqs_queue.ubi29-queue: tags.incident: (absent) -> "UBI-29-live-verify"
    change: ubi29demo.aws_sqs_queue.ubi29-queue: tags_all.incident: (absent) -> "UBI-29-live-verify"
```

created, not something derived later. See docs/reliability-report.md's

this transcript is drawn from, including the two real (and honestly
different) reasons the two `drift_adopt` entries above exist.

## A blueprint call's own provenance

A resource created by a blueprint call (a signed, reusable, parameterized
proposal template — `ubx blueprint build`/`ubx resolve`'s own
`blueprint_calls`) carries a `source: blueprint <name>:sha256:<hash>` line
right under its own create header — which blueprint made it, and which
version (a content hash of the blueprint's own files, not a hand-picked
version number). Real, unedited output — a `ci-platform` blueprint (ECR
repo + SQS queue + IAM role + policy + attachment) called once for the
`payments` stack, resolved against real `hashicorp/aws@6.54.0`, accepted,
and shipped:

```text
$ ubx why 6ece75b09ee254fd00db903d5a15932e2571338f66d4399bf69754a73afe05d9 --ledger-dir .
proposal 6ece75b09ee2… (change)
stack:  payments
status: accepted
intent: Instantiate the ci-platform blueprint for the payments stack with repo_name=payments-ci-artifacts-md, queue_name=payments-notifications-md, and retention_days=14; no resources are drafted directly since this is a blueprint call.
  source: document /path/to/create_ci_platform.md (content_hash=sha256:2c3d5d1a12472b9a6d2eed2f36b60fb6c40862c041218f87d342eb5dd3c93069)
  source: intent_provider claude:claude-sonnet-5 (content_hash=sha256:26d105efa33beeedadd9d4a59cf6c903dc6df3c2f941e2e94a72aa18979705ad)
accepted by [roozbeh] via local at 2026-08-04T22:50:37Z
blast radius: +5 ~0 -0
+ aws_ecr_repository.container-repo create
  source: blueprint ci-platform:sha256:f893af6e945f…
    (this resource's own creation is signed by the CALLING stack's own acceptance below; the blueprint's own authorship has no separate signing ceremony in this build yet)
    image_scanning_configuration:
    {
      "scan_on_push": true
    }
    image_tag_mutability: "IMMUTABLE"
    name: "payments-ci-artifacts-md"

+ aws_sqs_queue.pipeline-events create
  source: blueprint ci-platform:sha256:f893af6e945f…
    (this resource's own creation is signed by the CALLING stack's own acceptance below; the blueprint's own authorship has no separate signing ceremony in this build yet)
    message_retention_seconds: 1209600
    name: "payments-notifications-md"
...
```

Two things worth naming explicitly. First, `intent.sources` above (the
`document`/`intent_provider` lines right under `intent:`) is
**document-level** provenance — which `.md` file and which model drafted
the CALL itself. Each create's own `source: blueprint ...` line is a
completely different, **per-resource** field — which blueprint the call
actually invoked. A document can legally mix a blueprint call with a
hand-authored resource in the same proposal, so only the resources the
blueprint call actually produced carry the `blueprint` source; a
hand-authored sibling in the same document has none.

Second, the note under each `source: blueprint` line is a deliberately
honest gap, not an oversight: the design calls for TWO separate signed
acts — the blueprint AUTHOR's own signing of the blueprint's definition,
and the CALLING stack's own signing of THIS instantiation. This build has
no ceremony for the first one at all (no `ubx blueprint accept`, no
ledger entry for a blueprint's own definition independent of any call) —
only the second, real one is rendered, as the proposal's own `accepted
by [...] via ... at ...` line above.

Looking the SAME resource up by address shows the identical provenance,
plus real ship history:

```text
$ ubx why payments.aws_ecr_repository.container-repo --ledger-dir .
payments.aws_ecr_repository.container-repo: 1 proposal(s), newest first
- change 6ece75b09ee2… (2026-08-04T22:50:20Z): Instantiate the ci-platform blueprint for the payments stack with repo_name=payments-ci-artifacts-md, queue_name=payments-notifications-md, and retention_days=14; no resources are drafted directly since this is a blueprint call.

    + aws_ecr_repository.container-repo create

        (this resource's own creation is signed by the CALLING stack's own acceptance below; the blueprint's own authorship has no separate signing ceremony in this build yet)
        image_scanning_configuration:
        {
          "scan_on_push": true
        }
```

recently added under each proposal in this chain view, alongside the

## A resource's tombstone: destroyed via `ubx ship`

A `change` proposal's own `delta.destroys` (accepted with
[`--confirm-destroys`](/cli/accept#confirming-a-destroy), shipped by
[`ubx ship`](/cli/ship)) is rendered here too, both the destroy entry
itself and — once shipped — its own terminal transition annotated
`(destroyed)` or `(already_absent)`, the same distinction the ledger's
`reconcile:` line already carries but easy to miss without the
annotation:

```text
$ ubx why payments.aws_sqs_queue.ubi30-killtarget --ledger-dir .
payments.aws_sqs_queue.ubi30-killtarget: 6 proposal(s), newest first
- change 1a916b015bc9… (2026-07-18T02:29:51Z): UBI-30 live finale: destroy the kill-9 target, for real this time, with the PlanResourceChange fix in place
    destroy: payments.aws_sqs_queue.ubi30-killtarget
apply history:
  attempt 1: unsealed (interrupted or still in progress)
    payments.aws_sqs_queue.ubi30-killtarget:
      pending at 2026-07-18T02:30:18Z
      in_flight at 2026-07-18T02:30:20Z
      reconcile: present_matches at 2026-07-18T02:30:19Z
  attempt 2: outcome=applied
    payments.aws_sqs_queue.ubi30-killtarget:
      pending at 2026-07-18T02:30:54Z
      applied at 2026-07-18T02:31:32Z -- confirmed by reconciliation (destroyed)
      reconcile: destroyed at 2026-07-18T02:31:32Z
- adoption 765405df1179… (2026-07-18T02:29:21Z): adopt existing payments.aws_sqs_queue.ubi30-killtarget into the ledger (discovered by scan)
```

Attempt 1 here is a real `kill -9`, sent after the resource's own destroy
call had already landed against AWS but before the executor recorded the
result — the same interrupted-attempt shape any `drift_revert`/`change`
proposal can show (see above), just for a destroy. Attempt 2, a plain
re-run of `ubx ship`, reconciles it correctly: a not-found read, following
an immediately-preceding `present_matches`, resolves `destroyed` rather
than the ambiguous `already_absent` — and the transition line makes that
distinction visible without having to separately read the `reconcile:`
line below it. `already_absent` (a destroy whose target was already gone
*before* `ubx ship` ever attempted it) renders the same way:
`applied at <time> (already_absent)`.

A fully-destroyed address also drops out of [`ubx status`'s own
report](/cli/status#ledger-only) the moment the destroy seals — `why`'s
own full history above is unaffected either way, since `why` always shows
everything ever recorded for an address, tombstoned or not.

## Re-verifying a PR-merge acceptance

`--verify-acceptance` re-checks a `pr_merge` acceptance against current git
history and, if `--github-repo` is given, the GitHub API's current reviewer
state:

```text
$ ubx why 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae \
    --ledger-dir . \
    --verify-acceptance --repo-dir . --github-repo acme/infra
proposal 3ac4ad60be63… (change)
stack:  payments
status: accepted
intent: postgres for payments
  source: dialogue d-1 (content_hash=)
accepted by [roozbeh] via pr_merge at 2026-07-11T16:10:34Z
blast radius: +1 ~0 -0
--- verify-acceptance ---
git: merge commit 1f4a193321c803340fcc3ae1d7bc387c74922763 exists in .
git: proposals/pending.json at that commit still hashes to 3ac4ad60be63780420495d6f6dc16e06c206ad5960fa0a664facce27e73ec6ae
github API: PR #42's approvers are unchanged ([roozbeh])
```

Two independent checks run: whether the merge commit and proposal-file hash
still check out against git history (reported clearly if not — a commit
rewritten out of history, or a file whose content no longer matches, is a
serious finding), and whether the PR's current approvers still match what
was recorded (reported as a `MISMATCH` — the ledger correctly recorded what
was true at acceptance time; a reviewer later withdrawing their approval is
exactly what this check exists to surface, not evidence the ledger entry
itself is wrong). Either case is always *reported*, never silently dropped —
and both exit `1`, an actionable finding rather than success, since the
claimed acceptance no longer checks out or a reviewer's stance has changed
(see [Exit codes](/cli/exit-codes)). That's a different thing from a genuine
tool error (git or the GitHub API itself failing), which exits `2`. Running
it against a `local` acceptance, or a proposal with no acceptance at all,
reports "nothing to re-verify" and exits `0` rather than erroring.

<Note>
  `--github-repo` falls back to [`.ubx/config`](/cli/config)'s `github_repo`
  if not given explicitly.
</Note>

## `--json` output

`--json` replaces the human text with one JSON document on stdout. Exactly
one of `proposal` (single-id form) or `chain` (resource-address form) is
set, never both:

```text
$ ubx why dc4bb1e0dd0f8ec7083d0d5e3d418121598b01de53ef3436250a9ce82364ac30 --ledger-dir . --json
{
  "format": 1,
  "proposal": { "...": "the full proposal, same shape ubx accept/ubx scan already produce" }
}
```

For a shipped `drift_revert` or `change` proposal, the single-proposal
form also carries an `applies` array — the same
[apply record](/concepts/apply-record) objects `ubx ship --json` itself
returns, oldest attempt first, omitted entirely (not an empty array) for
anything that isn't one of those two kinds, or has never been shipped:

```json
{
  "format": 1,
  "proposal": { "...": "..." },
  "applies": [
    { "...": "attempt 1's full apply record" },
    { "...": "attempt 2's, if any" }
  ]
}
```

```text
$ ubx why payments.fake_widget.api-cache --ledger-dir . --json
{
  "format": 1,
  "chain": [
    { "...": "newest proposal" },
    { "...": "oldest proposal" }
  ]
}
```

`chain` is ordered newest first, matching the human view's own ordering.
Adding `--verify-acceptance --json` embeds a `verify_acceptance` object
alongside `proposal` instead of (or in addition to) printing the
`--- verify-acceptance ---` text block:

```json
{
  "format": 1,
  "proposal": { "...": "..." },
  "verify_acceptance": {
    "applicable": true,
    "method": "pr_merge",
    "git_ok": true,
    "reviewers_checked": true,
    "reviewers_match": false,
    "current_approvers": [],
    "recorded_approvers": ["roozbeh"]
  }
}
```

`applicable` is `false` (every other field omitted or zero-valued) for a
`local` acceptance or a proposal with no acceptance at all -- confirmed
above, where this exact proposal's `local` acceptance yields
`"applicable": false`. `git_ok: false` means the merge commit or
proposal-file hash no longer check out against git history; the exit code
still carries the actionable-finding signal (see
[Exit codes](/cli/exit-codes)) -- the JSON payload isn't the only place
this shows up, since a script gating on exit code alone must still see it.
`reviewers_checked` is `false` if `--github-repo` wasn't given --
`reviewers_match`/`current_approvers`/`recorded_approvers` are only
meaningful when it's `true`.

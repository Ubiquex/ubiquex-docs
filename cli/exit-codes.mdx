title: "Exit codes"
description: "The 0/1/2 contract every ubx verb follows -- what to gate CI on"
---

`ubx` is meant to be scripted against, not just read by a human. Every verb
follows the same three-way exit-code contract:

| Exit code | Meaning |
| --- | --- |
| `0` | success -- nothing needs a human's attention beyond the command's own normal output |
| `1` | an actionable finding -- the command ran correctly and surfaced something worth looking at |
| `2` | an error -- bad input, a missing/malformed file, a provider that couldn't be launched or read a resource, a ledger it couldn't write to |

Exit `1` is not a failure. `ubx scan` finding drift, or `ubx accept` refusing
a stale reverify, is the tool doing exactly its job -- the same way `grep`
exits `1` for "no match," not "grep is broken." Exit `2` means the command
itself couldn't do what you asked.

<Note>
  Before this contract existed, every command except [`ubx status`](/cli/status)
  (which introduced 0/1/2 first) funneled any error through a single
  fallback that exited `1` -- so "exit 1" used to mean nothing more specific
  than "something went wrong." That's now exit `2`. If you have a script
  that gates on "exit 1 means any error," update it to `exit 2` for that
  check.
</Note>

## Per-verb reference

### `ubx scan`

| Exit code | When |
| --- | --- |
| `0` | `no drift` -- live state matches the ledger |
| `1` | `new` or `drifted` -- a proposal was generated |
| `2` | bad flags, provider launch/read failure, proposal generation failure |

`--all` (bulk onboarding) is the same idea at fleet scale: `1` if anything at
all was skipped (unknown type, no identity in state, a duplicate address,
already known to the ledger, ...), `0` if the whole state file adopted
cleanly, `2` for a hard failure that stops the walk (can't read the state
file, can't launch the provider).

### `ubx status`

See [`ubx status`'s own exit-code table](/cli/status#exit-code-the-ci-contract) --
it's the verb this contract started with (a slightly richer table, since
`--drift` distinguishes `drifted` from `unreadable`).

### `ubx accept`

| Exit code | When |
| --- | --- |
| `0` | accepted |
| `1` | `--reverify-with`/`--reverify-source` blocked a stale proposal; a proposal's `parent` no longer matches the ledger head (the ledger moved since this proposal was resolved); `--from-merge`'s claimed acceptance doesn't check out (trailer hash mismatch, merge commit gone from history, proposal file gone from that commit, no PR associated with the commit, or no `ubx-proposal` trailer in the PR body) |
| `2` | missing/malformed proposal file, a proposal already carrying an id/acceptance, a duplicate of an already-ledgered proposal, provider launch/read failure during reverify, bad `--github-repo`, or [`.ubx/lock`](/concepts/ledger#concurrent-access) genuinely held by another process (or confirmed stale) |

### `ubx why`

| Exit code | When |
| --- | --- |
| `0` | nothing to re-verify (no `--verify-acceptance`, a `local` acceptance, or no acceptance at all), or the check ran and everything still holds |
| `1` | `--verify-acceptance` found the claimed acceptance doesn't check out: the merge commit or proposal-file hash no longer check out against git history, or the PR's current approvers no longer match what was recorded (a `MISMATCH`) |
| `2` | proposal/address not found, malformed argument, or a genuine git/GitHub API failure while re-verifying |

### `ubx writeback`

| Exit code | When |
| --- | --- |
| `0` | every changed attribute applied cleanly, or there was nothing to write back |
| `1` | at least one attribute was declined (its `.tf` value isn't a literal), or a resource block couldn't be located at all -- manual steps are needed |
| `2` | proposal not found, wrong kind (not `drift_adopt`), not accepted, or an I/O failure writing/diffing the file |

### `ubx revert-plan`

| Exit code | When |
| --- | --- |
| `0` | nothing to plan, or (with `--tf-dir`) every changed attribute got a real `.tf` diff |
| `1` | manual steps are needed -- a declined attribute, or a resource block absent from `--tf-dir` |
| `2` | proposal not found, wrong kind (not `drift_revert`), not accepted, or an I/O failure diffing the file |

### `ubx ship`

| Exit code | When |
| --- | --- |
| `0` | every resource applied (including a genuine no-op: already fully applied) |
| `1` | `partially_applied` or `failed` -- an actionable finding: retry, or investigate why |
| `2` | proposal not found, wrong kind (not `drift_revert`), not accepted, or a provider/ledger failure |

See [Apply record](/concepts/apply-record) for what `partially_applied` vs.
`failed` actually means -- both are real, recorded outcomes of a run that
completed, not command failures.

### `ubx version`, `ubx init`, `ubx propose`

These three have no "finding" concept -- they either succeed or they don't:

| Exit code | When |
| --- | --- |
| `0` | success |
| `2` | bad input, conflicting flags, or an I/O failure |

## Gating a CI step

```bash
ubx scan --stack payments --type aws_s3_bucket --name logs \
  --source hashicorp/aws --provider-version 6.54.0
case $? in
  0) echo "no drift" ;;
  1) echo "drift found -- see the generated proposal above" ;;
  2) echo "scan itself failed" && exit 1 ;;
esac
```

Whichever code is worse always wins where a command reports more than one
kind of outcome across a batch (`ubx status --drift`'s `unreadable` beating
`drifted`; `ubx scan --all`'s skip count is a simple count, not a
worse-wins comparison, since it only ever has one non-zero code to report).

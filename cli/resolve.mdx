---

```text
ubx resolve <intent-file> (--provider <path> | --source <src> --provider-version <v>) [flags]
ubx resolve --from-code <entry>.ts [flags]
ubx resolve --from-code <entry>.go [flags]
ubx resolve --from-code <entry>.py [flags]
```

<Note>
  Most workflows use [`ubx plan`](/cli/plan), which fuses this step — see
  [`ubx plan`](/cli/plan). This page stays the full reference for `ubx
  resolve` on its own, including the intent-file format every medium
  ultimately produces.
</Note>

Resolves a hand-written, machine-shaped [intent file](#the-intent-file) --
or a [TypeScript](#authoring-in-typescript)/[Go](#authoring-in-go)/
[Python](#authoring-in-python) SDK program, `--from-code`, dispatched by
the entry file's own extension -- into a draft `kind:"change"` [proposal](/concepts/proposal)
-- creates, modifies, and destroys. Intra-stack references are checked
against the [ledger](/concepts/ledger)'s own dependency graph, with real
cycle detection, and emitted in dependency order; cross-stack references
are pinned against a neighbor ledger's current head, so a later `ubx
accept` can tell whether that neighbor has moved on since (see
[Cross-stack references](#cross-stack-references) below).

A destroy is explicit intent only -- see [Destroying a
resource](#destroying-a-resource) below -- never inferred from a resource's
absence from the intent file.

The result is a draft: it has no `id` or acceptance yet. Pipe it into
[`ubx propose`](/cli/propose) for a PR-body trailer hash, or
[`ubx accept`](/cli/accept) directly, exactly like a proposal `ubx scan`
generates.

`ubx resolve` never reads live provider state at all -- a change proposal's
"before" comes from the ledger's own recorded state, not a fresh cloud
read (that happens later, at `ubx ship` time). A provider is still
launched, for exactly one reason: its schema is what tells the resolver
which attributes are `Computed` or `Sensitive`.

<Note>
  A stack with a real [`[providers]` table](/cli/config#multi-provider-stacks)
  in `.ubx/config` ignores `--provider`/`--source`/`--provider-version`
  entirely (with a warning if given) and launches every declared
  provider instead, one per type it might need to own -- the intent file
  itself still names only types, never a provider.
</Note>

## Flags

| Flag | Description |
| --- | --- |
| `--from-code string` | evaluate a [TypeScript](#authoring-in-typescript), [Go](#authoring-in-go), or [Python](#authoring-in-python) SDK program, dispatched by extension, instead of reading an intent file (mutually exclusive with the positional argument) |
| `--ledger-dir string` | root directory containing `ledger/` and `.ubx/` (default `.`) |
| `--provider string` | path to the provider binary (mutually exclusive with `--source`) |
| `--source string` | provider source address, e.g. `hashicorp/aws` (mutually exclusive with `--provider`; requires `--provider-version`) |
| `--provider-version string` | explicit provider version to acquire (required with `--source`) |
| `--known-dependent stringArray` | `ledger_dir` of a neighbor stack to check for cross-stack orphan references before destroying (repeatable) |
| `--out string` | write the resolved proposal here instead of stdout |
| `--timeout duration` | timeout for launching the provider and fetching its schema, and (`--from-code`) evaluating the SDK program -- one shared budget for the whole command (default `2m0s`) |
| `-h`, `--help` | help for resolve |

`ubx resolve` has no `--provider-config` -- unlike `ubx scan`/`ubx accept
--reverify-with`, it never configures or reads through the provider, only
fetches its schema.

## The intent file

An intent file (`ubx:intent/v1`) is a hand-written, typed description of
one stack's desired resources:

```json
{
  "schema_version": 1,
  "kind": "ubx:intent/v1",
  "stack": "payments",
  "intent": {"summary": "add the api-cache widget"},
  "resources": [
    {
      "type": "fake_widget",
      "name": "api-cache",
      "op": "create",
      "config": {"name": "api-cache", "tags": {"env": "prod"}}
    }
  ]
}
```

`op` is always explicit -- `"create"` or `"modify"` -- never inferred from
whether the ledger already has that address. This is deliberate: a
`"modify"` naming an address the ledger has never recorded is a real
authoring mistake `ubx resolve` catches (`did you mean "create"?`), not
something silently reinterpreted; a `"create"` naming an address the ledger
already has is caught the same way, in the other direction.

```text
$ ubx resolve intent.json --provider ./fakeprovider --ledger-dir .
resolved: payments: 1 create(s), 0 modify(ies)
{
  "schema_version": 1,
  "stack": "payments",
  "parent": "",
  "kind": "change",
  "intent": {
    "summary": "add the api-cache widget"
  },
  "delta": {
    "creates": [
      {
        "config": {"name": "api-cache", "tags": {"env": "prod"}},
        "name": "api-cache",
        "stack": "payments",
        "type": "fake_widget"
      }
    ]
  },
  "resolution": {
    "resolved_at": "2026-07-17T13:23:18Z"
  },
  "cost_delta": {"monthly_usd": 0},
  "blast_radius": {"creates": 1, "modifies": 0, "destroys": 0},
  "status": "draft"
}
```

## Authoring in TypeScript

`--from-code <entry>.ts` evaluates a TypeScript [SDK program](/sdk)
through a hermetic, sandboxed Deno subprocess instead of reading an
intent file from disk -- no network, filesystem, or environment access
for the program itself, confirmed empirically, not just documented as a
goal. The resulting `intent/v1` document is provenance-stamped with the
entry file's own content hash and handed to the exact same resolution
pipeline as any other intent producer.

First, generate typed bindings for the providers you've declared (see
[`ubx sdk gen`](/cli/sdk-gen)):

```text
$ ubx sdk gen --out sdk/generated
generated 1682 resource type(s) for hashicorp/aws@6.54.0 -> sdk/generated/hashicorp-aws.ts
```

Then author a program against them:

```typescript payments.ts
import { intent, resource, stack } from "@ubx/sdk";
import { AwsDbInstance } from "./sdk/generated/hashicorp-aws.ts";

export default stack("payments", () => {
  intent({
    summary:
      "Provision a small Postgres RDS instance in the payments stack, modeled on the staging database but downsized for low initial traffic.",
  });

  resource(AwsDbInstance, "payments", {
    engine: "postgres",
    instanceClass: "db.t3.small",
    allocatedStorage: 20,
    dbName: "payments",
    username: "payments_admin",
  });
});
```

```text
$ ubx resolve --from-code payments.ts --ledger-dir . --out resolved.json
resolved: payments: 1 create(s), 0 modify(ies), 0 destroy(s)
```

```json
{
  "intent": {
    "summary": "Provision a small Postgres RDS instance in the payments stack, modeled on the staging database but downsized for low initial traffic.",
    "sources": [
      {
        "kind": "document",
        "ref": "payments.ts",
        "content_hash": "sha256:ace1f28bd1c577e0f8788533d44232799eec52f9ec8f094dda5950f406e430a4"
      }
    ]
  },
  "delta": {
    "creates": [
      {
        "config": {
          "allocated_storage": 20,
          "db_name": "payments",
          "engine": "postgres",
          "instance_class": "db.t3.small",
          "username": "payments_admin"
        },
        "name": "payments",
        "provider": {"source": "hashicorp/aws", "version": "6.54.0"},
        "stack": "payments",
        "type": "aws_db_instance"
      }
    ]
  }
}
```

Notice `intent.sources` names one `"document"` entry -- the entry file
itself, content-hashed -- the same `"document"` kind a markdown authoring
document gets (see [`ubx propose --from-doc`](/cli/propose)).
There's no separate "which adapter drafted this" entry the way an
LLM-transcribed document (`ubx propose --from-doc`) gets: a TypeScript
program has no interpretation step, so there's nothing analogous to
name. This isn't a coincidence --
the exact resolved `delta.creates[]` above is byte-for-byte identical
(after canonical JSON normalization) to what resolving the equivalent
markdown-authored, LLM-transcribed document produces for the same
infrastructure -- three independent producers (a hand-written intent
file, a markdown document, and this TypeScript program) converging on the
same signed shape.

`.instanceClass` has no `?` in the generated `AwsDbInstanceConfig`
interface -- it's required by the real AWS schema, and TypeScript
enforces that before the program ever runs, not after a failed resolve.

### `Computed<T>`: wiring one resource's output into another

A `resource()` call returns a handle whose fields are all `Computed<T>` --
references, never real values (nothing exists yet). Passing one into a
sibling resource's own config produces a `$ref`, exactly like the JSON
`$ref` marker above:

```typescript
const primary = resource(AwsDbInstance, "payments", { /* ... */ });

resource(AwsDbInstance, "payments-replica", {
  instanceClass: "db.t3.small",
  replicateSourceDb: primary.id as unknown as string,
});
```

Trying to use a `Computed<T>` as a real value -- string interpolation,
`JSON.stringify`, arithmetic -- throws immediately, naming the address
and the attempted operation, rather than silently producing
`"[object Object]"`.

### What `--from-code` can't do (yet)

A program can only ever describe **creates** -- there's no way to author
a `"modify"` from TypeScript today. A hermetic, sandboxed program has no
filesystem or network access, so it has no way to check whether an
address already exists in the ledger; expressing `"modify"` intent needs
real design work this hasn't had yet. Use a hand-written intent file (or
[`ubx scan`](/cli/scan)'s own drift-generated proposals) for modifies.

## Authoring in Go

`--from-code <entry>.go` evaluates a Go [SDK program](/sdk) instead of
reading an intent file from disk -- dispatched by the entry file's own
extension (`.ts` and `.go` share the same `--from-code` flag). Unlike
TypeScript, which needs a sandboxed *interpreter* (Deno) because the
runtime executing the program is shared and otherwise capable of
anything, a Go SDK program is compiled and runs as an ordinary OS
process -- hermeticity comes from restricting that process itself
(`sandbox-exec` on macOS, [bubblewrap](https://github.com/containers/bubblewrap)
on Linux), confirmed empirically, not just documented as a goal. The
resulting `intent/v1` document is provenance-stamped and resolved through
the exact same pipeline as TypeScript, a hand-written intent file, or a
markdown document -- an SDK program is just another producer, regardless
of language.

First, generate typed bindings for Go (see [`ubx sdk gen
--lang go`](/cli/sdk-gen)):

```text
$ ubx sdk gen --lang go --out sdk/generated
generated 1682 resource type(s) for hashicorp/aws@6.54.0 -> sdk/generated/hashicorp-aws.go
```

Then author a program against them. A Go SDK program is its own real Go
module, requiring `github.com/ubiquex/ubx-sdk-go` (the tiny runtime
package -- not yet published, so a local `replace` is needed until it
is):

```go go.mod
module payments

go 1.23

require github.com/ubiquex/ubx-sdk-go v0.0.0
```

```go payments.go
package main

import (
	sdk "github.com/ubiquex/ubx-sdk-go/runtime"

	generated "payments/sdk/generated"
)

func main() {
	sdk.Main(sdk.Stack("payments", func() {
		sdk.Intent(sdk.IntentInfo{
			Summary: "Provision a small Postgres RDS instance in the payments stack, modeled on the staging database but downsized for low initial traffic.",
		})

		sdk.Resource(generated.AwsDbInstance, "payments", generated.AwsDbInstanceConfig{
			Engine:           "postgres",
			InstanceClass:    "db.t3.small",
			AllocatedStorage: 20,
			DbName:           "payments",
			Username:         "payments_admin",
		})
	}))
}
```

```text
$ ubx resolve --from-code payments.go --ledger-dir . --out resolved.json
resolved: payments: 1 create(s), 0 modify(ies), 0 destroy(s)
```

```json
{
  "intent": {
    "summary": "Provision a small Postgres RDS instance in the payments stack, modeled on the staging database but downsized for low initial traffic.",
    "sources": [
      {
        "kind": "document",
        "ref": "payments.go",
        "content_hash": "sha256:4fb60e40af94ab09c9bdad31fb1dc8bc284a78de2800bbd8d702adc1f5797a5d"
      }
    ]
  },
  "delta": {
    "creates": [
      {
        "config": {
          "allocated_storage": 20,
          "db_name": "payments",
          "engine": "postgres",
          "instance_class": "db.t3.small",
          "username": "payments_admin"
        },
        "name": "payments",
        "provider": {"source": "hashicorp/aws", "version": "6.54.0"},
        "stack": "payments",
        "type": "aws_db_instance"
      }
    ]
  }
}
```

The exact same real transcript shown above under [Authoring in
TypeScript](#authoring-in-typescript) -- `delta.creates[]` is byte-for-
byte identical, canonicalized, run for real against the real
`hashicorp/aws@6.54.0` schema. Only `intent.sources` differs, and only
because it names a different real file -- `payments.go` instead of
`payments.ts` -- with its own real content hash, exactly the honest
difference a genuinely independent producer should have.

### `Computed`: wiring one resource's output into another

A `sdk.Resource()` call returns a `*sdk.Computed` handle -- a reference,
never a real value (nothing exists yet). Go has no equivalent of a JS
Proxy, so drilling into a nested attribute is an explicit method call
rather than implicit property access:

```go
primary := sdk.Resource(generated.AwsDbInstance, "payments", generated.AwsDbInstanceConfig{ /* ... */ })

sdk.Resource(generated.AwsDbInstance, "payments-replica", generated.AwsDbInstanceConfig{
	InstanceClass:     "db.t3.small",
	ReplicateSourceDb: primary.Field("id"),
})
```

produces the same `$ref` marker TypeScript's own `Computed<T>` produces.

### What Go's `--from-code` can't do (yet)

The same limits as TypeScript: creates only, no `"modify"` (a hermetic,
sandboxed program has no way to check whether an address already
exists). On Linux specifically, evaluation requires
[`bwrap`](https://github.com/containers/bubblewrap) on `PATH` -- `ubx`
refuses to evaluate unsandboxed rather than silently degrading if it's
missing, or if the current environment can't create its own namespaces
(a real, found edge: this can happen inside an already-hardened
container, e.g. some CI images -- see [the SDK
guide](/sdk#the-go-evaluator) for the full account).

## Authoring in Python

`--from-code <entry>.py` evaluates a Python [SDK program](/sdk) --
dispatched by extension, same as TypeScript/Go. Python has neither
TypeScript's sandboxed-interpreter story nor Go's compiled-program
cheat, so this evaluator's own mechanism is the most different of the
three: [WASI](https://wasi.dev) -- [`wasmtime`](https://wasmtime.dev)
running a real CPython build compiled to WebAssembly. Confirmed
empirically to be the *strongest* isolation of any of the three
evaluators: network and subprocess-spawning are absent as WASI
capabilities entirely, not merely denied by a sandbox policy, and the
identical mechanism runs on macOS and Linux alike (see [the SDK
guide](/sdk#the-python-evaluator) for the full empirical account).

First, generate typed bindings for Python (see [`ubx sdk gen
--lang py`](/cli/sdk-gen)):

```text
$ ubx sdk gen --lang py --out sdk/generated
generated 1682 resource type(s) for hashicorp/aws@6.54.0 -> sdk/generated/hashicorp_aws.py
```

Then author a program against them:

```python payments.py
import ubx_sdk as sdk
from sdk.generated.hashicorp_aws import AwsDbInstance, AwsDbInstanceConfig


def describe():
    sdk.intent(
        "Provision a small Postgres RDS instance in the payments stack, "
        "modeled on the staging database but downsized for low initial traffic."
    )

    sdk.resource(AwsDbInstance, "payments", AwsDbInstanceConfig(
        engine="postgres",
        instance_class="db.t3.small",
        allocated_storage=20,
        db_name="payments",
        username="payments_admin",
    ))


if __name__ == "__main__":
    sdk.run("payments", describe)
```

```text
$ ubx resolve --from-code payments.py --ledger-dir . --out resolved.json
resolved: payments: 1 create(s), 0 modify(ies), 0 destroy(s)
```

```json

    "summary": "Provision a small Postgres RDS instance in the payments stack, modeled on the staging database but downsized for low initial traffic.",
    "sources": [
      {
        "kind": "document",

        "content_hash": "sha256:b01e09f8afd29792c6cf301a579834a24ded46941ead76f6887f7269f57af391"
      }
    ]
  },
  "delta": {
    "creates": [
      {
        "config": {
          "allocated_storage": 20,
          "db_name": "payments",
          "engine": "postgres",
          "instance_class": "db.t3.small",
          "username": "payments_admin"
        },
        "name": "payments",
```

The same real transcript shown above under [Authoring in
TypeScript](#authoring-in-typescript) and [Authoring in
Go](#authoring-in-go) -- `delta.creates[]` is byte-for-byte identical,
canonicalized, run for real against the real `hashicorp/aws@6.54.0`
schema. Only `intent.sources` differs, and only because it names a
different real file -- `payments.py` this time -- with its own real
content hash.

### `Computed`: wiring one resource's output into another

A `sdk.resource()` call returns a `sdk.Computed` handle -- a reference,
never a real value. Unlike Go (which needs an explicit `.Field(name)`
method call, having no Proxy), Python's own `__getattr__` hook lets
attribute access work exactly the way it reads:

```python
primary = sdk.resource(AwsDbInstance, "payments", AwsDbInstanceConfig(...))

sdk.resource(AwsDbInstance, "payments-replica", AwsDbInstanceConfig(
    instance_class="db.t3.small",
    replicate_source_db=primary.id,
))
```

produces the same `$ref` marker TypeScript's/Go's own constructs
produce. Trying to use a `Computed` as a real value -- `str()`, `bool()`,
arithmetic, iteration -- raises `ComputedCoercionError` immediately,
naming the address and the attempted operation, rather than silently
producing a wrong value.

### What Python's `--from-code` can't do (yet)

The same limits as TypeScript/Go: creates only, no `"modify"`.
Evaluation requires [`wasmtime`](https://wasmtime.dev) on `PATH` -- `ubx`
refuses to evaluate unsandboxed rather than silently degrading if it's
missing. The first evaluation against a `.py` entry also downloads and
caches a real CPython-WASI build (~40MB, under `~/.ubx/python-wasi/`) --
a one-time cost, not repeated on later runs.

## Intra-stack references

A resource's `config` can reference another resource in the *same* intent
file with `$ref`, addressed as `<stack>.<type>.<name>.<attribute path>`.
`ubx resolve` builds the dependency graph from these references (detecting
real cycles, something v1 XCL's own single-stack graph never did), resolves
in topological order, and emits each create's `depends_on` alongside it:

```json
{
  "resources": [
    {
      "type": "fake_widget", "name": "primary", "op": "create",
      "config": {"name": "primary", "tags": {"env": "prod"}}
    },
    {
      "type": "fake_widget", "name": "mirror", "op": "create",
      "config": {
        "name": {"$ref": {"to": "payments.fake_widget.primary.name"}},
        "tags": {"peer_id": {"$ref": {"to": "payments.fake_widget.primary.id"}}}
      }
    }
  ]
}
```

```text
$ ubx resolve intent-refs.json --provider ./fakeprovider --ledger-dir .
resolved: payments: 2 create(s), 0 modify(ies)
{
  "delta": {
    "creates": [
      {
        "config": {"name": "primary", "tags": {"env": "prod"}},
        "name": "primary", "stack": "payments", "type": "fake_widget"
      },
      {
        "config": {
          "name": "primary",
          "tags": {"peer_id": {"$computed": {"from": "payments.fake_widget.primary.id"}}}
        },
        "depends_on": ["payments.fake_widget.primary"],
        "name": "mirror", "stack": "payments", "type": "fake_widget"
      }
    ]
  }
}
```

Two different things happened to the two `$ref`s here, both correct:

- `mirror.name`'s ref targets `primary.name`, an **ordinary** (non-`Computed`)
  attribute -- resolved straight to `primary`'s own literal value, `"primary"`.
- `mirror.tags.peer_id`'s ref targets `primary.id`, which the provider's
  schema flags `Computed` -- there's no value to substitute yet (it won't
  exist until `primary` is actually created), so it's left as a `$computed`
  marker for [`ubx ship`](/concepts/apply-record) to fill in from the real
  applied result, mid-walk.

A `$computed` value can never be used somewhere the schema requires a
concrete value -- attempting that is a resolve-time error, not a deferred
runtime surprise.

### `$ref`/`$cross` embedded inside a JSON-encoded string attribute

Some provider attributes are typed as a plain string but treated as
nested JSON by the resource itself -- an IAM policy document, a trust
policy. A `$ref`/`$cross` (or `$secret`/`$computed`/`$ephemeral`) can
live one level down, inside that string's own decoded structure, and
`ubx resolve` finds and resolves it there too -- including computing the
same dependency edge a top-level reference would:

```json
{
  "config": {
    "name": "{\"description\":\"mirrors\",\"target\":{\"$ref\":{\"to\":\"payments.fake_widget.primary.name\"}}}"
  }
}
```

```text
$ ubx resolve intent-embedded-ref.json --provider ./fakeprovider --ledger-dir .
resolved: payments: 2 create(s), 0 modify(ies), 0 destroy(s)
```

```json
{
  "config": {
    "name": "{\"description\":\"mirrors\",\"target\":\"primary\"}"
  },
  "depends_on": ["payments.fake_widget.primary"]
}
```

Resolved and re-encoded back to a JSON string, byte-for-byte canonical
(Go's own JSON marshaling already sorts map keys) -- an ordinary string
that merely happens to parse as JSON but carries no marker anywhere is
left completely untouched.

### A JSON-embedded ref to a same-batch `Computed` sibling: a template, filled in at ship time

The flagship AWS pattern -- an IAM role's own inline policy naming a
sibling resource's ARN (a queue, a bucket) created in the very same
batch, before that sibling has ever actually applied and so before its
real ARN exists. `ubx resolve` doesn't refuse this: the ref still
resolves to a `$computed` marker (exactly like the top-level case
above), still embedded inside the re-serialized string -- the signed
proposal genuinely carries a **template**:

```json
{
  "resources": [
    {"type": "fake_widget", "name": "primary", "op": "create", "config": {"name": "primary"}},
    {"type": "fake_widget", "name": "policy-holder", "op": "create", "config": {
      "name": "{\"Statement\":[{\"Effect\":\"Allow\",\"Resource\":{\"$ref\":{\"to\":\"payments.fake_widget.primary.id\"}}}]}"
    }}
  ]
}
```

```text
$ ubx resolve intent-embedded-computed.json --provider ./fakeprovider --ledger-dir .
resolved: payments: 2 create(s), 0 modify(ies), 0 destroy(s)
```

```json
{
  "config": {
    "name": "{\"Statement\":[{\"Effect\":\"Allow\",\"Resource\":{\"$computed\":{\"from\":\"payments.fake_widget.primary.id\"}}}]}"
  },
  "depends_on": ["payments.fake_widget.primary"]
}
```

The embedded `$computed` marker contributes the identical real
dependency edge a top-level one would (`depends_on` above) -- `ubx ship`
always ships `primary` first, then fills the real applied value into
`policy-holder`'s own template in place before its own
`ApplyResourceChange` call, exactly like it already does for a top-level
`$computed` marker. See [`ubx ship`'s own create-chain
example](/cli/ship#a-two-resource-create-chain) for the general
mechanism this reuses.

<Warning>
  This templating only ever applies to `$computed` -- a `$secret` marker
  embedded inside a JSON-encoded string attribute is still always a
  resolve-time error, no exception: no redaction path exists for a
  marker buried inside a string attribute the provider schema doesn't
  itself flag `Sensitive`.
</Warning>

<Warning>
  A reference written as a plain string -- `"target": "$ref:payments.fake_widget.primary.name"`,
  anywhere, top-level or JSON-embedded -- is always a resolve-time error,
  never silently passed through. The real wire shape is always an
  object, `{"$ref": {"to": "..."}}`; a string prefixed with `$ref:` (or
  `$cross:`/`$secret:`/`$computed:`/`$ephemeral:`) is refused outright.
</Warning>

## Cross-stack references

`$cross` references a resource in a *different* stack's ledger, addressed
the same way plus a `ledger_dir`:

```json
{
  "tags": {
    "vpc_name": {
      "$cross": {
        "ledger_dir": "../networking",
        "to": "networking.fake_widget.vpc.name"
      }
    }
  }
}
```

Unlike `$ref`, a `$cross` target is always resolved against the neighbor
ledger's own currently-recorded state -- always concrete, never
`$computed` -- and records a `cross_stack_pin` resolution input carrying
the neighbor's ledger head *at resolve time*:

```text
$ ubx resolve payments/intent.json --provider ./fakeprovider --ledger-dir payments --out payments/resolved.json
resolved: payments: 1 create(s), 0 modify(ies)
```

```json
{
  "resolution": {
    "inputs": [
      {
        "kind": "cross_stack_pin",
        "resource": "networking.fake_widget.vpc",
        "observed_hash": "e84c0a302ecd78281126ad0daed0d53a78ecb24ba6daef993436245918786afa",
        "pinned_head": "7a069a2a22e2b4edc6e1ed3aae58108415371c3a9dc6b72c19fc62c6acb9bd33",
        "ledger_dir": "/tmp/ubx-resolve-docs5/networking"
      }
    ]
  }
}
```

`ubx accept` re-derives that neighbor ledger's head at accept time and
refuses the proposal if it's moved on since -- see
[`ubx accept`'s cross-stack pin verification](/cli/accept#cross-stack-pin-verification).
This check is unconditional, not opt-in: unlike a live provider round trip,
reading a neighbor ledger's head is a free, local filesystem read, so
there's no reason an operator would need to ask for it explicitly.

## Destroying a resource

A destroy is a dedicated, top-level `destroys` list in the intent file --
canonical addresses (`<stack>.<type>.<name>`), never an `"op": "destroy"`
value on a `resources[]` entry, and never inferred from a resource's
absence from `resources[]`. A resource the ledger knows about that an
intent file simply doesn't mention is not a destroy signal, now or ever --
only an address explicitly named in `destroys` is removed:

```json
{
  "schema_version": 1,
  "kind": "ubx:intent/v1",
  "stack": "payments",
  "intent": {"summary": "decommission the old widget"},
  "resources": [],
  "destroys": ["payments.fake_widget.old-widget"]
}
```

```text
$ ubx resolve destroy-intent.json --provider ./fakeprovider --ledger-dir .
resolved: payments: 0 create(s), 0 modify(ies), 1 destroy(s)
{
  "schema_version": 2,
  "stack": "payments",
  "parent": "9944c6a148f5f1a59af0178f40d03667b9e8abc8417f554c14a12fa219a9ea03",
  "kind": "change",
  "intent": {"summary": "decommission the old widget"},
  "delta": {
    "destroys": [
      {
        "address": {"stack": "payments", "type": "fake_widget", "name": "old-widget"},
        "state": {"id": "old-widget", "name": null, "tags": {}}
      }
    ]
  },
  "resolution": {
    "resolved_at": "2026-07-17T21:15:42Z",
    "inputs": [
      {
        "kind": "destroy_target",
        "resource": "payments.fake_widget.old-widget",
        "observed_hash": "c9c672b5a57e403a38cc0d6d2e1381f458e50758d9d0f4117477526a620b426a",
        "lookup": {"id": "old-widget"}
      },
      {
        "kind": "cross_stack_orphan_check",
        "resource": "payments.fake_widget.old-widget",
        "status": "not_performed"
      }
    ]
  },
  "cost_delta": {"monthly_usd": 0},
  "blast_radius": {"creates": 0, "modifies": 0, "destroys": 1},
  "status": "draft"
}
```

A destroy carries its target's **full** recorded state inline (`delta.destroys[].state`)
-- not just the attributes that changed the way `delta.modifies[].before`/`after`
do. Everything about the resource is being lost, not a subset of it, so
whoever reviews and signs this proposal sees exactly what's being removed
without having to separately look it up.

### Orphan protection

Destroying a resource that another live resource still depends on is
refused, not silently allowed -- checked against the whole ledger's own
recorded history, not just this intent file:

```text
$ ubx resolve destroy-intent.json --provider ./fakeprovider --ledger-dir .
Error: resolve: resolve: destroy target is still referenced by a resource this proposal does not
also destroy or update: payments.fake_widget.old-widget is still referenced by
payments.fake_widget.mirror, which this proposal does not also destroy or update
```

Two ways to make a destroy that would otherwise be refused legal:

- **Destroy the dependent too**, in the same `destroys` list -- a mutual
  destroy is never an orphan, since destroying always happens in reversed
  dependency order (the dependent goes first).
- **Repoint the dependent away first**, in the same intent file's own
  `resources`, as a `"modify"`. The destroy target's `depends_on` then
  names the repointing modify, so `ubx ship` waits for it to complete
  before destroying:

```json
{
  "resources": [
    {
      "type": "fake_widget", "name": "mirror", "op": "modify",
      "config": {"id": "mirror", "tags": {}}
    }
  ],
  "destroys": ["payments.fake_widget.old-widget"]
}
```

```text
$ ubx resolve destroy-with-repoint.json --provider ./fakeprovider --ledger-dir .
resolved: payments: 0 create(s), 1 modify(ies), 1 destroy(s)
{
  "delta": {
    "modifies": [
      {
        "target": {"stack": "payments", "type": "fake_widget", "name": "mirror"},
        "before": {"name": null, "tags.peer_id": {"$computed": {"from": "payments.fake_widget.old-widget.id"}}}
      }
    ],
    "destroys": [
      {
        "address": {"stack": "payments", "type": "fake_widget", "name": "old-widget"},
        "state": {"id": "old-widget", "name": null, "tags": {}},
        "depends_on": ["payments.fake_widget.mirror"]
      }
    ]
  }
}
```

A `$ref`/`$cross` that resolves to an address this same proposal is also
destroying is always refused (`resolve: $ref/$cross target is being
destroyed in this same proposal`) -- referencing a value that's being
removed in the same breath is never sound, and rejecting it is what
guarantees a repointing modify like `mirror`'s above provably no longer
references the destroy target by the time it's resolved.

Orphan protection here is a real check against this stack's own ledger
history, not an exhaustive guarantee: it can only ever see a dependency
that was itself recorded via `$ref` at some point (a resource that simply
hardcodes another's value as a plain literal, never through `$ref`, leaves
no edge to find).

### Cross-stack orphan protection

A neighbor stack pinning this stack's destroy target via `$cross` is a
harder problem: the pin is recorded entirely on the *neighbor's* own
ledger, so this stack has no built-in way to know who, if anyone, depends
on it. Pass `--known-dependent` (repeatable) for every neighbor ledger
directory worth checking:

```text
$ ubx resolve destroy-intent.json --provider ./fakeprovider --ledger-dir . \
    --known-dependent ../networking
Error: resolve: resolve: destroy target is still referenced by a resource this proposal does not
also destroy or update: payments.fake_widget.old-widget is pinned by a cross-stack reference in
../networking
```

If none of the named neighbors actually pin the target, the resolve
succeeds and records an honest `checked_clear`:

```json
{
  "kind": "cross_stack_orphan_check",
  "resource": "payments.fake_widget.old-widget",
  "status": "checked_clear",
  "checked_ledger_dirs": ["../networking"]
}
```

**Omitting `--known-dependent` doesn't mean "no dependents exist"** -- it
means none were checked, and the resolved proposal says so honestly
(`status: "not_performed"`, the first transcript above) rather than
silently implying a guarantee this command has no way to actually make
without knowing every stack that might reference this one.

## When resolution fails

An intent file naming a type the provider schema doesn't recognize is
refused outright (exit `2` -- `ubx resolve` has no "finding" concept, the
same audit outcome as `ubx propose`/`ubx init`):

```text
$ ubx resolve intent-bad.json --provider ./fakeprovider --ledger-dir .
Error: resolve: resolve: provider schema has no such type: "fake_widgit"
```

The same tier covers a circular reference between two resources in the
same file, a reference to an address that doesn't exist anywhere in the
batch or the ledger, a `$secret` placed at an attribute the schema doesn't
flag `Sensitive`, and a `$cross` naming a `ledger_dir` that's never been
initialized or doesn't have the referenced address recorded. Destroy-specific:
a `destroys` entry naming an address the ledger has never recorded, a
duplicate address within `destroys`, an address appearing in both
`resources` and `destroys`, orphan protection's own refusal (see
[Destroying a resource](#destroying-a-resource) above), and a
`--known-dependent` naming a `ledger_dir` that's never been initialized.

### A resource's config uses a key that doesn't exist on its real type

Every key in a resource's `config` -- attributes and keys nested inside a
block alike -- is checked against the real provider schema for that
resource's type, at the pinned provider version. This catches a
plausible-sounding but fictional attribute name (the kind an AI-authored
draft can produce) before it ever reaches a real `ApplyResourceChange`
call, not partway through a real `ubx ship` -- possibly after other
resources in the same batch have already applied:

```text
$ ubx resolve intent-bad-keys.json --provider ./fakeprovider --ledger-dir .
resolve: resolve: unrecognized config key: platform.aws_iam_role.ci-runner: config key "assume_role_policy_document" does not exist on aws_iam_role (did you mean "assume_role_policy"?)
resolve: unrecognized config key: platform.aws_iam_role.ci-runner: config key "role_name" does not exist on aws_iam_role (did you mean "name"?)
```

Every unrecognized key across the *whole* intent file is reported at once
-- a resource with three wrong keys gets three distinct lines, not just
the first mistake -- each with a suggested real key name when one is close
enough to be worth suggesting (omitted otherwise; a wrong suggestion is
worse than none). This check has no idea, and doesn't need one, whether
the intent file was hand-written, generated by an SDK program, or drafted
by an AI adapter (see [`ubx propose --from-doc`](/cli/propose) and
[`ubx chat`](/guides/chat)) -- the same schema is checked either way.

<Note>
  A resource's own `config` is opaque to AI structured-output schemas (they
  can only express a closed object shape, and a resource's real attribute
  set differs per type) -- so an AI-authored draft with a hallucinated
  attribute key always passes that layer *and* `ubx propose --from-doc`'s
  own structural validation cleanly. This check, here at resolve time, is
  the first point in the whole pipeline with both a real provider schema
  and a decoded config to check it against.
</Note>

<Note>
  `ubx resolve` runs its whole resolution twice internally and compares the
  two results byte-for-byte, hard-failing on any divergence rather than
  ever hashing an unstable result -- the same determinism guarantee every
  other proposal-producing path in `ubx` makes, applied here for the first
  time to something as involved as a dependency-ordered, schema-aware
  resolution pass.
</Note>

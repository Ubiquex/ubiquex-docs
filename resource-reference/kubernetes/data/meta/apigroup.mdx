`kubernetes_meta_apigroup` reads one real API group the cluster's API server currently serves -- its name and the API versions available within it -- part of the same discovery mechanism `kubectl api-versions` uses.

## Example

<Tabs>
  <Tab title="Go">
    ```go
    package main

    import (
    	ubx "github.com/ubiquex/ubx-sdk-go/runtime"
    	meta "github.com/ubiquex/ubx-sdk-kubernetes/sdk/go/kubernetes/data/meta"
    )

    func main() {
    	ubx.Main(ubx.Stack("example", func() {
    		ubx.Intent(ubx.IntentInfo{Summary: "look up kubernetes_meta_apigroup"})

    		ubx.Data(meta.Apigroup, "example", meta.ApigroupConfig{})
    	}))
    }
    ```

_This lookup takes no arguments._

<ResponseField name="kind" type="string">
  Kind is a string value representing the REST resource this object represents. Servers may infer this from the endpoint the client submits requests to. Cannot be updated. In CamelCase. More info: https://git.k8s.io/community/contributors/devel/sig-architecture/api-conventions.md#types-kinds Returned by the lookup.
</ResponseField>

<ResponseField name="name" type="string">
  name is the name of the group. Returned by the lookup.
</ResponseField>

<ResponseField name="preferred_version" type="object">
  GroupVersion contains the "group/version" and "version" string of a version. It is made a struct to keep extensibility. Returned by the lookup.
  <Expandable title="properties">
    <ResponseField name="group_version" type="string" required>
      groupVersion specifies the API group and version in the form "group/version" Required lookup argument.
    </ResponseField>
    <ResponseField name="version" type="string" required>
      version specifies the version in the form of "version". This is to save the clients the trouble of splitting the GroupVersion. Required lookup argument.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="server_address_by_client_cidrs" type="list(object)">
  a map of client CIDR to server address that is serving this group. This is to help clients reach servers in the most network-efficient way possible. Clients can use the appropriate server address as per the CIDR that they match. In case of multiple matches, clients should use the longest matching CIDR. The server returns only those CIDRs that it thinks that the client can match. For example: the master will return an internal IP CIDR only, if the client reaches the server using an internal IP. Server looks at X-Forwarded-For header or X-Real-Ip header or request.RemoteAddr (in that order) to get the client IP. Returned by the lookup.
</ResponseField>

<ResponseField name="versions" type="list(object)">
  versions are the versions supported in this group. Returned by the lookup.
</ResponseField>

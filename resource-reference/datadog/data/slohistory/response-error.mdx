## Lookup arguments

<ResponseField name="apply_correction" type="bool">
  Whether known SLO corrections are applied to this result. **(AI-inferred)** Optional lookup argument.
</ResponseField>

<ResponseField name="from_ts" type="number" required>
  The real, inclusive start of the time range this request covers, as a Unix timestamp. **(AI-inferred)** Required lookup argument.
</ResponseField>

<ResponseField name="slo_id" type="string" required>
  The real, unique identifier of this Service Level Objective. **(AI-inferred)** Required lookup argument.
</ResponseField>

<ResponseField name="target" type="number">
  The real object this reference points to. **(AI-inferred)** Optional lookup argument.
</ResponseField>

<ResponseField name="to_ts" type="number" required>
  The real, inclusive end of the time range this request covers, as a Unix timestamp. **(AI-inferred)** Required lookup argument.
</ResponseField>

        <ResponseField name="history" type="list(list(number))">
          The state transition history for `monitor` or `time-slice` SLOs. It is represented as an array of pairs. Each pair is an array containing the timestamp of the transition as an integer in Unix epoch format in the first element, and the state as an integer in the second element. An integer value of `0` for state means uptime, `1` means downtime, and `2` means no data. Periods of no data count as uptime in time-slice SLOs, while for monitor SLOs, no data is counted either as uptime or downtime depending on monitor settings. See [SLO documentation](https://docs.datadoghq.com/service_management/service_level_objectives/monitor/#missing-data) for detailed information. Optional lookup argument.

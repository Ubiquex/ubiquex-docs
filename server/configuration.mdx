Real, confirmed precedence: **flags override environment variables, environment variables override
the YAML file, YAML overrides these built-in defaults.** Every layer only overwrites a value the
layer above it actually set -- an unset flag never blanks out whatever the YAML/env layers already
established underneath it.

## The real key mapping

Every scalar setting has a real YAML key, a real environment variable
(`UBX_SERVER_<UPPER_SNAKE_CASE>`), and a real flag (`--kebab-case`):

**`github_webhook_secret` has no YAML key, deliberately.** A webhook secret is exactly the kind of
value that shouldn't sit in a config file that might get committed -- set it via
`UBX_SERVER_GITHUB_WEBHOOK_SECRET` or `--github-webhook-secret` only, the same "self-provisioned,
masked variable, never literally in the file" discipline every [CI/CD
guide](/integrations/github-actions) already applies to its own platform tokens.

**`azure_devops_token`/`azure_devops_webhook_secret` have no YAML key either, same reasoning.** A
Personal Access Token and a real, shared-secret webhook header value are exactly the same kind of
credential `github_webhook_secret`'s own doc comment describes. `azure_devops_webhook_secret_header`
itself, by contrast, is real, non-secret config (just a header *name*, not a value) -- it does have
a YAML key, defaulting to `X-Ubx-Webhook-Secret` since Azure DevOps has no fixed convention of its
own to defer to (confirmed directly against Microsoft's own current Service Hooks docs: no
cryptographic webhook signature scheme exists at all, only an optional custom header the operator
names and values themselves).

**`bitbucket_server_token`/`bitbucket_server_webhook_secret` have no YAML key either, same
reasoning.** An HTTP access token and a real, bundled HMAC-SHA256 webhook secret are exactly the
same kind of credential `github_webhook_secret`'s own doc comment describes. `bitbucket_server_url`
itself, by contrast, is real, non-secret config -- it does have a YAML key, and unlike every other
platform's own API base, it has **no default at all**: Bitbucket Server is self-hosted, with no
single fixed host the way `gitlab.com`/`dev.azure.com` each are (confirmed directly against
`bitbucketserver.Client`'s own doc comment) -- always required for Bitbucket Server support.

**`repos` is YAML-only, for the opposite reason:** it's a real list of structured objects
(platform, owner/name or project, or project/repository, and each repo's own ledger directory), not
a scalar a single flag or environment variable can sensibly represent. `--repo` is a real,
repeatable flag covering the common one-or-few-repos case without needing a YAML file at all -- not
a full substitute for the list. An entry with no `platform` key defaults to `"github"`, real
backward compatibility for every config written before GitLab/Azure DevOps/Bitbucket Server support
existed.

## `repos` is a real, enforced allowlist (UBI-166)

**Every webhook-triggered action -- plan, re-plan, approval-derived acceptance, ship, whether
automatic or via comment -- refuses outright unless the event's own repository is explicitly
listed in `repos`.** This applies identically on all four platforms, GitHub included: a GitHub
App's own installation scope (which repos it's installed on) is a real, coarser gate, but `repos`
is checked independently and additionally, not assumed to already cover it. For GitLab/Azure
DevOps/Bitbucket Server -- each authenticating with one real, static credential that can reach
every repository it has permissions on, with no narrower per-repo concept at all -- `repos` is the
**only** real scope boundary that exists; nothing else stops a webhook pointed at this server from
an unintended repository from triggering automation.

<Warning>
  Before UBI-166 (fixed 2026-08-15), an unlisted repository was never refused -- it silently
  defaulted to `ledger_dir "."` and ran anyway. If you deployed `ubx server` before this fix,
  re-check your own `repos` list names every real repository you intend to watch; anything missing
  now refuses instead of silently running at the repo root.
</Warning>

A refusal is never silent: `ubx server` logs a real, structured `ERROR`-level line naming the
platform, the repository, and the event -- for example:

```
ERROR ubx server: refusing pull_request event -- repository not in Config.Repos allowlist (UBI-166) platform=github repo=acme/unlisted-repo action=opened pr=1
```

No comment is posted back to an unlisted repository itself (there's nothing to say to a repo that
was never opted into this server's own automation at all) -- the refusal is loud only to the
operator's own logs, watch them for exactly this line if a webhook you expected to trigger
automation appears to do nothing.

### Two real stacks in one repository

A single repository can have more than one `repos` entry (same platform/owner/project, different
`ledger_dir`) -- a real, legitimate multi-stack configuration, not a misconfiguration. UBI-166 also
fixed a real, latent bug this uncovered: before it, only the **first-listed** entry for a given
repository was ever consulted, for every event, regardless of which stack a given PR's own changes
actually touched. Now, when more than one entry matches, `ubx server` fetches the event's own real
changed files and picks the most specific configured `ledger_dir` whose own subtree contains at
least one of them (a nested stack wins over a coexisting repo-root stack, the same "most specific
route wins" convention path-based routing already uses elsewhere) -- refusing outright, loudly
logged, if the changed files touch zero or more than one configured stack at once, rather than
guessing. This extra resolution only runs for a genuinely multi-stack repository; a repository with
exactly one `repos` entry never pays for it.

**`intent_provider_key` has no YAML key either, for the same reason.** It's a real LLM/intent-
provider API key ([markdown-authored proposals](/tutorial/markdown), [`ubx
plan`](/cli-reference/plan)'s own `--from-doc`), not a VCS credential, but the same secrets
discipline applies. When set, `ubx server` forwards it into every `ubx plan` subprocess as a fixed
environment variable, `UBX_INTENT_PROVIDER_KEY` -- point a watched repo's own `.ubx/config`
`[intent]` table's `key_ref.env` at that exact name so `ubx plan --from-doc`'s own configured
intent-provider adapter can read it. Leave it unset if you never accept markdown-authored
(`--from-doc`) proposals through this server at all; a markdown-authored PR/MR's automatic plan step
then fails with `ubx plan`'s own real, existing error (`key_ref.env names "...", but that
environment variable is unset or empty`), posted as an ordinary plan-failure comment -- not a silent
hang.

## The YAML file

```yaml
listen_addr: ":8080"
work_dir: "/var/lib/ubx-server/repos"

github_app_id: 123456
github_app_private_key_path: "/etc/ubx-server/github-app.pem"
github_bot_login: "ubx[bot]"

gitlab_bot_username: "group_1234_bot_5678"

azure_devops_organization: "acme-org"
azure_devops_bot_display_name: "ubx-bot"
azure_devops_webhook_secret_header: "X-Ubx-Webhook-Secret"

bitbucket_server_url: "https://bitbucket.example.com"
bitbucket_server_bot_name: "ubx-bot"

provider_source: "hashicorp/aws"
provider_version: "6.54.0"
provider_config: '{"region":"us-east-1"}'

ship_on_merge: true
allow_destroy: false
surface_as: "issue"
drift_watch_interval: "24h"

repos:
  - platform: "github"
    owner: "acme"
    name: "infra"
    ledger_dir: "."
  - platform: "github"
    owner: "acme"
    name: "payments-infra"
    ledger_dir: "stacks/payments"
  - platform: "gitlab"
    project: "acme/backend/infra"
    ledger_dir: "stacks/payments"
  - platform: "azuredevops"
    project: "acme-infra"
    repository: "payments-infra"
    ledger_dir: "stacks/payments"
  - platform: "bitbucketserver"
    project: "INFRA"
    repository: "payments-infra"
    ledger_dir: "stacks/payments"
```

Point `ubx server` at it with `--config /etc/ubx-server/ubx-server.yaml`. `gitlab_token`,
`gitlab_webhook_secret`, `azure_devops_token`, `azure_devops_webhook_secret`,
`bitbucket_server_token`, `bitbucket_server_webhook_secret`, `github_webhook_secret`, and
`intent_provider_key` are deliberately absent here -- real secrets, set only via their own
environment variables or flags.

## `--repo`'s own shorthand

```bash
ubx server --repo acme/infra --repo acme/payments-infra:stacks/payments \
  --repo gitlab:acme/infra --repo gitlab:acme/backend/infra:stacks/payments \
  --repo azuredevops:acme-infra/infra --repo azuredevops:acme-infra/payments-infra:stacks/payments \
  --repo bitbucketserver:INFRA/infra --repo bitbucketserver:INFRA/payments-infra:stacks/payments
```

`owner/name` alone defaults `ledger_dir` to `"."`, matching [`ubx
plan`](/cli-reference/plan)'s own default; `owner/name:ledger_dir` sets it explicitly, the same
real shape a YAML `repos` entry carries. A real `gitlab:` prefix selects the GitLab shorthand
instead -- `gitlab:namespace/project` or `gitlab:namespace/project:ledger_dir` -- the project path
kept as one whole, opaque string (never split into separate fields) since a real GitLab project can
be nested under any number of real groups/subgroups. See [GitLab setup](/server/gitlab-setup) for
the full, real GitLab configuration walkthrough. A real `azuredevops:` prefix selects the Azure
DevOps shorthand -- `azuredevops:project/repository` or `azuredevops:project/repository:ledger_dir`
-- project and repository kept as two real, separate identifiers (never one opaque string) since a
real Azure DevOps project can host many real repositories. See [Azure DevOps
setup](/server/azure-devops-setup) for the full, real Azure DevOps configuration walkthrough. A
real `bitbucketserver:` prefix selects the identical two-real-identifier shape for Bitbucket
Server -- `bitbucketserver:PROJECTKEY/repository-slug` or
`bitbucketserver:PROJECTKEY/repository-slug:ledger_dir` -- matching the existing `ubx accept
--bitbucket-server-project PROJECTKEY/repository-slug` flag's own real format. See [Bamboo
setup](/server/bamboo-setup) for the full, real Bitbucket Server configuration walkthrough.

## A worked example: env overrides YAML

```yaml
# ubx-server.yaml
listen_addr: ":9090"
```

```bash
UBX_SERVER_LISTEN_ADDR=:7070 ubx server --config ubx-server.yaml
```

`ubx server` listens on `:7070` -- the environment variable wins over the YAML file, exactly the
confirmed cascade order. Add `--listen-addr :6060` to the same command and it listens on `:6060`
instead -- the flag wins over both.

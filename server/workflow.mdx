This walks through [the core flow](/server/overview#the-core-flow) in order, against the real,
tested behavior of `ubx server`'s own code -- not a hypothetical. A full live run needs a real
GitHub App installation (or a real GitLab Group Access Token, a real Azure DevOps Personal Access
Token, or a real Bitbucket Server HTTP access token) on a real repository, not reproducible inside
this documentation build; every mechanic below is instead grounded in the same real, adversarial
test suite that verifies it (`server/*_test.go`) and a real, captured transcript of the one piece
that doesn't need any platform's own credentials at all -- the webhook endpoints themselves. The
steps below are written against GitHub; see [the GitLab section](#gitlab), [the Azure DevOps
section](#azure-devops), and [the Bitbucket Server section](#bitbucket-server) for
the real, structural differences on each platform.

## Prerequisites

- A real GitHub App installed on the repo(s) you want watched (see [GitHub App
  setup](/server/github-setup)), a real GitLab Group Access Token plus webhook signing token (see
  [GitLab setup](/server/gitlab-setup)), a real Azure DevOps Personal Access Token plus Service
  Hooks shared secret (see [Azure DevOps setup](/server/azure-devops-setup)), or a real Bitbucket
  Server HTTP access token plus its own bundled webhook shared secret (see [Bitbucket Server
  setup](/server/bitbucket-setup#bitbucket-server)).
- Each watched repo's own `.ubx/config` pointing at a real [remote ledger
  store](/tutorial/remote-stores) (S3, GCS, or Azure Blob) -- `ubx` itself never runs `git commit`/
  `git push`, so a local git-directory ledger written inside this server's own working clone never
  persists once that clone is next re-fetched.
- `ubx server` itself running and reachable at the Webhook URL each platform is configured with --
  see [Docker deployment](/server/docker).

## 1. A PR opens

GitHub delivers a real `pull_request` event (`action: "opened"`) to `/webhook/github`. `ubx server`:

1. Validates the delivery's own `X-Hub-Signature-256` against the configured webhook secret --
   confirmed live below.
2. Resolves an installation-scoped API client from the event's own `installation.id` (never a
   separate lookup call -- every webhook payload already carries it).
3. Clones (or fetches, if already cloned) the repo into `--work-dir`, checks out the PR's own real
   head commit.
4. Runs `ubx plan --ledger-dir <configured>` [--source ... --provider-version ...]` as a real
   subprocess of the exact same `ubx` binary.
5. Posts the captured stdout/stderr as a single PR comment, prefixed with a hidden
   `<!-- ubx:plan -->` marker.

## 2. Re-plan via comment

A new commit lands on the PR (`synchronize`) -- the same real steps run again, editing the
existing marked comment in place rather than posting a new one, the exact `--edit-last` mechanism
[GitHub Actions' own plan-on-push guide](/integrations/github-actions#workflow-2-plan-on-push)
already documents.

The PR's own creator can also comment `ubx plan` directly to force a re-run. `ubx server` reads the
comment, confirms it starts with `ubx plan`, and checks a real, live authorization rule before
running anything:

- **The commenter is the PR's own real creator** (read from the PR object itself, via the API,
  never assumed from the comment's own claim) -- authorized.
- **The PR was opened by this server's own bot** (a drift-watch-opened PR, step 6 below) -- there's
  no real human creator to compare against, so the rule falls back to the commenter's own real,
  live write access on the repository (GitHub's collaborator-permissions API, checked fresh every
  time, never cached).
- Anyone else -- refused, with a comment explaining why.

<Note>
  **The authorization check runs before any clone or fetch** (UBI-168), on every platform. An
  unauthorized comment therefore costs one authorization lookup and nothing else: no clone, no
  fetch, no stack resolution, no working copy on disk.

  Before UBI-168 this held on [Bitbucket Cloud](/server/bitbucket-setup#bitbucket-cloud) only. The other four
  platforms resolved the stack first, which since
  [auto-discovery](/server/configuration#stack-locations-are-auto-discovered-never-declared-here-ubi-167)
  means a real clone or fetch, so anyone who could comment on an allowlisted repository could make
  the server do that work on every comment before being told no. Only the ordering changed: the
  same checks run against the same inputs and produce the same refusal comments.
</Note>

## 3. Approve derives acceptance

GitHub's own native **Approve** review action -- never a comment -- fires a real
`pull_request_review` event (`state: "approved"`). `ubx server`:

1. Reads the PR's own body for a real `ubx-proposal: <hash>` trailer.
2. Reads the proposal file at **the review's own commit** specifically (`review.commit_id`), never
   the PR's current head -- a real, deliberate choice: new commits can land on a PR after a review
   without invalidating it (unless branch protection requires re-review), so reading at the PR's
   current head could silently accept something nobody actually reviewed.
3. Recomputes the file's own hash and requires it to match the trailer exactly -- the identical
   "hash mismatch is a hard failure" rule [`ubx accept
   --from-merge`](/cli-reference/accept#notes) already enforces for the merge-derived tier.
4. **Refuses outright if `blast_radius.destroys > 0`** -- a destroy is never accepted from a
   review, regardless of any configuration. See [Configuration](/server/configuration)'s own
   `allow_destroy` note; that flag governs ship, never acceptance. A human accepts a real destroy
   locally with [`ubx accept --confirm-destroys`](/cli-reference/accept) instead.
5. Otherwise calls `core.AcceptFromReview` directly (in-process, not a subprocess -- the one real
   flow step that doesn't shell back out to `ubx` itself, since it needs no provider round trip and
   the acceptance logic is small enough to call as a library function safely), recording the
   approver and their own review comment in the ledger.
6. Posts a real confirmation comment: `accepted <hash> (stack <name>) via PR #<n>, approved by
   @<reviewer>`.

## 4. Ship

**Automatically on merge**, when `ship_on_merge` is on (the default): a real `pull_request` event
(`action: "closed"`, `merged: true`) checks out the PR's own base branch (now carrying the merge
commit) and runs `ubx ship --yes` -- **never** with `--confirm-destroys`, no exception, regardless
of `allow_destroy`. There's no human present in an unattended, merge-triggered path to give the
real, separate confirmation a destroy needs, so a destructive proposal always fails `ubx ship`'s
own existing confirm-destroys enforcement here, by design -- the manual path below is what a real
destroy actually needs.

**Manually via comment**, `ubx ship [--confirm-destroys]`: `ubx server` checks the commenter
against the repository's own real `CODEOWNERS` file -- real gitignore-style glob matching (via
`github.com/hmarr/codeowners`) against the PR's own actual changed files, a team owner resolved via
a real, live GitHub team-membership call. Unauthorized -- refused, with a comment explaining why.
Authorized, and the comment included `--confirm-destroys` explicitly, and the server's own
`allow_destroy` is also on -- **both** real, both required -- `--confirm-destroys` is forwarded to
the real `ubx ship` subprocess.

## 5. Drift-watch

On `drift_watch_interval` (default `24h`), for every repo in `Config.Repos`, on every platform:
checks the repository out at its own main branch and runs
[`ubx scan --surface-as <issue|pr>`](/cli-reference/scan) over every stack that repository declares,
opening one real issue or draft pull request **per drifted resource** when real drift is found. A
drift-opened pull request is attributed to that platform's own configured bot identity -- see step 2
above for what that means for its own re-plan authorization.

<Warning>
  Before UBI-165 (2026-08-15) this step worked on **no** platform, GitHub included. Two separate
  defects, both fixed:

  - The loop shelled out to `ubx status --drift --surface-as ... --github-repo ...`. `ubx status`
    has no `--surface-as` flag and never had one, so every drift sweep ever run died on
    `unknown flag` before reaching any API. The loop now runs `ubx scan`, which is where the
    `--surface-as` machinery has always lived.
  - The surfacing itself was GitHub-only, and the loop resolved a GitHub App installation for every
    configured repository regardless of its platform.

  If you were relying on drift-watch before this fix, it was silently doing nothing. Check your
  server logs for the `unknown flag` line.
</Warning>

### What each platform actually opens

The receipt is byte-identical everywhere. What differs is where it goes, and that is genuinely
per-platform rather than one API with five names:

| Platform | `--surface-as issue` opens | `--surface-as pr` opens |
| --- | --- | --- |
| GitHub | an issue | a draft pull request |
| GitLab | an issue | a merge request, `Draft:` in the title |
| Azure DevOps | a **work item** | a pull request, real `isDraft` flag |
| Bitbucket Server | **refused, see below** | a pull request, `Draft:` in the title |
| Bitbucket Cloud | an issue | a pull request, `Draft:` in the title |

Three real consequences worth knowing before you configure `surface_as`:

- **Bitbucket Server has no issue tracker at all.** Atlassian's own model is that issue tracking
  lives in Jira, a separate product with separate credentials. `surface_as: "issue"` is refused
  there with an explanatory error, never silently downgraded to a pull request: an operator who
  asked for an issue and got a commit to their repository instead would be getting something
  materially more privileged than they asked for.
- **Azure DevOps has work items, not issues,** and they live in Azure Boards, a separate service
  from Repos that a project can have disabled. Their type comes from the project's own process
  template: `Issue` exists in the Agile and Basic processes and is the default, but a Scrum project
  needs `Product Backlog Item` and a CMMI project needs `Requirement`. Set
  `--azure-devops-work-item-type` accordingly; ubx cannot infer a project's process and will not
  guess.
- **Bitbucket Cloud's issue tracker is opt-in per repository.** A repository with it switched off
  rejects the call, which is the right place for that to surface rather than being hidden behind a
  fallback.

## GitLab

The identical core flow, against GitLab's own real structural differences -- confirmed directly
against GitLab's own current API/docs, not assumed symmetric with GitHub. See [GitLab
setup](/server/gitlab-setup) for the full walkthrough. Two real differences worth calling out here:

- **Step 3's acceptance trigger is GitLab's own real "approval" action** (an individual user's own
  Approve click), not "approved" (fired only once every required approver has approved) -- the
  identical per-approval-firing parity GitHub's own tier already has.
- **The TOCTOU safety check is structurally different.** GitLab's approvals API carries no
  per-approval commit SHA at all (unlike GitHub's `review.commit_id`); instead, `ubx server`
  verifies the project's own `reset_approvals_on_push` setting is on before trusting any approval at
  all -- see [GitLab setup](/server/gitlab-setup#reset_approvals_on_push).

## Azure DevOps

The identical core flow again, against Azure DevOps' own real structural differences -- confirmed
directly against Microsoft's own current API/docs. See [Azure DevOps
setup](/server/azure-devops-setup) for the full walkthrough. Real differences worth calling out
here, genuinely distinct from both GitHub's and GitLab's own:

- **No webhook signature scheme at all.** Azure DevOps Service Hooks carry no cryptographic
  signature; `ubx server` verifies a real, static shared-secret custom header instead (Microsoft's
  own documented recommendation), configurable via `--azure-devops-webhook-secret-header`.
- **`git.pullrequest.updated` folds push/vote/status/reviewer-list changes into one real event
  type**, distinguished only by which of several real, separately-configured Service Hook
  subscriptions delivers it -- never a payload field. `ubx server` asks the operator to encode that
  distinction in the subscription's own target URL via a `notification` query parameter
  (`?notification=push`, `?notification=vote`) -- see [Azure DevOps
  setup](/server/azure-devops-setup) for the real, complete subscription table.
- **Step 3's acceptance trigger is a real vote of `10` ("approved")** on the real five-value vote
  scale (10 approved, 5 approved-with-suggestions, 0 no vote, -5 waiting-for-author, -10 rejected)
  -- only `10` counts; `5` is a real, distinct, qualified vote, never rounded up.
- **The TOCTOU safety check uses a real branch policy instead of a project-wide setting.** Azure
  DevOps' own vote objects carry no per-vote commit/iteration reference at all (like GitLab, unlike
  GitHub); `ubx server` checks the target branch's own "Minimum number of reviewers" policy for its
  real `resetOnSourcePush` setting before trusting any approval -- refusing outright if no such
  enabled policy exists at all, a real, distinct outcome from "exists but doesn't reset."
- **No native CODEOWNERS support at all.** `ubx server` overlays its own real, consistent
  CODEOWNERS-file convention anyway (same file, same three locations as GitHub/GitLab); Azure
  DevOps' own real "Automatically included reviewers" feature is a separate, UI/API-configured
  mechanism, not read by `ubx server` at all.
- **Two real, separate identifiers address a repository** (project and repository), never one
  opaque path or a fixed owner/name pair -- see [Azure DevOps
  setup](/server/azure-devops-setup#--repo-s-own-azure-devops-shorthand).

## Bitbucket Server

The identical core flow again, against Bitbucket Server's own real structural differences --
confirmed directly against Atlassian's own current API/docs. See [Bitbucket Server
setup](/server/bitbucket-setup#bitbucket-server) for the full walkthrough. Real differences worth calling out here, genuinely
distinct from GitHub's, GitLab's, and Azure DevOps' own:

- **A real, bundled webhook signature scheme, no plugin required.** Bitbucket Server/Data Center
  has shipped native webhooks since version 5.4 -- confirmed directly against Atlassian's own
  current docs, contradicting an earlier "likely a plugin" assumption; every delivery carries a
  real HMAC-SHA256 digest in a header literally named `X-Hub-Signature` (a real naming collision
  with GitHub's own older, deprecated SHA-1 header -- the *value* format, `sha256=<hex>`, matches
  GitHub's newer scheme instead, never assumed from the header name alone).
- **Every semantic PR change gets its own separate, real event key** (`pr:opened`,
  `pr:from_ref_updated`, `pr:reviewer:approved`, `pr:merged`, `pr:comment:added`, ...) -- no folded
  event needing a query-parameter disambiguation trick the way Azure DevOps' single
  `git.pullrequest.updated` needs.
- **The TOCTOU safety check uses a real per-reviewer commit reference, delivered on the approval
  event itself.** Unlike GitLab's project-wide setting or Azure DevOps' branch-policy fallback (no
  per-vote commit reference exists there at all), Bitbucket Server's own real
  `pr:reviewer:approved` payload carries the approving reviewer's own `lastReviewedCommit` directly
  alongside the PR's own current head -- no separate live query needed at all; a mismatch (a push
  landed after the approval) refuses outright.
- **No native CODEOWNERS support at all**, the identical real gap every other platform has -- `ubx
  server` overlays its own consistent CODEOWNERS-file convention. Bitbucket Server does have a real,
  stable username (unlike Azure DevOps' DisplayName-only fallback), so CODEOWNERS "username" owner
  entries match directly; a CODEOWNERS "team" owner entry is a real, deliberate non-match against
  Bitbucket Server (no group-membership-by-name lookup exists for this package's own scope).
- **A genuine, single-call "does this user have write access" check exists**, unlike Azure DevOps'
  own ACL/security-namespace model (which needed a Contributors-group-membership approximation
  instead) -- Bitbucket Server's own repository permissions API answers this directly.
- **Two real, separate identifiers address a repository** (project key and repository slug), the
  identical shape Azure DevOps' own project/repository pair has -- see [Bitbucket Server
  setup](/server/bitbucket-setup#--repo-s-own-bitbucket-server-shorthand).

## Verified: the webhook endpoints themselves

A real, captured transcript against a running container (see [Docker deployment](/server/docker)),
all four real routes:

```bash
# GitHub -- /webhook/github
curl -s -o /dev/null -w "no-signature: %{http_code}\n" -X POST http://localhost:8080/webhook/github -d '{}'

curl -s -o /dev/null -w "bad-signature: %{http_code}\n" -X POST http://localhost:8080/webhook/github \
  -H "X-Hub-Signature-256: sha256=deadbeef" -H "X-GitHub-Event: ping" -d '{}'

payload='{"zen":"test"}'
sig=$(echo -n "$payload" | openssl dgst -sha256 -hmac "test-secret" | sed 's/^.* //')
curl -s -o /dev/null -w "valid-signature: %{http_code}\n" -X POST http://localhost:8080/webhook/github \
  -H "X-Hub-Signature-256: sha256=$sig" -H "X-GitHub-Event: ping" -H "Content-Type: application/json" -d "$payload"
```

```bash
no-signature: 401
bad-signature: 401
valid-signature: 202
```

```bash
# GitLab -- /webhook/gitlab (real Webhook-Id/Webhook-Timestamp/Webhook-Signature scheme)
curl -s -o /dev/null -w "no-signature: %{http_code}\n" -X POST http://localhost:8080/webhook/gitlab -d '{}'

curl -s -o /dev/null -w "bad-signature: %{http_code}\n" -X POST http://localhost:8080/webhook/gitlab \
  -H "Webhook-Id: 1" -H "Webhook-Timestamp: 1700000000" -H "Webhook-Signature: v1,deadbeef" \
  -H "X-Gitlab-Event: Merge Request Hook" -d '{}'

payload='{"object_kind":"merge_request","object_attributes":{"action":"close","iid":1},"project":{"path_with_namespace":"acme/infra"}}'
id="delivery-1"; ts="1700000000"
key=$(echo -n "test-signing-token" | base64)
sig=$(python3 -c '
import sys, hmac, hashlib, base64
key = base64.b64decode(sys.argv[1])
msg = f"{sys.argv[2]}.{sys.argv[3]}.{sys.argv[4]}".encode()
print("v1," + base64.b64encode(hmac.new(key, msg, hashlib.sha256).digest()).decode())
' "$key" "$id" "$ts" "$payload")
curl -s -o /dev/null -w "valid-signature: %{http_code}\n" -X POST http://localhost:8080/webhook/gitlab \
  -H "Webhook-Id: $id" -H "Webhook-Timestamp: $ts" -H "Webhook-Signature: $sig" \
  -H "X-Gitlab-Event: Merge Request Hook" -H "Content-Type: application/json" -d "$payload"
```

```bash
bad-signature: 401
valid-signature: 202
```
